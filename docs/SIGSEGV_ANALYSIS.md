## 1. 机制（已验证）

**蜂窝 MD 固件经 DPMAIF 的 RX DMA，按 MD 侧私有持有的陈旧（stale）缓冲页
列表，持续向 AP DRAM 写 16/32 字节环记录。被写页一旦被复用——用户进程的
anon 页、或已释放回 buddy 的内核页——就成为全家族 SIGSEGV 的注入源。**
printf 家族只是最高频的污染内存解引用路径（选集效应，§5.1），不是缺陷方。

机制链（每一环都有实测锚点，见 §3/§4）：

```
[AP] dpmaif/ccci RX 缓冲池页（4KB/条，环记录 PLEN0=4096 管理）
  → 生命周期事件（队列重建/端口关闭 churn）后页被释放回 buddy，
    但 MD 侧私有持有的缓冲页列表【不失效】（§3-E4：AP 全量不可见）
[MD] MD 经 DPMAIF RX DMA 继续向列表内 PA 写环记录
  → 输出与当前活环内容字节一致（§3-E2：活 PIT 环尾值 0x92d7a600 已落盘在案；⟦证据不足："两次原值注入两个不同用户页"无主机落盘，仅存于本文⟧）
[受害] 被写页已被复用：用户 anon 页（绊网活捉）/已释放内核页（死后写入）
  → 污染块落在任意数据结构上，按形状表现为 va_list 崩溃/NULL 解引用/
    .bss 指针损坏等不同签名（全家桶"看起来"是多个缺陷，实为一个机制）
[排除] AP 驱动映射路径干净（§3-E5：1465 次映射零坏页）；
  活 BAT/PIT 表在 2026-10-22 单次快照中未见陈旧基址（§3-E4；⟦证据不足：一次性快照、每窗仅前 0x200、PA 判据上限 0xa0000000、未跨越 stop/start；且 dpbatfix.c:4-11 有直接反例，见 §3-E4 与 §10⟧）
```

## 2. 已验证判据（照抄使用，不要自己发明）

### 2.1 注入块签名（识别新 core/现场用）

- 16B 块 `{small, 0}`：small ∈ [0x2710, 0x40000] ∪ {0}，非单调；
- 16B 块另有**指针型**：`{0x9xxxxxxx, 0}`（值域落在 RAM 段，如 0x92d7a600/0x92d79e80 族）——与上一条"长度型"是两类，历史文档只记了长度型；
- ⟦口径不全更正（2026-10-27）：§3-E2 记录的注入值 0x92d7a600 ∉ [0x2710,0x40000]，属指针型。识别现场时两类都要查。⟧
- 32B 块 `{small, 0, 0x????????_0000_06xx, 0}`：低 32 位落在 0x6xx/0x1180 族；
- 同页可多块（16B 节距）；页尾 0xfc0 起（word 504+）高发； ⟦证据不足："页尾高发"可能部分是采样位置偏差——历史上两台仪器都只在 +0xfc0 取样（dphook.c:496/604）⟧
- **禁止用 magic 值当指纹**：`0x1c28416e00000680` 等高 32 位在现场间会变，
  只能作个案旁证（曾在 6 处/4 个独立构建重复出现）。

### 2.2 va_list 健康判据

- 三个指针字段（`__stack/__gr_top/__vr_top`）落在用户态可访问范围；
- **`*_offs == 0` 不是坏值**：第 9+ 个变参正常走 `__stack`（musl pop_arg
  0x51e8c：`gr_offs>=0` → 走栈）；旧判据"两个 offs 都为负才健康"会误判合法
  长参数列表；
- 健康基线（实测）：`{栈地址, 栈地址, 栈地址, -48, -128}`。

### 2.4 内核 fault 行读法

arm64 是 `unhandled exception: DABT`，`[base+size]` 是**故障指令所在 VMA**

## 3. 写入者身份（坐实，2026-10-22）

**写入者 = 蜂窝 MD 固件经 DPMAIF 的 RX DMA（活体）**——它参与当前环维护
（输出与活环同源），只是写目标（缓冲页列表）是陈旧的。

## 5. 受害者生态与缓解定性

### 5.1 选集效应

污染块落在进程内存任意位置，多数落点无人解引用；printf 的 pop_arg 是全系统
最高频的解引用点，所以全家桶"看起来"是 libc 缺陷。`-l 200` 降幅、纯字面量
不崩、自有可变参数"不崩"（解引用点少一个量级）由此统一解释。

### 5.2 已落地缓解（保留+冻结，§22 口径）

| 项 | 实测效果 | 定性 |
|---|---|---|
| logc v1.4 去 printf | 7 崩/h → 0（A/B 10:0） | 保留：摘掉最高频解引用点 |
| logcut 替换 awk | 18.4/d → 0 | 保留：少 spawn+无大数组堆页 |
| procmatch 替换 pidof/pgrep | 2.7/d → 0 | 保留（另修 busybox pgrep -x 真 bug） |
| P2 静态工具链农场 | **崩溃零改善**（静态件同崩） | 保留但**冻结**（F1：不再为治崩溃扩面）；退役须根修验收后两臂 A/B |
| core_trap/core_meta、watchdog aee 增量判据 | 证据管线有效 | 保留 |
| `ap_auto_logging=0` 护栏 | 防 logread -f 常驻复活 | 保留（红线） |
| hardened vfprintf（guard 拦截） | 技术有效但 guard 误伤 gr_offs=0 合法态 | 归档不部署 |

**冻结规则**：F1 不再为治崩溃新增用户态替换；F3 文档/注册表不得再把 musl/
awk/pidof 写成缺陷根因；gw 侧无崩溃修复主线，主线=§8。

### 5.3 运营注意

- dropbear 高频 spawn 会卡死（accept 后 EOF/无 banner，不可恢复，只能
  `sys_reboot`）——取证脚本限并发、结果落 /data；
- 取证探针自身崩溃会进 ne_events/aee 台账，普查按 §2.3 规则扣除。

## 8. 修复主线：dpquarantine（页隔离内核模块）

### 8.1 设计（为什么是它）

- MD 侧列表 AP 不可达（E4）⇒ **修不了写入者，只能切断"被写页进入复用流"**⟦证据不足：该前提依赖 §3-E4，而 E4 的寄存器清点是单次快照且已有反例（dpbatfix.c:4-7）；"AP 不可达"需重审⟧；
- memmap 预留（LK cmdline）：依赖"失效 PA 跨重启稳定"，与观测（受害页随
  剧集滚动、分布跨 175MB）不符——**降级为兜底**；
- stop-path leak-on-timeout（A6 顺序缺陷）：⟦推理已撤回（2026-10-27）⟧ 原降级理由是"实测注入发生在无 stop 的稳态（基址 1h 不动）"。**这个论证不成立**：①"1h"无落盘，唯一存活的计时日志是 ticks=29115×50ms≈**24.3 分钟**（dphook_final.txt:1、dphook.c:53）；②**基址长期不动恰恰是陈旧基址应该有的表现，不是反证**——若基址在某次 stop 后就没被重新编程，它本就会一直不动，而 MD 会持续经它写下去。该线**不得据此降级**，见 §10 待裁决反例。

### 8.2 方案

`dpquar.ko`（源码 `gw/src/dpquar.c`，调用点补丁机械与 dphook 同款、已验证）：

1. 钩 dpmaif 的 `dma_unmap_page_attrs` 释放点（6 处，站点表见源码），shim 在
   原调用前对 `dma_addr`（=PA，无 IOMMU）解析页，`get_page_unless_zero` 加
   引用 → 页不回 buddy，入隔离表；
2. 策略：在押 TTL（默认 24h，`hold_s`）+ 总量上限（默认 4096 页/16MB，`cap`），
   FIFO 逐出——**有界**，无 OOM 风险（队列稳态长寿命，隔离事件罕见）；
3. 观测面：每站点计数（调用/隔离/逐出）+ 在押页页尾监视（**writer-hit =
   在押页被写次数——修复有效性与机制命中的直接验收读数**）+ /proc/dpquar；
4. 站点启用按位掩码（`qmask`）：teardown/错误路径（冷站点）默认隔离，每包
   路径（热站点）默认只计数——防隔离洪水；
5. rmmod：先还原补丁、msleep 让在飞 shim 退出、逐出全部在押页。

### 8.3 验收口径（§22.7 原则）

模块在位 + 补丁点命中计数 + **writer-hit>0 证明机制命中**；injwatch4 剧集期
用户页命中 → 0。**装后残余属预期**：已被 MD 列表持有的存量页会继续被写，直到
MD 列表自然失效/MD 重启——残余期"只降不零"，文档化。崩溃率只作旁证（26/d
基线下 7 天期望 182 次，统计判据不敏感）。两臂 A/B（开/关各 7 天）后才谈
农场退役（§5.2）。**（2026-10-23 更新：两臂观察经操作者决定取消，依据与
收尾见 §8.4；农场退役待定。）**

- 4 个稳定成员 findpa 交叉：全部为扫描器自匹配（§3-E6 特征）——**AP 侧零引用，

交接"的分配侧原因。换 `GFP_HIGHUSER_MOVABLE` 后立即命中。

### 8.8 原厂对照：为什么纯原厂"不发病"（2026-10-23 逆向轮）

证据源：2026-09-29 纯原厂全盘备份（RP0102，slot b 出厂态）+ rp103 官方镜像
解包（rootfs/kernel/lk/md1img）+ 运行实况对照。结论：**原厂没有任何绕开该
机制的刻意设计，同一 bug 在原厂处于"低暴露 × 零观察"的静默态。**

- **机制原厂同样存在**：双槽共享内核——运行内核与 rp103 官方内核版本串逐字符
  一致（5.15.134，2026-09-09 厂商 CI 构建；刷机管线只写 p26 rootfs）；

### 8.9.3 遗漏/缺陷清单

结构性遗漏（残余率的成因，非回归）：

- **S1 阶层盲区**：order-0 采样只见本 CPU pcp+order-0 热池；签名页与空闲伙伴合并入
  高阶块后不可见（且 order-0 非空+NORETRY 下采样不触发分裂），直到分配压力拆块才
  重新暴露。
- **S2 SMP 可见性**：system_wq 单 CPU 执行，1024 次 alloc/free 在同一 pcp FIFO 里
  循环同一小池（alloced=122880 而独立可见池 ~10³ 页量级）；其他 CPU pcp 不可见。
- **S3 UNMOVABLE 成员嫌疑**：本轮 buddyscan 考古字段（a8）见内核指针残影成员——
  若属 UNMOVABLE 迁移链，GFP_HIGHUSER_MOVABLE 采样永不可见（§8.6 migrate 盲区的
  反方向）。
- **S4 原位投毒不可防**：写入者对 PA 直写不问分配状态；页在持有时被写=原位损坏
  （E1 本质）。dpclamp 只能压缩"自由态可见存量"，压不掉分配态命中。
- **S5 无剧集反应**：idle 退火到 60s 巡检，剧集窗口内新签名页要等下一轮 sweep；
  首 NE 后无任何加速——滴漏与簇的共同窗口来源。

实现缺陷（dpclamp v1.2 源码级）：

- **D1** `test_and_hold` 存 digest 时 `t[3]` 被 XOR 两次（t[3]^t[3]=0）≠ watch 用的
  `tail_digest()`——首轮 watch 对 t[3]≠0 页产生伪 writer-hit（whits 污染一次后自愈）。
- **D2** watch 每轮只扫 ctab[0..255]——held>256 后尾部页永不监视（cap=8192 下必发）。
- **D3** 签名窗只认末 64B 的 t[0]/t[1] 两个 16B 槽位——记录单独落在 0xFD0/0xFD8 的
  页漏判（本轮 65 页宇宙未见该形态，风险降级但存在）。
- **D4** 无 /proc 写接口、无 episode 台账——触发与运维反推都无处落。

测量面缺口：**M1** ne_events 有 104 行 epoch 无效行（pre-NTP 落账）+ 多行 args 破坏
TSV 结构（boot 窗口 NE 不可统计）；**M2** 开机自载在 syslog/dmesg 零留痕（本 boot
grep=0，只能靠 lsmod 事后确认）；**M3** logread 单发崩溃 6 起/天，spawn 方未定位；
**M4** 两臂对照取消后无压制效果基线，只能对 10-20/21 的 25.8–44.2/d 口头对比。

**结论**：dpclamp 的机制与方向成立（持续收敛、无 KE 复发、内存稳态），残余率是
"覆盖=单 CPU 热池 + 反应=固定周期"的必然结果。下一轮方向=事件反应+深度遍历（§8.10）。

## 8.10 下一轮方案设计：dpclamp v1.3（剧集反应式 + 深度排空）【已实施，见 §8.10.3】

> 设计原则：F1 冻结不变（不新增用户态替换）；内核改动限定 dpclamp 本体 + 一个
> /proc 写接口 + core_meta 一行触发；dpquar 不动；v1.2 可随时 rmmod 回退。

1. **深度排空（deep drain，主武器）**：两阶段遍历全部 buddy 空闲链表（全
   order × 全 migratetype，不问 S1/S2/S3 的阶层与类型）——
   阶段一（持 zone->lock）：仅摘链表头页指针入本地有界数组，不读内容（锁窗目标
   <5ms/zone）；阶段二（无锁）：读页尾签名；命中页重取锁复核（PageBuddy 仍在 +
   签名仍在，容忍竞态）后按 rmqueue 语义整块取下、释放无签名兄弟页、仅扣住签名页
   （order-N 块按 2^N 记 cap）。依据：buddyscan 已在生产反复实证该遍历安全（本轮
   5×23624 页零异常）。pcp 仍由 burst 覆盖（pcp 无稳定遍历面）。
2. **触发器三路**：
   - T-a 内核：whits delta≥1 → deep+burst（前置修复 D1；剧集期写入者每秒级重写
     集合，检测延迟≈1 个 watch tick）；
   - T-b 用户态：core_meta v1.1 在 exec aee 前追加 `echo deep > /proc/dpclamp`
     （/proc 已 0666）——**NE 即探测器**，零内核风险，覆盖"whits 未鸣而 NE 先至"
     的窗口（受害者生态保证每个剧集至少一次 NE 可供触发）。模块侧冷却 300s 合并
     同源触发；deep 命中 ≥8 签名页才升级 burst（NE 探测默认只买 deep 的 ~1s，
     不买 burst 的 90s）；
   - T-c 开机：insmod 后立即 deep×1 + burst 90s（= §8.4 备案未实施的预热排水，
     覆盖 04:00 定时重启后毒页跨重启流转窗）。
3. **burst 模式（次武器，覆盖 pcp 热池）**：batch=1024 背靠背（sweep 完成即续；
   实测 1024 批 wall 2.5–8s → 90s 场 ≈11–30 轮、11–30K 页采样；4096 为参数上限
   不作缺省），时长 ≤90s、有 clamp 续期、硬帽 10min；NORETRY/NOWARN/minfree/
   cond_resched 全继承；连续 3 轮空 burst 提前终止。与 KE#3 的本质区别：事件驱动
   有界 vs 固定周期无退火。
4. **SMP 轮转**：sweep/deep 间轮换 kthread CPU 亲和性（4 核轮转），覆盖各 CPU pcp
   （关 S2 的采样侧）。
5. **缺陷修复**：D1 双 XOR；D2 watch 改滚动游标；D3 签名窗扩到 t[0..3]（单块命中，
   other-count 判据不变）；D4 /proc 增 episodes/bursts/deeps/last_trig 与触发来源。
6. **配套测量面**（非 dpclamp 本体）：core_meta v1.1（args 去换行、epoch 无效标
   `unsync`，关 M1）；自载与触发留痕写 /data/gw/logs/fixstack.log（关 M2）；
   logread spawn 方定位一轮（M3）。
7. **边界（不做并明示）**：不 hook 分配路径；S4（分配态原位投毒）不可防——残余
   下限存在；deep 只在事件触发/手动时执行，不进任何热路径。

### 8.10.1 性能预算（实现前分析）

**结论：可接受——稳态成本低于现行 v1.2，增量全部落在事件触发的有界突发
（单核、秒级、占空比 <1%），数据面零新增钩子；且"dpclamp 高强度采样"这一
负载类已有两轮 A/B 判清白。**

已有实证（成本上界，2026-10-24 03:00 串流卡顿轮，同方法论可复用为部署门禁）：
- 带载 A/B：25.8Mbps×210s，修复栈在/撤，eth 路径 ping 逐百分位一致
  （p50 1.4ms / p95 12ms）；
- 强制扫描 A/B：fresh insmod batch=4096 剧集强度扫描进行中，真实串流路径
  （PC→WiFi 客户端）三态 p50 全部 3–4ms，扫描阶段反而最干净。
→ 未测面只剩 deep 的锁窗与 burst 的节律，两者均有硬界（见下表护栏）。

成本模型（4 核 arm64 实测锚点，本轮新测）：

| 项 | 成本 | 锚点/推算 |
|---|---|---|
| v1.2 稳态·快周期 | 1024 页 sweep wall **2.5–8s** / 15s 周期 ≈ 单核 17–50% wall | 91s 双采样（含幻影 load 8 下调度延迟；band 上界含 kworker 等待） |
| v1.2 稳态·退火 | 同上 / 60s ≈ 单核 4–13% | 同上（idle=14 态实测 2 sweep/91s + 1 次 clamp 即回快周期） |
| v1.3 巡检（拟 120s） | ≈ 单核 2–7% | 反应性改由触发器承担，巡检可拉长 |
| deep 单轮 | 全子页尾读 ~31.6 万页 ≈ **0.3–1s 单核**；每命中块取还 ~1ms | buddyscan 同法实测（4725 子页尾读 + 180K PFN 探测 ≤2s；deep 免探测直取链表头 ~1473 块，只多读尾不探 PFN） |
| deep 锁窗 | 摘链表头指针 ≤256 条/块 ≈ **≤25µs/次持锁** | 1473 块头 × ~100ns/条，分块取放 |
| burst 单场 | batch 1024 背靠背 ≤90s ≈ 11–30 轮、11–30K 页采样 | sweep wall 实测外推 |

| 内存 | deep 相位数组分块 ≤64KB；命中页受 cap 8192 页（32MB 硬界）记账；块级瞬时扣取当轮归还兄弟页 | 现有 ctab 结构复用 |

设计内建护栏：巡检拉长（稳态较 v1.2 降 ~2×）；NE 探测只买 deep 不买 burst
（≥8 签名页或 whits 才升级）；锁窗分块 + cond_resched；burst 硬帽 10min + 3 空轮
早停 + minfree 150MB 门槛不变；**热路径（转发/软中断/分配快速路径）零新增接触**
——pcp/zone 锁接触均为微秒级窗口，且已被强制扫描 A/B 的负载类覆盖。

__isolate_free_page 逐行对齐（NR_FREE_PAGES/CMA 统计 + page->index pcp 迁移型 +
导出的 split_page 分裂兄弟页），free 路径垃圾 index 由内核钳制兜底（已核 5.15
源码 free_unref_page 的 ≥MIGRATE_PCPTYPES 回落）。

实测要点（全部 /proc/dpclamp v2 + dmesg + buddyscan 现场）：

- **deep 实弹（首轮，冷缓存）**：95ms 走完全部空闲链表（1799 块头 / 314,145
  子页尾读 ≈ 全量空闲池），114 候选块 re-verify **114/114 全部摘除成功**，344 页
  扣住，锁窗峰值 122µs。≥8 页自动升级 burst 的链路当场触发。
- **存量瞬时清零 + 写入者重建直接实证**：deep 后 buddyscan 仍有 ~50 distinct
  （20–30s 窗口内重现）——不是 deep 漏（100% 候选命中），而是 MD 侧 ~1 页/s 的
  持续重签：**"触发器+burst 反应式"的设计前提被当场证实**。人工风暴（1Hz×22 轮
  force deep + burst）累计 30 deeps/226 块摘除，锁窗峰值 317µs，零异常。
- **sweep 成本校准（sweep_us 遥测首功）**：1024 页 sweep 真实 CPU ≈ **550µs**
  （§8.10.1 表中 2.5–8s 的 wall 估计几乎全是幻影负载下的调度延迟）——性能预算
  全面宽裕，稳态成本实际 ~0.0005% 单核/巡检。
- **性能 A/B（严格重叠）**：持续 deep+burst 负载中 PC→CPE ping p50=1ms /
  p90=2ms / max=3ms，与无负载基线逐分位一致（§8.10.2 门禁 p50≤+0.5/p95≤+2 通过）。
- **warm-up（T-c）**：默认参数重载后 boot deep 自动执行（62 块/65 页/2ms 热缓存）
  → burst esca 升级 → 3 空轮 2ms 早停——开机预热排水（§8.4 备案项）闭环。
- **NE 探针链（T-b）**：kill -SEGV 实弹 → core_meta v1.1 落干净单行 TSV（args
  换行清洗生效）+ meta 文件 + `echo deep` 到达模块；boot deep 后 30s 内被 300s
  冷却正确抑制（suppressed=1，设计行为）。接受路径与 force 同代码分支已验。
- **未实弹项**：whits 触发（本窗写入者未击中持有页）；neprobe 接受路径与抑制
  同分支。二者留给常态运行自然覆盖。

**常态观察开始**：指标 = ne_events 7 天滚动（对照 §8.9.1 的 10-23/24 基线 25–48/d
与剧集簇 12 起/6min）+ stability_metrics 新列；04:00 定时重启将首次带 rc.extend
v2.8 panic 守卫 + warm-up 全链上机。

### 8.11 T1 定时排空 + T3 跨启动集持久化（2026-10-25 下午部署, dpclamp v1.4）

> 背景：10-25 白天实测残差 0.66/h（04:00–11:37, 5 起自然 NE = 4 个反应剧集,
> 反应链每次闭环但总慢一拍）。机理定位（§8.10 模型细化）：NE = MD 写**已分配**
> 页；空闲 buddy 里的签名页是"上膛的枪"——sweep 只见 pcp（1024 页/次）, 只有
> deep 全量走能拆除, 而 v1.3 的 deep 只在剧集后跑 = 每把枪都要等下一个受害者
> 触发。决策（操作者批准三件套）：守护面加固 + T1 + T3 探查。守护面加固见
> AVAILABILITY_DESIGN §8.1.1（NE 假红修正）与 healthdog v1.6。

**T1 定时 deep（deep_every_s=60, 0=off）**：kthread 定时全量 buddy 遍历,
把签名页在"空闲可见期"内拆除, 暴露窗压缩到 ~1 分钟。成本实测 95–101ms/次
≈ 0.3% CPU, zone 锁窗 ≤288µs（10 次定时 deep 实测, sched 计数按 60s 前进）。
预期: 剧集簇（同窗 2–3 连发）→ 单发; 残差率进入"只有首写即分配类"的地板。

**T3 PFN 种子（确定性清零路径的探针+工程本体）**：
- `/proc/dpclamp_seed`：流式 hex PFN 喂入（跨 write() 分块安全）, 每页 O(1)
  buddy 夺取（PageBuddy 头判定 + list_del + rmqueue 同款会计 + split + 持有
  目标页/释放兄弟页）, **无签名要求**——成员资格由既往 boot 的签名背书。
- `/proc/dpclamp_pfns` 导出持有集; log_keeper v2.10 每 5min 收割：union 文件
  `/data/gw/dpclamp_pfns.txt`（喂下次开机）+ 每 boot 快照
  `logs/dpclamp_pfn/<boot_id>.txt`（跨启动集合 diff 证据, held 数变化才重写）。
- rc.extend v2.9：dpclamp insmod 后立即喂 union（守护动物园拉起前）。
- **假设**：MD 陈旧集跨启动稳定（旁证：两次 Boot warm-up deep 同为 95ms/百余
  页量级）。若成立 → 开机预抢 = 集合成员永远到不了受害者手里 = 确定性近零,
  无"每 boot 首发税"; 若不成立 → 围堵维持（定时 deep 兜底）。
- **判读法（每个 04:00 boot, fixstack.log `seed:` 行）**：`fed=N ok=K dup=D
  miss_nb=M`——ok/(fed-dup) 比例高 = 集稳定; miss_nb（分配中/块尾; 新 ctab
  上 dup≈0）高 = 集漂移。结合当日 NE 率终判。
- 首次实弹（13:2x 手动喂本 boot union 307 PFN）：fed=307 **dup=307** 零副作用
  ——解析器/查重链验证 ✓。注：miss_nb 计数把 dup 也算入（返回值同路）; 开机
  时 ctab 为空故 dup≈0, 判读语义不受影响。
- 已知偏差：seed 会计用 MIGRATE_MOVABLE（分配侧同款语义; 页块级
  get_pfnblock_flags_mask 未导出）。唯一漂移是顾问计数 NR_FREE_CMA_PAGES
  （若种子页恰在 CMA 页块）; free_pcppages_bulk 会按真实页块 mt 归位释放页。

**热换事故记录（13:0x, 已修）**：首版 v1.4 .ko 链接未导出符号
（get_pageblock_migratetype → get_pfnblock_flags_mask）, insmod 失败; 且热换
命令是 `rmmod && insmod && ...` 单链——失败点被 && 短路, 只看到 /proc 空输出,
**dpclamp 缺位约 6 分钟裸窗口**。修复后 warmup 即时抓回 77 页。教训：模块热换
必须分步执行并显式回显 rc（&& 链掩盖失败点）。

**部署后基线（判后续用）**：13:1x–13:3x, held 77→412（重建中）, sched deeps
10+/10min; NE 观察窗从 13:00 起算; 次日 04:00 reboot 后首个 seed 判读 = T3 终判。

### 8.12 Phase 2 两臂判决协议（预登记，2026-10-26）

> **本节是预登记**：判据在看任何 A/B 数据之前写定。事后不得修改本节判据；
> 若必须改，另开一节说明理由并保留本节原文 —— 这是 2026-10-25 复核得出的
> 唯一纪律结论：§8.9.1 的「无台阶下降」正是先有数、后找说法的产物。

**为什么必须两臂，而不是「放一周看看」**

P0 改变了观测口径：logc 自崩在 v1.5 之前根本不进台账（`_exit` 绕过
`do_coredump`），现在会进。因此 **P0 之后测到的率天然高于历史数字** ——
不是因为变糟，而是因为能看见了。任何「新窗口 vs 历史 27–50/d」的对比都是
无效对比。唯一有效设计：在同一套仪器下先测 A 臂，再测 B 臂。

**主指标**

全部 NE / 24h（按排除规则扣除后）。分母 = 窗口实际小时数折算 24h；报率时
分子、分母、口径必须同时给出。`origin` 列（our-tree / vendor-tree /
unknown）**只作诊断分组，不参与主判** —— 「ip 命令崩了」对用户就是服务受损，
不因调用者是谁而免责。

**排除规则（缺一不可；1–5 与 §2.3 一致，6 为本节新增）**

1. 每 boot 后前 10 分钟不计（boot 窗口，core_meta 链尚未就绪）；
2. `args` 含 `kill -SEGV`（自测注入）；
3. `comm=?` 且 `exe=?`（进程已回收，不可归因）；
4. `exe` 前缀 `/tmp/pf_*`、`/tmp/v_*`、`/data/p0*`、`/data/repro/*`（自建探针）；
5. `args` 含 `busybox awk`（复现循环）；
6. **新增**：`args` 含 `avail_hourly.tsv` 的 awk 行（`api_avail.sh` 的 GUI 聚合
   自崩；v1.2 起已改纯 shell，此规则只用于剔除历史行）。

**两臂协议**

| 臂 | 配置 | 最短 | 建议 |
|---|---|---|---|
| A（当前） | `FIXSTACK_ENABLE=0`，内核修复栈不加载 | 3 天 | 4 天 |
| B | `FIXSTACK_ENABLE=1`，dpquar + dpclamp 加载 | 3 天 | 4 天 |

- 臂间切换用 reboot 完成，以每日 04:00 定时重启为自然边界（`reboots.log` 有据）；
- 每臂须覆盖 ≥3 个 04:00 周期，且每日数据无 >2h 缺口；
- 窗口期间禁止手工 SSH 干预与高频 GUI 轮询 —— 二者都会注入额外崩溃
  （§8.9.1 的 41 条自噪声即此教训）；确需访问时在 `ne_window.tsv` 记一行。

**判决规则**

1. **默认判「无收益」**：修复栈必须自己证明有用，而不是我们去找它有用的证据。
2. 判「有收益」须同时满足：B 臂相对 A 臂的 24h 率下降 **≥30%**；两臂各 ≥3 天；
   每日数据完整（无 >2h 缺口）。
3. **安全条款（优先于统计）**：任一 boot 的 pstore 回溯点名修复栈符号
   （`dc_main` / `run_deep` / `grab_cand` / `process_block` / `dpclampd` /
   `quarantine_page`）→ 立即判**退役**，不必等窗口跑完。
4. 数据不足（时长或完整性不达标）→ 判「未定」，**不得**判「有收益」。

**窗口锚点**

设备侧 `/data/gw/logs/ne_window.tsv`，制表符分隔一行：

    <epoch>\t<boot_id>\t<当时 ne_events 行数>\t<臂 A|B>\t<备注>

该文件不进任何消费方解析；`ne_events.tsv` 格式不动 —— 往里加哨兵行会被
按行数/sig= 解析的消费方当成一次真实崩溃，反而污染刚要干净的基线。

**已知混淆变量（解读时必须声明）**

- GUI 可用性页轮询频率（v1.2 前每次轮询跑一段会崩的 awk）；
- 每日 04:00 定时重启（`reboot_sched.sh`），非异常；
- 剧集簇：单次剧集可 6 分钟内连发 12 起，单日率方差大，故需 ≥3 天；
- 环境因素：蜂窝/WAN 无上游时 `boot_gate` 判 degraded，与 NE 无关。

**复核方式**

### 8.14 新方案尝试一：牺牲页池（设计 + 负结果，2026-10-26）

**设计依据（来自 §8.6 的 buddyscan 定性）**

MD 的陈旧列表约为 **400 个 PA** 的页集合 ⟦已证伪（"固定、不增长"这一限定语）：本文 §8.19 自身 distinct 242→809→3720 表明集合持续扩大；"固定"亦无落盘⟧，成员是 ex-anon 零填页、
位于 **MOVABLE** 迁移链表，45s 窗口 44 进 44 出 ≈ **1 页/s 被写**。当时据此设想的根治是**把这 400 页永久扣住**——写入落在无人读取的内存里。

**实现**：`tools/oneoff/printf_repro/sacpool.c`（纯用户态，无内核模块）
—— mmap 一块 anon 内存并逐页 touch，强制内核分配 MOVABLE 页（与陈旧页同迁移类型），
然后长期持有、每 30s 重 touch 一次，**永不读取内容**。撤池即整块 munmap。
选择纯用户态而非内核模块，是因为它不可能把设备搞死——而旧栈的三次故障都是内核级。

**实验**：A-B-A-A 四块各 20 轮，指标为 pfcanary 的 TTC（秒）：

| 块 | n | 均值 | 中位 | 标准差 | 60s 截断 |
|---|---|---|---|---|---|
| P0 基线 | 20 | 21.84 | 20.09 | 18.05 | 2 |
| P128（池 128MB） | 20 | 20.51 | 7.45 | 22.43 | 2 |
| P256（池 256MB） | 20 | 23.94 | 13.59 | 24.72 | 5 |
| P0b 基线 | 20 | 8.06 | 1.49 | 14.11 | 0 |
| P0c 基线（撤池后补测） | 20 | 16.67 | 11.15 | 18.41 | 2 |

**结果：未证明有效。**

- 无单调剂量-反应：P128(20.51) < P256(23.94)，但 P256 相对基线 +60% 的 t 仅 1.45；
- 相邻两块基线的差异 **−13.78 s（t=−2.69）**，比任何"效果"都大；
- 补测 P0c 回到 16.67 s，与 P0 无显著差异（t=−0.90）→ **P0b 的下探是瞬时漂移，
  不是池子留下的持续效应**。

**方法学结论（比结果本身更重要）**

pfcanary 的 TTC 在 **5–10 分钟尺度上自身摆动 2.7 个标准差**（均值 8–22 s）。
这意味着：

1. **块级 A-B 设计在本指标上无效**——块内漂移与块间差异同量级，n=20 无法分辨
   小于约 2 倍的效应；
2. 任何短于漂移周期的对照都必须**逐轮交替**（每次运行换臂），而不是分块；
3. 这也解释了 §8.12 为何坚持 ≥3 天/臂：长窗口平均掉的正是这个漂移。

**对 §8.12 的影响**：快层目前只能可靠地**否决巨大效应**（例如"修复后完全不再崩"），
不能分辨 30% 量级的改善。要分辨小效应，必须改成逐轮交替设计。

**当前状态**：旧栈已退役（§8.13）；牺牲页池**既未被证实也未被否决**，不纳入生产，
保留在 oneoff 供后续用逐轮交替设计重测。


### 8.15 新方案尝试二：直接测量（buddyscan）+ 牺牲页池被证伪（2026-10-26）

**换仪器：从赛跑指标换成确定性计数**

§8.14 的 TTC 指标噪声太大（基线块间摆动 2.7σ）。本轮改用项目已有的
`/data/repro/buddyscan.ko`（§8.6 的定性数据即出自它）：

    /proc/buddyscan → scans=N buddy_pages=.. signed=.. hits_now=..

`hits_now` = **当前 buddy 空闲链表中带注入签名的页数**。实测噪声：

- 连续 12 次扫描：`hits_now=48` **全部一致**；
- 6 分钟观察窗（18 次采样）：恒 48，仅两次瞬时 42/44。

**噪声≈0**，与 TTC 的 8–22 s 摆动不可同日而语。这回答了"静默/换仪器能否
降噪"——能，而且靠的是换仪器，不是靠静默设备。

**牺牲页池实验（§8.14 的方案）**

池子 256MB 实测确实分配并持有（MemFree 1295424→1033512 kB，65536 页），
释放后干净归还。持有一整 6 分钟，逐 20 s 采样：

| 时刻 | T0 | T4 | T5 | T6–T18 | AFTER |
|---|---|---|---|---|---|
| hits_now | 48 | 42 | 44 | **48** | 48 |

**结论：牺牲页池被证伪。** 持有 256MB 空闲页 6 分钟，签名页人口毫无变化。

**根本原因（比结论本身重要）**

buddy 里那 ~48 张签名页是**无害子集**——它们空闲、无人使用，写入落在没人读的
内存里。真正危险的是 MD 列表中**已被活进程持有的那 ~350 张**（§8.6：列表总人口
~400，任一时刻约 48 张处于空闲态）。池子只能拿空闲页，**结构上碰不到危险的那部分**。

由此得出两条推论：

1. **"扣住空闲页"这一整类方案都不可能奏效** —— dpquar（teardown 隔离）、
   dpclamp（采样扣留）、sacpool（大池持有）同属此类，全部被同一条理由否定。
   这解释了 dpclamp "排空存量"路线的必然失败：**污染是稳态过程，不是可耗尽的存量**
   （§8.6：44 进 44 出，自维持）。
2. 修复空间因此收窄为三条，且都不轻松：
   - (a) 停掉 MD 的写入 —— 写入者在 MD 固件侧，**AP 侧不可达**（§8.7）；
   - (b) 让受害者容错 —— 重试/加固解引用点，属缓解不属根治；
   - (c) 检测并修复**活页** —— 需周期扫描在用的用户页，代价与误伤风险都高。

**当前状态**：旧栈已退役（§8.13）；sacpool 与 injcount/injdiag 保留在 oneoff
供后续参考，**不纳入生产**。buddyscan 是本轮唯一被确认有价值的资产——
它是可用的低噪声仪器，只是它测的量（空闲签名页人口）已被证明与"危险面"不重合。


### 8.16 新方案尝试三：用户态自检可行性评估 + 重新设计（2026-10-26）

§8.15 排除了"扣住空闲页"整类方案后，剩下的候选是 (c) 检测并修复活页。
本节回答一个更基本的问题：**坏页在用户态到底能不能被看见？**

**测试一：长期持有的页会被写吗？（injcount）**

分配 64MB、逐字写入已知图案、等 20 秒、统计被改动的页：

    pages=16384  modified=0   （8MB/5s 同样为 0）

**结论：不会。** 污染不落在长期持有的内存上——这与 §8.15 一致：
陈旧页是**新分配**的页，不是老页。

**测试二：崩溃那一刻，注入值在不在现场？（faultprobe）**

与 pfcanary 同样的 snprintf 循环，但装 SIGSEGV 处理器，记录故障地址、
SP、以及栈映射区内命中注入签名的位置。6/6 全部捕获（剧集期）：

| 故障地址 | 对应 §2.1 形态 |
|---|---|
| `0x28416e00000640` ×3 | 32B 块 `0x????????_0000_06xx`（低 32 位 0x640 在 0x6xx 族） |
| `0x1698c` | 16B 块 `{small,0}`，small ∈ [0x2710,0x40000] |
| `0x13917` | 同上 |
| `0x10a65` | 同上 |

**故障地址就是被注入值覆盖后的 va_list 指针**——两种形态与 §2.1 的签名定义逐字吻合。

**可行性判决**

1. **周期自扫（持有页）不可行** —— 测试一证明污染不落在老页上；
2. **故障点可观测，因此"解引用前校验"可行** —— 测试二证明被污染指针的取值极其离谱：
   aarch64 上合法栈指针是 `0x7fxxxxxxxxxx` 量级，而注入值是 `0x1698c` 这种
   或 `0x????????_0000_06xx` 形态。**一个地址范围检查就能拦住**。

**重新设计：解引用前的指针合理性闸门**

不做周期扫描（太慢、覆盖不到短命进程），改为在**解引用点**加一道极廉价的检查：
若 va_list 指针不在进程已映射区间内 → 判定为污染，返回错误而不是解引用。
进程存活，调用方拿到一次格式化失败。

实现路径：项目已有 `layerchk`（可单独编译 musl `vfprintf.c` 并显式链接在
libc.a 之前覆盖同名符号，README 记载"未打补丁仍崩 → 覆盖链有效"）。静态农场
的工具（busybox/iproute2）正是需要覆盖的对象。

**必须说清的三条限制**

1. 这是**缓解不是根治**——污染仍在，只是不再把进程打死；
2. 只覆盖 printf 解引用路径。§1 说 printf 是**最高频**路径（选集效应），
   但不是唯一路径；非 printf 形态的污染（NULL 解引用/.bss 指针损坏）拦不住；
3. 污染是**剧集式**的 ⟦已证伪：原始表述"剧集期 10/10 崩、平静期 0/5 崩"被本文 §8.19 自身推翻——`watch.tsv` 在 4.2 小时内记录 18 次 CRASH（≈4.3 次/小时）持续不断，不存在"平静期"⟧。
   任何验证都必须落在剧集窗口内，否则测到的是"零"而不是"有效"。

**待办**：部署 hardened vfprintf 并用 §8.15 的 buddyscan + 剧集期 pfcanary 双指标验证。


### 8.17 剧集触发条件调查：两个假设均被否定（2026-10-26）

§8.16 的重新设计依赖一个未验证的前提——剧集何时发生。本节做触发条件调查。

**先挖已有台账（零设备交互）**

`/data/gw/logs/ne_events.tsv` 全量 548 行，按 §2.3 排除后 **285 次**崩溃，
跨 6.6 天。结构：

- 到达间隔：中位 **478 s**、均值 1998 s、p90 **5557 s**、最大 **40107 s（11 小时）**；
- 间隔 <10 s 的 **49 次**、>600 s 的 **137 次** → **双峰**：要么成串，要么孤立；
- 按 gap>300 s 切分得 **154 个剧集**，其中 ≥5 次崩溃的 **10 个**；
- 大剧集：持续 **中位 420 s**（35–891 s），间隔 **中位 3900 s**（402 s–60 小时）。

剧集是真实且成形的对象，但触发条件未知。

**假设一：AP 侧页分配突发（mmap churn）**

依据：A7（受害者＝新页获取率高的短命进程；长命探针 0 命中）+ §8.14 中误启
injwatch（128 MB 翻腾）曾伴生 106 秒 13 次崩溃 + injcount（长持页 20 s 0 命中）。

实验：A / B / A 各 8 样本（每样本 pfcanary 25 s 封顶），B 相做 8×128 MB 分配并各持 20 s。

| 相位 | CRASH | TIMEOUT |
|---|---|---|
| A1 平静 | 1/8 | 7 |
| B churn | 2/8 | 6 |
| A2 平静 | **3/8** | 5 |

**否定**：崩溃数 1→2→3 是随时间单调上升，A2 平静相反而是最高 —— 漂移盖过效应。

**假设二：进程 spawn 突发**

依据：一次大 mmap 与 500 次 exec 是不同形状——陈旧 PA 只有当它被发成某个进程的
新栈页时才致命。故改用 spawn 突发（500 次短命进程）。

| 相位 | CRASH | TIMEOUT |
|---|---|---|
| **A1 平静** | **5/6** | 1 |
| B spawn 突发 | 2/6 | 4 |
| A2 平静 | 2/6 | 4 |

**否定**，且方向相反：第一个平静相位崩溃最多。

**结论**

1. **两个 AP 侧触发假设均不成立**；剧集触发条件仍未识别；
2. 两次实验合计约 25 分钟里，设备恰好经历了一次剧集结束（5→2）与一次剧集开始
   （1→3）——**相位间差异远大于任何人为操纵效应**；
3. 因此：**在不知触发条件的前提下，无法用短时对照实验控制变量**。这不是实验
   设计的问题，是对象本身的属性——剧集是自主的，而我们的操纵在它面前是噪声。

**推论（对后续方法的影响）**

要识别一个不能主动操纵的触发条件，唯一可行的方法是**连续观察**：常驻哨兵按分钟
记录"剧集开/关"，同时记录候变量（MD 侧 /sys/kernel/ccci/*、内存、spawn 率、
uptime 等），跑足数小时后找出**转变前**的共性，而不是在转变中做对照。

这也意味着：§8.16 的 hardened vfprintf 若要验证，必须在**剧集窗口内**做，且
窗口由系统决定而非由我们决定——除非先把触发条件搞清。

### 8.19 通宵决定性实验：跳过 04:00 重启（2026-10-27 夜）

**设计**

设备每日 04:00 定时重启（`reboot_sched.sh`），使 **uptime ≡ 钟点**，无法分离
"累积效应"与"钟点/外部因素"。今晚经受支持配置项 `/data/gw/settings.conf` 设
`REBOOT_EN=0`（`reboot_sched.sh` 每轮重应用，**不改任何部署代码**），跳过一次
04:00 重启，其余条件不变。观测器（`/data/gw/logs/episode_watch.tsv`）以约 50 秒
粒度连续记录哨兵状态。

**结果（04:00 前后，同一仪器内对照）**

| 时段 | 时长 | 样本 | 崩溃 | 率 |
|---|---|---|---|---|
| 04:00 前 | 3.53 h | 257 | 12 | **3.40 /h** |
| 04:00 后（未重启） | 1.17 h | 85 | 6 | **5.12 /h** |

比值 1.51，95% CI **0.57 – 4.02**（含 1，不显著）。

设备确认未重启：04:00 过后 uptime 持续增长（越过 21,500 s）。

**结论一：累积/uptime 假设【并未被否定】。** ⟦已证伪：本结论与本文 §8.18 预登记的判据方向相反——原判据明写"若 04:00 后崩溃继续 → 是累积/uptime 效应 ⇒ 加频重启即为可行缓解"。实测崩溃正是继续（5.12/h vs 3.40/h，方向上升），按预登记判据应判**成立**；比值 1.51 的 95% CI 0.57–4.02 含 1 只说明**功效不足**，不等于无效应。**"加频重启"应保留为候选缓解**，不得据此关闭。⟧

**结论二（更重要）：污染源在深夜是持续存在的，"夜里安静"是受害者侧现象。**

同一观测窗口内按小时统计：

| 小时 | 样本 | 探针崩溃 |
|---|---|---|
| 00 | 37 | 1 |
| 01 | 72 | 3 |
| 02 | 73 | 6 |
| 03 | 73 | 2 |
| 04 | 72 | 3 |
| 05 | 15 | 3 |

探针（pfcanary）在 00:00–05:00 全程维持 **约 3–5 次/小时**的崩溃率；而历史自然台账
在同一时段（§8.18：03:00–09:00）几乎为零。**两者不矛盾**——探针是人为提供的高灵敏
受害者，它证明**污染一直在**；自然台账只记录"恰好被自然受害者撞上"的事件。

因此 §8.17 中"剧集是自主的、我们无法控制"这一提法需要修正：

> **剧集结构主要反映受害者侧的变化（进程种类/分配模式），而不是污染源的开关。**
> 污染源本身在整个夜间连续工作。

这与 §8.15/§8.16 的结论自洽：既然污染持续存在且落在**新分配**的页上，
那么"何时崩溃"由"何时有新进程拿到那些页"决定，而不是由 MD 何时写入决定。

**结论三：buddyscan 的 `distinct` 单调增长，`hits_now` 恒定**

| 时刻 | scans | hits_now | distinct | maxrep |
|---|---|---|---|---|
| 00:40 | 111 | 48 | 242 | 111 |
| 01:13 | 746 | 48 | 809 | 716 |
| 05:12 | — | 48 | **3720** | 5278 |

空闲态签名页恒为约 48 张，而被写入过的 PA 集合在约 4.5 小时内从 242 扩到 3720。
即：**MD 以稳定速率持续"污染新页"，但任一时刻暴露在空闲池里的只有约 48 张**。
这解释了为什么"扣住空闲页"无效（§8.15），也解释了为什么受害者必须**新分配**到那些页
才会崩（§8.16）。

**局限（必须记录）**

1. 探针在污染存在时几乎必崩，**灵敏度接近饱和**，因此它不能分辨污染密度的细变化——
   它能回答"有没有"，不能可靠回答"多了多少"；
2. 04:00 后仅 1.17 h，样本 6 次，统计功效低；
3. 本次只跳过一晚重启，无法排除"多日累积"型效应。

**对修复方向的含义**

既然污染连续存在、且只在新分配页上致命，那么"阻止污染"（与 MD 固件对抗，AP 侧不可达）
与"扣住页"（§8.15 已否定）都不可行。剩下的可行方向只有**降低新分配页被污染的概率**
或**让受害者不因污染而死**——后者即 §8.16 的解引用前指针闸门。

崩溃 49.2 s vs 正常 49.8 s，故非时长伪迹）：

|---|---|---|---|
| **spawn 速率** | **83.0 /s** | **97.9 /s** | **−7.4** |
| runq（可运行队列） | 2.2 | 1.3 | +4.9 |
| memfree | 1,271,278 kB | 1,273,763 kB | −4.6 |
| eth0 tx 增量 | 400 | 587 | −3.2 |

**方向与"页抖动量"假设相反**：崩溃前的进程 spawn 速率**更低**。这与 §8.17 的两个
操纵实验（churn / spawn 突发均未能抬高崩溃率）方向一致，共同指向"崩溃不是由
AP 侧分配压力驱动的"。

但必须克制：n=18、同时比较 7 个候变量，多重比较风险高，且机制不明（可能是反向
因果——崩溃前后系统节律变化）。**本条只作待验证线索记录，不作为结论。**

### 8.20 二分排除法：AP 侧两个候选均被排除（2026-10-27 晨）

**方法：换用高事件率指标，让二分变得可行**

崩溃率只有 3.4/h，每档需数小时才够判。改用 buddyscan 的 `distinct`
（被污染过的唯一 PA 累计数）的**增长速率**——这是污染源活动的直接量度，
平台期约 **15–17 个新 PA/分钟**，20 分钟窗口可获 ~320 个事件。

**必须先注意的仪器特性**：刚加载模块时 `distinct` 有 **约 15 分钟的初始瞬态**
（快速枚举存量污染页，表观速率 30+/分钟），之后才稳定。**用瞬态段做对照会
产生假阳性**——本轮第一档最初就误读为"守护关闭使速率腰斩"，实为瞬态衰减。

**三档结果（每档约 19 分钟，同一仪器内连续）**

| 档 | 处置 | 平台期速率（新 PA/min） | 判定 |
|---|---|---|---|
| — | 基线（全正常） | 26.7 / 16.8 / 32.0（瞬态）→ 稳定 ~16 | — |
| 1 | **全部守护关闭**（仅留 healthdog.sh + dropbear） | 16.4 / 16.0 / 8.2 | **无效** |
| 2 | 守护恢复 | 15.6 / 17.0 / 14.8 | **无变化**（也未"回升"，因为档 1 本就非因果） |
| 3 | **WiFi 关闭**（hostapd 停、ra0/rai0 down） | 27.8 /（18.8 分钟总）20.5 | **无效**（反而略高，在噪声内） |

**结论**

1. **AP 侧守护舰队的进程/页分配活动不驱动污染速率** —— 全停 19 分钟无变化。
   这与 §8.17（churn/spawn 突发均不能抬高崩溃率）、§8.19（跳过重启无变化）
   三处独立证据一致。
2. **WiFi 驱动不参与** —— 停 hostapd + down 双射频 19 分钟，速率不降。这与 §3 的
   排除清单（"mt76 无 RXWI/帧头"）在内容侧一致，现在在**动力学侧**也独立确认。
3. 因此：**MD 的写入节律是自主的，不随 AP 侧活动变化**。这解释了为什么此前所有
   "在 AP 侧加/减负载"的操纵实验全部落空。

**剩下的唯一候选：MD/DPMAIF 自身**

要再往下二分，只能动 MD 侧，而 AP 侧可用的手段有限：

- 发送 AT 命令改变 MD 状态（设备有 `atcid`，但未验证可用 AT 通道）；
- 用 `dphook.ko` / `dpreg.ko` 直接读 DPMAIF 内部寄存器与 DMA 描述符，
  观察写入节律与 MD 侧事件的相关性——这是 §8.6 之后一直没做的下一步；
- `AT+CFUN=1,1` 只暂停注入 1–2 分钟（E4），不足以做对照。

**方法学收获**：`distinct` 增长速率是一个可在 20 分钟内判定的二分指标，
比崩溃率快约 7 倍；但必须先用约 15 分钟度过初始瞬态并在同一段内取基线。


### 8.21 既有证据深挖：cores/meta 与 dmesg 均无前兆（2026-10-27 晨）

**一、cores/meta 深挖（120 份现场）**

| 维度 | 结果 |
|---|---|
| 受害进程 | `pf_canary` 112、`faultprobe` 6、`ip` 2 |
| **父进程** | **`sh` 115 / `ash` 5** —— 绝大多数受害者由 shell 脚本（我们的守护）拉起 |
| 崩溃时刻 dmesg 尾部 | **几乎全是 `aee_aed`**（崩溃处理器自身输出），另加 `watchdogd` 心跳 |

两条结论：

1. **父亲几乎全是 sh**，与 §8.18 的受害生态（守护舰队调用的短命工具）完全一致；
2. **meta 文件对找触发条件无用** —— 它的 80 行 dmesg 尾部窗口被崩溃自身的处理日志
   （`aee_aed` 的 start/copy_file/Exception/Count 等）填满，崩溃前的信息已被挤掉。

**重要损耗记录**：该目录配额为 120 份（保留最新），今日的测试现场已把历史自然崩溃
的 meta 全部轮转掉——现存 120 份中 118 份是本次轮次的仪器（`pf_canary`/`faultprobe`）。
历史现场只能用 `ne_events.tsv`（未轮转）回溯。

**二、dmesg 系统关联（当前 boot 全量 5,314 行 / 25,867 s）**

先按 uptime 回落定位启动边界（`dmesg.log.1`+`dmesg.log` 合计 99,803 行、12 个
boot 边界），取当前 boot 段做关联。该 boot 内 6 次崩溃。

对每种内核消息，比较"崩溃前窗口内的出现率"与"全段平均率"：

| 消息 | 崩溃前 30 s | 崩溃前 60 s | 期望（30/60 s） | 判定 |
|---|---|---|---|---|
| `mipc_cellular`（ccci 端口层） | **0** | **0** | 0.92 / 1.84 | **无前兆** |
| `aee_aed`（崩溃处理器） | — | 188 | 30.0（6.3×） | **伪迹** |

`aee_aed` 的"升高"是**崩溃聚集造成的**：前一次崩溃的处理日志正好落在后一次的
"之前"窗口里，与触发无关。

**结论：没有任何 AP 侧内核消息类型先于崩溃出现。**

**三、把三段负面结论合起来看**

到目前为止，触发条件已在 AP 侧被系统性地排除：

| 候选 | 检验方式 | 结论 |
|---|---|---|
| AP 进程/页抖动 | churn 与 spawn 突发操纵（§8.17） | 无效 |
| 设备累积/uptime | 跳过 04:00 重启（§8.19） | 无效 |
| 守护舰队活动 | 全停 19 分钟，测污染速率（§8.20） | 无效 |
| WiFi 驱动 | 停 hostapd + down 双射频（§8.20） | 无效 |
| 负载/内存/队列 | 观测器候变量对照（§8.19 附） | 无前兆 |
| 内核消息（ccci/DPMAIF） | dmesg 逐类对率（本节） | 无前兆 |

**因此：MD 的写入节律在 AP 侧不可观测、也不受 AP 侧活动影响。**
继续定位只能进入 DPMAIF 内部——用 `dphook.ko`/`dpreg.ko` 直接读寄存器与 DMA
描述符，把写入节律与 MD 侧事件对上。这是 §8.6 之后一直未做的下一步，也是本目标
唯一剩下的方向。


### 8.22 ~~物理地址聚集：污染页集中在 32MB 区间~~（2026-10-27 晨）

> **⚠ 本节结论已作废，见 §8.23。** 本节依据的 buddyscan 在找到 maxhits(48) 个签名页后
> 即停止扫描，报出的 48 页是**扫描路径的前缀**而非样本，其地址分布必然偏向扫描终止处。
> 全量扫描（§8.23）证明真实结构是**约 12 个离散热点**，不是单一 32MB 区间。
> 本节保留仅为记录该误判及其成因。

**一、MD 侧对照做不成（记录为受阻）**

要证明"关掉 MD 污染就停"，尝试了三条路，均不可行：

1. `/sys/kernel/ccci/md_en` 虽可写（`-rw-rw----`），但写入 `D-D-D-D-D` 后读回
   仍是 `E-D-D-D-D (1->5)`——**格式不对或被拒绝**，且写入瞬间 SSH 会话超时（设备
   本身存活，ping/GUI 正常）；
2. `ccci_mdinit` 的字符串里没有干净的 enable/disable 选项，只有 boot/reset 相关；
3. `mipc_wan_cli` 可执行 AT 命令，但 **E4 已证明 `AT+CFUN=1,1`（MD 完整复位）只暂停
   注入 1–2 分钟** —— 不足以支撑 20 分钟的对照档。

**因此"MD 关掉后污染是否停止"这一决定性对照，在 AP 侧无法实施。**

**二、物理地址分布：一个没有被审视过的维度**

buddyscan 每次读给出约 48 个签名页的**物理地址**。六次连续快照：

| 快照 | 落在 0xa4000000–0xa6000000 | 占 48 |
|---|---|---|
| 1 | 34 | 71% |
| 2 | 37 | 77% |
| 3 | 38 | 79% |
| 4 | 38 | 79% |
| 5 | 39 | 81% |
| 6 | 33 | 69% |

**均值约 76%，稳定复现。** 单次全量分布（16MB 桶）：

    0xa5000000-0xa6000000  31
    0xa4000000-0xa5000000   8
    0xa2000000-0xa3000000   4
    0x90000000-0x92000000   3
    其余 1-2 各

48 个签名页的物理跨度达 335MB，但四分之三挤在 32MB 内。

**三、这个区间在物理内存图上的位置**

    a30a0000-a3f9ffff : reserved        ← 15MB 保留区
    a3fa0000-afefffff : System RAM      ← 污染聚集区在此段的最底部

聚集区 **0xa4000000** 恰是那个 15MB 保留区之后的第一个 4MB 对齐边界。
符合"DMA 缓冲池在 boot 时从 zone 低端分配"的常见形态。

**四、必须声明的局限**

本轮**没有建立零假设的对照**：只能证明"签名页在 0xa4-a5 区间富集"，还不能排除
"该区间本来就是内核空闲页的主要分布区"。粗算：该 32MB 占 System RAM 区域
（0xa3fa0000–0xafefffff，187MB）的 17%，却容纳 76% 的签名页，**富集约 4.5 倍**
——但若空闲页本身在该段底部高度集中，这个富集就会被高估。

要证伪需要一个**空闲页物理地址分布**的对照，这只能由内核侧导出（buddyscan 目前
只报数量、不报被扫页的地址范围）。

**五、若被证实，这是一条从未尝试过的修复方向**

此前所有方案（dpquar/dpclamp/牺牲页池）都是**无差别**地处理页。若污染确实集中在
32MB 物理区间，则：

- 在 boot 时保留该区间（`memmap=32M$0xa4000000` 类手段，或内核模块 init 时扣住），
  可让约 76% 的污染页**永远不进分配器**；
- 这是第一个**有空间针对性**的候选，量级远优于此前所有方案；
- 代价极小（32MB / 1.7GB = 1.9% 内存）。

**下一步（需内核侧）**：给 buddyscan 加一个"被扫页地址直方图"输出，或直接 dump
buddy 空闲链表首地址分布，用于建立零假设对照。


### 8.23 更正 §8.22：仪器缺陷导致误判；全量扫描给出真实的"多热点"结构（2026-10-27 晨）

**一、撤回 §8.22**

§8.22 曾据 buddyscan 报出的 48 个签名页得出"污染集中在 0xa4000000–0xa6000000 这
32MB"的结论。**该结论作废**，原因是仪器缺陷：

> buddyscan 的扫描循环是 `for (pa = PA_BASE; pa < PA_END && n < maxhits;)`——
> **找到 maxhits（默认 48）个签名页就停止**。所以它报出的 48 个页不是随机样本，
> 而是**扫描路径的前缀**，其地址分布必然偏向扫描终止处。任何基于它的空间推断
> 都是无效的。

这是本轮自己引入、又自己发现并纠正的一个错误。

**二、修好仪器：加地址直方图 + 强制全量扫描**

在 `tmpfiles/repro/buddyscan2.c`（原 buddyscan.c 的副本）上加两个 256 桶直方图
（按 `pa >> 24`，每桶 16MB）：`hist_scan` 记录**每一个被扫描的空闲页**（零假设分布），
`hist_sig` 记录**每一个签名页**（实验分布）。一次读同时给出两组。

并用 `maxhits=100000` 强制全量扫描——因为命中计数在 64 处封顶（`if (n < 64)`），
`n < maxhits` 恒为真，循环走完整个 PA 空间。

**三、真实结构：不是单一热点，而是约 12 个离散热点**

单次全量扫描：**263,125 个空闲页，101 个签名页，整体率 0.0384%**。

按 16MB 桶对率做泊松检验（`z = (obs - exp)/sqrt(exp)`）：

| 桶（pa>>24） | 物理地址 | 扫描 | 签名 | 期望 | z |
|---|---|---|---|---|---|
| 186 | 0xba000000 | 2576 | 24 | 0.99 | **23.1** |
| 166 | 0xa6000000 | 989 | 7 | 0.38 | 10.7 |
| 182 | 0xb6000000 | 3042 | 12 | 1.17 | 10.0 |
| 165 | 0xa5000000 | 2586 | 9 | 0.99 | 8.0 |
| 164 | 0xa4000000 | 1336 | 5 | 0.51 | 6.3 |
| 188 | 0xbc000000 | 2049 | 5 | 0.79 | 4.8 |
| 183 | 0xb7000000 | 2362 | 5 | 0.91 | 4.3 |
| 173 | 0xad000000 | 3511 | 5 | 1.35 | 3.1 |

- **z>3 的桶共 12 个**；
- 它们只占被扫页的 **9.7%**，却容纳 **85.1%** 的签名页。

**热点位置在两次独立全量扫描之间保持稳定**（186/182/183/165/166/164/173/188 均重复
出现），说明这不是采样偶然，是写入者缓冲池的固定栖息地。

**四、这条结论的意义（与前几节的关系）**

1. 它**不推翻** §8.15（扣住空闲页无效）——那些方案是无差别扣页，而热点只占 9.7%，
   随机扣页几乎碰不到；
2. 它**给出**了第一个有空间针对性的修复候选：**保留这 12 个热点区（约 192MB，
   占 1.7GB 的 11%）可让 85% 的污染页永远不进分配器**；
3. 实现手段现成：内核模块在 init 时对热点 PA 区间调用 `alloc_contig_range()` 并永久
   持有（标准 API，CMA/透明大页同款），或走 `memmap=` 启动参数。

**五、局限**

1. 热点是否**跨 boot 稳定**未知——本轮只在同一 boot 内验证（2 次扫描）；跨 boot 需
   重启后再测，而重启会重置 MD 状态；
2. 192MB 的代价（11% 内存）是否可接受需权衡；
3. 各热点的签名率差异（0.1%–0.9%）说明即便在热点内也只有少数页被写，保留是
   按"区间"而非"页"做的粗粒度操作。


### 8.24 跨 boot 验证：稳定核心 + 开机重建高峰（2026-10-27 晨）

**一、方法**

把修好的 `buddyscan2.ko`（含地址直方图）持久化到 `/data/repro/`，重启设备后重新
加载做全量扫描，与重启前的热点分布对比。

**二、结果**

| 时点 | uptime | 扫描页 | 签名页 | 率 |
|---|---|---|---|---|
| 重启前（稳态） | ~28,000 s（7.8h） | 263,125 | 101 | **0.0384%** |
| 重启后第 1 次扫描 | ~450 s（7 min） | 271,081 | 453 | **0.1671%** |
| 重启后第 2 次扫描 | ~1,440 s（24 min） | 270,634 | 400 | **0.1478%** |
| 重启后第 3 次扫描 | ~2,500 s（42 min） | 269,687 | 394 | **0.1461%** |
| 重启后复测 | ~10,595 s（2.94 h） | 268,514 | 425 | **0.1583%** |

**⚠ 本节关于"4 倍高位平台会衰减"的解读已被后续数据推翻（2026-10-27 上午复测）。**

实测序列：0.167%（7 min）→ 0.148%（24 min）→ 0.146%（42 min）→ **0.158%（2.94 h）**。

**近三小时内稳定在 0.15–0.16%，没有衰减趋势。** 因此：

- 不是"开机高位平台逐渐回落"，而是**这个密度就是常态**；
- 重启前测到的 0.0384%（uptime 7.8 h）是该 boot 的**异常偏低值**，不应作为"稳态"基准；
- §8.25 中"稳态仅约 100 个空闲签名页"的推算据此**不成立**（按 0.1583% 计约 425 页）。
这与 E4"MD 复位后 1–2 分钟内注入恢复"一致，并给出量化：复位后不是恢复到稳态，
而是先进入一个**数小时量级的高位平台**。

**三、热点跨 boot 的稳定性：有稳定核心，也有开机期扩展**

两次 boot 中签名数均 ≥3 的区段共 **8 个**：

    166 (0xa6)  173 (0xad)  176 (0xb0)  182 (0xb6)
    183 (0xb7)  186 (0xba)  187 (0xbb)  188 (0xbc)

其中 186/182/165/166/176/164 在重启前位居前六。**存在一个跨 boot 稳定的热点核心。** ⟦已证伪：按 hist.txt 重算，重启前前六为 186,182,165,166,176,164（不含 187；183 仅与 164/173/188 并列第 6，"183/186/187/188/182 都在前六"不成立）⟧

同时，重启后出现 **171/172/177/189 等新区段**（172 在重启前只有 1 个签名，重启后
有 91 个），对应上述"开机重建高峰"。重启前排名靠前的 165 在重启后归零。

**四、对修复方案的含义（修正 §8.23 的建议）**

§8.23 建议"保留 12 个热点区约 192MB 覆盖 85%"。跨 boot 数据要求把这个建议改成分层：

1. **稳定核心 8 个区（约 128MB，占 RAM 7.5%）**：跨 boot 持续有污染，保留它们
   是持续有效的；
2. **开机重建期的临时热点（171/172/177/189 等）**：随机化的、每次 boot 不同，
   无法用静态保留覆盖——但它们随时间衰减，且此时系统本来就在开机扰动中。

**因此一个可行的分层修复**：静态保留稳定核心 + 开机后一段时间内不做重度操作
（或接受开机期的高位平台）。

**五、局限**

1. 跨 boot 只验证了 **2 次**（重启前 / 重启后），稳定性结论强度有限；
2. 42 分钟采样已显示平台化，但**未观测到回落至稳态 0.038% 的过程**，其时间常数未知
   （需在 uptime 数小时后复测）；
3. 保留区间的实现（`alloc_contig_range` 或 `memmap=`）尚未验证可行性。


### 8.25 空间结构的定量结论：弥散聚类 + 绝大多数污染页处于空闲态（2026-10-27 上午）

**一、4MB 粒度（pageblock order-10）下的聚类**

单次全量扫描：269,094 个空闲页 / **439 个签名页** / 整体率 0.1631%（重启后 42 分钟内）。

按 4MB 块的累计覆盖（按签名数降序累加）：

| 保留量 | 块数 | 覆盖签名页 |
|---|---|---|
| 32 MB | 8 | 41.2% |
| 64 MB | 16 | 65.4% |
| 96 MB | 24 | 80.9% |
| **128 MB** | 32 | **90.4%** |
| 192 MB | 48 | 98.2% |

439 个签名页集中在 **56 个 4MB 块（合计 224MB）**内，平均每块 **7.8** 个。⟦已证伪（原文）：原写"322 个 4MB 块、平均 1.4 个"——322 是 `hist4m.txt` 中"含任意空闲页"的块数，不是含签名的块数；该文件列 3 是 scanned、列 4 是 signed（见 h4.py），按列 4 重算得 56 块 / 439 页⟧

**判定：污染页高度集中（17% 的块承载全部签名，约 9 倍富集），但不存在单一主导块（最大块 38 页 = 8.7%）。** ⟦原表述"弥散"系分母错误所致。要让保留方案覆盖 90% 仍需 **128 MB（RAM 的 7.4%）**，且放过 10%——代价数字不变，但"没有针对性"这一否决理由不成立。⟧

**二、污染页在物理上互不相邻**

64 个签名页的相邻 PA 间隔：63 个间隔中**只有 1 个是单页间隔**，其余全部为
8 页及以上的倍数（32KB×6、64KB×5、160KB×3、416KB×3…），跨度 448MB。

**判定：写入不是顺序扫描式的，而是落在彼此独立的分散页上**——与"陈旧缓冲页
被分配器打散后再未重聚"的图景一致。

**三、最重要的一条：污染页绝大多数处于空闲态**

把本轮量化与 §8.6 的定性并置：

- §8.6 buddyscan 定性：陈旧列表总人口 **~400 个固定 PA**；
- 本轮全量扫描：**439 个"空闲且带签名"的页**。

**两者几乎相等 ⇒ 任一时刻，陈旧列表里的页绝大部分都躺在 buddy 空闲链表中。**

这条推论把整个问题重新聚焦：

1. 污染页**空闲时无害**——没人读它；
2. 危险窗口只有一处：**它被分配给某个进程、而该进程解引用到被写的字节**；
3. 因此"分配前的检查"是**可行的**——页在分配给用户之前就在空闲链表里，
   此刻扫描它的尾部即可判定是否已被污染。

**四、这使一条此前被我搁置的修复路径重新成立**

§8.16 曾判断"分配时擦洗没用，因为 MD 在分配之后才写"。本轮的量化否定了那个前提：
既然污染页在分配前就已带签名（439 个空闲签名页即证据），**分配时检查就能拦下它们**。

修复形态：在页交付给用户态之前，读该页尾部 64 字节（签名高发区，§2.1）并比对
16B 块 `{small,0}`（small ∈ [0x2710,0x40000]）；命中则换一页或清零。

- 代价：每页一次 64 字节读 + 一次比对，量级远低于任何扫描式方案；
- 覆盖：只要污染发生在页空闲期间（本轮数据显示这是主要形态），就能拦住；
- 局限：若某页在被进程使用**期间**才被写，分配时检查拦不住——这条残余路径的
  占比目前未知。

**五、局限**

1. 439 vs 400 是**跨轮次**比较（§8.6 的 400 来自 6 月前的 6 分钟窗口），不是同窗实测；
2. ~~稳态下的空闲签名页数应更低（0.038%% × 269k ≈ 100 页）~~ —— **该推算已作废**：
   2.94 小时复测为 0.1583%%（425 页），说明 0.038%% 是该 boot 的异常偏低值，
   本节"空闲签名页（约 425）≈ 列表总人口（约 400）"的推论**方向仍然成立**；
3. "分配时检查"的实现需要钩住分配器热路径，风险与性能影响均未评估。

### 8.27 D3 可行性评估：分配时检查不可行（2026-10-27）

**评估对象**

§8.26-E 列出的首选下一步 D3：做一个只读原型，在页交付路径上统计"交付页中有多少
带注入签名"，据此验证"分配时检查"是否可行。

**评估方法：先读内核源码，而不是先造模块**

用户态匿名页的来源路径（`mm/memory.c`）：

    3808:  page = alloc_zeroed_user_highpage_movable(vma, vmf->address);

`do_anonymous_page()` 用的是 `alloc_zeroed_user_highpage_movable`；其定义在
`include/linux/highmem.h:154`，注释明确写着 **"Allocate a zeroed HIGHMEM page"**。
COW 路径（`wp_page_copy`，`mm/memory.c:3021`）同样调用它。

**结论：用户匿名页在分配时被内核清零。**

**判定：D3 不可行**

任何在页空闲期间就被 MD 写入的签名，在交付给用户态的那一刻**已经被清零抹掉**。
因此在交付路径上扫描签名，测得的值必然为 0——这个原型即使造出来也只会给出
一个早已预知的零，毫无信息量。

**连带更正 §8.26 B2**

§8.26 B2 曾推断："大多数污染页永远不会被分配因此无害，致命的是会被分配的页，
所以分配时检查恰好对准危险子集。" **该推论作废**，理由即上。

**但这次检查反而把机制钉得更准了**

结合 §8.26-B1（约 66% 的签名 PA 长期驻留空闲态，`maxrep = scans`，
0x901ce000 连续 44 次扫描都有签名）与本次源码事实，可以确定：

1. **MD 的写入不区分页的状态**——它按自己的陈旧 PA 列表写，页空闲时写、被占用时也写；
2. **页空闲期间的写入是无害且不可积累的**：签名会被下一次分配清零；
3. **真正的伤害只发生在"页已被某进程占用、MD 仍在写"这一个窗口内**；
4. 因此**唯一有效的 AP 侧防线必须在分配之后**——检测进程内的活页，或让受害者
   在解引用前自保（§8.16 的指针闸门）。

**对后续优先级的影响**

| 方向 | 状态 |
|---|---|
| D3 分配时检查 | **否决**（本节） |
| 页保留/回收类（dpquar/dpclamp/牺牲池/热点保留） | 已否决（§8.15、§8.25） |
| §8.16 解引用前指针闸门 | **仍是唯一有证据支撑的 AP 侧方向** |
| D1 DPMAIF 内部仪器 | 仍是定位触发条件的唯一途径 |
| D4 更多跨 boot 样本 | 仍缺 |

**方法学记录**：本轮先用 20 分钟核源码，避免了一次内核模块的开发。若直接动手造
D3 原型，会得到"交付页签名率 = 0"这一预知结果，白费工且引入风险。
**先证伪前提，再决定是否造仪器**——这条应固化。


### 8.28 D1 第一轮：DPMAIF 寄存器/环窗只读仪表 + buddyscan 前缀偏置标定（2026-10-27）

**一、`dpscan.ko` 实跑（92 分钟，5307 次全窗逐字比对）**

只读仪表：`ioremap` + `readl` + `copy_from_kernel_nofault` + 页状态 inline；不写寄存器、
不打文本补丁、work 内不分配。92 分钟内无 Oops / 无 RCU stall / 无重启。

| 判据 | 结果 |
|---|---|
| 窗口内容变化 | **chg = 0**（10,240 个 BAT 字 + 32,768 个 PIT 字，一个字未变） |
| 窗口内 PA 的页状态 | **OWNBAD = 0**；5,110,641 次分类全为 counted，buddy/anon/slab 各 0；`trunc=0 copyfail=0` |
| 基址寄存器 | **无 MOV**，92 分钟稳定 bat=0x8fe40000 / pit=0x8fec0000 |

这不是仪器失明：同一时段寄存器区有 **77 个字在变**，模块在读、在比、在判。

**二、但这个负结果不能当"活跃区不变"用**

idle-vs-load 的逐字 diff 解出 `+0x184` 是 **BAT 生产指针**，全程走位：

```
+0x184   idle=8fe4f678  load=8fe51b50  load2=8fe522f8  end=8fe56d00
```

相对 BAT 基址 0x8fe40000 即 **+0xf678 → +0x16d00（22.8 页）**，而本仪表扫的窗口是
**0xa000（10 页）**。**指针从一开始就在扫描区之外**——这 92 分钟看的是 BAT 的低位
**静态区**，活跃区（约 12.8 页）从未进入视野。同理 `+0x094` 是另一条 PA 指针，全程落在
PIT 基址 +0x20000 之外（0x226e0…0x2e5e0）。

⟦证据不足（限界必须随结论引用）：本轮只否证了"低位表项陈旧"，**未**否证"表项陈旧"。⟧

**三、从 77 字四态 diff 解出的寄存器语义**（idle / load / load2 / end）

| 偏移 | 语义 | 依据 |
|---|---|---|
| `0x1022d000+0x184` | BAT 生产指针（单调递增） | 0xf678→0x11b50→0x122f8→0x16d00 |
| `0x1022d000+0x094` | 另一条 PA 指针，在 PIT 窗之外 | 0x8feee5e0→0x8feed380 |
| `0x10011000+0x864`/`+0xc28` | dpmaif 活动标志（0→0x300 并**锁存不回**） | 停载后仍为 0x300 |
| `0x1022d000+0x330/334/33c/340` | 队列深度/信用（0x120→0x140→0x170→0x110） | 四字联动 |
| `0x1022d000+0x064/084/088` | 随活动翻转的状态位（load2 回到 idle 值） | 非计数器 |

**四、外部限制：蜂窝口没有流量**

6.53 GB 下行全部走 eth0；`ccmni3` 92 分钟只涨 **205 kB**（模组 PDP 无 internet 出口）。
但 dmesg 里 dpmaif `txq` 同期走 **8400 → 9767（+1367 包）**。即 dpmaif 有活动、却没有改写
这两张表——"表不变、写入仍在发生"这个矛盾本身指向：写入目标并非现取于这两张表。

**五、buddyscan 前缀偏置标定（同 30 分钟窗，前缀 vs 全量）**

`maxhits` 默认 48 且 `module_param(...0444)` 运行时不可改（`buddyscan2.c:37,39-41`），
扫描循环是 `for (pa = PA_BASE; pa < PA_END && n < maxhits; )`（`:136`）——**每轮从最低址重来、
凑满 48 个就停**。因此它截断的是**遍历**，不只是输出。

| 指标 | 前缀 maxhits=48 | 全量 maxhits=100000 | 比 |
|---|---|---|---|
| 同窗 30 min 新 distinct PA | 10.5 /min | 15.3 /min | **低报 1.46×** |
| 每扫描检出 Δsigned | 恒 48（截断） | 354.3 | 7.4× |
| 每扫描检查空闲页 Δbuddy_pages | 5,689 | 258,312 | **45.4×** |
| 签名密度 signed/buddy_pages | 0.844 % | **0.137 %** | 前缀**高估 6.1×** |
| maxpa（可达地址） | 178 min 只到 0xa2295000 | 首次扫描即 0xc0a3f000 | +488 MB |

**全量扫描耗时 min 0.07 s / median 0.09 s / max 0.11 s。** ⟦结论：`maxhits=48` 不可辩护——
全量只贵 0.1 秒，却多 45 倍覆盖。历史上一切用默认 maxhits 的 buddyscan 定量结论，
密度与可达地址两项一律按上表换算；§8.22 的"32 MB 集中"正是这个偏置的产物。⟧

修复方向（下一轮）：`maxhits=0` 表示不限、达上限时打印 `TRUNCATED`、轮起点改为**轮转**
（N 轮覆盖全域）、参数改 0644。同时任何"0"必须写成 `0 / N 次观测，检出下限 X`。

|---|---|---|
| PIT 环长 | **0x20000** | `+0x1e4` 是尾指针，90 分钟恒等于 base+0x1fff8 = 0x20000-8 |
| BAT 环长 | **0x20000** | `+0x184` 走位 0x174a0 → 0x1c9b0 → 0x1ea58 后**回绕到 0x2bb8**，只有环长 0x20000 能解释 |
| `+0x094` | 落在 [0x20000, 0x40000) 的邻居缓冲内 | 0x2e4b0 / 0x2c210 / 0x24860 |

**§8.28 的 v1 窗口（BAT 0xa000）短了 0x16000 = 22 页。** v2 里 **4,867 / 6,267 次变化
（77.7%）发生在 0xa000 以上**——即 v1 从未看过的地方。⟦这坐实了 §8.28 二节给出的限界：
v1 的 `chg=0` 描述的是低位静态区，与活跃区无关。⟧

**二、OWNBAD 首次开火（181 条），但有两种解释并存**

三阶段速率：

| 阶段 | OWNBAD | 速率 |
|---|---|---|
| 加载前 20 min | 13 | 0.65 /min |
| 加载中 30 min | 125 | **4.17 /min（6.4×）** |
| 停载后 40 min | 43 | 1.07 /min |

同一时段**窗口 churn 本身与加载无关**（69.7 vs 69.6 次/分，完全平坦）——所以"陈旧描述符
出现率随加载上升"不是背景噪声，是一个独立信号。

命中集中在三个 PIT 槽（全部 `cnt=0 buddy=1`）：

| 槽偏移 | PA | 次数 | 跨度 |
|---|---|---|---|
| 0x3138c | 0x91118000 | 113 | 82.3 min |
| 0x312d4 | 0x91008800 | 63 | 77.8 min |
| 0x31d14 | 0x9100a000 | 5 | 3.5 min |

⟦**未裁决**：至少两种解释与现有数据同样自洽——
(A) **use-after-free**：表项仍指向已释放页且写入者仍在用；
(B) **槽消费后不清零**：页正常释放回 buddy，槽里留旧值，但无人再读。
判别点只有一个：**页处于 buddy 期间，该描述符是否被重写过**。本轮采样是 1 Hz 全窗差分，
只记录"槽值变了"，未把"变化时刻 × 该 PA 当时的页状态"配成对，因此**无法区分 A 与 B**。
v3 正在做这个判别；在此之前，本条不得作为"已找到陈旧列表"引用。⟧

**三、MD 共享内存路线：结构性关闭**

`/proc/iomem` 实测：

```
94000000-9820ffff : reserved        <- ap_md_c_smem
9a000000-9a10ffff : reserved        <- ap_md_nc_smem
bfd60000-bfd6ffff : System RAM      <- ccci_tag_mem（唯一可读，64 字内无 PA）
```

前两块**不是 System RAM**，不在 arm64 线性映射内，`LINMAP() + copy_from_kernel_nofault`
只能得到 -EFAULT（逐页读，失败页数 67/67、2/2，非整块丢弃）。**这不是实现问题，是架构限制。**

⟦对 §10-U1 的意义：E4 中"MD 侧列表 AP 读不到"这半句在**共享内存**这条路上得到支持；
但 AP 可见的 dpmaif 表区**确实**存在指向已释放页的槽（第二、五节），所以"AP 完全看不到
陈旧 PA"这个更强的说法不成立。⟧

**四、判据缺口：描述符低位带 flag（v3 第一优先修）**

CHG 流里出现 `8f028010`、`ab5bbe10`、`acf16810`、`91306210`——**PA 在高位、低位是 flag**。
而 `pa_like()` 要求 `(v & 0x7ff)==0`，故所有带 flag 的表项对扫描不可见：

- `bat` 区 `pa_words = 0`（它根本不是零 flag 的 PA 表）；
- **181 是下界**，不是全量。

**五、未分类桶：1,004,571 字（16.6%）**

PIT 区 `pfn_valid` 且 `page_count==0` 但既非 buddy/anon/slab 的字，占 PA-like 字的 16.6%。
在查清它们是否落在 `reserved` 区间之前，OWNBAD 的语义不完整——若多数指向 MD 保留区，
那它们根本不是错误。

**六、限制（必须随结论引用）**

1. **蜂窝口依旧零流量**：`ccmni3` 90 分钟仅涨 91 kB；两轮加载共 17.6 GB 全部走 eth0。
   dpmaif RX 这条路径从未被真正压到。
2. 时间基准：`date` 与 `/proc/uptime` 分属两个 fork，重载下偶尔跨秒，导致原始 epoch 列
   有 59/75,918 行（0.078%）回退 ≤0.16 s；已用 uptime 重建排序键（`dpscan2_fixed.tsv`
   全程严格递增，墙钟漂移 0.160 s = 1.8 ppm）。⟦仪器缺陷，已修；原始列未改动。⟧

### 8.30 D1 第三轮：判别结果 —— 陈旧描述符是"死槽"，不是 use-after-free（2026-10-27）

**一、判别结论**

§8.29 二节提出两种解释并存，(A) use-after-free 与 (B) 消费后不清零。v3 的判别结果指向 **B**：

| 判据 | 结果 |
|---|---|
| `slot_changed_while_buddy` | **0** |
| `slot_changed_while_counted` | **0** |
| `buddy_flicker_only` | 3（slot 2 / 7 / 12） |
| 15 槽 × 16,995 次采样（200 ms）的 `rawchg` | **全部为 0** |

即：那一片描述符在 56 分钟里**一次都没被重写过**，而其中三个槽所指的页在
buddy ↔ counted 之间反复翻转。教科书级的一行（slot 7，连续三条，`raw` 完全相同）：

```
id=7 off=0x312d4 raw=91008800 pa=0x91008800 cnt=0 st=0x2   (F_BUDDY)
id=7 off=0x312d4 raw=91008800 pa=0x91008800 cnt=1 st=0x8   (F_CNT)
id=7 off=0x312d4 raw=91008800 pa=0x91008800 cnt=0 st=0x2   (F_BUDDY)
```

**二、v2 的 6.4 倍相关性被解释掉了**

| 量 | 加载前 | 加载中 | 加载后 |
|---|---|---|---|
| 页状态翻转 FLIP | 2.9 /min | **22.2 /min（7.7×）** | 0.2 /min |
| 窗口级 CHG | 1354 | 1402 | 1394（**平**） |
| `new_buddy`（把空闲页写进描述符） | 0 | 0 | 0 |

⟦结论：加载驱动的是**页的回收/再分配节奏**，不是描述符写入。§8.29 里"陈旧描述符出现率随
加载上升 6.4 倍"应改述为"**所指页变空闲的频率随加载上升**"，与写者无关。⟧

**三、判据订正：不是 mask 问题，是 filter 问题**

实测步距：pit 活跃环 **16 B**、bat **8 B**。活跃环低位规律是 `0x010 + k*0x200`。
`~0x7ff` 与 `~0xfff` 差不超过 0x800，**永远落在同一个 4 KiB 页**——所以 mask 从来不是问题，
问题只是 `(v & 0x7ff) == 0` 这个**过滤器**。

去掉过滤器后（真实数量）：

| 阶段 | buddy | anon | slab | counted | none |
|---|---|---|---|---|---|
| start | 201 | 0 | 2923 | 1094 | 742 |
| load | 195 | 0 | 3312 | 811 | 642 |
| end | 247 | 0 | 3126 | 610 | 977 |
| blk0 静态表（三阶段） | 0 | 0 | 0 | 16384 | 0 |

**活跃环任何时刻都有 195–247 条描述符指向 buddy 链上的页，anon 恒为 0。**§8.29 的 181 是下界。

**四、16.6% 未分类桶：良性，风险关闭**

123 个抽样字：100% 落在 iomem `System RAM`，且 `page_flags = private = mapping = 0`
——**allocator 从未 online 进任何 zone 的页**。这种页不可能被分配给用户进程，
不构成 use-after-free 风险。§8.29 五节的疑点关闭。

**五、剩余问题**

内存侧已经没有可测的了。活跃环里约 200 条描述符指向已释放页，但槽是死的、无人重写、
也不指向任何用户可分配的页。**真正的风险窗口只剩"谁在读这张表"**，这只能从 dpmaif 驱动侧
（而非内存侧）取证。

**六、本轮仪器缺陷（如实记录）**

1. 首次窗口 pass 与**全零 prev 缓冲**比较，产生 `chg=52992 / ovf=20202 / new_buddy=201` 的
   污染值；运行 36 秒后 `echo reset` 就地清账，**本报告全部窗口数字均为 reset 之后**。
   代价：阳性对照基线被重置一次（序列中出现两个 0）。
2. HB 行打印 `raw=00000000`（`e->new` 在 HB 恒为 0）——**纯显示 bug**；权威的 `rawchg`
   来自真实比较，FLIP 行打印的是真 raw。
3. 构建期两处：`g_pit_base` 只在首 tick 赋值导致初始 read=FAIL；未分类桶抽样只扫 blk0 得 0 样本。

### 8.31 D1 第四轮：蜂窝通路跑通，环写入被真实 RX 驱动，new_buddy 首次非零（2026-10-27）

**一、蜂窝通路（首次真正压到 dpmaif RX）**

`MODE=eth_prio → cell_prio` 后默认路由确实落到模组：

```
before : 223.5.5.5 via REDACTED126 dev eth0 src REDACTED28
during : 223.5.5.5 dev ccmni3 src 10.18.220.249
after  : 223.5.5.5 via REDACTED126 dev eth0 src REDACTED28
ccmni3 rx bytes 694,320 -> 4,955,163,202
```

实测速率 17.5 MB/s（~140 Mbit/s）。**本轮用量 5.02 GB**（`cell_quota.txt` = 5,024,133,836），
在 20 GB 授限内。⟦用量超出预估（2–4 GB）的原因：软闸只掐了加载器、未掐模式，模式在窗口内
多挂了约 15 分钟，网关自身客户端流量继续走模组又累积 1.32 GB。**规则订正：加载器一停即复原模式。**⟧

**二、环写入确实由真实 RX 驱动（本轮最硬的副产品）**

| 条件 | 窗口 CHG 速率 |
|---|---|
| 零 dpmaif RX（v3） | 69.6 次/分 |
| 真实蜂窝 RX（v4） | **160,850 次/分** |

**2311 倍。** 这确证了被监视的窗口就是 dpmaif RX 描述符路径，而不是静态区。

**三、new_buddy 首次非零，但只是上界口径**

```
new_buddy   = 1937          (窗口级，1 Hz)
old_buddy   = 40,617
窗口 CHG    = 3,217,065 / 1207 s
ovf         = 3,090,338     (事件环溢出；new_buddy 在入环前累加，故此数完整)
```

⟦**口径必须随数字一起引用**：窗口差分是 1 Hz，"新值的页是 buddy"是在**写入之后最多 1 秒**
才判定的。因此每次都可能只是"写入时页还在、一秒内被释放"的正常瞬态，
**不能直接等同于"写者把空闲页写进了描述符"**。⟧

唯一无歧义的判据是 200 ms 槽级配对，它在蜂窝负载下仍为 **0**：

```
slot_changed_while_buddy   = 0    (15 槽 × 6,249 采样 @200 ms)
slot_changed_while_counted = 0
slot rawchg                = 0
```

**而且这 15 个槽（pit+0x312b4…0x313ac）位于活跃写入区（0x20000…约 0x30700）之外**，
所以它们在环整体每秒被刷约 2700 次的同时仍然是死的。**决定性测试必须把 200 ms 配对
搬到活跃前沿，而不是这些槽。**

**四、PA 内容监视：三个 PA 全部零写入**

| PA | 采样 | 页状态 | refcount | 内容变化 |
|---|---|---|---|---|
| 0x91118000 | 2839 | counted 2839/2839 | 15 | **0** |
| 0x9100a000 | 2839 | counted 2839/2839 | 16 | **0** |
| 0x91008800 | 2839 | 误报 hole | — | 判据 bug |

⟦两个可读 PA 全程是 counted（被持有者钉住），**没有人在写这 256 B**；`SIGMATCH = 0`。
限制：只覆盖页首 64 B + 页尾 192 B，页中部写入不可见。⟧
⟦bug：`class_pa()` 要求 `(pa & 0xfff)==0`，把 2 KiB 对齐的 0x91008800 判成 hole；
描述符本身是 2 KiB 粒度，判据应按 2 KiB。⟧

**五、事故（必须留档）**

切换命令里用了 `$(...)` 与 `$VAR`，**被本机 bash 展开**：`ip`/`awk` 在本机执行、
远端 `sed` 却照常生效 → **MODE 已被切成 cell_prio、默认路由已落到 ccmni3，而操作者
在看本机的乱码输出**。下一次连接才发现，2 秒内复原。**暴露约 60–70 秒，期间无下载，
只有守护自身流量。** 死开关（sleep 2700）全程在跑。

⟦教训：向设备下发的命令串里**禁止**出现 `$(...)` / `$VAR` / 反引号——本项目此前已因
同一原因浪费过一次（awk 被本机展开成 `{print }`）。需要远程变量就把逻辑写成设备侧脚本再 put。⟧

### 8.32 D1 第五轮：活跃前沿 200 ms 配对，答案是"否"，但只是弱负载下的"否"（2026-10-27）

**一、结果**

```
slot_rawchg                   = 90
slot_changed_newvalue_buddy   = 0      <- 本轮要的那个数
slot_changed_oldvalue_buddy   = 4      （旧值已死，属正常，作对照）
slot_changed_newvalue_counted = 83     （新值指向活页）
```

9 个槽 × 2,621 采样（200 ms，同一 tick 内比对槽值并查页状态）。
**90 次真实重写里：83 次写入活页、4 次覆盖了旧值已死的槽、0 次写入已释放页。**
v4 的 `class_pa()` 4 KiB 对齐 bug 已修（2 KiB 对齐的 0x91008800 现能正常分类）。

**二、三条限制（必须随结论引用，不得省略）**

1. **选点在起载之前做的**——依据的是**空载 churn（23 次/秒）**。256 个桶里只有 9 个有命中，
   且连成一条带 `0x2e600…0x2f7ff`。**加载后真正最热的位置很可能不在这 9 个里。**
2. **选点的每桶命中计数被自身 bug 丢失**：完成判定用了 `grep -c` 读 `/proc/dpscan5`，
   **这次读把事件环抽干**，携带 `bucket_hits` 的 SEL 记录被消耗。偏移可复原，计数不可复原。
3. **负载弱了约 40 倍**：占空比 3 s 打 / 30 s 停，平均 **0.41 MB/s**（v4 为 17.5 MB/s），
   3 秒的 wget 大部分时间花在 DNS+建连。故 524 秒里只发生 90 次重写。

⟦结论定级：这是**弱负载 + 空载选点**下的干净阴性，**不是**强负载下的干净阴性。
不得据此宣布"活跃前沿在任何负载下都不会写入已释放页"。⟧

**三、用量**

本轮 222 MB；`cell_quota.txt` 5,024,133,836 → **5,246,611,534（5.25 GB）**，在 20 GB 授限内。

**四、险情：v4 的死开关没杀**

v4 收尾漏了"杀掉死开关的 sleep"这一步，`pid 9209 / sleep 2700` 仍在跑，
**会在 v5 开始后约 115 秒触发，把模式在加载中途复原**。v5 开跑前一刻被 `ps` 扫出并 kill，
确认为 `OLD_DEADMAN_GONE`。

⟦规则订正：**每轮开始前必须全量扫 `ps` 杀历史死开关，并在报告中列出 PID 清单**；
每轮收尾必须把"已杀"作为显式验收项，不能只写"复原了模式"。⟧

**五、下一步**

唯一能把这条阴性做实的是：**先起载 → 再选点 → 采样周期收到 20 ms**，负载拉到 v4 量级。
按 17.5 MB/s、150 秒计约 2.6 GB，硬顶 4.0 GB。

| 事件丢失 | — | **ovf = 0** |

32 个前沿槽全部取自当前写入前沿（`0x29a00…0x2e500`，每桶 `bucket_hits=288 / slot_hits=9`）。

**二、结果**

```

slot_changed_newvalue_buddy   = 0        <- 判据
slot_changed_newvalue_counted = 798
slot_changed_oldvalue_buddy   = 66       （旧值已死，正常，作对照）
```

**821 次真实描述符改写里，798 次写入活页、0 次写入已释放页。** 32 个槽每个恰好变 25 次。

**三、D1 收口结论（AP 侧内存问题）**

⟦**AP 可见的 dpmaif 描述符表，在写入那一刻是干净的。**
在真实 dpmaif RX 驱动下（窗口 churn 160,850 次/分，为静默态的 2311 倍），
以 31.5 ms 分辨率盯当前写入前沿 150 秒，821 次改写中**没有一次**把已释放页写进描述符。⟧

这条把 §8.26-A2「陈旧列表在 MD 侧持续重建，AP 侧不可见」从**弱证据转为强证据**：
此前它只靠 §3-E4 的一次性快照（§8.29 已指出该快照有三条覆盖缺口），现在有了一个
**覆盖正确、负载正确、分辨率为毫秒级的正面阴性**支撑。

**四、残余限制（随结论引用）**

1. 实测周期 **31.5 ms** 而非 20 ms：页在写入后 31.5 ms 内被释放仍会被判成 newvalue_buddy。
2. 仍未做的缺口一：**BAT 区在修正 flag 判据后没有做页状态分类**（v1 报 `bat pa_words=0`
   是旧过滤器所致；v3 的直方图与分类都只覆盖 pit 的 blk0/blk1）。
3. 仍未做的缺口二：**§10-U1 未裁决**——dpbatfix 记的"BAT 基址指向已释放页"至今没有对照实验。
   v2 只验证了基址 2 KiB 对齐、`pfn_valid`，**没有查该基址页自身的 page_state**。
   ⟦这是一个极小成本的缺口：模块里加一行 `page_state_pa(bat_base)` 即可回答。⟧
4. MD 侧不可达：共享内存 `no-map`（§8.29 三节）、AT 通道未验证。

**五、下一步（按性价比）**

1. **补缺口二**（BAT 基址页的 page_state）+ **补缺口一**（BAT 区按修正判据分类）——一次短跑即可，不需要蜂窝。
2. **驱动静态分析**：MD 侧既然读不到，就反过来查 AP 驱动在什么路径下把页 PA 发布进 BAT/描述符、
   以及有没有"释放后仍被引用"的路径。kallsyms 与反汇编工具在库（`kern_an.py`），**纯主机侧、零成本**。
3. 剧集触发条件的调查，若还要继续，只剩 MD 侧，而 MD 侧的三条通路（共享内存 / AT / 固件逆向）目前都被堵死。

### 8.34 静态反汇编：BAT 发布/归还路径与危险窗口（2026-10-27，纯主机侧）

工具 `tmpfiles/p0x/kern/kern_an.py`（capstone + kallsyms 注解，BASE_VA=0xffffffc008110000），反汇编约 2800 条指令。**本轮未访问设备。**

**一、结构定位（纠正一个此前的心智模型）**

qctx = base + qid*0x81c0；描述符上下文在 qctx+0x488：

| 偏移 | 含义 |
|---|---|
| +0x490 | PIT VA（16 B 项 × 0x2000 = 0x20000） |
| +0x4a4 / +0x4a6 | PIT ridx / hw-wridx |
| +0x4b0 / +0x4b8 | BAT VA / BAT PA（8 B 项 × 0x4000 = 0x20000） |
| +0x4d0 | BAT 影子 VA（{skb@0, dma@8, len@0x10}，步距 0x18） |
| +0x4500 / +0x4520 | 同构 FRG 表 / 影子（步距 0x20） |

⟦**PIT 项里放的是 BAT 槽号，不是 PA**（word0 bit0=有效，bits3..15 与 word1 bits40..42 合成 16-bit 槽号）。PA 只在 BAT / FRG 表里（低 32 位 + 字节 4 = PA>>32）。**此前把 PIT 当「PA 表」的所有推理须按此重读。**⟧

**二、发布点**

| 函数+偏移 | 指令 | 目标 |
|---|---|---|
| `alloc_med_rx_buf+0x2b0` | `str w0,[x28,x23]` | BAT 槽低 32 位 = dma_addr（x23=idx*8，x28=[qctx+0x4b0]） |
| `alloc_med_rx_buf+0x2a8` | `strb w1,[x2,#4]` | 槽字节 4 = PA>>32 |
| `alloc_med_rx_frag+0xf4/+0xf0` | str / strb | FRG 表槽 |
| `bat_init+0x60/+0x64` | dma_alloc_attrs | **只建空表，不填任何 PA** |

提交门铃 `med_bat_recycle_cmd+0x6c`：命令字 0x90000000|qid<<27|count<<16|wridx，成功后才推进 wridx。

**三、归还点（没有一个同步撤销 MD 可见结构）**

| 函数+偏移 | 动作 | 撤销 BAT[idx]？ |
|---|---|---|
| `collect+0xd68` | __dev_kfree_skb_any | **否** |
| `collect+0xa48/+0xfb8` | dma_unmap_page_attrs | **否** |
| `stop_rx_sw+0x228/+0x274` 两个循环 | unmap + 归还页 | **否（当轮不清表）** |
| `stop_rx_sw+0x1c0/+0x1d4` | memset(pit_va) / memset(bat_va) | **是**（先释放后清零；不清基址寄存器） |

**四、危险窗口**

| # | 路径 | 需要 stop？ | 能否解释稳态注入 |
|---|---|---|---|
| A | refill 失败：free 与影子清零无条件，覆盖只在 dma_map 成功后 ⇒ BAT[idx] 永久持已释放 PA。但失败分支**不响门铃** ⇒ MD 消费指针停在 idx ⇒ **RX 停摆**而非注入 | 否 | 否（症状不符） |
| B | 每包 free→publish 间隙内 BAT[idx] 持已释放 PA | 否 | 否（无门铃 MD 不能越过 idx，推断） |
| **C** | **tasklet 与 work 都调用 collect，而 collect 内无并发保护**（+0xf40 只护 log-history；tasklet 设的 [qctx+0x85c4]=1 无人检查）。若二者同解一条 PIT 项：同一 skb 被 kfree 两次 + 连发两次 recycle_cmd ⇒ MD 消费指针 +2，表里只有后写者 ⇒ **idx+1 槽被当有效** | **否** | **是（唯一候选）** |
| D | stop/start 窗口 | 是 | 否（与 §8.28–§8.33 阴性一致） |

⟦窗口 C 目前是**推断，未证明 tasklet 与 workqueue 真能并发进入 collect**。证伪方法见 §8.34 五节。⟧

**五、窗口 C 的证伪路径（任一即可）**

1. 在反汇编里找到 collect 的真正互斥点（in_collect 计数/原子、tasklet_disable、cancel_work_sync 之类），并证明两上下文不会同时进入；
2. 在 collect 入口/出口记录 CPU id + ktime，实测两上下文是否重叠。

若确认无重叠，则只剩 A/B（只造成 RX 停摆），**稳态注入在 AP 侧无法成立**，须转向 MD 侧或「PIT 槽号被篡改」。

**六、连带更正：§4-A6 方向写反了**

原文「stop 路径先归还 RX 页、后等 medmcu ack」。实测顺序是 disable_irq(+0xd8) → **stop_hw(+0xe4，DL idle/ack 等待)** → stop_tx_sw(+0xec) → **stop_rx_sw(+0xf4，还页+清表)**，即**先等 ack 再还页**。

⟦这使「stop 路径留下 MD 可见陈旧 PA」的假设从「很可能」降为「不成立」，与 D1 六轮的阴性互相印证。⟧

**七、本轮未覆盖**

谁把 [qctx+0x4b8] 的表 PA 写进 MD 寄存器 0x1022d180/0x184（dpmaif_set_addr_and_size_from_medmcu / dpmaif_start / drv_dpmaif_dl_* 未通读）。
### 8.35 回撤与影响范围：PIT 不是 PA 表，§8.29–§8.33 的结构语义作废（2026-10-27）

触发：§8.34 的反汇编实测——**PIT 项（16 B）里放的是 16-bit BAT 槽号 + u16 长度，不是 PA**；
PA 只在 BAT / FRG 两个表里（`qctx+0x4b0` / `qctx+0x4500`，8 B 项，低32位 + 字节4 = PA>>32）。

**一、作废的结论**

| 原结论（位置） | 处置 |
|---|---|
| 「活跃环任何时刻有 195–247 条描述符指向 buddy 上的页」（§8.30 三节） | **作废**。那是`pa_like()` 命中的“像 PA 的字”，不是描述符；PIT 项本身不含 PA |
| 「三个 PIT 槽 0x3138c / 0x312d4 / 0x31d14」的叫法（§8.29 二节、§8.30 一节、§8.31 三节、§8.32 一节） | **语义标签作废**——它们不在 PIT 环内（PIT 环只有 0x20000） |
| 「32 个前沿槽」的叫法（§8.33 二节） | 同上 |
| 「D1 收口：AP 可见的 dpmaif 描述符表在写入时刻是干净的」（§8.33 三节） | **降级**，见下 |

**二、仍然成立的观测事实（与结构语义无关）**

1. 被监视的那片字，在六轮里**从未被写入过一个解出来是已释放页的值**（`newvalue_buddy` 六轮累计 0）；
2. 其中少数几个字的值在 6 轮里**恒为常量**，而它们解出的页在 buddy ↔ counted 之间反复翻转；
3. 蜂窝负载使那片区域的**字级变化率**从 69.6 次/分升到 160,850 次/分（2311 倍）——这是纯计数事实；
4. 基址寄存器（+0x180 / +0x1e0）六轮无 MOV，期间没有发生 stop/start。

**三、真正的缺口：BAT 表从未被扫描过**

⟦v1 报 `bat pa_words=0` 是旧的 `(v & 0x7ff)==0` 过滤器所造成（BAT 项低 11 位带 flag）；
v3 的 flag 直方图与页状态分类**只覆盖了 pit 的 blk0/blk1**。
也就是说：**存放真实缓冲页 PA 的那张表（BAT），D1 六轮一次都没有按修正判据分类过。**⟧

因此 §8.33 的收口应降级为：

> **被监视的那片内存没有被写入已释放页指针；但存放 PA 的真正表格（BAT）尚未测。**
> 「AP 可见描述符表保持干净」这句话目前**没有证据**，撤回到「未测」。

**四、对 §8.26-A2 的影响**

§8.33 曾把 A2「陈旧列表在 MD 侧、AP 不可见」从弱证据升为强证据。**该升级一并撤回**，
A2 回到证据不足状态（仍只有 §3-E4 的一次性快照支撑，而该快照有三条覆盖缺口）。

**五、下一步的顺序（因本节而调整）**

1. **先测 BAT 表**（按修正后的 flag 判据、在真实 RX 负载下分类页状态）——这是 D1 欠下的唯一实测；
2. 同时做静态侧的互斥点排查（§8.34 窗口 C 的证伪）；
3. 两者都做完再谈收口。
### 8.36 静态排查：`collect` 无互斥，窗口 C 结构上成立（2026-10-27，纯主机侧）

**一、判定 (b)：没有互斥**

| 项 | 结论 |
|---|---|
| `collect` 入口前 80 条 | **无** `ldaxr/stxr/casa/ldadd/ldset`，**无** 任何锁/BH/抢占/`tasklet_disable` 调用。唯一门槛是 `+0x40 ldrb w0,[x19,#0x489]`（rx_enabled），**是纯读不是 test-and-set** |
| 两个乒乓函数 | 都只测 rx_enabled，**都不测 busy 标志**，都无条件先 `str 1` 置位 |
| `tasklet_kill`/`tasklet_disable`/`cancel_work_sync` | dpmaif 区间内**一次都没有**；只有停机路径两处 `flush_work` |
| `queue_work_on` 的 cpu 参数 | `mov w0,#4` = **`WORK_CPU_UNBOUND`**（可跑任意 CPU）；`tasklet_hi_schedule` 只在本 CPU ⇒ **跨 CPU 重叠结构上可能** |

**二、`g_ctrl+0x85c4`（busy 标志）的全部读写点**

| 函数+偏移 | 指令 | 读写 |
|---|---|---|
| `tasklet+0x20` | `str w0,[x20,#0x5c4]` | 写 1 |
| `tasklet+0x30` / `+0x90` | `str wzr,[x20,#0x5c4]` | 写 0（两条返回路径） |
| `work+0x28` | `str w24,[x0,#0x24]` | 写 1 |
| `work+0x40` | `str wzr,[x19,#0x24]` | 写 0 |
| `stop_hw+0x2c8` | `ldr w1,[x2,#0x5c4]` / `cbnz` | **唯一读点**，停机路径的软等待，且非原子 |

⟦**这标志不可能是互斥**：全部是「无条件写 1、退出写 0」，**没有一次读-改-写**。
停机时那个读点只是空转等待，不是入口闸门，且普通读+普通写会丢更新。⟧

**三、乒乓协议（结构层）**

`collect` 返回值决定交给谁：返回 0 → 自续跑（tasklet_hi_schedule）；返回 2 → 交给另一方（queue_work_on）。
`give_more`（ISR 侧唯一触发器）**不看任何标志**，无条件 `tasklet_hi_schedule`。

内核只保证「tasklet 自身串行」「work 自身串行」，**唯一可能的并发对是 {tasklet} × {work}**，而二者入口都只测 rx_enabled（只在 stop_hw 被清 0）⇒ **稳态下两者都能进**。

⟦窗口 C 由「推断」升为「结构上成立」。\*\*但尚未观测到重叠。\*\*⟧

**四、钉死 C 需要的运行期证据（按性价比）**

1. **失同步（更便宜、更致命）**：在 `drv_dpamif_med_bat_recycle_cmd` 记录 `(wridx, count)` 序列。若出现同一 wridx 的连续两次 count=1 门铃而 PIT 消费不匹配，则门铃/表内容已失同步，MD 必然读到游离 PA。
2. **重叠**：在 `collect` 入口与全部 return 站点记 `smp_processor_id()` + 在飞计数（O(1)）。在飞计数 ≥2 即成立。

**五、下一轮最该补的一刀（免费）**

`tasklet+0x110/+0x130` 与 `work+0xec/+0x110` 有对称的「清零 + `dmb ish`」写法，对象疑为 `qctx+0x5cc/+0x5c8/+0x5d4`，**其读者尚未定位**。若这三处构成隐含的「同一时刻只允许一方持有」约束，C 会被削弱。

**六、本轮更正（对 §8.34 的自我修正）**

§8.34 曾写「`[qctx+0x85c4]=1` 无人检查」——**一半错**：它有一个读点（`stop_hw+0x2c8`），但该读点在停机路径且非原子，**不改变「无互斥」的结论**。
