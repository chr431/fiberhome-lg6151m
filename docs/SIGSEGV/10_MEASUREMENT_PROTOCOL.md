# 10 · SIGSEGV 测量协议（canary 命中率）v1.0 · 2026-11-01

> 本协议是**测量能力的边界声明**，不是研究失败的记录。它防止后来人拿两个不同会话的数字做因果推断。

## 0. 一句话

**canary 命中率不是可复现的量化指标**：它在 **~1/min 与 ~127/min** 之间随**未知的慢变设备状态**漂移
（同一批"新起 canary"在不同时间相差 **19 倍**）。
因此 **「1.3 命中/千包」只能在同一会话内做相对比较，跨会话一律不可比**。

## 1. 只用会话内对照（硬规则）

- **同一批 canary 进程**贯穿全部对照臂；中途不重启（重启会改变栈页，等于换了被测量）。
- **连续多档位**：在同一次连续观测内依次测多个流量档位（例如 0 / 2 MB/s / 20 kpps），档间留 ≥60 s 静默。
- **每档必须记录三项**：`h4 增量`（绝对命中数）、`设备侧 RX 包数`（来自 `/proc/net/dev` 的 rx packets，不是估算）、`时长`。
- 判据一律用 **命中/千包**，但**同时报绝对命中数**（见 §3）。

## 2. 跨会话数字：必须标注「不可比」

**反例（2026-11-01 实测）**：

| 会话 | 条件 | 命中率 |
|---|---|---|
| 10:20 LAN 臂（Lead 发 400 MB / 24 s） | 同一批 canary，热态 | **127.6 / min（1.38 / 千包）** |
| 11:35 形态实验（四臂，含 1.04 M 包小包臂） | 新起 canary，冷态 | **1.2–2.4 / min（0.001–2.6 / 千包）** |
| 11:45 重启实验（5 批新 canary） | 每批 60 s | **1.0 / min** |
| 11:52 环重置实验第 2 轮 | 新起 canary | **19 / min（4.6 / 千包）** |

同样是"新起 canary"，**1.0 / min vs 19 / min 差 19 倍**。
**任何跨会话的速率比较都必须标注「不可比」**，除非能证明当时的慢变状态相同（目前做不到）。

## 3. 报告格式：绝对数 + 速率，二者缺一不可

- **只给速率会误导**：4 个 canary 跑 60 s、命中 1 次 → "1/min"；命中 2 次 → "2/min"，但两者在统计上无法区分。
- 规范：`命中 N 次 / 时长 T s / RX 包 P 个 → N/T 次每分钟，1000·N/P 次每千包`，
  并注明 **N < 10 时不做速率推断**（小样本）。

## 4. 必须记录设备状态协变量（为将来逼近"慢变状态"）

每次采样/每档位至少记录：

| 协变量 | 采集方式 |
|---|---|
| uptime | `cat /proc/uptime` |
| 可用内存 / 缓存 | `free` 或 `/proc/meminfo` 的 MemAvailable / Cached |
| 活跃连接数 | `/proc/sys/net/netfilter/nf_conntrack_count` |
| 各口 RX/TX 包数 | `/proc/net/dev`（eth0/eth1/br-lan/rai0/ra0/ccmni2） |
| 链路事件 | 是否有 `ip link set down/up`、模块 load/unload、soak-qa 类注入 |
| canary CPU | `/proc/<pid>/stat` 的 utime+stime 求和（归一用） |
| 时间源可靠性 | 设备时钟是否跳变过（今天 10:35/11:18/11:21 各跳一次） |

## 5. 已被排除的三个杠杆（不要重复做）

| 杠杆 | 变化幅度 | 命中率响应 | 结论 |
|---|---|---|---|
| 流量（RX 包数） | **1,366×**（758 → 1,035,961） | 恒定 1.2–2.4/min | **流量不是决定性因子** |
| canary 重启（新栈页） | 5 批 | 1.0 vs 长期运行 2.75/min | **"热页"假设不成立** |
| eth0 环重置（down/up ×2） | 2 次 | 4.6 → 4.2/千包 | **"环重置创造 stale 描述符"不成立** |

## 6. 仍然成立的结论（不因上述阴性而动摇）

- **写入者在有线端口共用的 EDMA RX 路径**：LAN-only 臂（eth0 RX 反而下降、rai0 TX 全程 0）命中率 ×71；
- 记录形状 `{u32 X, 0, u32 len≈1601, __be32 本机 IP, 0,0,0,0}`（32 B），w1/w3 恒 0；
- 记录内容随**当时的流量构成**变化（WAN 为主时是 WAN 地址，LAN 为主时是 LAN 地址）——
  **IP 分布是流量构成的反映，不是写入者的属性**。

## 7. 下一轮唯一未排除的方向

**慢变设备状态**（页池组成 / stale 描述符存量 / 其它）。建议做法：
连续 4–6 小时，每 5 分钟记录「命中率 + §4 的全部协变量」，看命中率跳变时**哪个协变量先动**。

## 9. 数据完整性断言 = 行数 + 字段数 + 校验和（2026-11-01 新增，skeptic 提案 / Lead 已批）

任何跨 SSH 的批量拉取：先设备侧 `wc -l`，再分页（≤250 行/页），落地后**三条全过**才算成功：

1. `wc -l` 与设备侧相等；
2. **每行字段数**符合格式（例：h4_meta 必须 7 字段；corr tsv 必须 18 字段）；
3. **md5/sha256** 与设备侧一致（或整文件 md5）。

**反例（2026-11-01，实弹）**：
- `h4_meta.txt` 2554 行**通过** `wc -l` 断言，但其中 **2 行只剩文件名**（h4_19810_3.bin / h4_19811_1.bin）→ 行数断言挡不住「行被截断」。
- `h4_rec200.txt` 落地 **0 字节**，无人发现。

二进制/大文件：一律 `md5sum` 双端比对（沿用 deploy.py put 的口径）。

## 10. canary 类「0 命中」的判据（2026-11-01 新增）

报「0/N」时必须同时写清三件事，缺一不得进结论：
1. **N 是多少次观测**；
2. **检出下限**是多少（rule of three：0/N 的 95% 上界 ≈ 3/N）；
3. **正对照是否打出**（能构造出目标状态一次，证明仪器看得见）。

例：rxring「0 次 DD=1 / 24.9 万次全环扫描」必须附一句「**未能构造 DD=1 正对照**」；否则只能写成「该仪器未验证，结果不可判读」。

## 11. 「未知」必须写 NA，禁止用 0 充当"未测"（2026-11-01 新增，Lead 批准）

**规则**：任何字段只要是"没测到/读不到/不适用"，一律写 `NA`（或省略该字段）；**禁止写 0**。解析脚本必须把 0 视为"未测"，并把它与真实的零区分开。

**前科（全部造成过误读风险）**：
| 事件 | 表现 | 后果 |
|---|---|---|
| sampler2（2026-11-01） | 11,430/11,430 行 `sp=0x0`（阻塞态读不到），派生 `sp_minus_rec=0x0` | 若当真值 ⇒ "记录正好落在 sp 上"的灾难性误读 |
| lab S2 别名 | `alias 192.168.9.77 = 0/565`（实为字节序读反） | 差点否掉"记录能携带注入地址" |
| C-142 自然 NE | `0/4`（实为判据 bug） | 影响面评估从 ≤49% 反转成 ≥51% |
| h4_meta | 2554 行里 2 行只有文件名（其余字段空） | 行数断言通过而内容已损 |
| 本协议 §10 | "0 次 DD=1" 无正对照 | 无法区分"没有"与"看不见" |

**落地检查**（每次数据落地）：① 统计每个数值列的 0 占比；② 0 占比 >95% 的列 ⇒ 视为"未测"，不进计算；③ 任何"0/N"必须附正对照与检出下限。

## 12. 设备级硬约束：`panic_on_taint` + `panic_on_oops`（2026-11-01 新增，Lead 批准）

**事实**：本机两者都开。`bad_page()` 只 `add_taint(TAINT_BAD_PAGE)` 就会触发 `panic_on_taint` → 直接 panic；任何内核 Oops 触发 `panic_on_oops` → 直接 panic。
⇒ **结论：任何内核模块的 bug ≈ 一次非计划重启 + 一次数据代次切换。** 本会话已两次验证（uwhook IABT / pte_redirect bad page）。

### 12.1 模块 bring-up 流程（可回滚）
```
# 0) 记原值（连同 boot_id 写进实验日志）
cat /proc/sys/kernel/panic_on_taint   # ORIG_T
cat /proc/sys/kernel/panic_on_oops    # ORIG_O
cat /proc/sys/kernel/random/boot_id
# 1) bring-up 窗口内临时放开（只改"是否 panic"，不改行为语义）
echo 0 > /proc/sys/kernel/panic_on_taint
cat /proc/sys/kernel/panic_on_taint   # 回读 0
# 2) 空模块先跑：insmod 只注册 /proc、不打任何补丁 → rmmod → 检查 dmesg 无异常
# 3) 一次只开一个站点/一个功能；打印解析出的 64 位地址（%016llx）
# 4) 立即恢复
echo $ORIG_T > /proc/sys/kernel/panic_on_taint ; cat …
echo $ORIG_O > /proc/sys/kernel/panic_on_oops  ; cat …
```
注意：关掉 `panic_on_taint` **不等于安全**——坏页/坏状态仍在，只把"立刻重启"变成"带伤继续跑"，所以窗口结束必须重启一次回到干净状态（并记新的 boot_id）。

### 12.2 数据代次（boot generation）必须写进 manifest
- 每次重启 = **新代次**；跨代次**一律不可比**（速率、PA/VA、页池、"热态"全部重置）。
- 落盘 manifest 至少：`boot_id`、`date +%s`、`uptime`、本次代次内做了哪些写操作/模块加载。
- 截至 2026-11-01 13:40，本会话已 **3 个 boot**（72c136ea… → bbf535d5… → 当前）；任何把跨 boot 数据合并统计的分析都必须显式分层。

## 13. 上机件身份钉死（2026-11-01 新增）

任何要上机执行的二进制/内核模块，实验记录里必须钉死五元组：**`(文件名, 字节数, md5, 构建时间, 源码 diff 摘要)`**，并做到：
1. **上机前**在设备侧 `md5sum` 一次；**上机后**再 `ls -l` 一次，与记录逐项核对；
2. 同一实验的多份报告必须引用**同一个**五元组；引用不一致的按"未验证身份"处理，结论不得进台账；
3. 与 §12.2（boot 代次）配套：**"哪个 boot + 哪个二进制"** 必须能唯一确定一份数据。

**触发本次新增的实例**：`uprot.ko` 先报 187,664 B / `9fc7cca…`，后更正为 **187,656 B / `d3f0dd70505f9405cf99bf51d569b164`**（改格式串之前的构建被误引）。差 8 字节本身无害，但**如果在上机后才发生这种更正，数据就无法归属到具体二进制**。

### 12.3 三类重启必须分开记（2026-11-01 新增）
| 类型 | 判据 | 本会话实例 |
|---|---|---|
| **panic 型** | pstore 里有 Oops/BUG + `Kernel panic` | uwhook（IABT）、pte_redirect（bad page → panic_on_taint） |
| **hang → watchdog 型** | pstore 里**无 Oops**，末尾是 `healthdog: heartbeat stale >90s → EMERGENCY RESTART` | uprot `ro` on nerepair 栈页 |
| 冷复位/断电型 | pstore 为空、`uptime` 归零、无 panic 记录 | （本会话未确认到） |
**报表要求**：每次重启必须写"类型 + 证据文件 + md5"，并更新 boot 代次；**hang 型不能记成 panic 型**（两者根因完全不同）。

### 12.4 实验靶子的禁忌（2026-11-01 新增，Lead 裁定）
**禁止把 `nerepair`（或任何 ptrace 监督者）的 mm 当成 `ro`/`pte_redirect`/`uprot` 的实验对象**——它的 mm 与 ptrace 路径竞争，加写锁极易挂死（表现为 hang→watchdog 重启，不是 panic，最难诊断）。
靶子选：**无 ptrace、无 mmap_write_lock 竞争的阻塞普通 daemon**（dnsmasq 类），或**让 victim 自己 mprotect**（rovictim2 式，最干净）。

### 12.5 本轮允许重启（用户授权，2026-11-01 第 7 轮）与「重启也算数据」
- **授权范围**：仅本轮实验；串口 LK 为兜底恢复手段。
- **重启前必记**：`boot_id` / `date +%s` / `uptime` / 当前臂与目标 `pid+VA` / 已采到的对照数据。
- **重启后立刻**：拉 `/sys/fs/pstore/console-ramoops-*` → **md5 落盘**（下次 panic 会覆盖）→ 用 `analysis/kern/kallsyms.txt` 反查地址。
- **判读**：pstore 的 `CPU/PID/Comm` + 调用栈 = **写入者路径的直接证据（E3）**；仍按 §12.3 三分法归类（panic / hang→watchdog / 冷复位），**hang 不得写成 panic**。
- **代次**：重启即新代次，跨代次不可比（本条不因"允许重启"而放松）。

### 12.6 槽身份前置：槽必须是「写入者的槽」，不能是受害者自己的 syscall 输出缓冲（2026-11-01）
任何用于判读的"槽"（记录出现的位置）在使用前必须过四条：
1. **内容域**：wait4/read 之类 syscall 输出是 16 位状态值（≤0xffff，正常退出 ≡0 mod 256）；记录族 A 值是 40k–220k 且 mod 256 无集中；
2. **变化宽度**：4–8 字节的 syscall 输出**不会**改到 32B 窗口的 `+0x10..+0x17`；若 len/ip 也在变 ⇒ 不是 4 字节输出；
3. **偏移级归因**：faultwatch 一类仪器必须记录 **fault VA**，与槽的 `top−K` 逐字节比对——**页级归因不算**（同一页可能既有 status 缓冲又有记录槽）；
4. **同会话**：内容统计与 fault 归因必须同一次会话内采集（跨会话不可比，§2）。
**反例（2026-11-01）**：faultwatch 注册了 nerepair `top−0x3b0` 所在**页**，9 min 抓到 33,959 次缺页全部来自 `__do_sys_wait4` ⇒ 那是**页级**的 status 缓冲写入，不是该槽；该槽的内容域检验（q0 无一 ≡0 mod 256、89% 在记录 A 域、len/ip 也在变）证明它**不是** status 缓冲。
