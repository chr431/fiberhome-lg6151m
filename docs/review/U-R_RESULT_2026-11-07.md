## 1. p11 的推导

### 1.1 U-Q p9 对照的范围错误

p9 = v7 全集 255 站点（q0..q7）。对静态 busybox 的 objdump 普查：

- `str q → [sp]` 390 条 + `stp q → [sp]` 9 条 = **399** 条 q 存储；
- v7 补 255，未补 **144**；
- 未补里的升序块（q0..q7、16B 步进、偏移升序）：
  - `ioctl_or_perror_and_die` 0x409f38..54（8）
  - `zbc_posix_error_fmt` 0x41071c..38（8）
  - `fmtstr` 0x462894..b4（8）
  - `out1fmt` 0x462d98..db8（8）
  - `ash_msg_and_raise_error` 0x46371c..3c（8，另 0x463778 是 va_list 拷贝，保留）

根因（capstone 实测）：上述前四个用 `stp xN,xM,[sp,#-imm]!` 预索引分配（无 `sub sp`），
且 `mov w?,#-0x80` 在保存块之后（ioctl 甚至晚于首个 `bl`）；第五个有 `sub sp`，但
`-0x38/-0x80` 在 q 存之后。v7 的 `find_prologue`/`vr_offs_sig`/`loaded_recently` 三条
护栏分别误拒。**护栏是为了防 U-M 过匹配，但把真块也挡了。**

### 1.2 p11 站点集

- 基座：p8 的 197 条（v7 内 q2..q7）；
- 补 5 块的 q2..q7：30 条；
- 补 ioctl 第二块缺失的 q7：1 条（0x409fe4）；
- **不补 q0/q1**（浮点实参通道；p9/p10 已证删 q0/q1 或把 vr_offs 置 0 会破坏 awk/printf）；
- 合计 **228**，md5 `eedfbe41da1535dd5aeb3e39d8049b47`。
- 全镜像普查：未补的升序 q 块 **0**；残余 162 条 `str q` 为 q0/q1 对、数据 spill
  （decfloat/__floatscan/fmt_fp 等）与 9 条 `stp q0,q1` va_list 拷贝（不可删，语义需要）。

## 4. T1/T3 残余路径复核（本轮核心问题）

### 4.1 T1：内容已关闭，任务层未测

- **已关**：C-300 的 2×2（feed 冻结后本地洪水 λ 仍 14.2/min = 80%）；C-297（λ 随
  设备面向处理活动：本地 INPUT 17.7 > 转发 4.6 ≈ 空闲 2.6）。"断内容饿死写者"无主张空间。
- **未测 1：厂商 MED IPI 任务停止**。AP 侧符号齐：`mtk_ipi_send`（0xffffffc0084b9ab8,
  T）、`mtk_ipi_register`、`med_stop_ack_ipi_handler`（0xffffffc0085a3c14, t）；MED 固件
  的 `med_ipi_stop_rx_handler` 轮询 0xa5a5a5a5×4 邮箱。C-298 已重建头树，kmod 可构建；
  但 `emiuctl` 只能 `call <addr> <int>`（单参），而 `mtk_ipi_send` 需要
  (dev, ipi_id, opt, data, len, timeout) 多参 ⇒ 需新 kmod；IPI 设备指针/通道号/消息
  布局仍需 RE。预期值低（C-300 已证内容非必要），但这是 AP→MED 唯一带语义的停止面，
  做了就是任务层的收口。风险：参数错 → MED reset/AP 重启（授权内，计划重启）。
- **未测 2：per-CPU λ / 亲和性（4 CPU）**。`/proc/cpuinfo` = 4；引擎按 store PA 嗅探，
  但从未比较"同一受害者在 CPU0/1/2/3 上的 λ"。若存在 per-CPU/簇差异，把关键守护钉到
  安静 CPU 就是低成本缓解。实验：scanary + taskset，同 boot 配对，4 臂 ×10min。
- **未测 3：纯 CPU 负载（无网络）**。C-297 的三臂是 local INPUT/forward/idle；缺"纯
  CPU 忙"臂。若 CPU 空转也抬 λ，则"设备面向处理"其实是通用 CPU 活动；若不抬，则是
  网络处理特有。诊断价值高，无缓解价值。
- **不建议**：FE/PPE 时钟/电源门控（会断网，只能做因果诊断）。

### 4.2 T3：子区窗已关闭，ISU 顶层窗未测且仪器此前没编译

- **已关**：C-280 的 0x9c200000/2MB（pfn_valid=1 的 pl-drambuf 子区）双窗 RR 1.096/0.939，
  冷半区 0 命中，同 pc 同几何击杀 ⇒ "引擎需要 buddy 页/System RAM 子区"被否证。
- **未测：ISU 顶层保留窗 0xbf000000/8MB**。U-H 用 /dev/mem 探测时 `pfn_valid=0` →
  非缓存映射 → 未对齐 SIGBUS，于是改用 9c200000；**原 T3 设计点（ISU 窗）从未被测试**。
  引擎对"顶层 reserved carveout"的可达性是空白，不是负结果。
- **仪器状态**：`tmpfiles/repro/kmod/exilewin.c` 就是为此写的（/proc/exilewin +
  `remap_pfn_range`），但用了 5.15 不存在的 `pgprot_cached()`，**从未编译成功**；
  U-R 改为保留 VMA 默认的 `PAGE_SHARED`（MT_NORMAL 可缓存、带 PTE_USER）后，
  `exilewin.ko` 构建成功（123,800B, md5 c9c80e1c）。`scanary_exile` 已支持
  `--win-dev /proc/exilewin`，`wmd5` 也支持模块缓存映射。
- **上机设计**：emiuctl `mtk_emiisu_control(0)` 关 ISU（C-262，md5 冻结验证）→ insmod
  exilewin → `/proc/exilewin` 报 pfn_valid=0 → mmap 1MB + wmd5 定时（期望 ~1.4GB/s）→
  scanary_exile 栈放窗 → 2400pps 洪水 → 同 boot ABAB，窗口 vs 匿名栈 RR 预注册
  [0.7,1.4]，功效门 λ_A≥20/600s。若窗口 λ=0 ⇒ 放逐可用（可给 dnsmasq/dropbear/v3httpd
  做栈放逐）；若 parity ⇒ T3 真正收口。风险：保留 DRAM 缓存映射（ISU 已关、无 MMIO、
  可 canary/guard），中低；失败即重启回滚。
- **其他廉价变体**：非缓存栈（`pgprot_writecombine`，测引擎是否只认可缓存 store）；
  栈偏移 padding（测固定槽位 vs 实时跟随）；SRAM/TCM 栈（非 DRAM，映射/栈可行性未证）。

**[B] 未核实/边界**

5. T1b 的 IPI 设备/通道/消息布局未提取；预期值低是分析判断，不是实测。

**[C] 下轮入口**
