## A. 补丁机制 —— **PASS（带 1 个真缺陷；v6 未引入回归）**

### A.1 站点字/EXP_WORD —— 通过（字节级）

`ktext.bin`（基址 `_stext=0xffffffc008110000`，与 `kallsyms.txt:1` 一致）在 `0xffffffc00812673c` 起：

```
73c: d503233f  paciasp
740: a9be7bfd  stp x29, x30, [sp,#-0x20]!   <- 补丁点 = EXP_WORD
744: 910003fd  mov x29, sp                  <- 设计上的 resume
748: a90153f3  stp x19, x20, [sp,#0x10]
```

- `kallsyms.txt:621` `fixup_exception = 0xffffffc00812673c`，下一个符号 `do_bad = 0xffffffc0081267a4`
  ⇒ size 0x68 = 104，与源码注释一致。
- `BAKED_PATCH_SITE=0xffffffc008126740`（`fxhook.c:50`）、`EXP_WORD=0xa9be7bfdu`（:52）与实读一致；
  `fx_install` 先比 `p_site != BAKED_PATCH_SITE`（:208）再 `rd32(site)==EXP_WORD`（:213-218）⇒
  **KASLR 基址若变，拒装发生在调用 `p_patch` 之前**，不会野调 `aarch64_insn_patch_text`
  （`kallsyms.txt:508` 0xffffffc008122394，与 `fxhook.c:55` 一致）。这个顺序是安全的关键，v6 保留。

### A.2 PAC / 寄存器 / SP —— 通过

`fx_shim`（`fxhook.c:156-171`；.ko `.text+0xa34`，32 B）实读：

```
0a34 fd7bbea9  stp x29,x30,[sp,#-0x20]!
0a38 fd030091  mov x29,sp
0a3c e00b00f9  str x0,[sp,#0x10]
0a40 00000094  bl  fx_record            (CALL26 relocation)
0a44 e00b40f9  ldr x0,[sp,#0x10]
0a48 fd7bc2a8  ldp x29,x30,[sp],#0x20
0a4c fd7bbea9  stp x29,x30,[sp,#-0x20]!   <- 重放被替换指令
0a50 00000014  b   .                      <- init 回填
```

- 补丁点 `+4` 在 `paciasp` 之后、原 stp 之前（ARM64_PTR_AUTH_KERNEL=y，config:440）；x0=regs 在
  `+4` 处尚未被任何指令消费，shim 存/恢复 x0 正确。
- `bl fx_record` 只破坏 x0–x18/x30（AAPCS caller-saved）；`fixup_exception` 的调用者本就假定这些被破坏。
  `fx_record` 反汇编确认保存 x19–x21（0x0000–0x0004），未触 x22–x29。
- SP/PAC 链：shim 的 `stp/ldp` 配对使 `bl` 期间 SP=entry-32；重放的 `stp` 使 SP=entry-0x20，与原生序言一致；
  函数尾部 `ldp x29,x30,[sp],#0x20` 先恢复 SP=entry 再 `autiasp` ⇒ PAC 校验点用同一 SP，x30 是 shim 保存的
  *已签名* LR。**PAC 链完好**（v5 设备实跑亦证）。

### A.3 ★ 真缺陷 A1：resume 跳过 `mov x29, sp`（v5 遗留，v6 未改）

- `fxhook.c:51` 定义了正确的 `BAKED_RESUME 0xffffffc008126744UL /* fixup_exception+8 */`，**但全文件未使用**
  （grep：仅 :51 一处）。
- `fxhook.c:226-227`：`g_resume = p_site + 4;`（=0x…744）**只用于打印**；`fx_resume_addr = p_site + 8;`
  （=0x…748）才是回填的 B 目标。
- v5 与 v6 的 `init_module` 反汇编完全同构（v5 `.init.text+0x16c` / v6 `+0x230`）：
  `add x10,x19,#8` → 存 `fx_resume_addr`；`add x8,x19,#4` → 存 `g_resume`。⇒ **v5 上机时也是跳到 +0xc**。
- 影响评估：`fixup_exception` 全函数（0x73c–0x7a4）**没有一条 x29 相对访问**——`stp/ldp x19,x20 [sp,#0x10]`、
  其余全是 sp/xN 直接寻址；x29 只被保存/恢复。因此跳过 `mov x29, sp` 对**本内核此构建**功能无害
  （v5 219 s armed + go/no-go + 回滚全绿是旁证）。
- 但这是真缺陷：代码注释与 U-B1 skeptic「无跳过」的结论均不成立；未来任何一次 `fixup_exception` 使用帧指针
  （或换内核/换编译器）都会让 x29 指向调用者帧 → 局部变量/恢复错位，后果不可预测。
- **处理**：本轮若不重建，必须把上述字节级证据写进报告作书面豁免；**任何重建都改成 `fx_resume_addr = p_site + 4`
  （直接用 BAKED_RESUME）**。顺带：`pr_info` 打的 `resume=…744` 是 `g_resume`，**不是真正的分支目标**，
  这条日志会误导后续审计，应一并修正。

### A.4 回填与自检 —— 通过

- 先回填 `fx_back` 的 `b .`（`fxhook.c:228-253`）、再做反解自检（`gotimm` 符号扩展 + `back+(imm<<2)==resume`），
  **最后**才 `apply_patch(p_site)`（:254）。顺序正确：`b .` 活着的窗口内没有任何路径能进入 shim。
- 范围检查：`d > 0x07fffff0 || d < -0x08000000` 拒绝（:220-223）；回填 B 用 `-(1<<27)..(1<<27)`（:234）。
  注：`RANDOMIZE_MODULE_REGION_FULL=y`（config:478）+ `ARM64_MODULE_PLTS=y`（:474），模块区随机化后
  shim 有概率落在 ±128 MB 之外 → **安全拒装**（`-ERANGE`）。这是可用性风险，不是安全问题；U-B1/U-C1
  两 boot 都恰好落在范围内。

### A.5 v6 增量是否破坏 v5 —— 未破坏

v6 只改 `fx_record`（+mm 门，.text 0x05c–0x08c 新增 `current->mm/active_mm` 读取）与 `fx_write`（+probe 分支，

## B. mm 门 —— **PASS（语义）/ BLOCKING（未验证）**

### B.1 `current->mm ?: current->active_mm` 是正确的身份（E2）

- `do_page_fault` 用 `struct mm_struct *mm = current->mm`（fault.c:526）；`!mm`（内核线程未借用 mm）时
  直接 `goto no_context`（fault.c:539-540）→ `__do_kernel_fault` → `fixup_exception`（fault.c:367）。
  即：修复上下文里的 `current` **就是发生该 fault 的那个执行体**（进程/线程），而 TTBR0 页表属于
  `current->mm`，内核线程属于 `current->active_mm`（`kthread_use_mm` 用 mmgrab + active_mm；懒 TLB 时
  active_mm 是上一个用户 mm，恰好也是 TTBR0 实际加载的 mm）。fault.c 自己的 `show_pte()` 对
  `is_ttbr0_addr()` 也用 `current->active_mm`（fault.c:129-131）——语义与模块一致。
- 抢占/中断状态：`CONFIG_PREEMPT_NONE=y`（config:103），uaccess 拷贝不睡眠、不调度；设备启动日志
  `CPU features: detected: Privileged Access Never`（`d28b_lab_segment.txt:221`）⇒ `system_uses_hw_pan()`
  为真，`system_uses_ttbr0_pan()` 为假（`cpufeature.h:747-751`）⇒ `uaccess_ttbr0_enable/disable` 是
  **运行时 no-op**，拷贝期间**不加 IRQ 屏蔽**（.ko 里 0x864/0x874、0xa04/0xa14 的 `cpu_hwcaps` 分支即此判定），
  fault 发生在正常进程上下文。即使发生在 IRQ/softirq，`current` 也仍是"被中断的 task + 当前 TTBR0 mm"，
  mm 身份仍正确（见 D.4 的 comm 归属注意）。
- 记录字段偏移（v6 .ko 反汇编）：`current->mm=+0x3a0`、`active_mm=+0x3a8`、`pid=+0x458`、`comm=+0x618`；
  `regs->regs[30]=+0xf0`、`regs->pc=+0x100`。构建用内核树 `autoconf.h` 与厂商 `.config` 的布局相关项
  （SMP/THREAD_INFO_IN_TASK/CGROUP_SCHED/FAIR_GROUP_SCHED/AUDIT/KEYS/RSEQ…）逐项一致；且 U-C1 的
  P1/P2/H1 记录里 `comm=vmwrite32/mempoke`、`pid=15116/15117` 逐字正确 ⇒ `≤0x618` 的布局在设备上成立。
  这**间接支持** 0x3a0/0x3a8，但不等于验证。

### B.2 ★ 致命缺口：该门从未被正对照"放行"过

- `g_victim_mm` 由 init 的 `find_get_pid→get_pid_task→get_task_mm` 捕获（`fxhook.c:398-409`），
  `fx_record` 在 `g_victim_mm != NULL` 时比较（:122-128）。
- U-C1 的 P1/P2 验证的是 **H1/H3 传入的 `x0(mm)` 与 `g_victim_mm` 的比较**（wrhunt v4），**不是**
  `current->mm` 的读取路径；U-C1 的 H4/H5 在联合窗 `hit=0`，而该窗 victim 以 `--ro 0` 正常跑、
  没有 EL0 fault，所以 H4 也从未有过"已知正例"被放行/拒绝。U-C1 的 v3→v4 只证明了"假阳性被拒绝"，
  一个坏掉的 `current->mm` 读取（恒 NULL/恒垃圾）会产生**同样的 0 命中**。
- 失败模式是**静默假阴性**：门若读错，所有真实事件被丢弃 → ring=0 → 判读表落 "E2 写者不是内核 uaccess"
  —— 与"写者确实不走 uaccess"不可区分。这是本轮最危险的失效方向，因为它会把一个仪器缺陷写成机制结论。
- **必须在开窗前补一个正对照**（见 C.6 / M2），用"目标进程自己对自己 RO 页做一次内核 uaccess 写"来
  同时验证 mm+far+fault 类+ring 写入路径。P2 现有设计做不到（C.1–C.4）。

### B.3 生命周期 —— 通过

- `get_task_mm()` 用 `mmget()`（`kernel/fork.c:1310-1324`），持的是 `mm_users` 引用；`mm_count` 在
  `mm_users` 归零的 `__mmput()` 里才 drop（`kernel/fork.c:1118-1148`），所以我们的引用**确实保活整个 mm**。
- `mmput` 覆盖所有路径：init 的 `proc_create` 失败（`fxhook.c:411`）、`fx_install` 失败（:415）、
  exit（:426）；`get_task_mm` 返回 NULL 时无引用（:407）。`find_get_pid` 的 pid 引用在 `get_pid_task`
  后立刻 `put_pid`（:403），task 引用在 `get_task_mm` 后 `put_task_struct`（:406）。**无泄漏、无 UAF**。
- victim 在 rmmod 前退出：mm 由我们的 `mm_users` 引用保活，rmmod 的 `mmput` 在进程上下文触发
  `__mmput()`（exit_mmap 等，可睡眠）——合法；代价是拆解被推迟到 rmmod。若 victim 的 mm 很大（此处
  scanary 很小）只是耗时。竞态安全（`mm_users` 原子）。
- `PF_KTHREAD` → `get_task_mm` 返回 NULL → `-ESRCH`（:1317-1318），符合预期。
- vpid 失效/复用：`g_victim_mm` 持有旧 mm 引用，新进程即使复用 pid 也有不同 mm → 门拒绝 ⇒ **只会假阴性，
  不会假阳性**。跨进程假阳性结构上被消除（同 mm 只可能是 victim 的线程；helper 线程同 mm/同 comm，见 D.2）。

## C. probe 正对照 —— **BLOCKING：按预注册不可执行，且验证的不是它声称的东西**

### C.1 vpid>0 时 P2 必被自己的 mm 门拒绝（100%，非概率）

`echo probe > /proc/fxhook` 由 **shell** 执行（busybox sh/ash）；`fx_write` 的 `copy_to_user` 在 shell 的
`current` 上下文里（`fxhook.c:365-376`），`current->mm` = shell mm ≠ `g_victim_mm` ⇒ `fx_record` 在
`:122-128` 直接 return。P2 期望的 ring 记录**永远为 0**。而预注册 §2/§4.1 把 P2 失败定义为整轮 INVALID。
→ P2 不是"连续 20 次没撞上 ON 窗"的概率问题，是**结构性 0 概率**。

### C.2 载荷缺 `probe_va=`（第二个独立的必失败点）

预注册 §1 行 27 的 insmod 载荷是 `lo hi vpid site`，**没有 `probe_va`**；模块 `p_probe_va` 默认 0，
`echo probe` 在 `fxhook.c:369` 直接 `-EINVAL`，连 `copy_to_user` 都不会调用。

### C.3 即使 vpid=0，验证的也不是"victim RO 页的权限故障"

`probe_va` 是 victim 的栈 VA，但 probe 在 **shell 的 mm** 里解释它：
- shell 在该 VA **无映射**（大概率）→ **translation fault**（不是 RO 权限故障），走
  `do_page_fault → __do_page_fault → VM_FAULT_BADMAP → no_context → fixup_exception`；
- shell 恰好在该 VA 有映射（小概率，ASLR 重叠）→ `copy_to_user` **成功**（rc=0），**无故障无记录**，
  并向 shell 自己的内存写 32 个 0（只伤用户态）。
两种都不是本轮要验证的"内核 uaccess 写 victim mm 的 RO 页 → 权限故障 → fixup"。它只能验证
"far 数值窗口 + 模块外 uaccess 故障 → fixup → ring"这条弱链，且还需 vpid=0 另装一次模块。

### C.4 pc/lr 预期也是错的（会把成功判成失败）

`copy_to_user` 在模块内的展开链（.rela.text 实证）：
`fx_write+0x81c → bl 0x914`（**无 relocation**，本地 `_copy_to_user`）→ `_copy_to_user+0x9b0 → bl
__arch_copy_to_user`（relocation 283）。故障指令在 **`__arch_copy_to_user`**
（`kallsyms.txt:18142` = `0xffffffc00843b680`，size 536）的 `sttr`，**不在模块 .text**；只有
`lr`（返回地址 0x9b4+）在模块。预注册 §2 要求 "pc/lr 落在 fxhook_v6 模块地址段" ⇒ 会把正确的链判成 FAIL。
（另：`comm=fxhook?/insmod` 也不对——probe 由 shell 触发，comm 应为 `ash`/`sh`。）

### C.5 安全性 —— 通过（probe 本身不会 panic）

- `copy_to_user` 走真实 uaccess 站点：`access_ok` 失败（内核 VA）→ 不拷贝、不故障；用户 VA → `sttr`。
  常数 32 字节使 `check_object_size` 被 `!__builtin_constant_p(n)` 跳过
  （`include/linux/thread_info.h:191-205`），不会触发 usercopy abort；即使调用，zbuf 在 VMAP_STACK
  内也合法。
- HW PAN（`system_uses_hw_pan()` 真）下 `is_el1_permission_fault()` 对 TTBR0 权限故障返回真
  （fault.c:242-256），fault.c:569-575 的 die 门会先 `search_exception_tables(regs->pc)`；
  `__arch_copy_to_user` 的每条 store 都有 `_ASM_EXTABLE_UA` ⇒ 不 die，走 `no_context → fixup`
  ⇒ 无 oops / 无 `panic_on_oops` 触发。translation fault 则根本不进 die 门（fsc_type==FAULT）。
- `faulthandler_disabled() = pagefault_disabled() || in_atomic()`（uaccess.h:272）；HW PAN 下拷贝不关中断，
  正常上下文 ⇒ 走完整 do_page_fault，行为可预期。

### C.6 正确的 P2（不改模块即可做）

用**独立的控制进程**做 vpid 目标：控制进程 `mmap` 一页 → 填值 → `mprotect(PROT_READ)` → 调一个会把
数据写进该页的系统调用（如 `getrandom(page,n,0)` / `read(/dev/zero,page,n)`）→ 内核 `copy_to_user`
在**它自己的 mm** 里对 RO 页触发权限故障。用 `vpid=<控制进程 pid>` 另装一次 fxhook，期望：
`far=控制页`、`comm=控制进程`、`pid=控制 tid`、`pc ∈ __arch_copy_to_user`、`lr ∈ 内核调用者`。
这一步同时验证 **mm 门能放行 + far 门 + 权限故障类 + fx_record 的 ring 写入路径**（后者在 v5 设备上
从未被执行过：U-B1 `hit=0`）。随后 `echo 0 > /proc/fxhook` 重复（负对照）→ `echo clear` → rmmod
（逐行 readback）→ 再以 `vpid=<victim>` 装联合窗。P3 的路径也必须改成 `/proc/fxhook`。

## D. 与脉冲臂的相互作用 —— **CONDITIONAL**

### D.1 victim 自身 EL0 fault：不进 fixup（E3，已证）

`do_page_fault` 对 `user_mode(regs)` 走 `arm64_force_sig_fault`（fault.c:609-610、633-634 只对内核态
`goto no_context`）；EL0 写入 RO 页 → 信号 → scanary 的 victim-only siglongjmp。U-B1 的 151,097 次
自写 fault + `calls=0` 是实锤。**这条无污染。**

### D.2 victim 自己的内核态 uaccess（真正的污染源，未量化）

scanary 在热循环里确实有内核 uaccess：
- `now_us()` 的局部 `struct timespec ts; clock_gettime(...)`（`scanary_ro.c:180-184`）；
- `logline()` 的 `char b[640]` + `write(g_logfd,b,n)`（:230-243；`--calltrace` 时每 iter 两次，:1186-1191）；
- `hold_sleep()` / `nanosleep` 的 timespec（:1088-1100，pulse 臂 `--hold-us` 未给时可能不执行 syscall，
  但帧仍可能分配）。

如果这些缓冲区落在**被 mprotect 的那一页**，内核 `copy_to_user` 在 ON 窗会故障 → fixup → 记录
`comm=scanary_ro_v24`。设计上已做了两层规避：`--ro` 时 snprintf 目标强制走堆（:1151 注释）、
`D != 0` 把 `&ap` 推离 TCB 页（:1803 注释）；`--depth-list 0x1000` 的 4 KiB pad 也把 `vcall` 帧压到
循环帧下方一页以上。但**没有实测证据**证明 `logline`/`now_us` 的帧永不与该页重合。
- 判读表第 2 行能标注"装置注记"，但**容量**是问题：ring 每 CPU 16 槽（`fxhook.c:78`/`:140-150`），
  窗末才 `cat`。若 victim 自记录速率高于写者（写者 ~0.04/s），真实写者记录会被覆盖。
- **必须**：开窗后用 60–120 s 的 armed 预窗确认 `hit=0`（或 `comm=scanary` 计数为 0），否则先解决；
  最好在模块里按 `pid == victim_tid` 分流（自记录只计数不入 ring）或把 ring 扩到 256/CPU。记录里
  已有 `pid`（tid），判读时**用 tid 区分**，不要只比 comm（helper 线程同 comm、同 mm）。
- 监督者 `nerepair` 的 `process_vm_readv` 是 GUP **读**（U-C1 已点名），对 RO 页读合法、无 fixup；
  若它写（`process_vm_writev`）→ GUP FOLL_WRITE 在 RO VMA 上直接 -EFAULT，**不产生 fixup**（H1/H3 域，
  U-C1 已排除）。不污染。
- SIGSEGV 的 sigframe 写在 altstack（`v_alt` 静态数组），不在守护页；helper 的 mprotect/snapshot 也不写该页。

### D.3 `far` 窗与页的对应

窗是整段栈 [base,top)（预注册:24），但脉冲只让**一页** RO；其余栈页 RW，uaccess 写它们不会故障。
所以 `far∈窗 ∧ 记录` 实际只可能来自那一页的**写**权限故障（读在 RO 页合法）。这个性质对判读有利，
建议写进报告：**记录=写故障**（ESR.WNR 未存，但由 RO 页语义保证）。

### D.4 归属注意

`fx_record` 记的是 `current->pid/comm`——即"触发 fault 的 task"。若 fault 发生在 IRQ/softirq
（合法 uaccess 不应如此），current 是被中断的 task，comm 会张冠李戴；此时 **pc/lr 才是权威**。
窗口内若出现 `comm=scanary` 但 `pid` 不是 victim 主线程 tid，也不要直接当"victim 自身"。

## E. 判读表 —— **BLOCKING：推断不成立/分支不可观测**

### E.1 "ring 0 + 落地≥10 ⇒ 排除内核 uaccess 直接 store" 前提不成立

该推断要求 (a) mm 门能放行、(b) far 窗正确、(c) 写者在 ON 窗仍有尝试、(d) ring 未被自记录冲掉。
预注册的 P1 只验证 shim 活、P2（按现设计）验证不到 mm、P3 的路径还不存在 ⇒ **(a)(b)(d) 都无对照**。
在补上 C.6 的正对照前，ring=0 与"仪器坏了"不可区分。

### E.2 "无 extable ⇒ 静默" 是错的：会 panic

HW PAN 下，内核对 TTBR0 用户地址的**普通 store** 产生权限故障；`is_el1_permission_fault()` 为真，
fault.c:569-575 先查 `search_exception_tables(regs->pc)`——**没有 extable 就 `die_kernel_fault(
"access to user memory outside uaccess routines")`** → `die()` → `panic_on_oops=1`（config:5930）→ panic。
所以不存在"无 extable 的静默 store"分支；正确表述是：
- 有 extable 的 uaccess store → fixup → 记录（ring 应有条目）；
- 无 extable 的普通 store → **panic**（die 消息 + 寄存器 dump 直接点名 pc；这是**正面结果**，不是单纯 INVALID）。
预注册 §4.3 把 panic 一律当"停一切"会丢掉这个阳性出口；且 `panic=10`（cmdline）会自动重启，
按 AGENTS.md bootctrl 语义每次 panic 重启都会 `TRY_A+1`，**三次即回退官方槽**——必须把这条代价写进预注册。

### E.3 "ring 0 ⇒ GUP 类" 过度推断

U-A2 已排除 **内核别名写**（mprotect 只改用户 PTE，直映射/kmap 别名仍可写；若写者用别名，ON 段会有
~50% 落地，实测 2/50 ⇒ 排除）。剩下 ring=0 的可能性至少有三类：
1. **用户态写者**（EL0，同 mm 线程）——U-B1 的最优解释，**U-E1 结构上看不见**；
2. **先查 VMA/PTE 再写**的内核写者（GUP/follow_page/fixup_user_fault…）——H7 只是其中一族；
3. 写者的尝试恰好与 ON 窗不重合（触发与脉冲相位相关，样本少）。
ring=0 只能得出 "**不是盲目的内核 uaccess 写**"，不能直接跳到 "GUP 类"；下一步应把 (1) 与 (2) 并列。
这与 U-B1 §0 的"用户态写者最优"结论也矛盾，判读表必须自洽。

### E.4 §4.2 的 `far∉窗` 条目**永远不可能出现**

`fx_record` 在 `far < p_lo || far >= p_hi` 时 **return，不写 ring**（`fxhook.c:120-121`）。所以
"ring 出现 far∉窗 ⇒ 窗口配置错"是不可观测条件（死条款）。要检测窗口错配，必须新增一个
"far 被拒计数"（percpu counter，`/proc/fxhook` 打印）或依赖 C.6 的正对照。

### E.5 其它表项问题

- 第 2 行按 `comm=scanary_ro_v24` 判"victim 自身"：helper 线程同 comm、同 mm；应按 **tid**（记录里的
  `pid` 字段）。
- "lr = 调用者 = 写者"只对**直接 `copy_to_user` 调用者**成立（`_copy_to_user` 内联在调用者 TU，
  faulting store 在 `__arch_copy_to_user`，lr = 调用者）。若走 iov_iter/`copy_to_iter`/`_copy_to_iter`，
  故障在 `__arch_copy_to_user`，lr 在 **iter 代码**里，真正的写者还要再上一层；本仪器没有栈回溯
  （只有 pc/lr 一帧），这类路径只能"近邻点名"，不能保证"就是写者"。
- BPF：`fixup_exception` 先 `search_bpf_extables()`；若故障 pc 在 BPF JIT 里，会走
  `arm64_bpf_fixup_exception`，记录 pc 在 JIT 区——判读时按 pc 落在 `__arch_copy_to_user` 与否区分。

## F. 速率/暴露 —— **PASS（1200 s 够；阈值与预案要改）**

- U-A2：1200 s、556,920 脉冲、duty 49.7%，**50 条 landed**；`first_seen` OFF 48/50。
  landed ≈ OFF 窗尝试数；ON 窗尝试数 ≈ 同量级 ⇒ 若写者是盲目 uaccess store，联合窗期望
  **约 50 条 fixup 记录**。Poisson：P(0|50)=e⁻⁵⁰≈2e-22。即使按 U-B1 的低 λ（3.6/min → 72/1200 s）
  或 U-A2 后臂（8.6/min → 172/1200 s），功效都充足。**1200 s 对"盲目 uaccess"假设是够的。**
- **门槛 10 太松**：期望事件数 ≈ landed（均匀尝试模型），N=10 ⇒ P(0)=4.5e-5；N=30 ⇒ 9e-14；
  N=50 ⇒ 2e-22。要下"决定性阴性"，建议门槛提到 **≥30**（最好 ≥50），并在报告里写清
  "expected ≈ landed" 这个换算与它的相位独立假设。
- **功效对"先查 PTE 的写者"恒为 0**（它只在 RW 时尝试，永不 fault）。这正是实验要区分的分支，
  但也意味着 ring=0 不能推出"没有写者"——只能推出"不是盲目 uaccess"（见 E.3）。
- **早死预案缺失**：U-B1 的联合窗在 245 s 被 victim SIGSEGV 截断（113,760 脉冲时死亡）。
  U-E1 的 1200 s 目标有同样的 ~50% 早死史；预注册没有"victim 早死→怎么办"的条款（§4.4 只会判
  INVALID）。早死会强迫重装模块（新 vpid/新窗），与 §5 步 6"不重装模块"冲突，必须预先写清：
  早死 ⇒ 停、记、重来（含重新 go/no-go 与正对照），不得续用旧 ring。
- 对齐：落地记录必须来自"armed 之后的同一窗"；U-B1 是人工对齐的。预注册应写死对齐方法
  （模块安装时刻 / `clear` 后的第一条 EV 时间戳）。

## G. 回滚 —— **CONDITIONAL：restore 失败不可恢复**

### G.1 通过项

- `fx_remove()`：`apply_patch(p_site, g_saved)` + `rd32` 回读 + 日志（`fxhook.c:287-301`）；
  go/no-go 失败路径先 `fx_remove()` 再返回（:277），init 再 `proc_remove`+`fx_mmput`（:414-415）。
- exit 顺序：`fx_remove()` → `proc_remove()` → `fx_mmput()`（:424-426）；`proc_remove` 等读者退出，
  mmput 最后，顺序正确。
- percpu：`g_ring/g_ridx/g_hits/g_inhook/g_win_start/g_win_cnt/g_calls/g_dropped` 全是
  `DEFINE_PER_CPU`（:80-93）；v4b 的"普通 static + `__this_cpu_inc` 幻影地址"缺陷已消失（v5 报告 §1）。
  `clear` 用 `per_cpu(var,c)` 直接写（:362-364），进程上下文安全（仅与并发记录竞争，丢计数不崩溃）。
  `g_win_start/g_win_cnt` 未被 clear 复位（jiffies 边界内无影响，可忽略）。
- 热路径 O(1)、无锁、无 GFP_KERNEL、无 O(n) 遍历 ⇒ 2026-10-22 的锁内 O(n) panic 类教训不适用。

### G.2 ★ 必改：restore 失败 = 模块带着活补丁卸载

`fx_remove()` 在 restore **失败**时也只打 `RESTORE FAILED`，然后**无条件** `g_patched = 0`（:300）。
`rmmod` 的 exit 不能被"取消"，模块内存随后释放；而 `fixup_exception+4` 仍是 `b fx_shim` ⇒
**下一次任何 fixup_exception 调用 = 跳进已释放内存 = panic**（panic=10 → 重启 → TRY_A+1）。
预注册 §4.1 把"缺 readback 行"判 INVALID 是不够的：此时设备已经处于"随时可能 panic"的状态。

另外一条同族路径：`apply_patch(p_site, ins)` 若**补丁已生效但回读失败**（`rc==0 && !ok`），
`fx_install` 返回 -EIO（:254-255），但 `g_patched` 还没置 1（:256）⇒ `fx_remove` 直接 return（:291-292）
⇒ 同样带活补丁卸载。必须改成"调用过 patch 就登记 attempted，任何失败都尝试 restore"。

**处置（不改码的运营版）**：rmmod 后若没看到 `restored … readback … ok=1`，**立刻 sysrq-b**（不要再
执行任何会触发 fixup 的操作，不要二次 rmmod）。**处置（推荐，下一构建）**：加
`echo restore > /proc/fxhook`，在模块仍加载时执行 restore 并回读；看到 `ok=1` 才允许 rmmod
（exit 里 `g_patched==0` 自然跳过）。restore 失败时**不 rmmod**——模块文本还在，补丁指向的内存有效，
可以安全地安排重启。

### G.3 rmmod 在途 shim 竞态

`b fx_shim` 不取模块引用；若另一 CPU 正在 shim/fx_record 内时 rmmod 释放模块文本 → 崩溃。
窗口 ~百纳秒级；本系统 fixup_exception 近乎不调用（U-B1 219 s、U-C1 930 s 的 `calls=0`）⇒ 概率极低。
先 restore（G.2 的 restore 命令）可以把它降到 0。

### G.4 身份/登记

- `fxhook_v6.ko` 本地 md5 `22e395764201cadac470bcd1d7add1f5` / 203,856 B；**`FIVETUPLE.txt` 尚无 v6 行**
  （最后一行是 mempoke）。按 AGENTS.md 版本登记纪律，上机前必须补登，并在设备侧 `md5sum` 复核。
- 预注册说"v5 已验证；v6 只加 mm 门"——不准确：v6 还加了 probe 分支、`probe_va` 参数、新的
  `/proc/fxhook` 写命令；而 **v5 的 ring 写入路径从未在设备上执行过（hit=0）**，所以 v6 的记录路径
  是全新未跑过的代码。C.6 的正对照必须真正产生一条记录，否则 ring 代码仍未被验证。

## H. 其它 panic / stall / 假阳性

1. **`/proc/fxhook` 的 lseek = NULL 调用 = panic**（`fs/proc/inode.c:276-288`：`proc_reg_llseek`
   **无 NULL 回退**，5.15.134 实证；read/write/poll/ioctl 都有 NULL 检查，只有 llseek 没有）。
   `fx_ops` 只注册 read/write（`fxhook.c:384`）⇒ `tail`/`dd skip=`/`xxd`/任何带 seek 的读都会 panic。
   必须把 U-B1 skeptic 的约束 2（只 cat / echo）继续写进预注册并现场张贴；`cat`（busybox read/write 循环）
   与 `echo` 安全。
2. **P3 路径不存在**：预注册:36 `echo 0 > /proc/fxhook/armed` —— 模块只有 `/proc/fxhook`；改为
   `echo 0 > /proc/fxhook` 后**必须**补 `echo 1 > /proc/fxhook` 重武装，并 `cat` 确认 `armed=1`
   （见 0 节 blocking 1）。`fx_install` 装完自动 `p_armed=1`（:283），不要误以为 insmod 后是 0。
3. **P2 残留污染**：步 4 的 `clear` 在 P2/P3 **之前**；P2 若真产生记录（vpid=0 场景），它会留到联合窗，
   且 `far=probe_va` 在窗内、`comm=ash≠scanary` ⇒ 判读表第 1 行会把它当 **E4 写者**。必须在 P2/P3 后
   再 `echo clear > /proc/fxhook`（并在步 6 开窗前 `cat` 确认 ring 空、`armed=1`）。
4. **panic 的代价**：`panic=10`（cmdline:94）⇒ panic 后 10 s 自动重启；AGENTS.md bootctrl：LK 每次
   启动 A 槽 `TRY_A+1`，>3 回退 B。任何 panic 都是"烧一次回滚额度"，不是普通重启。预注册应把
   LK 救砖链和 TRY_A 计数写进 §4.3。
5. **`panic_on_taint=0x20`**（`d28b_lab_segment.txt:7`）= `TAINT_BAD_PAGE`（bit 5），**不含**
   OOT_MODULE(bit 12) / WARN(bit 9) ⇒ insmod 的 OOT taint 与可能的 WARN 不会 panic；只有坏页会。
6. **KASLR**：`RANDOMIZE_BASE=y`（config:477），baked 站点是绝对地址。EXP_WORD 检查会安全拒装；
   但开窗前应 `grep fixup_exception /proc/kallsyms` 确认为 `0xffffffc00812673c`（若设备允许读），
   并确认没有其它改内核文本的模块（tuphook/dmahook/wrhunt）在 `lsmod` 里。
7. **`probe_va` 是 0644 参数**：任何 root 可改；值若指向自己的用户页，probe 会往自己 mm 写 32 个 0
   （只伤用户态）。不是内核风险，但现场应写死后再开窗。
8. **`strncmp(kb,"clear"/"probe",5)` 在 len<5 时读未初始化内核栈**（`fxhook.c:360-366`）：不会 fault，
   最坏是极小概率误判（~2⁻³²）；`kb` 无 NUL 终止也应修（下一构建加 `kb[len]=0`）。
9. **`initcall_debug` / `page_owner=on`**（cmdline）只增噪声/开销，无功能影响。
10. **RCU stall**：hook 路径无循环/无锁；`fx_read` 循环有界（`n<7800`）；无 stall 风险。
11. **跨 CPU ring 读**：`fx_read` 无同步遍历 `g_ridx/g_ring`，并发写可能读到半条记录（comm 混杂）；
    只在窗末读一次，影响可忽略，但判读时不要把"半条"当异常。

## 必改项

**M1（blocking，文档）** 预注册 §1 行 28 的 site 地址改为 `0xffffffc008126740`（或干脆不传 `site=`，
用模块默认）；同时纠正 §2 的 P2 pc 预期（pc 在 `__arch_copy_to_user`，lr 才在模块/调用者）。

**M2（blocking，正对照）** 用 C.6 的"控制进程自写 RO 页"另装一轮（`vpid=<控制进程>`）作为 P2：
期望 `far=控制页 / comm=控制进程 / pid=控制 tid / pc ∈ __arch_copy_to_user / lr ∈ 内核调用者`；
`armed=0` 重复为 P3（路径 `/proc/fxhook`）。这是唯一能验证 mm 门＋far 门＋故障类＋ring 写入的对照。

**M3（blocking，armed 状态）** P3 之后、联合窗之前必须有 `echo 1 > /proc/fxhook`，并 `cat` 确认
`armed=1`（见 0 节 blocking 1；这是 U-C1 V3 的复发）。

**M4（blocking，残留）** P2/P3 之后加 `echo clear > /proc/fxhook`，并 `cat` 确认 ring 空、`calls` 基线；

## 定向问题

**(a) `echo restore` 从 proc write 调用是否安全、失败是否自洽 —— PASS。**

- **pc = `0xffffffc00843b32c`**（首个 `sttr xzr,[x0]`；32 字节、页对齐时确定）
- **lr = `0xffffffc0084ea1e0`**（`read_zero` 中 `bl __arch_clear_user` 的返回地址）
预注册 v2:31 的 `pc ∈ __arch_copy_to_user (0xffffffc00843b680)`、`lr ∈ zero_read/vfs_read` 均不符。故障类仍是“内核 uaccess 写 RO 页 → 权限故障 → extable → fixup”，控制有效；改一行判据，或把 roprobe 换成 copy_to_user 型 syscall（如 `getrandom`）。
