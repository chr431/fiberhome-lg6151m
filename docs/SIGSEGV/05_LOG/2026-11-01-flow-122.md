## 0. 结论先行

1. **`pipe_to_user` 与 `sk_msg_recvmsg` 都被否证**（E2→接近 E3）：两者的 `dst` 都是**当前 syscall 自带的 iovec**，
   不是"某条长期流的接收缓冲地址"。`sd` 是 `vmsplice_to_user()` 的**栈上局部变量**，生命期 = 那一次 syscall。
   ⇒ **"H2 = 内核持有受害者栈 VA"这条，在可穷举的 6 个站点里已经全部落空**（详见 §3）。
2. **没有核心网络结构同时持有"目的地址 + 逐包长度"**（§2）：FOE/PPE 元组是 `{src_ip,dest_ip,ports}`（12B，无 len）；
   conntrack 有地址无 len；`iphdr` 有 len 和 daddr 但相隔 14B 且 len 是 16 位网络序。⇒ 该 8B 对 `{u32 len; __be32 addr}` 更像**厂商私有结构**。
3. **新的判决实验（D ≥ 0x1000）**：让 va_list 移出"栈顶页"，可以一次分开"写目标 = 活 VA"与"写目标 = 某个 4KB 页"（§6）。
   这是本轮我给出的最高价值单点实验。

## 1. Q1：哪类流量会形成"单一公网对端 + 1600 字节级 + 长期存在"的流

**先修正方向**：len 里出现 **4416 / 4480 > MTU(1500)**，而 GRO **只在接收方向**发生 ⇒
这 82% 的记录对应**入方向（RX）报文**，此时 122.227.201.3 是**源地址**。
⇒ `addr` 更准确的说法是「**这条流的对端地址**」（入向=源、出向=目的；alias 那条是"发给我们/从我们发往 alias"的那一侧）。

**长度谱的算术特征**（把 +8 归一化后）：

| len | 分解 | 说明 |
|---|---|---|
| 321 | — | 单个小段（ACK/控制/短响应） |
| 1600 / 1601 | 1472 + 128 / +129 | 1 个满段（1472 = 1500−28）再叠 128B |
| 4416 | **3 × 1472** | 3 段 GRO 聚合 |
| 4480 | 3 × 1472 + **64** | 同上 + 一个 64B 加数（**注意：厂商 EDMA 缓冲头正好是 0x40 = 64**） |

⇒ **bulk TCP 下载/上传流**的长包 + 少量小段，典型是**一条长期 TCP 连接在持续传输**。
82% 独占 ⇒ 这条流是设备上**唯一的流量主源**。

**候选（按设备上常见度，需用端口/进程落地，静态只能排序）**：
1. **厂商云/遥测长连接**（FiberHome 自家 fhrom/ccmni 侧的云心跳 + 数据上报，TCP 443/8080 一类）——最可能：
   ①长期存在 ②单一公网对端 ③设备自己发起 ⇒ 与"设备自身是端点"一致；
2. **客户端的大流量下载经设备转发**（PPE/NAT 路径）——次可能，但那样对端应随客户端而变（除非只有一个客户端在下载）；
3. TR-069/CWMP（7547）：报文小、心跳为主 ⇒ **与 1600B 长包不符**；
4. NTP/DoH：NTP 是 48–76B（**否**）；DoH 走 443 但通常小包；
5. 私有探测/打点：报文小 ⇒ 不符。

**落地的三条零成本取证**（给 lab，各一条命令）：
* `conntrack -L 2>/dev/null | grep 122.227.201.3`（若 busybox 无 conntrack：`cat /proc/net/nf_conntrack | grep 122.227`）→ 拿到 **dport/sport + 状态 + 字节计数**；
* `cat /proc/net/tcp /proc/net/tcp6 | grep -i <hex of 122.227.201.3>` → 拿到**持有该连接的进程 inode**，再 `ls -l /proc/*/fd | grep socket:[<inode>]` 定进程；
* `cat /proc/net/dev` 与 `/sys/class/net/*/statistics/rx_bytes` 前后差分，确认这条流的量级。
⇒ 若定到**厂商守护进程**，则写入者与 AP 的 socket 栈强相关；若定不到任何进程（连接属于 MD/内核侧），
   那**注意力应推回 MD/DMA**（我在 §3 的否证也正是这个方向：AP 侧 uaccess 已无处可指）。

## 2. Q2：conntrack / NAT / PPE / hw_nat 里"目的地址 + 长度 + 逐包更新"的字段级候选

**逐个排除（源码级，5.15.134 树）**：

| 结构 | 地址字段 | 同结构里有"长度"吗 | 逐包更新吗 | 判定 |
|---|---|---|---|---|
| `struct mtk_ipv4_tuple`（PPE FOE 元组，`mtk_ppe.h`） | `src_ip`(+0), `dest_ip`(+4), `ports`(+8) | **没有** | 否（建流时写） | **否**（但 `{src_ip,dest_ip,ports}`=12B 形状记下） |
| `struct mtk_foe_ipv4` | `orig`(+0..11), `ib2`(+12), `new`(+16..27), timestamp(+28)… | **没有 len** | 否 | **否** |
| `struct nf_conn`（conntrack） | `tuplehash[2].tuple.dst.u3.ip`（`nf_inet_addr` 是 16B union，ip 在 +0，其余 12B 为 0） | 无 len；只有 `nf_conn_counter{atomic64 packets; atomic64 bytes}` | **是**（计数/状态） | **否**（有地址、有 16B 计数，但计数不是 len，且次序是 {pkts,bytes}） |
| NAT（`nf_conn_nat`/`nf_nat_range2`） | `min_addr/max_addr` | 无 | 否 | **否** |
| `struct iphdr` | `daddr`(+16) | **有** `tot_len`（**__be16 @+2**） | 是（本来就在包里） | **否**：两者相隔 14B，且 tot_len 是 16 位网络序；本记录是 host-order u32 |
| `struct ipv6hdr` | `daddr`(+24) | `payload_len`(__be16 @+4) | 是 | **否**（同上） |
| `struct rtable`/`dst_entry` | `rt_dst`/`rt_src`/`rt_gateway` | 无 | 按路由 | **否** |
| `struct neighbour` | `primary_key`（地址在结构尾部） | 无 | 否 | **否**，且**邻居只可能在链路层** ⇒ 公网对端**根本不在邻居表** ⇒ 强力排除 |
| `ip_tunnel`/`ip6_tnl` | `parms.iph.daddr` | 无 | 否（每隧道） | **否** |
| `struct flowi4` | `daddr`/`saddr` | 无 | 每包 | **否**（无 len） |
| `get_hash_ipv4` 一类 5 元组压 64 位 | 只有 hash 结果 | 无 | 每流 | **否**（hash 不可逆，且本记录 addr 是**真 IP**） |

**⇒ 结论（E2）**：**核心网络栈里没有"目的地址 + 逐包长度"成对出现的小结构。**
这有两种解释：
(a) 该 8B 对来自**厂商私有结构**（hw_nat vendor / eth driver / FHO 的 flow cache）——与"记录不是 RXD"叠加，指向厂商私有；
(b) 它并不是一个"流结构"，而是**某个更大结构的两个不相邻字段被 32B 窗口同时覆盖**（可能性低：中间 8B 必须恒 0）。

**可证伪预测**：若 (a) 成立，则在 169 个 `.ko` 里应该能找到一个含 `{u32 len; __be32 addr}` 相邻字段、且大小 ≤64B 的结构；
我可以用 `vmlinux+ko` 的字符串/常量侧扫再试（需要你批一次全量 `.rodata`+ko 扫描窗口）。

## 3. Q3：`pipe_to_user` / `sk_msg_recvmsg` 的 `dst` 会等于"长期流的接收缓冲地址"吗 —— **不会（否证）**

### 3.1 源码事实（5.15.134，`fs/splice.c`）

```c
struct splice_desc {            /* include/linux/splice.h:29 */
    size_t total_len; unsigned int len; unsigned int flags;
    union { void __user *userptr; struct file *file; void *data; } u;
    loff_t pos; loff_t *opos; size_t num_spliced; bool need_wakeup;
};
static int pipe_to_user(struct pipe_inode_info *pipe, struct pipe_buffer *buf,
                        struct splice_desc *sd)          /* fs/splice.c:1202 */
{ int n = copy_page_to_iter(buf->page, buf->offset, sd->len, sd->u.data); ... }
static long vmsplice_to_user(struct file *file, struct iov_iter *iter, unsigned int flags) /* :1213 */
{ struct splice_desc sd = { .total_len = iov_iter_count(iter), ... };
  ret = __splice_from_pipe(pipe, &sd, pipe_to_user); }
```
* `sd` 是 **`vmsplice_to_user()` 栈上的局部变量**，生命期 = 那一次 `vmsplice()`；
* `sd.u.data` = **本次 `vmsplice()` 的 `struct iov_iter *`**（由 `iter` 传入，来自当前 syscall 的 iovec）；
* 因此 **`dst` = 调用者本次 syscall 自己的用户缓冲**——不是任何"流"的缓冲。

### 3.2 反汇编一致
`pipe_to_user` 0x82b998c：`ldr x0,[x0]`(buf->page) / `ldr x3,[x19,#0x10]`(**sd.u，即 iter 指针**) /
`ldr w1,[x1,#8]`(buf->offset) / `ldr w2,[x2,#8]`(**sd->len**) → `copy_page_to_iter`。
⇒ 目的来自 **sd（本次 syscall 的栈上局部）**，不是常驻结构。

### 3.3 `sk_msg_recvmsg`
`net/core/skmsg.c`：`sk_msg` 队列里存的是**页面**（`msg->sg.data[i].page`），
用户地址来自**本次 `recvmsg` 的 `msg->msg_iter`**（反汇编里 iter 从栈上转出、page/offset/length 从 `sk_msg` 取）。
⇒ 同样 **dst = 当前 syscall 的 iov**。

### 3.4 "什么调用序列会让 dst 恰好落在某个进程栈的高位" —— 唯一条件
要让 `dst` 落在受害者栈上，**受害者本人必须**用**指向自己栈的 iovec**发起 `vmsplice()` 或 `recvmsg()`。
vsurv4 canary **没有任何 socket、也不调用 splice/vmsplice** ⇒ **不可能**。
⇒ **H2 在"可穷举的 6 个站点"上全部落空**（两个厂商站点是 24/16B 的 `ifr_data`、两个是本次 syscall 的 iov、两个是 bpf attr / syscall 参数）。

### 3.5 那么 AP 侧还剩下什么可能（留给下一步）
canary 交给内核的栈 VA 只有三类：
1. **handler 里 `write(fd, (void*)(startstack − k·4096), 4096)` —— 8 个 4KB 页**（**唯一覆盖 va_list 所在页的那一个**）；
2. musl 的 `sigset_t`（8B）与 `timespec`（16B）栈局部（`rt_sigprocmask`/`clock_gettime` 回写）；
3. `&h`（120B，在 **altstack** 上）。
⇒ 若 H2 成立，写入目标必须与这三类之一重合。**第 1 类是唯一覆盖 va_list 的 4KB 范围** ⇒ 应立即查
"**`write()` 路径有没有可能回写用户源缓冲**"（`iov_iter` 被复用、`copy_page_from_iter_atomic` 之后的 bounce、加密/校验原地操作、`O_DIRECT` 对齐缓冲）。

## 4. 打点判据（给 kdev 的 uwhook/fxhook）

**位点（精确到指令）**：
| 站点 | 指令 | 打点位置 |
|---|---|---|
| `pipe_to_user` | 0xffffffc0082b998c `bl copy_page_to_iter` | **bl 之前**：`x0`=page, `w1`=buf->offset, `w2`=sd->len, `x3`=iter ⇒ 用 `x3`（iter）里的 `ubuf`/`iov_base` 作 dst，长度取 `min(w2, iter->count)` |
| `sk_msg_recvmsg` | 0xffffffc008806fe8 `bl copy_page_to_iter` | 同上，`x3`=iter |
| `mtk_do_priv_ioctl` | 0xffffffc00859d26c | `x0`=`[x19+0x10]`（ifr_data）, `x2`=0x18 |
| `mtk_qdma_ioctl` | 0xffffffc00896ea70 | `x0`=`[x23+0x10]`, `x2`=0x10 |
| 通用兜底 | `_copy_to_user` @0xffffffc00859bbb0 等 | `x0`=dst, `x2`=len |

**判据（C 片段）**：
```c
/* victim_va = startstack - 0x390 (A 型) 或 - 0x3a0 (B 型)，由用户态 canary 上报；
 * 窗口 = [va - 0x40, va + 0x40) 覆盖两型 + 16B 抖动。 */
static inline bool in_win(unsigned long dst, unsigned long va) {
        return va && dst + 64 >= va && dst <= va + 64;
}
/* 站点桩：dst 已从上述寄存器/iter 取出，len 已知 */
if (in_win(dst, cur_victim_va))
        pr_info("SIGW site=%d dst=%#lx len=%u pid=%d comm=%s\n",
                SITE_ID, dst, len, current->pid, current->comm);
```
* **必须的护栏**：只对"canary 登记的 VA"打点（`cur_victim_va` 由用户态 `/proc/va_reg` 写入），
  否则每个站点都会被普通流量刷屏；
* **正对照**：先用 `rectest`（自己往 va_list 注入记录）验证桩能命中自己；
* **判据**：出现 `site=SIGW` 且 `dst ∈ 窗口` ⇒ 该站点就是写入者（**1 次即决**）；
* **停止规则**：一个 10 min 窗口内所有桩都没有 `dst∈窗口` ⇒ **H2 整体否**，转向 H1/H3（PA/pin）。

## 5. 16B 槽家族 vs 历史 §2.1/§14（③ 补完）

| 项 | 历史（`SIGSEGV_ANALYSIS.md`） | 本轮 | 关系 |
|---|---|---|---|
| 形状 | §14「**live PIT 表项 16B：`{u64 PA, u64 0}`；4KB 页 256 项，最后一项在 0xfc0**」 | 记录 = 1~2 个 16B 槽 `{u64 v, u64 0}` | **同一形状类** |
| 值域 | §2.1「**长度型 16B 块 `{small,0}`：small ∈ [0x2710,0x40000]∪{0}，非单调**」 | `A_w ∈ [0xBF45,0x28658] ⊂ [0x2710,0x40000]` | **完全落进历史值域** |
| 分布 | §2.1「同页可多块（16B 节距）；页尾 0xfc0 高发」 | A 型写 2 槽（32B）、B 型只覆盖 1 槽 | 一致（"可多块"） |
| 载体 | 历史判定：dpmaif **PIT 环**（MD 侧） | 本轮载体未定（AP 侧已无候选，见 §3） | **注意**：历史载体是 MD/DMA，这与"AP 侧 uaccess 无处可指"同向 |

⇒ **合并结论（E2）**：历史上被证为"MD 侧 16B 表项注入"的那一族，与今天这 32B 记录**形状与值域同族**；
而今天 AP 侧 uaccess 候选已被穷举否证 ⇒ **重心应回到 MD/DMA 侧**（这与 Lead 的"若像 MD 侧就明说"一致：
**我认为更像 MD/DMA，而不是 AP 的 socket**）。

## 6. 本轮最高价值实验：**D ≥ 0x1000 臂**（能一次分开"活 VA"与"4KB 页"）

scanary 的 D 臂已经证明"命中点随 D 移动"，但 D ≤ 0x900 时 va_list **一直留在栈顶页内**，
因此"写目标 = 活 VA" 与 "写目标 = 某个 4KB 页的固定偏移" 在 D≤0x900 时**都能解释**（后者只是要求页内偏移固定，
但 top-0x390 的页内偏移随 top 的 16B 随机化而变 ⇒ 上一轮已否）。

**新增判据**：取 D ∈ {0x1000, 0x1800, 0x2000}（把 va_list 推出栈顶页）：

| 模型 | 预测 |
|---|---|
| **写目标 = 活 va_list VA**（H-VA，scanary 已支持） | 命中**继续**，且 `topva = 0x390+D`；命中点换到 **top 的第二/三页** |
| **写目标 = 某个固定 4KB 页**（含"handler write 的 8 个页"这一类） | va_list 离开该页 ⇒ **命中率 → 0**（记录仍落在原页，但不再覆盖 va_list ⇒ 不崩） |
| 写目标 = `sp + 0x210`（Lead 观测到的 spva 恒定） | 与 H-VA 同（va_list 本身就在 sp+0x210）⇒ **不可分**，需再用"只改 va_list 深度不改 sp"的变体 |

⇒ 若 D≥0x1000 仍命中 ⇒ **"某个 4KB 页/缓冲"类模型全部出局**，只剩"活 VA/活 sp 派生"，
   这时 H2 就要求内核**精确知道 va_list 的地址**——而 AP 侧已无可指路径 ⇒ 只能指向 **MD/DMA 侧按 VA 解析**（如 SMMU/IOMMU 存在）
   或 **我们对 AP 内核的覆盖仍有缺口**（厂商私有模块，169 个 ko 之外）。
