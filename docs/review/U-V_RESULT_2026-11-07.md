> 授权：用户指示"对官方固件静态分析，二进制 diff 两版官方固件看是否有与本轮主题相关的变更；
> 顺便查写入者写入内容是否有合法消费者、官方组件是否避免了被当成写入目标"。

> `dev_put`，CCCI/conninfro 邻域）+ 新字符串 `ccmni_start_xmit`/`port_mirror`（P40→P56 小版本
> 迭代）——**内存子系统（mm/page/slab/DRAM/DFX/写者）零变更**；32B 记录 `{A,0,{len,ip},0}` 的

> busybox 290 / dropbear 122 / dnsmasq 75 条），且 RP102==RP103 逐组件全等——官方组件不靠"避免
> 32B 存储形状"自保，是否被命中与 va_list 使用面/进程形态相关而非二进制指纹密度。

## 1. 内核 Image 字节级 diff 归因

对象：`rp102_kernel.bin`（0add995a…，20,226,932B，2025-12-24 构建）vs `rp103_kernel.bin`
（00ec90c4…，20,227,004B，2026-09-09 构建）。同 5.15.134、同 SDK、同 PROJECTNAME
（基线档案见 `_re/reports/RP102_RP103_compat.md`）。

方法与数据：
1. **全量字节 diff + 64B 归并**：12,356 个差异段、合计 9,217,135B（45.6%）——粗看吓人，
   实为重链接位移伪差。
2. **分段最优位移搜索**（64B 块命中率，±步长 4/8）：0x0–0x44d 位移 0（≥97%）；
   0x44e–0x46 位移 **+576**；0x80 段 +592；0xb0 段 +56；0xc8 段 0；0xe0/0x110 段 **−512**；
   0x120–0x134 段 +72 —— 每个 section 独立重排（少量函数增删导致的段内再打包）。
3. **kallsyms 实证**（决定性证据）：两版 names blob 定位（0x9e8900 vs 0x9e8908，整体 +8B）；
   逐记录解析 49,322 vs **49,324** 条；`difflib.SequenceMatcher` 对齐 names 流：
   - **ADDED（仅 2）**：`t__refcount_sub_and_test.constprop.0`、`tdev_put`；
   - **DELETED：0**；**REPLACED：0**。
   - 插入点上下文：`__raw_spin_lock_bh` → **（新）** → `ccmni_is_odu_v6_addr`/`ccmni_open`
     ——即 CCCI/conninfro（蜂窝数据面）某调用点的 `dev_put()` 获得 refcount 硬化内联实例。
4. **字符串集**：全 Image 逐段 diff 内的字符串差异只有 `ccmni_start_xmit`、`port_mirror`
   （+2 条）；`mtk_suspend_emiisu`、`mdee_dumper_v5_emimpu_callback`、`emimpu_violation_irq`
   等内存/MPU 邻域符号计数两版全同。
5. **地址表核对**：kallsyms 表尾 `_stext` 0xc0aa00（102）vs 0xc0ac00（103），+0x200 ——
   `.text` 头部区段净增 512B，与"+2 符号 + 少量代码"一致。

**判读**：RP102→RP103 内核 = 一次蜂窝数据面小修（ccmni xmit/mirror + dev_put refcount 硬化）
引发的整链重链接。**mm/内存/引擎邻域零变更**——厂商两版都没碰写者可能相关的任何代码面。
对 U-T"T4 载荷未知、T2 全表无手柄、T7 唯一外路"的根修复收口没有新增路径：没有"官方在
某版本修过此问题"的迹象（若修过，diff 应出现在 DRM_DEBUG/DRAMC/DFX 邻域，实测为 0）。

## 2. 32B 记录的合法消费者搜索

记录家族 B：`{u64 A, 0, {u32 len, __be32 ip}, 0}`（U-T grep 栈闭环：A=0x263cd、len=0x141=321、
ip=192.168.9.1）。消费者候选逐层排查：

| 层 | 结果 | 判读 |
|---|---|---|
| LK（rp102/rp103_lk_b.img） | `mrdump` ×101：MRDUMP 崩溃 dump 引导参数/控制块 | 后果层（崩溃时读），不消费包摘要记录 |
| 内核 | `mrdump` ×78（cblock/mini/misc/extra_file 全套）；`emimpu_violation_irq`/`emimpu_vio_dump`（MPU 违例层）；`__refcount_sub_and_test` | 均不读 `{A,0,{len,ip},0}` 形 |
| 内核（数据面） | **DPMAIF PIT/PIT_NAT 全套**：`dpmaif_dump_partial_pit_nat`、`dpmaifq_rel_rx_med_pit_entry`、`drv_dpamif_med_dl_pit_nat_release`、`ccci_dpmaif_reset_pit_nat_indexes`、`assign PIT_NAT memory fail`、`dpmaif_rx_buf_init: PitNat: phy:0x%llx virt:0x%llx size:0x%x`、`poll_med_rx_pit: pit_cnt/sw_rd_idx/hw_wr_idx`、`pit(%d):data(%x,%x,%x,%x,%x,%x,%x,%x,%x)`、`pit_nat_idx[%d]: %d,%d,%d` | **格式最接近的合法消费者** |
| md1img（modem） | DRB LOST、PDN/ATP 等 PDN 层字符串；1222 条 desc 相关串 | modem 侧生产者邻域（MEDMCU 写 PIT），AP 侧由 dpmaif 驱动消费 |

**结构论证**：PIT_NAT = DPMAIF 的 NAT 卸载包信息环（MEDMCU/modem 写、AP dpmaif 驱动读），
条目携带"包指针/bat 索引 + 包长 + IPv4 摘要"——与 `{A,0,{len,ip},0}` 完全同形（A=0x263cd
量级正是一个 bat/index/短指针，而非内核 VA；U-T 记录载荷=洪水包 len+LAN 侧 IP 也吻合
"包摘要"）。此前 04_FAMILIES 的 B 家族假设域"网络/WiFi/NAT/PPE 的 flow descriptor"现在
收窄到**DPMAIF PIT_NAT（蜂窝数据面 NAT 卸载描述符）为第一候选**。

**关键推论**：合法消费者（AP 驱动）只从**保留内存中的 PIT 环**读这些条目；写者把同形事务
写到错地址（活 va_list）= 引擎的"事务生产"与"地址投放"解耦错误。因此：
1. **不存在用户态合法读者**——用户态进程读到记录即非法定向（含 nerepair 的 process_vm_readv
   也只是取证仪器，不消费）；
2. **验证手段**：PIT 环地址可从 `/proc/iomem`/`dpmaif_rx_buf_init` 日志串（phy/virt/size
   三元组）获取；下轮可在设备上 dump PIT_NAT 环内容与 U-T 记录逐字对照，若命中 `{bat_idx,0,
   {len,ip},0}` 即闭环"记录=PIT_NAT 条目"（E2 升 E3 需设备实测）。

## 3. 官方组件 32B q 事务普查（写入目标面量化）

方法：exec 节内扫描 AArch64 SIMD 128-bit 存储编码——`STR Qt,[Xn{,imm}]`（0x3D80/0x3DC0 掩码，
Rn=31 计 sp 槽）与 `STP Qt,Qt2,[Xn{,imm}]`（0xAD00 掩码）。此法与 U-T 的 objdump 普查口径
不完全同（缺 pre/post-index 变体、可能含少量 literal pool 误报），用于**相对比较与全等性
判定**足够；绝对数与 U-T 的 stock 399 条不可直接互换。

| 组件（rp103_rootfs） | str q→sp | str q→其他 | stp q,q→sp | stp q,q→其他 | 合计 32B 事务 |
|---|---|---|---|---|---|
| lib/libc.so | 1328 | 403 | 26 | 115 | **1872** |
| usr/sbin/wpad | 127 | 55 | 13 | 447 | **642** |
| bin/busybox | 167 | 7 | 63 | 53 | **290** |
| usr/sbin/dropbear | 64 | 1 | 8 | 49 | 122 |
| usr/sbin/dnsmasq | 16 | 22 | 5 | 32 | 75 |
| usr/bin/ccci_fsd | 10 | 3 | 4 | 4 | 21 |
| sbin/rpcd | 0 | 0 | 0 | 18 | 18 |
| sbin/netifd | 8 | 0 | 2 | 7 | 17 |
| usr/bin/ccci_mdinit | 0 | 0 | 2 | 2 | 4 |
| sbin/ubusd | 0 | 2 | 0 | 2 | 4 |
| **usr/bin/ccci_rpcd_com** | 0 | 0 | 0 | 0 | **0** |

RP102 vs RP103：busybox 二进制不同（d217b03e vs 28e91241）但 **q 事务计数逐项全等**
（167/7/63/53）；libc/wpad 本身字节全等（`_re` 报告 §2.2/§2.4 SAME），计数必然全等。

**判读**：
1. **官方组件没有任何"避免 32B 存储指纹"的设计**——核心组件（libc 1872、wpad 642）的事务
   密度远超自改 p11（p11 = 363 条 va_list 拷贝 + 9 stp，见 C-343），官方照样带上千 32B 事务
   在跑。
2. 历史受害者集中在 busybox（434 条家族）而 wpad/libc 面受补丁保护后未再见同类死亡——
   与"目标捕获=32B FP-save 事务形态 + 第二门=活 va_list 内容（K9）"模型一致：**决定命中率
   的是运行时 va_list 活性/进程形态，不是二进制里 32B 事务的绝对数量**。
3. 侧面证据：`ccci_rpcd_com`（0 条 32B 存储）、`ccci_mdinit`（4 条）这类蜂窝守护在全部历史
   NE 台账中零命中——与低 32B 面一致；但同一数据也符合"不跑变参打印"解释，两者在本轮
   无法分离（无设备实测）。
4. **对 p11 的影响**：官方都不避指纹 ⇒ "官方原版即安全"的隐身策略不成立；32B 拆宽
   （U-T C-343/C 下轮第 3 项）仍是唯一代码级隐身增强方向。

## 4. 三栏

**[A] 已核实**
1. 内核全量 diff：72B 级 delta；分段位移表；kallsyms +2 符号（`__refcount_sub_and_test.constprop.0`、
   `dev_put`，插入点 ccmi_open 前）；字符串仅 +2（`ccmni_start_xmit`/`port_mirror`）。
2. 内存/引擎邻域符号（mm/emi/mpu/mrdump/dfx）两版计数与字节面零相关变更。
3. 消费者排查：mrdump=后果层、emimpu=MPU 层，均不消费该记录；DPMAIF PIT/PIT_NAT 函数/dump
   串全套在内核内建，PIT_NAT 条目=包摘要描述符（bat/ptr+len+IPv4），与记录同形。
4. 官方组件 q 事务普查表（11 组件）；RP102==RP103 逐项全等；无任何规避设计。

**[B] 未核实/边界**
1. "记录=PIT_NAT 条目"目前是**格式同形论证（E1）**：需设备实测闭环——dump PIT_NAT 环
   （dpmaif_rx_buf_init 的 phy/virt/size 日志）与故障栈记录逐字对照；或 modprobe 层面从
   driver 源码（MTK 公开树）核对 pit_nat desc 布局。
2. q 事务普查为编码掩码法（imm 变体），绝对数与 U-T objdump 口径不可直接对比；未计
   pre/post-index 与寄存器偏移变体。
3. "低 32B 面 vs 不跑变参"两个解释在 ccci_* 零命中数据上不可分（无设备对照实验）。
4. RP102 busybox 与 RP103 busybox 的 q 计数全等但内容不同——未做行为级 diff（与本主题无关）。

**[C] 下轮入口**
1. **PIT_NAT 闭环（设备，30min 级）**：dmesg 抓 `dpmaif_rx_buf_init: PitNat: phy/virt/size`；
   `/dev/mem` 或 kmod dump 环内容，搜 `{bat_idx,0,{len,ip},0}` 同形条目并与最近 NE 记录对照。
   命中 ⇒ B 家族生产者=DPMAIF 写事务（引擎仿制 PIT_NAT 形状），写入目标=错投放。
2. 若闭环成立：**洪水包 vs PIT_NAT 对照**（洪水记录 len=321/1601、ip=192.168.9.1 应在环内
   有对应条目）——这能把"记录内容→生产者"链路从"包摘要"推进到"具体环+具体事务类型"。
3. 32B 拆宽工程照旧（U-T C 第 3 项），本轮无新增约束。
4. T4/T7 状态不变：官方两版本均未触碰引擎邻域，厂商侧"已修复版本"路径不存在。
