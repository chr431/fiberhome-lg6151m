## 2. 选择效应（Lead 任务 A）—— 哪些结论只能是"条件成立"

**机制**：h4 只在进程**已经崩了**之后才写；而崩的条件是"32B 写正好盖住 va_list，且 word0 被当指针解引用"。样本被双重截断：(i) 写入必须落在 **x2**；(ii) word0 必须是**不可解引用**的值。

| 结论 | 受污染? | 应该怎么表述 |
|---|---|---|
| C-002（103/106 同一记录）、C-003（71/32/3）、C-052（top−x2=0x390） | **是**。"记录在 x2"是被选进来的，不是测出来的 | 只能写"**在已崩溃样本里**记录位于 fault-time va_list"；不能当"记录的落点分布" |

| 记录 word0 = A（"40k–150k 小值/计数器/序列号"） | **是**。任何 word0 恰好是有效指针的写入不会崩、不进样本 | **A 的分布 = 崩溃选择后的分布**，不能反推写入者字段语义。可保留的只有"A 不是 8 字节对齐"（mod8 分布 1/7/3/6，无 0 聚集） |

## 3. 记录字段语义（Lead 任务 B）

### 3.1 现有 150 份样本混了两种形状（必须先分层）

我逐条解析 h4_rec150.txt：**A0B2 114 + B0A2 36**。A0B2 的 w2={ip,len}：len ∈ {1601×112, 1664×2}，**没有一个大值**；B0A2 的 w2 是小值 A'（不是 len），当 len 读就得到 57,497 / 63,388 / 70,029 / 72,085 / 75,922 / 81,299 / 107,677 …，并且 ip 读成 **0.0.0.0**。→ **09 结果 5 的"0.0.0.0 ×36"不是 IP 分布，是 B0A2 的占位读法**；"其余零散"也都来自 B0A2。**len 统计只能用 A0B2 子集**（112 条 1601 + 2 条 1664）。

### 3.2 对"len=包长"与"A=随机/哈希"的审计

| 假设 | 现有证据 | 判定 |
|---|---|---|
| len = 单个以太帧长度 | 1601 > MTU 1500；1592/1600/1608/1601 都在 1600 附近 | **排除** |
| len = GRO 聚合后的 skb->len | GRO 2 段应 ≈2×1448=2896 或 2×1400=2800，**不是 1600**；107677 类值若属 B0A2 混样则不算 | **未被排除但现有数字不支持**；1600 附近更像缓冲区/分配尺寸或"首段长度+头部" |
| len = 缓冲区尺寸（环配置 1920/1536） | 1601 不在 {1536,1920}；1600/1608/1592 都接近 1600 | **不能排除**；需要已知包长实验（§3.3） |
| A = 随机值/哈希 | A 的取值**被崩溃选择**（§2），mod8 无对齐聚集，同 pid 内非单调 | **两者都无法确证**；"A 是计数器"同样无法从这份样本证明 |

### 3.3 能一锤定音的**可控流量实验**（~20 min）

**判据（预注册）**：只统计 **A0B2** 形状；w2 拆成 ip/len 两半。
1. **已知长度单流**：PC 用同一源 IP（192.168.9.222）、固定 UDP 载荷灌 eth1，设备不跑其他业务（或夜间低流量窗）。臂 L1 载荷 200 B（帧 ~242 B）；臂 L2 载荷 1200 B（帧 ~1242 B）；每臂 ≥10 min，且**同会话 A/B/A 各一遍**。**判决**：len 随臂移动（~242 vs ~1242）→ len 是包长（或包长+固定偏移）；两臂都在 1600 附近不动 → len 是缓冲区/其它量。
2. **端点字段**：源 IP 用 192.168.9.222（非设备地址），目的 192.168.9.1。看记录 ip 半字是 **192.168.9.1（本机/目的）** 还是 **192.168.9.222（对端/源）**。若出现 222 → "本机端点"结论要改。
3. **对照**：同窗再跑一条已知长度、不同源 IP（192.168.9.223）的第二流，看两条流能否在记录里区分（len×ip 联合分布）。

**边界**：只回答字段语义，**不回答传输机制**；仍受§2 选择效应（只看到崩溃的那次写入）。样本量：热态（>50/min）10 min 够；冷态（~1/min）需 ≥60 min 或先找到进入热态的条件。

## 5. 反方质证：对"写入者=有线 EDMA RX 路径"的三条替代解释

### 5.1 替代解释 A（最强）：真正起作用的是 **SSH/TCP 接收的软件路径**，不是 EDMA DMA 引擎

**事实**：LAN-only 臂的流量是 lgssh → "cat > /dev/null"，即 **dropbear 用户态接收 600 MB**。它同时动了 EDMA RX DMA、TCP 收包/重组、socket 缓冲、copy_to_user、page_frag/slab 反复分配、dropbear 的读写。**这一臂无法把"DMA 引擎"与"TCP/用户态软件路径"分开**——它们是同一处理链的上下游。

**更强的反证**：09 结果 6 的"大包臂"用的**就是同一个生成器**（lan_rx_gen.py，2 MB/s TCP），在相似包率（1304 vs 1546 pps）下得 **2 命中/61 s（0.025/千包）**，而 LAN 臂是 **127.6/min（1.375/千包）**。**同一处理、不同会话、结果差 55 倍** → 效应不是由"这条处理路径"决定，而是由**会话状态**决定。

**判别观测**：
- **D1（最便宜、最决定性）同会话 A/B/A 反转**：SSH 灌流 5 min → 静默 5 min → SSH 灌流 5 min，同一批 canary。真处理效应应在第二段复现；不复现 → 状态驱动，R1 撤回。
- **D2 非 TCP 的 RX**：同包率（~1300 pps）的 **UDP**（目标端口 nft DROP，保证无用户态消费、无回包）vs SSH，同会话交替。只有 SSH 出效应 → 软件路径；两者都出 → RX 层。
- **D3 换用户态消费者**：SSH 换成设备自带 httpd / nc 接收同样字节数。dropbear 特异 → 说明是 dropbear 的某条路径。
- **D4 包率曲线（同会话）**：UDP 30/300/1500/15000 pps 四档 × 10 min。每包固定概率 ⇒ 命中/千包持平；状态驱动 ⇒ 命中/min 持平。

### 5.2 替代解释 B（对当前判决最致命）：**几何证据指向 VA-resolved 写入，而不是固定 PA**

- **固定 PA 模型预测页内偏移固定**：陈旧描述符的 DMA 目标是 PA X，落到页内的偏移 = X mod 4096（page_frag 的 buffer 起点）；所有命中应聚在**某个固定页内偏移**。
- **实测**：页内偏移 **53 种**，恒定的是 **top−x2=0x390**（相对栈顶 VA）。112 份里 82 份在 x2 命中。
- **定量**：要让固定-PA 模型解释 82/112，需要"仍被武装的陈旧描述符集合" ≈ 0.73 × 空闲页。**假设**空闲 ≈ 13 万页（RAM 共 523,008 页），需 ≈ **9.5 万页 ≈ 380 MB** 已释放缓冲仍被环指着 —— 与"环 512–1024 项 × 若干 ring"差 2–3 个数量级。**该假设可被推翻**：若实测空闲页只有 1 万页，则只需 7.3k 页（≈30 MB），仍是环容量的 7–14 倍；结论方向不变。
- **结论**：C-140 的论证方向反了（"PA/DMA+页复用能解释固定 top-relative 偏移"——不能）。不是"PA/DMA 已被证伪"，而是**当前表述与最强的几何数据冲突**：要么改成"VA-resolved（uaccess / GUP / 内核写用户 VA）"，要么给出按 VA 重新取 PA 的机制。

### 5.3 替代解释 C：**崩过的样本只告诉我们"被写坏的那一次"**
见 §2。这不是竞争假设，而是对 R1/R3 的共同削弱：所有"命中率"都是"崩溃选择的写入率"。

### 🟡 SMMU：结论对，理由错一条

### 🟡 pageguard 的前提依赖一个「待判」的模型
pageguard 的判据是「**曾经是 RX 环缓冲的物理页不再分配给用户匿名页**」——它成立的前提正是当前**被判为待判**的 PA/DMA 固定-PA 模型（audit §5.2）。若 D6 判成 VA-targeted，pageguard 对写入者无效。
→ 设计里已写反证条件 ✓；但**不要在 00_STATE/FIX 里把它写成「已定案的补偿控制」**，要写「**若 PA/DMA 成立则有效**」的条件句。

### ✅ 其它
- 「kprobe/ftrace/perf 全不可用 → 用 `aarch64_insn_patch_text` 打 bl」有先例（dphook 打过 3 个站点）→ 可行；但**热路径 shim 必须 O(1)**（AGENTS 教训：teardown 32K 连发线性去重导致 RCU stall panic）——fixer 的插入 ≤2 PFN / 查表 ≤8 步符合。
- `PAGE_FRAG_CACHE_MAX_SIZE=32768 / pagecnt_bias=32769` 这类常数若来自 .config，同样要给出处。

## 19. S 臂（SIGSTOP 冻结 + /dev/mem 直读）判据审计（Lead 2026-11-01 指派）

### ① SIGSTOP 会不会自己写用户栈 —— **不会，但有三段窗口要管**
- `SIGSTOP/SIGTSTP/SIGTTIN` 是**不可捕获**的：不跑用户 handler、**不建信号帧**、不写用户栈。停止动作本身对用户内存是只读的。
- 但 (a) **交付延迟**：从 `kill -STOP` 到任务真正 `TASK_STOPPED`，可能要过一个 tick 或一次系统调用返回；这段时间 victim 仍在全速改自己的栈 → **判据必须以 `/proc/<pid>/status` 的 `State: T` 为准（不是 kill 返回值）**，再加 settle（30 s 够）。
- (b) **停止点**若在 SIGSEGV handler 内，那就是 altstack（不在 `[stack]`）；对主栈无影响。
- (c) **窗口内禁止** SIGKILL/core dump（`core_meta.sh` 会调 stackdump 去 `PTRACE_ATTACH`，虽然只读/改寄存器，但会再停一次并引入新观测者）；禁止 nerepair/ptrace（已在 C4）。
- **建议加两个客观门禁**：① `State: T`；② 两次读 `/proc/<pid>/stat` 的 `utime+stime` **不变**（证明没在跑用户代码）。这两个比"内容不变"可靠得多（见 ③）。

### ② /dev/mem 读 RAM 的观测者效应 —— **只读、无引用、无 flags 变化；不要 mlock**
- 读路径对 RAM 走线性映射 `__va(p)` 的**纯读**：不 `get_page`、不改 `page->flags/_refcount/_mapcount`、不 fault、不置脏（脏位由 PTE 决定，不由 CPU 读决定）。
- 比 `/proc/<pid>/mem` **干净**：后者走 `get_user_pages`，会**临时 pin**（ref+1）并 mark accessed → 在 pageflags 五元组窗口里会污染 `extra = ref − map − 1`。→ **pageflags 读数时只用 /dev/mem**；`/proc/<pid>/mem` 只用于抽检。
- **绝对不要 mlock**：mlock 会给页加 `PageMlocked` 并计入不可回收引用，直接破坏 pageflags 判据；而且 mlock **不阻止迁移**（只防回收/换出），拿不到你们想要的好处。
- 必须要的守卫：
  1. **PA 新鲜性**：每轮用 patrace 重解析同一 VA→PA；PA 变了 → 该轮作废（见 ④）。
  2. **跨路径抽检**：S0 用 /dev/mem 与 /proc/pid/mem 各读同一 VA 的前 64 B，必须一致；不一致 = PA 陈旧或读路径异常 → 作废。
  3. **可读性正对照**（S 臂开始前一次）：读一页已知内容（canary 栈页），与 /proc/pid/mem 对齐 → 证明严格 devmem 没把 RAM 拒掉。
  4. 按 4 KB 对齐读，避免跨页（无必要变量）。

### ③ "整页变化字节数"的噪声底 —— **短间隔必须 0 B；但 30 s 的 S0/S0′ 门禁会有一半的假无效**
- **严格答案**：同一页**背靠背**两次读（≤1 s）必须**逐字节相同**，噪声底 = **0 B**。非零即装置问题（没真停 / PA 陈旧 / 读路径不对）。
- **但现行门禁（S0 与 S0′ 相隔 30 s 必须相同，否则判装置无效）会把真实事件当噪声**：同会话背景写入率约 1–2/min（10 §2），30 s 内出现事件概率 ≈ 1−e^(−λ·0.5) ≈ **39%–63%** → **假无效率约一半**。
- 更严重的是：该门禁的失败率**取决于待检假设**（若写入者只打活帧，冻结页永不被写，门禁永远通过；若打固定 PA，则常常失败）→ **用信号本身当门禁 = 循环论证**。
- **改法（建议直接改判读口径）**：
  1. **装置门禁**只用短间隔：S0a、S0b 相隔 ≤1 s，要求 **0 B** 差异；
  2. **状态门禁**：`State: T` + `utime/stime` 冻结（①的建议）；
  3. **长窗差分（S0→S1）不再要求为 0**：把差异**按形状分类**——出现 32 B 规范记录 ⇒ **事件**；其它位置或整页大面积差 ⇒ 装置/外力（判 INVALID 并写清）；
  4. "整页变化字节数"作为**协变量报告**，不作门禁。

### ④ 冻结进程的页会不会被迁移/回收 —— **回收/折叠不会；迁移可能会**
- **回收**：无 swap ⇒ 匿名页不可换出；`drop_caches` 只管 page cache；OOM 是杀不是回收 → 不会。**前提要复核**：`cat /proc/swaps`（空）+ `ls /sys/block/zram*`（无）。
- **THP 折叠**：`CONFIG_TRANSPARENT_HUGEPAGE` 未开（fixer 已核）→ khugepaged 不折叠。
- **迁移**：**可能**。内存规整（compaction）可以迁移**停止进程的匿名页**（迁移不需要进程运行），而 S 臂要开 LAN 灌流 → 分配 churn 正是触发规整的场景 → **PA 会变**。
  - 处置：每轮重解析 PA；S0/S1 各解析一次；PA 变化则作废该轮并记 covariate。
  - 另复核：`/sys/kernel/mm/ksm/run` 必须为 **0**（KSM 合并会引 COW，污染差分）。
- 结论："理论上不会"只对**回收/折叠**成立；**迁移不成立**，必须靠重解析兜住。

### ⑤ 功效：S 臂的 0 很贵，必须带对照与上界
- S 臂的 0 只说明"冻结页未被写"；其功效取决于**冻结页的真实写入率**（未知量），不能用活 canary 的 1–2/min 直接套。
- 必须同时报活性对照 A 的命中数；`B=0 & A≥3` 的上界按后验预测写（§18 修正：**A=3 → 5.9e-3**，不是 `e^-10 = 4.5e-5`）。

### ⑥ **S 臂 ≠ mprotect 臂的等价物（判的不是同一把锁）**

| | mprotect / RO 臂 | S 臂（SIGSTOP 冻结） |
|---|---|---|
| 问的问题 | 写入者是否**遵守 VMA 写权限**（uaccess vs 绕过） | 写入者是否**需要目标进程处于运行态**（活对象 vs 固定页/陈旧 VA） |
| 有命中 ⇒ | 理论上不该有；有 = 绕过 VMA | 写入者不需要活目标 ⇒ **削弱 H2-live**，与 H1b/H3/H5、uaccess-到陈旧VA 相容 |
| 0 ⇒ | 与 uaccess 相容（需排 COW 假阴性） | 与 **H2-live** 相容 |
| 主要混杂 | COW 假阴性（PTE 只读 + VMA 可写） | 冻结目标不再是目标 |

→ **可以拿 S 臂替代 mprotect 臂作为本轮唯一可执行的那一条（成本等价、无需改 VMA）**，但记分卡必须写清：**S 臂不判 VMA 权限**；mprotect/RO 的问题仍未回答（只是暂时没有可执行的臂）。

## 22. 待审新判据：`fixup_exception` 钩 + victim 自 mprotect(RO)（Lead 2026-11-01 指派）

### ① uaccess 缺页是否必经 `fixup_exception`（arm64 5.15）
**是，但有三个前提。**
- arm64 的 uaccess（`copy_{to,from}_user`、`__get/put_user`）用 `user_ldst` 宏，每条可能 fault 的指令在 **`__ex_table`** 里都有 fixup 项；缺页后走 `el1_da` → `do_mem_abort()` → `do_page_fault()`，当 fault 无法由 VMA 处理（无 VMA/权限不足/`!mm`/`in_atomic()`/pagefault_disabled）时进 `no_context` → `__do_kernel_fault()` → **`fixup_exception(regs, esr)`** 查 `__ex_table`，命中则改 `regs->pc` 到 fixup 处理器、返回；未命中才 `die()`。
- **前提 1（VMA 级只读）**：只清 PTE 的 `PTE_WRITE` 而 VMA 仍 `VM_WRITE` ⇒ 写缺页走 **COW** ⇒ **不 fault、钩子看不到**（假阴性）。**必须用 `mprotect(addr,len,PROT_READ)` 改 VMA**（victim 自做即可，且它必须处于睡眠/停止态，否则自己写栈会自崩；窗口结束前必须恢复 `PROT_READ|WRITE`）。
- **前提 2（必须是 uaccess 原语）**：若写入者是**普通内核 store 到用户 VA**（无 `__ex_table` 项）⇒ fixup 找不到 ⇒ **`die()` → 内核 Oops**（设备可能重启）。这不是缺点——它本身就是身份证据（PC/LR 直接给写入者），但**必须先确认 `panic_on_oops`/看门狗行为**，并准备好串口救援。
- **前提 3（钩子可实现）**：`fixup_exception` 是 `fault.c` 里的 **static** 函数，kallsyms 里通常有符号（`KALLSYMS_ALL` 只影响数据符号）；若找不到，退而打 `__do_kernel_fault()` 里那条 `bl fixup_exception`。**必须做 trampoline 调原函数**——替换而不调用原函数 = 所有 uaccess EFAULT 变成 die = 系统崩。

### ② "被吞掉的写不改变内存" ⇒ 怎么区分"没写"与"写者不存在"
**用钩子的记录当"写入尝试"的证据，用内存差分当"写入成功"的证据，两者交叉成 2×2：**

| 钩子有记录 | 内存出现记录 | 判读 |
|---|---|---|
| 有 | 无 | **写入者存在且是 uaccess 系，被 RO 拦住** → 点名（E4，PC/LR 就是身份） |
| 无 | 有 | 写入者**绕过 VMA**（DMA 或 `__va(pa)` 直映射/普通 store 未 Oops 的场合）→ PA 系证据（E3） |
| 有 | 有 | uaccess 写成功了（VMA 没真 RO / 恢复太早）→ 装置问题，重跑 |
| 无 | 无 | **三义**：①写入者是 DMA/直映射（不产生缺页）；②本窗口没有写入者（功效不足）；③RO 没生效。→ **不得写成"uaccess 不存在"** |

**必带的三个对照**：
1. **正对照**：模块对受害 VA 做一次已知 `copy_to_user` → 钩子必须记录（带 PC）；**没有它，钩子的 0 一律不可用**（audit §10）。
2. **活性对照 A**：同窗口一个未 RO 的 canary 持续出命中 ⇒ 设备在写、窗口有效；A=0 判无效窗口。
3. **负对照**：健康进程/未 RO 页上钩子应 0 记录（或只在 armed 窗口内命中我们关心的地址）⇒ 证明不会被无关 uaccess 刷屏。
另：**窗口内必须停 nerepair**（它也 ptrace 并截 SIGSEGV，会与 RO 臂互相抢事件、且会"修好"我们想观察的崩溃）。

### ③ 缺页风暴下的重入/性能风险
- `fixup_exception` 在**异常上下文**执行（可能关中断、`in_atomic`、pagefaults disabled），是**极热路径**（每次内核缺页都走）。
- 风险与对策：
  | 风险 | 对策 |
  |---|---|
  | 钩子里 printk ⇒ 风暴时拖死设备 | **禁止 printk**；只写 per-CPU 定长环形缓冲（如 64 项）+ 原子计数，用户态 `read /proc` 取 |
  | 钩子自身再缺页（访问用户地址/模块数据未驻留）⇒ 递归 `die()` | 钩子只碰 `regs`、`addr`、per-CPU 静态数组；**入口设 per-CPU `in_hook` 递归守卫** |
  | 锁 | 只允许 `spin_lock_irqsave`（或无锁 per-CPU）；**禁止 mutex/睡眠** |
  | 高频写入把 CPU 打满、改变被测行为（观测者效应） | **限速**（每 CPU 每秒 ≤N 次，超出只计数）；**armed 窗口开关**（未 armed 直接跳过） |
  | 复杂过滤逻辑放大开销 | 只做**简单数值范围比较**（addr ∈ [va_lo, va_hi]） |
  | 与 nerepair/其他 ptrace 冲突 | 窗口内停 nerepair，并在报告里记录当时 TracerPid |

**结论**：这个判据**方向正确、可实现**，但要把"VMA 级只读"（不是 PTE）、"正对照"、"ring buffer + armed 开关 + 限速"三件事写进设计，否则会得到假阴性或把设备打崩。

## 27. 事故记录：uwhook.ko insmod → 内核 IABT → 非计划重启（2026-11-01，E3 级仪器事故）

### 27.1 事实（来自 pstore，`_local/evidence/crash-root/pstore/console-ramoops-0`，262,132 B，md5 1629a33d…）
- 故障 VA：**0xffffffffc008b684**；
- **ESR = 0x86000005**：`EC = 0x21`（**IABT, current EL** —— 取指中止）、`IL = 32 bits`、`FSC = 0x05`（**level 1 translation fault**）；
- `Internal error: Oops: 86000005 [#1] SMP`；`swapper pgtable: 4k pages, 39-bit VAs`；
- 后续（同 pstore 旧副本）曾见 `Kernel Offset: 0x100000 from 0xffffffc008000000` → 内核文本基址 ≈ `0xffffffc008100000`；模块区实测在 `0xffffffc00153xxxx`（mtk_wed）。
- **ramoops 副本在 Oops 头之后就截断了**（共 2493 行，没有寄存器/调用栈/`Modules linked in`）——所以**无法从这份日志直接点名是哪个 patch 站点**。

### 27.2 我的判读（E2，方向明确）
**故障地址是「32 位地址被符号扩展」的典型形态**：
`0xffffffff_c008b684 == sign_extend32(0xc008b684)`；而一个真实的 39 位内核/模块地址应形如 `0xffffffc0_xxxxb684`。
⇒ 最可能是 **trampoline/补丁里把 64 位目标地址当 32 位处理**：
- arm64 上绝对地址要用 **4 条 `movz/movk`**（每 16 位一条）构造；只发 2 条就只剩低 32 位，符号扩展后正是这个形态；
- 或者把目标地址存进了 `u32`/`int` 字段、做了 `(u32)target` 截断；
- 或者 `bl` 的 ±128MB 立即数溢出（但那种会落在近处、不会呈符号扩展形态，故**优先级低于**上两条）。
这条与我在 **audit §22③** 写的"热路径钩子必须 trampoline 调原函数、且只碰已知映射"的风险判断一致 —— **事故印证了该风险**。

### 27.3 定级与后果
- **仪器事故，E3（事实级：insmod → IABT → 重启，因果清楚）**；与 C-035（cth_cfu 正对照 Oops）同类，**不是记录家族的 bug**。
- **uwhook 在本轮没有任何有效阴性/阳性数据**（这是第一次 insmod），因此不存在"要撤回的 uwhook 结论"；但**任何后续引用都必须先有修好的模块 + 正对照**。
- **新 boot_id**（bbf535d5-…，旧 72c136ea-…）：**跨 boot 一律不可比**（速率、PA/VA、页池状态、"热态"全部重置）。

### 27.4 受影响的既有数据（逐条）

### 27.5 建议的硬规则（进 10_MEASUREMENT_PROTOCOL / 模块开发 SOP）
1. **模块上线前先做"空模块"**：`insmod` 只注册 /proc、**不打任何补丁**、`rmmod` 干净 → 确认 vermagic/重定位/卸载链没问题。
2. **一次只打一个站点**，打完立即 `pr_info` 打印**解析出的目标地址（64 位，`%016llx`）** 与实际写入的指令字；用 `aarch64_insn_patch_text` 前先对**模块自有的已映射页**做一次自测。

## 29. sampler2 的活体观测（健康长驻进程栈）—— 口径与一个新模型

### 29.1 观测（lab，600 s 部分结果；原始件 `sampler2_partial.log`，断言 338==338）
- `nerepair`(9837) 槽 **top−0x3b0**：~60 s 内 **q0 出现 8 种、ip 出现 5 种** → 同地址被反复重写；
- `nerepair`(9837) 槽 **top−0x12d0**：2 种；
- `dnsmasq`(22033) 槽 **top−0x1b40**：**113 次观测完全恒定**（q0=0xe48f，len=1601，ip=192.168.9.1）；
- 两进程命中时都在**阻塞 syscall**（wait4=260 / ppoll=73）；`/proc/pid/syscall` 在阻塞态读不到 sp。

### 29.2 必须纠正的一句推断
lab 写「⇒ 记录不是由"当前 syscall 的栈指针"产生」。**这句不成立**：读不到 sp ≠ 不是由 sp 产生。
阻塞态任务的用户 sp 存在**内核栈上的 `pt_regs`** 里（`task_pt_regs(tsk)->sp`），`/proc` 读不到不代表它不存在。
这条观测能支持的只有：**在进程阻塞、栈帧固定的这一段时间里，写目标是稳定的固定 VA**（同一地址反复被写，113 次同值）。

### 29.3 这条观测真正有价值的地方（我的判读，E2）
把 sampler2 与 D9 深度臂放在一起，**只有一个模型能同时解释它们**：

| 观测 | 对模型的要求 |
|---|---|
| D9：命中点随 victim 的活帧深度 D 精确平移（残差 0） | 目标必须**跟着受害者的最近一次活帧**走 |
| sampler2：阻塞进程的同一地址在 60 s 内被反复写（8 种 q0），另一个进程 113 次同值 | 目标在**进程静止时固定不动** |
| 健康栈 2/12 含记录；自然 NE 4/4 | 写入对进程**无选择性** |
| `dnsmasq` 的偏移 0x1b40 与 nerepair 的 0x3b0/0x12d0 各不相同 | 偏移**不是全局常数**，是每进程/每调用点自己的值 |

⇒ **最简模型（暂名 H7：每进程"最近一次 va_list 地址"的缓存/陈旧指针）**：某个写入方持有**按进程缓存的一个用户栈 VA**（该 VA 是该进程最近一次 printf 族调用的 va_list 位置），进程活动时随帧更新（⇒ D9 的平移），进程静止时保持不变（⇒ sampler2 的 113 次同值）。
这与 **H2（uaccess + 陈旧用户指针）** 与 **H5（对该页 pin + 按 VA 派生偏移）** 都相容；与 **H6（用当次 syscall 的 sp）** 只在"更新时机"上不同，需专门判据（见 29.5）。

### 29.4 `q0=0` 的记录到底算不算——这个口径直接改变所有比例
我 strict 扫 12 份健康栈得 **2/12 文件、6 命中**：其中 `26710.stack` 的 **4 条全部 q0=0**（len=1601，ip=192.168.9.1）。
lab 报 **1/12**（14579 的 q0=0x1619e 那条）；Lead 报 1/12。**差异就在"要不要数 q0=0 的记录"**。

**这不是小事**：健康基线的分子直接决定"4/4 的富集倍数"（2/12 → 6×；1/12 → 12×）。必须先定死：**q0=0 是否计入，依据是什么**（建议：按 canary 语料里 q0=0 记录的存在率与形态来定，而不是按健康样本的方便与否）。

### 29.5 H6 的真正判据（现在就能做，且不用补丁内核文本）
- 需要的是**阻塞任务保存的用户 sp**：`task_pt_regs(tsk)->sp`（内核栈上，合法可读）。
- 最省的做法：一个**只读**的 `/proc/<name>` 条目（模块只做 `for_each_process` + 读 `task_pt_regs`，**不打任何补丁、不 hook 文本**），或由 lab 用现有 patrace 类似的只读模块扩展；
- 判据（预注册）：对**同一阻塞进程**的同一命中槽，比较 `top − va` 与 `sp_saved + K` 是否一致；对**不同 syscall 类型**（wait4 vs ppoll，栈深不同）重复。
  - 若 `top − va` 恒定而 `sp_saved` 随 syscall 类型变 ⇒ **H6 死**（目标不是当次 sp 派生）；
  - 若 `top − va` 随 `sp_saved` 平移 ⇒ **H6 活**。
- 风险提示：任何新模块都要按 **C-172 的 SOP**（空模块先跑、不打补丁、串口窗口、`%016llx` 打印 64 位地址）。

### 30.3 D15 预注册（阻塞进程稳定槽的 pte_redirect 判决；kdev 执行）
**对象**：lab 抓到的天然稳定槽——`dnsmasq` start_stack−0x1b40（113 次同值）、`nerepair` start_stack−0x3b0（60 s 内 8 种 q0）。
**操作**：`pte_redirect.ko` 把该 VA 所在页的用户 PTE 重定向到新页 **Q**（保留属性位），旧物理页记作 **P**（仍可经直映射读）。

**判据（预注册，三条）**：
1. **Q 页出现记录** ⇒ 写者跟随 PTE ⇒ **VA 解析**；
2. **旧页 P 继续出现记录** ⇒ 写者绕过 PTE ⇒ **PA 写**；
3. **两边都不变** ⇒ **INVALID**（先查同窗 canary/对照槽活性；不得写成"没有写入者"）。
4.（补充）**两边都有** ⇒ 双写者/双路径，必须分开报，不得合并。

**前置正对照（缺一不得判）**：
- ① 重定向前先证明该槽**在写**：dnsmasq 槽有 113 次/600 s ✓；`nerepair` 槽有 8 种 q0/60 s ✓；
- ② 同窗**未重定向的对照槽**（另一进程同型槽）必须持续被写 ⇒ 证明设备在写、窗口有效；
- ③ `pte_redirect` 自身正对照：模块向 Q/P 各写一条合成记录，扫描器必须分别报 kind=1/2；
- ④ **清零前置**（本轮新增，关键）：**重定向前后由模块把 P 与 Q 两页的该 32B 区域清零**。
  理由：`dnsmasq` 槽是**113 次同值**——**同值重写用"内容差分"根本看不见**（差分法会把它判成"没变"）。不先清零，判据 2/3 会系统性假阴性。
- ⑤ 记录检测仍用 strict 判据 + stride 8/16；**不用**宽松 shape。

**读数时机**：重定向后至少观察 **10 min**（沿用本会话速率，勿跨会话比）。
**风险**：改活进程的 PTE（BROKEN 史见 P-07）；必须 60 s 稳定性对照——受害进程 60 s 内死 = INVALID（F-07 既有条款）。

## 32. D15 **INVALID**：pte_redirect 的 zero 路径把设备打崩（本轮第二次仪器事故）

### 32.1 事实（pstore2，`_local/evidence/crash-root/pstore2/console-ramoops-0`，md5 cadf1fc7…）
```
[ 834.843813] kworker/3:7: BUG: Bad page state in process kworker/3:7  pfn:acdcb
[ 834.845358] kworker/3:7: Kernel panic - not syncing: panic_on_taint set ...
[ 834.846241] CPU: 3 PID: 518 Comm: kworker/3:7  Tainted: P    B   (B = bad page)
             Workqueue: events free_work
             free_pcppages_bulk <- free_unref_page <- free_the_page <- __free_pages
             <- __vunmap <- free_work <- process_one_work <- worker_thread <- kthread
```
⇒ **模块的 zero 路径在释放它不该释放的页**（或重复释放 / 释放仍被 PTE 映射的页），页状态检查 `check_free_page()` 报 bad page → `add_taint(TAINT_BAD_PAGE)` → **`panic_on_taint` 触发 panic**。

### 32.2 判读（E2，方向明确）
- 崩点在 **`__vunmap` → `__free_pages`**：这是 **vfree/vunmap 的延迟 work**，不是普通 kmalloc 路径。所以最可能是：模块对自己 **vmalloc 出来的 Q 页（或它借用/偷来的页）** 做了错误的释放顺序 —— 例如 PTE 还指着它、或同一页被 free 两次、或把 victim 的页当成自己的页 vfree。
- 触发者是 `panic_on_taint`（不只是 `panic_on_oops`）：**这台设备上任何"坏页"都会直接 panic**。
- **与 C-172（uwhook IABT）合并看：本会话 30 分钟内两次内核模块事故、两次非计划重启** ⇒ 模块路线在本设备上的风险等级要上调。

### 32.3 结论与要求
- **D15 本轮作废（INVALID）**，不是"VA/PA 判不出来"，是**仪器把设备打崩**——按判据纪律，这种情况绝不能写成阴性。
- **pte_redirect 的 zero 路径必须改**：① 只对自己分配的页做 `vfree`，且**先恢复 PTE、确认无人引用**；② 绝不对 victim 的页做 `__free_pages`/`vfree`；③ zero 用直映射 `memset(__va(pa))` 或对 Q 页 `memset`，不要用"释放再分配"来实现清零；④ 加 `page_count`/`mapcount` 前置断言，不满足就**放弃并报错**而不是继续。
- **设备侧硬约束**：`panic_on_taint` 与 `panic_on_oops` 都开着 ⇒ 任何内核模块 bug 基本等于重启。建议（需 Lead 批准）：模块 bring-up 期间临时把 `panic_on_taint` 置 0（只影响"是否 panic"，不改行为），做完恢复；否则每次调试都要付一次重启代价。

## 33. 教训：**仪器可用 ≠ 实验可用**（D15 的教训，Lead 指定）

D15 这次的事实链：
- `pte_redirect.ko` **加载成功**；
- **poison 正对照 PASS**（`chgP=769 / chgQ=658`，P/Q 两页都能被检测到变化）；
- 但模块的 **zero 路径**触发 `BUG: Bad page state pfn:acdcb` → `panic_on_taint` → **重启**；
- ⇒ **判决（VA vs PA）没拿到，实验 INVALID**。

**教训（写进纪律）**：
> **判据链任何一环崩掉，整条实验都是 INVALID，而不是"阴性"或"部分成立"。**
> 仪器"能加载/能自测"只证明它**在校准条件下**可用，不证明它**在目标操作下**安全或可用。
> 因此每个实验的"可用性"要单独验收：**校准正对照（poison/自注入）** + **目标操作的空跑（dry-run，不碰真页/不写寄存器）** + **失败时的回滚路径**，三者缺一不得开窗。

**对后续实验的直接要求（新增前置）**：
1. 凡是要"改别人状态"的仪器（改 PTE / 改寄存器 / 改页内容 / 打补丁），先跑一次**同代码路径的 dry-run**（目标换成模块自有对象）；
2. dry-run 通过后，**第一件真事**是"做一个可逆的小动作再撤销"，确认撤销路径有效；
3. 崩溃/重启 ⇒ 该实验 **INVALID**，不许把已经采到的"部分数据"当阴性；
4. 报告必须写清"在这次 INVALID 里，哪几项前置已经 PASS"（本次：加载 ✅、poison ✅、zero 路径 ❌）。

## 34. 统计意见：能否用"槽重写速率"给 nerepair 做 A/B（Lead 指定评估）

**结论先说：可以用，但必须改口径——它测的是"进程存活"，不是"写入率"，而且不能直接用"速率高低"。**

### 34.1 为什么不能直接用速率
- nerepair 的设计**只修复崩溃、不停止写入**（C-149）⇒ **写入速率在"修好"与"没修好"两臂里应当相同**；若把"速率下降"当成修复生效，方向就反了。
- 真正的信号是：**进程死了，它的槽就不再产生新内容**（槽冻结）。而 `dnsmasq` 的槽 **3197 次观测只有 1 种内容**却是**活着的** —— 所以"静止"**不等于**"死了"，速率为 0 也不是死亡判据。
- ⇒ 正确对象是 **"到槽冻结的时间"（time-to-freeze）**，即一个**生存分析**，不是两个速率的比值。

### 34.2 准入（admissibility）——三条必须满足
1. **代理有效性**：先证明"槽冻结"确实对应"进程死亡"。做法：正对照 = 人为 `kill -9` 一个已知活跃槽的进程 → 槽必须冻结；负对照 = `dnsmasq` 那种"活着但静止"的槽必须在判据里被**排除或分层**（按"该槽历史活动性"分层：活跃槽 vs 静止槽）。
2. **同会话内 A/B**：跨会话速率不可比（10 §2，19× 漂移）⇒ nerepair on/off 必须**同 boot、同会话、交替（ABAB）**，且两侧用**同一批进程**。
3. **同值重写不可见**："distinct content"只是**下界**；一旦写者重复同一内容（dnsmasq 就是），速率会被低估到 0。⇒ 判据里必须同时报 `观测次数`、`distinct 数`、"最后一次内容变化距今"三个量。

### 34.3 功效与 CI 口径
- 观测率 ≈ **0.62 次/s 的不同内容**（369/600 s，下界）。窗口 600 s ⇒ 单进程约 369 个事件 ⇒ 检测 20% 差异的 Poisson 功效 >0.9；但**分箱计数大概率过度离散**（bursty），所以：
  - 主报：**每个进程的到冻结时间 + Kaplan–Meier 曲线 + log-rank 检验**（含删失：窗口结束/采样器停）；
  - 辅报：事件数与速率（**精确 Poisson CI，再用设计效应放大**，设计效应由 1 分钟分箱的方差/均值比估计）；
  - **样本量**：每臂 ≥5–10 个**活跃槽进程**（不是 25 个随便挑的），并按"该槽历史活动性"配对。
- 判据写成：`HR（风险比）与 95% CI`，不要写"速率差"；若必须写速率，写成 `事件/观测秒` 并附过度离散系数。

### 34.4 给 FIX v2 §4.2 的一句话建议
> **把主判据从"槽重写速率"改为"槽到冻结的时间（生存分析）"**，并把"写入速率不变"明确写进预期（它恰好是 nerepair 只修崩溃不停止写入的旁证）；准入需 `kill -9` 正对照 + 静态槽分层 + 同会话 ABAB。

### 32.4 **更正（kdev 2026-11-01，我采纳）**：机制是"页归属"，不是"错误释放"
kdev 指出：模块的 zero 路径只有两句 `memset`，**不调用 `__free_pages`/`vfree`/`put_page`**；唯一的释放点是 `do_stop`/`rmmod`，而本次从未走到。真正的机制是：
- 模块用 `alloc_page(GFP_KERNEL)` 拿到 **Q 页**，直接 `set_pte_at` 把它塞进**用户 PTE** —— 但 mm **没有按 anon 记账、没有 rmap 条目**；
- 于是该 pfn（**0xacdcb**，与 lab 的 `pte_after=0xe80000acdcbf43` 帧号一致）处于「**页表里有、mm 账上没有**」的**双重归属**；
- 该页随后进入分配器（作为 vmalloc 区的一页）被释放时，`check_free_page()` 抓到状态不一致 → `bad_page` → `panic_on_taint`。
- 所以 pstore 里的 `__free_pages <- __vunmap <- free_work` 是 **vmalloc 释放路径**，不是模块帧。

**保留的教训（不变）**：任何"把模块页塞进用户 PTE"的设计，**必须先完成 mm 侧记账**（rmap/mapcount/anon 标记/`inc_mm_counter`），否则就是埋一颗定时炸弹；更稳的做法是**根本不要插入外来页**。
→ 我已按此更正台账 **C-174**（不再写"释放了不该释放的页"），并把"zero 用 memset"这条标为**原本已满足**（我原来的要求③属误判）。

## 35. 替代仪器 `uprot.ko` 的判据预审（kdev 计划，未上机）

**设计**：不分配/不释放页、不碰 rmap、不动引用计数，只改两个权限位——**用户 PTE 的写位** + **VMA 的 `VM_WRITE`**。
⇒ 32.4 那类"双重归属"风险**天然不存在**；它等价于此前设计的 **mprotect/RO 臂**，但在内核里执行、不需要 victim 自己动手。

**必须写进预注册的四点**：
1. **两处都要改**：只清 PTE 写位、VMA 仍可写 ⇒ 写缺页走 **COW** ⇒ 写"成功"到新页（假阴性）。**必须同时清 VMA 的 `VM_WRITE`**（kdev 已说明两者都改 ✓）。
2. **窗口内 victim 必须保持阻塞/停止**：VMA 只读后，victim 一旦醒来写自己的栈 → 用户态 SIGSEGV → 进程可能死 → 槽消失、判据污染。⇒ 选**阻塞中的 daemon**（dnsmasq/nerepair 那类），并在 victim 唤醒迹象出现时立即恢复。
3. **判据是"RO 槽静默 + 对照槽活跃"**：uaccess 写会被吞（-EFAULT，无记录）；DMA/直映射写不受 PTE 影响。所以：
   - **RO 槽无新记录 + 同窗对照槽持续有新记录** ⇒ 写者遵守 VMA 权限 ⇒ 指向 **uaccess（H2）**；
   - **RO 槽继续出现新记录** ⇒ 写者绕过 VMA ⇒ **PA 系（H1b/H3）或 DMA**；
   - **两边都静默** ⇒ INVALID（先查对照槽与设备活性）。
4. **正/负对照**：① 正对照——模块对 RO 槽做一次已知 `copy_to_user`，应失败且**不产生记录**；② 负对照——未 RO 的对照槽同窗必须活跃；③ 仪器自检——权限位改前/改后回读 PTE 与 `/proc/<pid>/maps`（确认无 `w`）。

**落地顺序建议**：先跑**空模块**（只读、不改任何位）→ 再对**一个**阻塞 daemon 的一个槽做 60 s RO 窗口 → 通过后再延长到 10 min。

## 36. `uprot.ko` 三阶段 bring-up 的判据复核（kdev 2026-11-01 修订后）

kdev 已落：① PTE 写位与 VMA `VM_WRITE` 同时清；② `rmmod` 无条件恢复所有 RO 表项并逐项打印 rc；③ 新增 `check`（只读打印 PTE/VM_WRITE/VM_MAYWRITE）与 `probe`（`access_process_vm(FOLL_WRITE)` 写 1 字节，RO 时应 REFUSED）；④ 三阶段：空模块只读 → 单槽 60 s → 10 min，阶段 1 必须 probe=REFUSED + maps 无 `w` + victim 仍阻塞存活。

**方向正确。但 `probe` 这个设计有三处必须补，否则会给出假阳/假阴：**

### 36.1 `probe` 的**前置正对照**不能省
`access_process_vm(FOLL_WRITE)` 返回 0（REFUSED）**不唯一指向"VMA 只读"**——VA 算错、mm 取不到、页不存在、`FOLL_WRITE` 被别的原因拒绝，全都返回 0。
⇒ **必须**先做一次**改 RO 之前**的 probe：同一 pid/VA 上必须返回 **1（写成功）**。
判据链变成：`probe_pre == 1` → 置 RO → `probe_post == REFUSED` ⇒ 才证明"RO 真的生效"。缺 pre 的 REFUSED 一律不算。

### 36.2 `probe` 自己会动页表 / 可能 COW——**严禁在窗口内跑**
`access_process_vm` 走 `get_user_pages*`：对**可写** VMA 会 pin + 可能在 `FOLL_WRITE` 下**触发 COW**（PTE 被换成新页）。对 pte_redirect/uprot 这类"靠 PTE 精确控制"的实验，**probe 本身就能毁掉装置状态**。
⇒ 规则：① probe 只在**置 RO 前**（正对照）与**置 RO 后、开窗前**（判据）各跑一次；② **窗口内禁跑 probe**；③ probe 的 VA 取**该页边缘**、避开 32B 记录槽本身（不要让 1 字节写碰记录）；④ 每次 probe 前后读一次 PTE 并打印，证明 probe 没改坏状态。

### 36.3 卸载顺序（本设备有前科）
本设备 2026-11-01 02:55 的 Oops 就是"模块卸载后仍有中断指向已卸载模块映像"（IABT 到 `mtk_wed+0x54`）。
⇒ `uprot` 的卸载必须：**① 先把所有 RO 表项恢复 RW 并逐项确认 → ② 确保没有并发执行模块代码（`stop_machine`/RCU 同步或明确的 quiesce）→ ③ 再卸载**。kdev 已做 ①，②建议显式做。

### 36.4 阶段 1 的闸门建议再补两条
- **控制进程对照**：对**另一个未置 RO 的进程**做同样的 probe，必须返回 **1**——证明"probe 仪器本身没坏"（否则全局 REFUSED 会被误读成"RO 生效"）；
- **写者活性**：同窗内**未 RO 的对照槽必须仍在产生新内容**（vsv 采样器即可），否则窗口无效（写者不在，RO 槽静默没有意义）。

### 36.5 源码层核账（kdev 自报，我采纳）
`pte_redirect` 全量 grep 释放原语：**6 处 `__free_pages` + 2 处 `kfree`，全部在 `do_redirect` 回滚、`do_stop`、`/proc` 读缓冲**；`zero`/`rebase` 各只有 `memset`/`memcpy` 两句。⇒ **崩溃与 zero 无关**，是 `do_redirect` 的**页归属**缺陷（见 §32.4）。这条与 C-174 一致。

### 37.2 一条必须写死的**反模式**：禁止给 `access_process_vm` 加 `FOLL_FORCE`
kdev 现在传的是 `access_process_vm(..., FOLL_WRITE)`（**不带 FOLL_FORCE**）——**这是对的**。
但要在协议里写死：**`FOLL_FORCE` 是 ptrace 语义，它会绕过 VMA 的只读检查**（调试器写只读页就靠它）。一旦有人为了"让 probe 能写"加上它：
- `probe` 会在**已置 RO 的 VMA 上照样写成功** ⇒ 返回 1 ⇒ 被误读成"RO 没生效"（假警报）；
- 更糟的是，如果将来有人拿这条路径当"写原语"，它会**静默击穿整个只读实验**。
⇒ 预注册里加一句：**probe/selftest 禁用 FOLL_FORCE；任何启用它的改动都要重新走审计。**

### 37.3 两个次要 review 点（不阻塞，但建议在 §6 里注明）
1. **对"别人的 mm"改 PTE** 的规范写法是 `ptep_modify_prot_start/commit`；直接 `set_pte_at` 在持有 `mmap_write_lock(mm)` 时通常也可接受，但要确认**它是非 current mm**、且改完**已 `flush_tlb_mm`**（协议里已写 flush_tlb_mm ✓）。
2. 恢复路径里 **PTE 与 VMA 的顺序**：建议 **先恢复 VMA `VM_WRITE`、再恢复 PTE 写位**（反向于"加锁"顺序），避免中间态出现"VMA 可写但 PTE 只读"引发意外 COW；kdev 的 `ro/rw` 是同一函数内成对执行的，建议在协议里把顺序写死。

### 37.4 grep 陷阱入纪律（同一个老毛病的新变种）
kdev 第一次宽匹配命中的是**注释**——这与 AGENTS 三定律的**定律②（子串会被"提及者"骗）**完全同族：判据是"出现这个词"，目标却是"调用点"。
⇒ 记入判据纪律：**匹配内核/源码里的"调用点"时，必须匹配带括号的调用形式**（`\bname[[:space:]]*\(`），并**排除注释/字符串**；任何"宽匹配 0 命中"或"唯一命中在注释里"都要当可疑。

### 37.5 FOLL_FORCE 这条我在**厂商树 5.15.134** 上独立核了（结论比 kdev 说的更硬）
证据（`_local/legacy/linux-5.15.134`，Makefile `VERSION/PATCHLEVEL/SUBLEVEL = 5/15/134`）：
```c
int access_process_vm(struct task_struct *tsk, unsigned long addr, void *buf, int len, unsigned int gup_flags)
{ ... ret = __access_remote_vm(mm, addr, buf, len, gup_flags); ... }   /* 原样透传，不补标志 */

static int check_vma_flags(struct vm_area_struct *vma, unsigned long gup_flags)
{ ... int write = (gup_flags & FOLL_WRITE); ...
    if (write) {
        if (!(vm_flags & VM_WRITE)) {
            if (!(gup_flags & FOLL_FORCE))
                return -EFAULT;                 /* ← 我们的 probe 走这条：返回 0 字节 */
            if (!is_cow_mapping(vm_flags))
                return -EFAULT;                 /* ← 私有匿名栈 is_cow_mapping()==true ⇒ FOLL_FORCE 会放行 */
        } }
}
```
⇒ 两条硬结论：
1. **本树 `access_process_vm()` 不补 `FOLL_FORCE`** ⇒ kdev 的 `probe`（只传 `FOLL_WRITE`）在 VMA `VM_WRITE` 被清掉后**必然返回 0 字节** ✓；
2. **一旦有人加 `FOLL_FORCE`，对"私有匿名栈 VMA"会通过 `is_cow_mapping()` 检查而放行** ⇒ probe 会成功写 1 字节、返回 1 —— 我上一条的警告**不是假设**，在这棵树上可精确复现语义。
3. 反过来这也**从源码层证实了"必须清 VMA 的 VM_WRITE"**：`check_vma_flags` 只看 `vma->vm_flags`；只清 PTE 时它照样放行，随后走缺页/COW 路径 —— 正是假阴性。

**运行期自检（建议加，且能跨内核版本存活）**：
用一个 helper 进程 `mprotect(PROT_READ)` 出一页专用测试页（不碰受害进程），对它跑一次 `probe`：
- 返回 **0** ⇒ 行为符合预期，可以继续；
- 返回 **1** ⇒ 说明存在 `FOLL_FORCE` 类行为（或 VMA 没真清）⇒ **立即中止本次实验**，不要用这版内核做只读判别。
**规则**：换内核/换厂商树/换分支后，必须重跑这项运行期自检（源码核对 + 运行期自检两条都要）。

## 38. `prot_helper` 复核（FOLL_FORCE 自检器）

### 38.1 身份与设计核对（主机侧）
- **`prot_helper` = 23,776 B / md5 `db2086eec1c80ce74bada857faf59e21`** ✓ 与 `FIVETUPLE.txt` 第 10 条一致（我按盘核过，10/10）；
- 源码：`mmap(4096, PROT_READ|PROT_WRITE, **MAP_PRIVATE|MAP_ANONYMOUS**, -1, 0)` → `mprotect(PROT_READ)` → 打印 `pid/page` → 阻塞。
- ⇒ **映射类型正确**：私有匿名 ⇒ `is_cow_mapping()==true` ⇒ 这正是能检出 `FOLL_FORCE` 的那一类 VMA（若用文件映射/共享映射，`is_cow_mapping()` 为假，即便存在 FOLL_FORCE 也会返回 EFAULT，自检器就失去检出能力）。

### 38.2 一条建议（让自检器**自包含**，不依赖受害进程）
现在 helper 一启动就 `mprotect(RO)`，所以只产出"RO 页上 probe 必须 0"这一半；"probe 本身能写"这一半要靠 **selftest 的 `pre_rc==1`**（在受害进程页上）来补。
跨两条命令链的配对**能用但脆弱**（任何一条没跑/跑错，另一条就无法解释）。建议 helper 同时暴露**两页**：
```
pW = mmap(4096, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS)   // 保持可写，打印 pageW
pR = mmap(4096, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS); mprotect(pR, 4096, PROT_READ)  // 打印 pageR
printf("PROT_HELPER pid=%d pageW=0x%lx pageR=0x%lx\n", ...);
```
判据一条命令闭环：**`probe(pageW) == 1` 且 `probe(pageR) == 0`** ⇒ 仪器行为正确；
- `probe(pageW) != 1` ⇒ probe 坏了（不是 FOLL_FORCE 问题）；
- `probe(pageR) == 1` ⇒ 存在 FOLL_FORCE 类放行 ⇒ **中止实验**。
（写 `pageW` 的那 1 字节由 probe 自己写，helper 不需要动它；这不影响它的"专用页"性质。）

kdev 已写死：**换内核/换厂商树/换分支后，源码核对（§37.5）+ 运行期自检（本节）两条都要重跑**。我确认这条足够；再加一句：**自检器自身的身份也要进 FIVETUPLE**（已进，✓），否则换了个 helper 二进制就测不出变化。

### 38.4 双页版复核（2026-11-01，主机侧）——**并且发现一个"看起来等价但会废掉自检器"的写法陷阱**
- 新件：**`prot_helper` = 23,912 B / md5 `6e1e52f680f458c3a99843b70796304f`** ✓ 与 FIVETUPLE 第 20 行一致（旧 23,776/`db2086ee` 已标注作废）。
- 源码：两页都 `MAP_PRIVATE|MAP_ANONYMOUS`、都先 `memset` 落实、`pageW` 保持可写、`pageR` 再 `mprotect(PROT_READ)`、打印两地址并阻塞 ✓。

**⚠️ 一个必须写进协议的细节**（kdev 的实现恰好满足，但很容易被后人"简化"掉）：
```c
static inline bool is_cow_mapping(vm_flags_t flags) {
    return (flags & (VM_SHARED | VM_MAYWRITE)) == VM_MAYWRITE; }
```
- 本 helper 是 **先 `PROT_READ|PROT_WRITE` 建映射、再 `mprotect(PROT_READ)`** ⇒ `VM_WRITE` 被清、**`VM_MAYWRITE` 保留** ⇒ `is_cow_mapping()==true` ⇒ 若真存在 `FOLL_FORCE`，`check_vma_flags()` 会放行、probe 返回 1 ⇒ **自检器能报警**。
- 但如果有人"简化"成 **`mmap(..., PROT_READ, ...)` 直接建只读页**：`VM_MAYWRITE` 从头就是清的 ⇒ `is_cow_mapping()==false` ⇒ 即便有 `FOLL_FORCE`，`check_vma_flags()` 也会在 `!is_cow_mapping` 分支返回 `-EFAULT` ⇒ probe 仍返回 0 ⇒ **自检器静默失效（假阴性）**。
- ⇒ 协议里应写死：**测试页必须"先可写、后 mprotect 只读"，禁止直接 `mmap(PROT_READ)`**。

（顺带：受害进程的栈 VMA 本来就是 `VM_MAYWRITE`，所以对真实目标而言，`FOLL_FORCE` 的确是危险路径——这也解释了为什么必须把这条自检做成"能真的报警"。）

### 38.5 外推有效性（external validity）：自检页必须与受害页**同类**
kdev 顺着 §38.4 补出了一条**必须与实现保持一致**的隐含条件，我确认并记录：
- `uprot ro` 只清 `VM_WRITE`、**保留 `VM_MAYWRITE`**（与 `mprotect(PROT_READ)` 语义一致；源码核对：`vma->vm_flags &= ~VM_WRITE;` 第 100 行，未见清 `VM_MAYWRITE`）；
- 受害进程的栈 VMA 本来就是 private+anon+`VM_MAYWRITE` ⇒ 测试页与真实目标**同属 `is_cow_mapping()==true` 这一类** ⇒ 自检结论**才能外推**到受害页；
- **反向条件（必须写进协议）**：如果哪天 `uprot` 改成连 `VM_MAYWRITE` 一起清，测试页与受害页就落入**不同类别**，旧自检的绿灯**不再代表真实目标**——协议必须同步改。

**一般化的纪律（建议并入判据纪律）**：
> **自检/正对照的"条件"必须与实验目标的"条件"同类**（同一个 VMA 类、同一个内存序、同一个页状态）。
> 仪器在 A 类条件下通过，只能证明它在 A 类条件下可用；把它外推到 B 类条件是**另一条假设**，必须单独论证。
（这与本轮其它教训同源：`stride 32 vs 16`、`q0=0 算不算`、`FOLL_FORCE 有无`——都是"条件差一点，结论就反了"。）

### 39.2 仪器交付清单：从"三件套"扩到"五件套"

1. **正对照**（能证明仪器看得见）；

3. **条件显式**（写进协议，不藏在代码里；并写明"若改 X 则自检不再代表真实目标"）；

## 43. 三次重启的三分法 + 一条新的实验前置（Lead 2026-11-01 裁定）

| # | 事件 | 类型 | 证据 | 机制 |
|---|---|---|---|---|
| 1 | uwhook.ko insmod | **panic 型** | pstore（262,132 B，md5 1629a33d…）：`EC=0x21 IABT` @ `0xffffffffc008b684` = sign_extend32 | 补丁/trampoline 把 64 位目标当 32 位（C-172） |
| 2 | pte_redirect zero/do_redirect | **panic 型** | pstore2（md5 cadf1fc7…）：`BUG: Bad page state pfn:acdcb` → `panic_on_taint` | 把内核页塞进用户 PTE、mm 未记账 → pfn 双重归属（C-174） |
| 3 | uprot `ro` on nerepair 栈页 | **hang → watchdog 型**（**不是 panic**） | pstore3（md5 30cf05f2…）：`healthdog: heartbeat stale >90s (hbs=6) — EMERGENCY RESTART`；全文件**无 Oops/BUG** | 系统挂住 >90 s，由项目自带 healthdog 强制重启 |

### 43.1 机制假设（E1，两个候选，可用一条证据区分）
**候选 A（Lead）**：对 **ptrace 监督者**的 mm 加写锁，与 ptrace 路径形成死锁 ⇒ 挂住。
**候选 B（我）**：`ro` 把 nerepair 的活栈页置只读 → 它下次写栈 fault → 自己进入修复/死亡路径 → 它 attach 的**大批 tracee 停在 ptrace-stop** ⇒ 用户态整体不推进 ⇒ 心跳停摆。
**区分证据**：`ro` 那条 procfs 写**是否返回**。
- 若 `ro` 命令就没返回（SSH 卡在写 /proc）⇒ 支持 A（模块持锁挂死）；
- 若 `ro` 正常返回、过一会儿才失联 ⇒ 支持 B（迟发效应）。
lab 的操作日志/SSH 时序能直接回答。**两种情况下"不要拿 nerepair 当靶子"都成立。**

### 43.2 新增实验前置（写进 10_MEASUREMENT_PROTOCOL §12.2）
**禁止把 `nerepair`（或任何 ptrace 监督者）的 mm 当作 `ro`/`pte_redirect`/`uprot` 的实验对象。**
靶子应选：**无 ptrace、无 mmap_write_lock 竞争、阻塞中的普通 daemon**（dnsmasq 类），或**让 victim 自己 mprotect**（`rovictim2` 就是这种，最干净）。

### 43.3 lab 的时间线回答（2026-11-01）—— A/B 未分，但**B 被形状强烈支持（E2）**
**时间线（pstore3 内核时间轴，同一 boot）**：
| 时刻 | 事件 |
|---|---|
| 625 s | `insmod: uprot: loaded`（**live dmesg**，ramoops 里没有——只收控制台） |
| 626 s | `check` PASS |
| 634 s | `selftest` PASS（pre=1 / ro=0 / post=0 / rw=0 / after=1） |
| ~640 s | 发出 `ro 9722 0x7fc4f01010`（靶子 = **nerepair 活栈页**） |
| **732 s** | `healthdog: heartbeat stale >90s (hbs=6) → EMERGENCY RESTART` |

**关键推理（我的）**：
- healthdog 行是**内核线程（swapper/0）**打的，它监视的是**用户态心跳**；`stale >90s` ⇒ **用户态整体停摆**，不是某个 mm 的问题。
- `732 − 90 = 642 s` ⇒ **停摆起点 ≈ 642 s，即 `ro` 之后约 2 s**。
- `nerepair` 是**全系统 ptrace 监督者**（C-147：attach 所有用户进程并跟随 fork）。它一旦被卡住（自己写栈 fault / 进不了修复循环），**它的全部 tracee 停在 ptrace-stop** ⇒ 心跳写入者（也在被 trace 之列）停下 ⇒ 2 s 内全系统停摆完全吻合。
- 候选 A（procfs 写里持 `mmap_write_lock` 死锁）**不会**让无关用户态进程停摆；它需要额外解释"为什么心跳也没了"。
⇒ **B（nerepair 被 RO → tracee 集体停 → 用户态停摆）优于 A，E2**；但**决定性证据（`ro` 的返回值）拿不到**，所以**正式记法仍是 A/B 未分（E1）**，只写"机制 = healthdog 看门狗重启；诱因 = uprot `ro` 打在 ptrace 监督者的活栈页"。

**lab 的一个方法学自查（值得记）**：他们原本想用"SSH 超时"当死锁证据，但那条命令里有 `sleep 60`、而 `lgssh.py` 的读超时正好 **60 s** ⇒ **即使设备完全正常也必然超时**。
⇒ 又一次"仪器假象被当成信号"：**判据必须与装置的超时设计对齐**，否则"超时"什么也证明不了。

## 44. rovictim2b（自 mprotect 的 VA/PA 判决臂）—— **BLOCKED，且功效只到"排除 ≥53%"**

### 44.1 事实（lab 2026-11-01）
- 4 个 `ro` 实例各 420 s、每 150 ms 扫自己 32 KB 栈（8B 步进、strict 形状、q0 允许 0）；全程 2 MB/s LAN 灌流；
- **4/4 `ROV NOSLOT warm=420s`**；2 个 `mon` 对照全程 `slot=no`；**无一条 `ROV ARM`**（从未 mprotect 任何页）；
- ⇒ 因为**没有活性对象**，RO 臂从未真正开窗 ⇒ **VA-vs-PA 判决 BLOCKED（不是阴性）** ✓（lab 自己的定性与我一致）。

### 44.2 功效复核（我算的）
- 采样不是瓶颈：`4 × 420 s / 0.15 s = 11,200` 次全扫 × 4096 窗 = **4,587 万个窗口**；而"槽一旦出现会延续数分钟"（dnsmasq 槽 600 s 内 3197 次观测）⇒ **单进程灵敏度≈100%**。
- **瓶颈是进程数 n=4**：`0/4` 的 95% 上界 = `1 − 0.05^(1/4)` = **52.7%**。
- 作为对照，健康栈的点估计是 **2/12 = 16.7%**；`n=4` 时对 17% 流行率的检出概率只有 **52.5%**（掷硬币）。**要用 0/N 排除 17%，需要 N ≥ 20**（0/20 上界 13.9%）。
⇒ **本臂只能写**：「新起 4 个进程在 7 min 内没有出现记录槽，⇒ 新进程的槽流行率 ≤ 53%（95%）」，**不能**写"记录不写新进程"，也**不能**用它检验 H7（H7 不预测每个进程都必然有槽——健康样本本身就是 2/12）。

### 44.3 另一个口径提醒
lab 说判据"q0 允许 0 / **top 允许 0**"：**top 未知时不能当 0 参与运算**（10 §11），否则"top−va"没有意义，任何记录都可能被算进来。建议：**top 未解析时该条记录只按形状+内容判，不做 offset 判**，并在日志里写 `top=NA`。

### 44.4 下一步（给 D15 找活性对象）
既然"新进程自己长出槽"不可控，**直接拿天然槽做**：`dnsmasq` 的 start_stack−0x1b40 是**静态槽**（3197 次观测 1 种内容）、`nerepair` 的是热槽（**禁用，见 §12.4**）。
⇒ **建议实验**：用 `uprot` 对 **dnsmasq 的那个槽页**做 `ro`（非 ptrace 目标），同窗用**另一个未 RO 的天然槽**（例如 nerepair 的——只观测、不触碰）作活性对照；
- RO 槽不再出现新记录 + 对照槽仍活跃 ⇒ **uaccess（H2）**；
- RO 槽继续出现新记录 ⇒ **绕过 VMA（PA/DMA 系）**；
- 两边都静默 ⇒ INVALID（先查设备活性）。
这比 rovictim2b 的"等新进程长槽"可靠得多，也避开了 nerepair 的 ptrace 陷阱。

## 46. P1 预注册：`process_madvise(MADV_DONTNEED)` 判 VA/PA（Lead 第 7 轮指派）

### 46.1 设计（我补全后的可执行版）
**原理**：对目标槽 VA 所在页做 `MADV_DONTNEED` ⇒ 私有匿名页被丢弃、**VA 不变、PA 换（内容清零）**。
- 写者按 **VA** 解析 ⇒ 记录会在**同一个 VA** 重新长出来；
- 写者按 **PA** 写（陈旧 PA/DMA） ⇒ 记录会写到**旧 PA**（受害者这边看不到）⇒ VA 保持空。
这是本轮少数能**直接分开 VA/PA** 的手段。

### 46.2 判据（三条，照 Lead 口径）
1. **槽 VA 重新长出记录 + 对照槽活跃** ⇒ **VA 解析**；
2. **槽 VA 静默 + 对照槽活跃** ⇒ **PA 写**；
3. **两边都静默** ⇒ **INVALID**（先查设备/写者活性，不得写成阴性）。

### 46.3 前置（Lead 四条 + 我的修正与补充）
- ① **目标槽活性证明**：madvise 前 10 min 内 **≥5 次内容变化**（见 46.4 的修正——Lead 原写"≥20 次"，对可用的目标不成立）；
- ② **对照槽同窗活跃**（另一个未被 madvise 的槽，例如另一个 sh 的槽）；
- ③ **madvise 生效证据**：`process_madvise` **返回值 == 4096**（或明确 errno）；madvise 后 `/proc/<pid>/mem` 读该 VA **全 0**，且 **patrace 的 PA 与 madvise 前不同**；
- ④ **进程必须活着**：窗口内进程死亡 ⇒ **INVALID**（除非预注册"故意牺牲"，本次不牺牲）；
- ⑤（我加）**madvise 前必须确认该页在活 sp 之上**（自然槽在栈的冷区，进程不会去碰它）——否则 DONTNEED 会直接毁掉它的活帧、必死。

### 46.4 🔴 我这边的关键发现：**按 Lead 原口径（≥20 次内容变化），P1 目前没有可用的靶子**
| 候选靶子 | 活性 | 可用性 | 结论 |
|---|---|---|---|
| `nerepair` 热槽（369 种/3065 次） | ✅ 最强 | ❌ **§12.4 禁止**（ptrace 监督者；madvise 它 → tracee 集体停 → 上次就是这么挂的） | **不可用** |
| `dnsmasq` 槽（3197 次观测 **1 种内容**） | ❌ 静态（内容不变 ⇒ "≥20 次变化"永不满足） | ✅ 安全 | **不满足活性前置** |
| `sh` 槽（如 14579：147 次观测 / **5 种内容**；29564：16 种/8 槽） | ✅ 有变化（但只有 5 种） | ✅ 非 ptrace | **最现实的靶子**，但要放宽到 **≥5 次变化** |
⇒ **P1 的可执行版本 = 在若干 `sh` 类槽上做（3–5 个槽），活性前置改为"前 10 min ≥5 次内容变化"**；`nerepair` 槽只能当**对照观测**（不碰）。
如果不放宽前置，P1 会被卡成"永远凑不出靶子"——那就是把实验设计成不可能成功。

### 46.5 已知混杂（Lead 已点，我再补两条）
1. **madvise 掉栈页可能改变目标行为甚至致死** ⇒ "槽消失"必须先排除"进程死了/栈换了"（查 State、pid 存活、`/proc/<pid>/maps` 的 [stack] 边界与 madvise 前一致）；
2. （补）**页被回收后可能被别的进程复用** ⇒ 旧 PA 上的"记录"可能来自别人；若要在旧 PA 侧取证，必须记录旧 PA 的**回收/复用**时间点；
3. （补）**madvise 后首次访问前**该页可能是零页（`ZERO_PAGE`）共享映射 ⇒ patrace 读到的 PA 可能是零页的全局 PA，**必须与"新分配匿名页"区分开**（判据：PA == 零页 PA 视为"未重新分配"）。

## 47. 缓解验收口径（给 fixer，Lead 第 7 轮指派）

### 47.1 两层判据（必须分开报）
| 层 | 指标 | 谁适用 |
|---|---|---|
| **写入活性** | 热槽重写率（sampler：distinct-content 事件/秒） | **只对能影响写入的缓解**（pageguard 类、SMMU、靶向隔离） |
| **后果** | ① canary 家族死亡数 ②**自然 NE 率** ③nerepair 的 REPAIR 事件率 | 所有缓解；**nerepair 只看这一层** |

⚠️ **nerepair 的验收只能在"后果"层**：它只修复崩溃、不停止写入（C-149）⇒ **写入活性预期不变**，若观察到写入活性下降，应怀疑"进程死了/目标换了"而不是"修好了"。

### 47.2 ① "速率降到多少算显著"——统计口径
- **设计**：**同 boot、同会话、ABAB 交替**（A=缓解关，B=缓解开，A，B），每臂 **≥10 min**，同一批进程/槽。
- **计数**：每臂 distinct-content 事件数 N 与观测秒数。
- **模型**：分箱（1 min）计数**大概率过度离散** ⇒ 用**准泊松/负二项**估计离散度 φ，或直接对**每臂总事件数**做**置换检验**（块交换）；不要直接套泊松 z。
- **判据（建议写死）**：
  - 主判据：**率比 RR ≤ 0.5 且 95% CI 上界 < 1.0**（即"至少减半且显著"）；
  - 反向保护：**A 两臂之间**的 RR 必须落在 [0.7, 1.4]（证明没有漂移）；否则整轮 INVALID。
- **功效**：热槽 0.62 次/s ⇒ 10 min 臂约 **372 事件**；检 20% 降幅约需 9.5 min/臂、50% 降幅约需 1.3 min/臂（等暴露、α=0.05 双侧、power=0.8，泊松理想化）⇒ **10 min/臂足够**（过度离散会打折，建议 15 min/臂）。

### 47.3 ② 自然 NE 需要多长窗口——**当前基线（0.5/h）下没有现实功效**
等暴露两臂、α=0.05 双侧、power=0.8、泊松理想化：
| 期望降幅 | 每臂所需时长 | 每臂期望事件 |
|---|---|---|
| 50% | **94.2 h** | 47 |
| 70% | **41.6 h** | 21 |
| 90% | **21.3 h** | 11 |
⇒ **结论：自然 NE 只能当"长期监控"，不能当本轮验收的主判据**。主判据用：①热槽写入活性（10–15 min/臂，见 47.2）②**nerepair 的 REPAIR 事件率**（事件率高，可在同会话内做 ABAB）③canary 家族死亡数（若 canary 会死）。

### 47.4 ③ "看起来修好其实没修"的假象清单（逐条打勾）
| # | 假象 | 检查 |
|---|---|---|
| 1 | **进程重启换栈** | 每臂记录 target pid + `[stack]` 边界；变化 ⇒ 该臂作废（新栈 = 新目标） |
| 2 | **写入者换目标** | 同窗监控 **≥3 个槽 + 系统级扫描**；若被监控槽静默而别处出现 ⇒ 不是修好，是转移 |
| 3 | **观测者污染** | 扫描器自身流量/CPU 影响被记录；用"停扫描"对照臂 |
| 4 | **boot 代次变化** | 每次重启 = 新代次；跨代次不可比（本会话已 3 个 boot） |
| 5 | **判据漂移** | 前后必须同一判据（q0 允 0 / len 区间 / IP 单播 / stride 8-16）；改判据 = 重新基线 |
| 6 | **幸存者偏差** | 只算活下来的进程 ⇒ 必须先算"臂开始时"的分母 |
| 7 | **均值回归** | 基线不能选在峰值；用 A 两臂一致性保护（47.2 的反向保护） |
| 8 | **缓解自身的副作用** | nerepair 类：**无崩溃 ≠ 无写入**（C-149）；pageguard 类：检查内存配额/分配失败率 |

### 47.5 一句话给 fixer
> **写入层面**用热槽率比（10–15 min ABAB，RR≤0.5 且 CI 上界<1，A 两臂须一致）；**后果层面**用 REPAIR 事件率/家族死亡数，**自然 NE 只做长期监控（50% 降幅需 ~94 h/臂）**；验收前先过 47.4 的 8 条假象检查。

## 48. D17（userfaultfd 点名）预注册 —— **但前提被证伪：本内核的 userfaultfd 是 -ENOSYS 桩**

### 48.1 🔴 先说结论：`__arm64_sys_userfaultfd` 是 **COND_SYSCALL 桩**，不是实现
反汇编（`analysis/kern/vmlinux.elf`，`vml_dis.py`）：
```
__arm64_sys_userfaultfd  va=0xffffffc00814fb78 size=0x40
  mov  x0, #-0x26      ; -38 = -ENOSYS
  paciasp / autiasp / ret
__arm64_sys_quotactl（已知的 cond 桩，对照）
  mov  x0, #-0x26 / paciasp / autiasp / ret      ← 完全同形
```
- kallsyms 里它是 **`W`（weak）**，与 `lookup_dcookie / quotactl / kexec_load / old_msgctl …` 等 **45 个 cond 桩**同类；
- 全 kallsyms **只有这 1 个** userfaultfd 相关符号，**没有 `handle_userfault` / `userfaultfd_ctx_*` / `userfaultfd_register`**。
⇒ **`CONFIG_USERFAULTFD=n`，该 syscall 返回 `-ENOSYS`。** 所谓".config 与设备不符"**不存在**——符号存在是因为 `kernel/sys_ni.c` 的 `COND_SYSCALL` 会为被关掉的 syscall 生成一个**弱桩**。
⇒ **D17 在当前内核上不可执行**（`UFFDIO_REGISTER` 拿不到 fd）。

**给 lab 的 30 秒确认（零风险，跑完就能钉死）**：
```c
// probe_uffd.c: 打印 syscall(__NR_userfaultfd, O_CLOEXEC|O_NONBLOCK) 的返回值与 errno
// 期望：rc=-1, errno=38 (ENOSYS)  ⇒ 与反汇编一致，D17 关闭
// 若 rc>=0（真的拿到 fd）⇒ 我的反汇编解读有误，立刻回滚本结论并重开 D17
```

### 48.2 若探针推翻上述（即 uffd 真的可用），D17 按下面预注册执行
**判据（Lead 三条）**：
1. 有事件 + 抓到**非本进程**的阻塞任务（`/proc/<pid>/stack` 含 `handle_userfault`）⇒ **CPU uaccess 写，栈即身份（E4）**；
2. 有事件但只有本进程 ⇒ 只是自身访问 ⇒ **调整保护区**后重跑（不算结论）；
3. 全程 0 事件 ⇒ 写入者**绕过页表**（DMA/直映射）⇒ PA 模型。

**必须的对照（Lead 三条 + 我补两条）**：
- ① **活性对照**：同窗用 sampler 证明**该受害进程的这个 VA 在注册前确实被写过**（≥5 次内容变化/10 min）；
- ② **自身访问对照**：让受害进程故意碰一下保护区 ⇒ **必须产生事件**（证明 uffd 装置可用）；
- ③ **保护区位置证明**：保护区在活 sp **之上**、且 `/proc/<pid>/maps` 显示它属于 `[stack]`；
- ④（我补）**有界阻塞**：事件到达后最多挂 **30–60 s** 就必须 `UFFDIO_COPY` 零页/撤销注册——否则写入者被永久阻塞，可能触发 healthdog 全系统停摆（§12.4 的教训）；
- ⑤（我补）**`/proc/*/stack` 可用性**：本内核 `proc_pid_stack`(t) 与 `stack_trace_save`(T) 都在 ✓，但**需实测** root 下 `cat /proc/<pid>/stack` 有输出（不能只看符号）。

**判据 ③（0 事件 ⇒ DMA）的致命前提（我补）**：**必须先在同一个 VA 上拿到"注册前确有写入"的证据**。否则"0 事件"有三种解释（写入者没来 / 保护区不是目标 / 真的绕过页表），**不得**直接写成 PA。⇒ **无活性证据的 0 事件 = INVALID**。

**已知混杂**：
- 若写入者在**原子上下文**：缺页会 `BUG: scheduling while atomic` 类 ⇒ `panic_on_oops` 重启；**但 pstore 里的调用栈恰好是写入者的路径** ⇒ 属于"高信息量失败"，见 §49 的"重启也算数据"规则；
- 受害进程自己若在保护区附近做 syscall/信号处理，可能被自己触发事件（判据 ② 会暴露）；
- 与 P1 相同的**靶子问题**：必须是"注册前已被写过"的进程；rovictim2b 显示新进程 7 min 内常常没有槽 ⇒ **D17 同样需要一个可证明被写的靶子**。

## 49. 本轮允许重启（用户授权）+ 「重启也算数据」判读规则（Lead 第 7 轮）

**授权**：本轮允许因实验导致的重启（用户已授权，串口 LK 兜底）。**但**：
1. 每次重启前**先记**：`boot_id`、`date +%s`、`uptime`、当前臂/目标 pid/VA、以及**已采集的对照数据**（活性/自身访问）；
2. 重启后**立刻**拉 pstore（`/sys/fs/pstore/console-ramoops-*`）并 **md5 落盘**（ramoops 会被下一次 panic 覆盖）；
3. **判读**：pstore 里的 `CPU: n PID: x Comm: y` + 调用栈 = **写入者路径的直接证据**（E3）；地址用 `analysis/kern/kallsyms.txt` 反查符号；
4. **归类**：仍按 §12.3 三分法（panic 型 / hang→watchdog 型 / 冷复位型）——**不得把 hang 型写成 panic 型**；
5. **数据代次**：重启即新代次，跨代次不可比；本轮的"允许重启"**不改变**这条。

## 50. dropwatch（纯用户态 VA/PA 判别）复核 —— 设计正确，补三条判据

### 50.1 设计我认可（这是本轮最干净的一条路）
- 只用 `madvise(MADV_DONTNEED)` + **`mincore()`**：**不依赖 userfaultfd**（已证是 ENOSYS 桩）、**不装模块**、**不阻塞写入者**；
- 原理正确：`MADV_DONTNEED` 后 PTE missing；**经页表**的写必须 fault 回来（resident），**按 PA** 的 DMA 不碰 PTE（仍 missing）；
- 并且**分两层报告**：`resident_events`（有人经页表写进来了）与 `DW_HIT`（看到 32B 记录本体）——这正是我要求的"写入活性 vs 后果"分离；
- 产物身份与 FIVETUPLE 一致：**34,408 B / md5 `aebadf7d9af16edaab37dfc39771ebce`**（旧 29,064/1696f62f 已标"自伤 bug"作废）✓。

### 50.2 🔴 三条要补（否则会得出错误结论）
**① 自检只验证了"匹配器"，没验证"驻地探测器"**：`--self-test` 是自己往带里写一条记录 → 自己把页 fault 进来 → 检出。它证明**形状匹配器**可用，**不证明**"别人经页表写也能让页变 resident"。
⇒ **必须补一条外部 fault 正对照**（2 分钟）：**另一个 helper 进程**对 dropwatch 的带做一次 `process_vm_writev`（写入一条记录形状的 32B）→ 必须产生 **1 个 resident_event + 1 个 DW_HIT**。
  这是唯一能证明"resident ⇒ 外部经页表写"的对照；缺它，`resident_events>0` 只说明"有东西 fault 了页"（可能是它自己）。

**② `resident_events == 0` 有**两种**含义，不能直接判 PA**：
- (a) 写入者按 PA/DMA 写（不碰 PTE）✓ 预期的 PA 结论；
- (b) **写入者在原子上下文做 uaccess**：`pagefault_disabled`/`in_atomic` ⇒ 缺页**直接失败**（fixup → -EFAULT），页**不会**变 resident ⇒ 同样是 0。
⇒ 判据要写成：**0 resident + 活性对照成立 ⇒ "PA 或原子上下文 uaccess 失败"**；要排除 (b) 需要额外证据（例如 pstore 里有 `BUG: sleeping function called from invalid context`，或换一个**已知非原子**的写者做同样实验）。**不得**把 0 直接写成"PA/DMA 已证"。

**③ 形状匹配器要收紧到 strict**：当前只查 `w1==0 && w3==0 && len∈[0x40,0x20000] && 首字节 1..254 且非组播`；**其余三个 octet 没查**，且**没查 q0**。
⇒ 建议改为：`q0 允许 0`、`len∈[0x40,0x20000]`、**四个 octet 全在 1..254**（必要时再叠"精确 Q2 集合"）；并**同时报宽松/严格两套计数**——本轮已经因为宽松判据在健康栈上吃到 55 处误报。

### 50.3 两条建议（不阻塞）
- **`--map` 同会话负对照**：`--map` 模式下写入者大概率不会打我们的私有 mmap ⇒ 期望 ~0；跑同一窗口，作为"区域选择"的阴性对照；
- **`resident 但无 HIT` 要单列**："有东西经页表写了这块带，但不是我们那 32B"——这是**另一类事件**（可能是别的写者/部分写），不能并进 hits 也不能当 0。

### 50.4 与 D17/P1 的关系
- D17（uffd）**已关闭**（C-179：syscall 282 → ENOSYS，lab 已实测确认）；
- **dropwatch 就是 P1/D15 的可执行替身**（同一个问题、更干净的手段）⇒ 建议把它登记为 **D18**，并在跑正式 600 s 窗口前先过 50.2 的三条。
