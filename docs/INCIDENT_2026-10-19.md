## 2. logread SIGSEGV 家族（长期异常）

### 2.1 现象

- aee 的 `db_history` 自 10-05 起累计 164+ 次 NE；近 24h 去重后 **117 次** core 事件，
  其中 `logread` 占 ~45%，其余 `awk`(19)、`ip`(18)、`grep`(7)、`sh`(6)、`pgrep`(6)、
  `hostapd`(2) 等。
- 单次 aee 转储约 **4 秒 / 500KB**；转储自身会跑 `ps/df/mount/logread/ip/awk`，
  偶发同族崩溃会再触发转储，形成放大（12:00 时段曾出现 400 条/小时的尖峰，含镜像重复）。
- 无数据损坏：受害进程以“读数据/解析”型短命工具为主，崩溃即退出。

### 2.2 关键取证

**(a) 内核 fault 行（此前被误判为“没有打印”）**

内核实际打印格式是 arm64 的 `unhandled exception: DABT`，不是 x86 的 `segfault at`：

```
[46869.933501] logread: logread[18115]: unhandled exception: DABT (lower EL),
  ESR 0x0000000092000006, level 2 translation fault in libc.so[7f9280d000+7b000]
```

持久 dmesg 镜像里的 15 条分类：

| 次数 | 进程 | ESR | 类型 | 故障指令所在 |
|---|---|---|---|---|
| 13 | logread | 0x92000006 | level 2 translation fault（读） | libc.so |
| 1 | logread | 0x92000006 | 同上 | logread 自身 |
| 1 | logd | 0x92000007 | level 3 translation fault（读） | libubox.so.20230523 |

> 注：该行里的 `[base+size]` 是**故障指令所在 VMA**，不是故障地址。

**(b) 三份未加密 core（绕过 aee 加密后抓到）**

做法：临时 `echo '/tmp/core.%p' > /proc/sys/kernel/core_pattern` + `ulimit -c unlimited`，
跑 `logread` 复现；抓完立刻恢复 aee 管道。三份 core 签名完全一致：

| 项 | 值 |
|---|---|
| 进程 | `logread` |
| 信号 | SIGSEGV / `si_code=1`(SEGV_MAPERR) |
| PC | `/lib/libc.so +0x51ffc`（三次相同） |
| 故障指令 | `ldr x0, [x3]`（x3 为野指针） |
| si_addr | 0x2475b / 0x25746 / 0x14f1b（三次不同，均为小整数） |
| 栈回溯 | logread `0x403590` → `ctime` → `asctime_r` → `snprintf` → `vfprintf` |

反汇编对上了：`0x403590` 就是 `bl ctime`；logread 每行输出的
`Mon Oct 19 …` 正是 ctime 的格式；入参由记录时间戳 `/1000` 得到。

**(c) 栈缓冲区内容（决定性线索）**

core 的栈段完整（`0x7fda4c0000+0x21000`）。崩溃前最后一条**已成功格式化**的行在
`fp+0x378` 的 0x480 缓冲区里：

```
Mon Oct 19 04:11:07 2026 daemon.info thermal_core[8358]: interval=5 temp: 50500 49000 46600 46600 47100
```

其后的 ` MRO-W00` 是下一条的片段。说明崩溃发生在 **04:11:07 之后的下一条记录**，
而不是开机 3.4s（输出文件只 flush 到那里，是 stdio 缓冲假象）。

**(d) 16KB 输入缓冲的边界截断**

core 里还有一块 16KB 的匿名映射（`0x7facbe8000`），内容是原始 syslog 行的滑动窗口，
最后一条在**缓冲区边界处被截断**：

```
7facbe8fb8 thermal_core[8358]: interval=5 temp: 49400 48400 46100 46200 46600
7facbe9058 thermal_core[8358]: interval=5 temp: 493
```

窗口内容以 `thermal_core` / `mipc_cli` 这类高频行为主——正是 log_keeper 降噪层
丢弃、但 RAM 环里仍然存在的那批行。

### 2.3 实验矩阵（全部为实测，非推断）

| 实验 | 结果 | 结论 |
|---|---|---|
| `TZ=UTC` 下 100 次 `logread` | 仍崩 1 次 | 与时区/`/tmp/TZ` 无关（`/tmp/TZ` 自开机未变） |
| `dmesg -c` 清内核环后跑 | 仍崩 | logread 读的是 **logd 的 syslog 环**，不是内核环 |
| **重启 logd 清 syslog 环后 2500 次** | **0 崩** | 触发记录随开机日志进入环并长期驻留（10MB 环数周才回卷） |
| 旧环 500 次全量读取 | 0 崩（清环后） | 与“含开机记录”的旧环形成对照 |
| `logread -l 200` 2000 次 | 0 崩 | `-l` 确实跳过大部分格式化（100 次全量 4.9s vs `-l 1` 0.49s） |
| `ip -o link` ×300 / `true` ×300 | 0 崩 | 不是“每次 exec 随机崩” |
| 注入 2000 字符 logger 消息 | 行被截到 1040B，未崩 | 单纯超长行不触发（缓冲 0x480=1152B） |
| 静态 memtest 256MB×3 遍（[tools/oneoff/memtest.c]） | 0 位翻转 | 不是简单 DRAM 损坏 |
| 同一 4MB 文件 60 次 md5 | 哈希唯一 | 不是读路径数据损坏 |
| `v3_steth/v3_fix` 符号检查 | 无 `force_sig/send_sig` 类导入 | 模块不主动发 SIGSEGV；`healthdog` 超时是 `emergency_restart` |
| 故意空指针（静态 crashme） | 内核打印 DABT 行 + core | 内核 fault 打印功能正常，之前的“无打印”是措辞/环回卷问题 |

### 2.4 结论与不确定性

> **2026-10-19 深夜轮更新**：本节所述”高置信结论”已完成逆向闭环并大幅细化，
> 家族清环后仍在新发事件（grep/awk/sh/ip）——完整因果链、core 级证据、
> 厂商 musl 缺陷定位与根治方案见 [SIGSEGV_ANALYSIS.md](SIGSEGV_ANALYSIS.md)。
> 以下为当时现场研判，保留原文。

**高置信结论**：崩溃是厂商 syslog 管线（logd 的 ustream 写路径 / logread 的格式化与
16KB 输入缓冲）在**开机期记录流**上的缓冲区边界缺陷；触发记录随开机日志进入环并长期
驻留，因此表现为”越早的环越容易崩、清环即好”。

**不确定/未闭环**：
- 未能定位到具体触发记录（镜像首轮只取尾部 64KB，缺开机段；环已被清）。
- 家族不止 syslog：18:34 仍出现一次 `grep` SIGSEGV（读 4MB 日志那次），说明还有
  其它“读/解析”路径的低频触发点，未根除。
- 未拿到 logread 在自身 text 里崩溃那一次（1/15）的 core。

### 2.5 已落地的缓解

1. **log_keeper v1.7**：开机 `uptime>=300s`（boot 日志已落盘）后一次性重启 logd 清环，
   以 `/proc/stat btime` 标记每 boot 一次；procd respawn 兜底。
   实测 17:32:13 执行，之后无 logread 崩溃（最后一条 logread NE 为 17:01）。
2. **watchdog v1.20/v1.21**：每轮统计内核 `unhandled exception` 行增量，新增即记 WARN
   （计数在 `/tmp/watchdog_faultcount`，不放进 state，避免 selftest 误判）。

### 2.6 后续可选路径（未实施）

1. **受控重启一次**：开机后立即完整抓取 syslog 环（不要只取尾部 64KB），再用
   `logger` 回放 + 二分定位触发记录。需要用户同意重启 CPE。
2. **替换厂商 syslog 采集**：logread 用的是 `ubus_invoke_async_fd` 的 fd 流，
   可自写采集器（静态 aarch64）绕开 logread/logd 的崩溃路径；代价是 GUI 日志页与
   logd 的耦合需要一并处理。
3. **aee 降噪**：对 logread 的 NE 免转储（减少 4s/500KB 的放大），但会失去证据。
4. **源头降量**：thermal_core（5s 一行）与 mipc_cli（每次调用 2 行）是环内绝对大头，
   若能在源头降频，可按比例降低触发概率。

## 3. eth0 显示误报（16:26 起）

### 3.1 事实：eth0 完全正常

```
carrier=1  operstate=up  speed=1000  duplex=full
inet 110.65.x.x/25
default via 110.65.x.x dev eth0
```

### 3.2 因果链

```
wan_agg 子命令连续 SIGSEGV（/tmp/wagg.out 十余条 "Segmentation fault"）
  → wan_agg.sh 退出（16:26）
  → /tmp/wan_alive 停更（home=1 cell=1 ts=16:26:44）
  → led_mgr.bb_data_alive(): ts 超过 30s → "未知=不亮" → WAN 灯灭
  → api_sys.sh: _fresh=0 → ETH_DP=0 → GUI 有线线路状态"离线"
```

关键设计（不是 bug，是“宁可灭灯也不谎报”的既有约定）：

- `led_mgr.sh` 注释：`ts 过期(>30s, 守护异常)按"未知=不亮"处理 —— 宁可灭灯也不谎报"已连接"`；
- `api_sys.sh` 注释：`ts 过期(>30s, 守护异常)时按"未知"处理(0), 不用旧值猜`。

问题不在判据，而在 **wan_agg 死后无人拉起**。

### 3.3 修复与验证

- **watchdog v1.19**：`wan_agg` 从“只 check”改为“死则按启动配方拉起”。
- 受控验证：`kill <wan_agg>` → 17:38:23 `EVT restart wan_agg` → 新 pid 30853 →
  `wan_alive` 恢复新鲜 → WAN 灯 `brightness=1` → 自检 `WAN 指示灯反映家宽数据面 ✓`。
- 现场恢复后：`wan_led=1`、`wan_alive=home=1 ts=…`、`ETH_DP` 判据恢复为 1。

验证过程中额外修掉三个只在冷启动/重启路径暴露的缺陷（已包含在上述提交）：
