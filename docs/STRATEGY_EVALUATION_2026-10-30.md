# 两个「掀桌子」思路的评估

> **历史文档（2026-10-30 归档）**：本文的策略评估基于“单一写入者”前提；当前先做自然 NE 分类与传输判定。见 [docs/SIGSEGV/00_STATE.md](SIGSEGV/00_STATE.md)。

结论先说：**两个都不可行，而且都不会修好这个 bug。** 但它们各自包含一个正确的内核，
那个内核可以用 1% 的代价单独执行。下面是数字依据。

## 0. 先把「300 个 vendor」这个前提校正掉

设备上真正的厂商二进制只有 **28 个制品**：

| 类别 | 数量 | 说明 |
|---|---|---|
| 内核模块 | **17** | air_en8811h / connac_if / conninfra / cryptodev / gps_drv / hw_nat / mapfilter / mt7992 / mt7992_dbg / mt_wifi / mt_wifi_cmn / mtk_hwifi / mtk_pci / mtk_pcie_smt / mtk_warp / mtk_wed / wifi_md_coex |
| 用户态守护 | **10** | ccci_fsd / ccci_mdinit / ccci_rpcd_com / aee_aed / atcid / thermal_core / scd / ql_ippt / powerkey_daemon / logd |
| 内核镜像 | **1** | 61455 个带地址符号，其中 MTK 命名 3786 个（6.2%，这是下限） |

其余 155 个 .ko 是 mainline 的 netfilter / ipset / ebtables / snd / ppp，不是厂商件。

**关键：这三个类别里，我们已经把「能写用户内存的代码」全部枚举完了。**

## 1. 提案一（把 vendor 全部逆向重写）—— 不可行，且不解决问题

### 1.1 已经逆到的深度（这不是「没做」，是「做完了也没用」）

| 对象 | 枚举结果 |
|---|---|
| 10 个守护 | 33 个 ioctl 点、全部 /dev /proc /sys 路径、全部异步机制（fasync/aio/mmap/poll）——**没有任何 F_SETOWN/O_ASYNC/aio**，没有把栈指针存进 .data/.bss |
| 17 个模块 | **内联 uaccess 存储（sttr）数量 = 0**（17/17，逐个实测）。它们写用户内存只能走 copy_to_user，而 copy_to_user 已被运行时探针排除 |
| 内核镜像 | 1278 个 user-copy 站点（其中厂商命名只有 50 个 / 19 个函数，全是同步 read/ioctl/write 处理器）；540 个 sttr 站点，**没有 32 字节的成组写** |

### 1.2 为什么「重写」不解决问题

**写入者不在模块里。** 17 个模块里一个内联 uaccess 存储都没有；它们唯一的用户写是 copy_to_user，
而 copy_to_user 已经在 200+ 起崩溃、四种过滤、探针字节级校验在位的情况下**零命中**。

⇒ 把 17 个模块全部重写，**一行都不会碰到写入者**。

### 1.3 为什么「重写」本身也不可行

重写 mt_wifi（13.5 MB）/ mt7992 / conninfra / hw_nat 不是逆向工程任务，是**芯片点亮任务**：
需要 MT6990 的 WiFi 6/7 寄存器手册、MD/CCCI 协议栈文档、NAT offload 描述符格式——
这些我们一份都没有。业界的现实是：这块 SoC 的 CPE 支持只有 MTK 自己的 SDK。

**成本量级**：人年；**修好概率**：接近 0。

## 2. 提案二（换公版 OpenWRT + 适配）—— 假设对，结论错

### 2.1 假设是对的

「问题可能出在魔改版 OpenWRT 内核」——从证据看**几乎肯定对**：写入是内核侧行为，
而内核就是 MTK BSP 构建的那份。

### 2.2 但公版跑不起来这台机器

| 事实 | 后果 |
|---|---|
| 公版 OpenWRT 没有 MT6990 CPE 支持（MediaTek 的 CPE SDK 不进上游） | 没有以太交换、没有 WiFi、没有 modem |
| 17 个厂商模块的 vermagic 是 `5.15.134 SMP mod_unload aarch64`，绑定这份内核 | 换 mainline 6.x 后**一个都加载不了** |
| 我们的固件本来就是 OpenWrt 风格的 rootfs，跑在厂商内核上 | 「魔改」的部分是内核，而那是唯一能驱动这台硬件的内核 |
| **我们没有厂商内核源码**（见 2.3） | 连「拿厂商源码重编一份干净内核」都做不到 |

### 2.3 一个必须先说清的事实：我们没有厂商内核源码

`_local/legacy/linux-5.15.134` 是**纯 mainline 5.15.134**：有 `drivers/clk/mediatek` 这类上游目录，
但**没有** `drivers/misc/mediatek`、没有 ccci、没有 dpmaif、没有 mt_wifi。
也就是说：内核里那 6.2% 的 MTK 代码（实际比例更高，很多是匿名静态函数）**只有二进制**。

**成本量级**：整机 bring-up，人年；**修好概率**：做完之后设备已经不是 CPE 了。

## 3. 两个提案里真正值钱的那部分（1% 代价，可执行）

两个提案的共同内核是「**把厂商代码从路径上拿掉**」。这件事不需要源码、不需要重写，
只需要**运行时消元**：

### 3.1 驱动消元二分（推荐，立刻可做）

17 个模块 + 内置驱动都可以在运行时摘掉：`rmmod`、`/sys/bus/*/drivers/*/unbind`、
`driver_override`。按组摘、按组加回，用崩溃速率判据。
**这等于「把 vendor 代码一个个关掉」，但成本是分钟级而不是人年。**

当前的障碍不是方法，是**速率太低**（地板 ~0.5/min，突发期 ~7/min）。
所以配套要做的是 **burst 探测器**：监测速率，一旦进入突发就自动全量抓转储 + 打时间戳，
把「等 10 小时」变成「抓 13 分钟」。本轮已经证明一次 burst 能给出 87 起事件。

### 3.2 静态收窄（零成本，我现在就能做）

既然 copy_to_user 被排除、17 个模块没有内联存储，剩下的形状只有一种：
**在 uaccess 窗口内对用户地址做普通 store**（SW TTBR0 PAN 下窗口内 TTBR0 是打开的，
普通 `str` 到用户地址会成功）。这是一个**有界**的静态搜索：
枚举每一个 `uaccess_ttbr0_enable` 窗口，找出窗口内非 `sttr` 的、基址来自用户指针的 store。

### 3.3 300 站点探针（已建成，待瘦身）

trampoline 从 160 字节栈降到 64 字节（只存 x0/x1/x2/x30）后再上满 300 站点，
就能直接点名「谁在中断上下文里开了 uaccess 窗口」。安全网（自动回滚）已经验证可用。

## 4. 建议

| 方案 | 代价 | 修好概率 | 结论 |
|---|---|---|---|
| 重写全部 vendor | 人年 | ~0（写入者不在模块里） | **否决** |
| 换公版 OpenWRT | 人年 | 设备失去 WiFi/modem | **否决** |
| 驱动消元 + burst 探测 | 天 | 中高 | **执行** |
| 静态收窄 + 探针瘦身 | 天 | 中高 | **执行** |

**什么情况下我会改变建议**：如果驱动消元把写入者指到某个模块（比如 mt_wifi 或 conninfra），
那么「不加载那一个模块」就是现成的缓解手段（代价是失去对应功能）；
如果指到某个内置 MTK 驱动，通常可以单独关掉它而保留其余功能。
那才是「拿掉厂商代码」真正可行的形态。
