## 0. 判决（三句话 + 三个数字）

1. **停事件面是宽的，处理面才是窄的。** 代码 `:1146` 只决定"是否处理"，**不决定"是否停"**：任何被跟踪任务收到**任何信号**、以及**每次 fork/vfork/clone/exec** 都会产生一次 ptrace 停，跟踪者必须 `PTRACE_CONT` 才能放行（`:1145/:1151/:1152`）。所以"开销可忽略"的常见前提（"它只在 SIGSEGV 时才醒"）**在本实现上不成立**。
2. **实测（E3）**：nerepair 自身 CPU = **2.46–2.51 % 单核**（寿命平均 2.32 %）；其 `voluntary_ctxt_switches` 增量 ⇒ **停事件率 ≥ 1,522 /s**（两个独立窗口 1,528.5 与 1,521.7，一致）；衍生的**每事件 CPU ≤ 16.2 µs**。折算：**≈1.3×10^8 停事件/日、≈35 min CPU/日**，占四核机时 0.63 %、占**忙时 CPU 3.91 %**、占**内核态 CPU 4.54–4.68 %**（两种口径的算式见 §7.1 注 1）。
3. **成本几乎与崩溃率无关，由进程 churn 决定**：本窗 SEGV 计数仅 2 次/103 min，而系统 `processes` 速率 **344–346 task 创建/s**；每次 fork/clone 结构上必产生 2 次停（父事件停 + 子初始 SIGSTOP），仅此一项就 ≥688 停/s。⇒ 要降本，要动的是"全量 ptrace 跟随"这个决定，而不是"少修几次崩溃"。

**代价性质**：CPU 上是"每次开机永远在交的固定税"（2.4 % 单核）；内存上极轻（RSS **124 kB**，实测）；真正的风险不是 CPU 而是**全系统停摆**（supervisor 一卡，57 个 tracee 全部停在 ptrace-stop，§6.4）与**重启期间 81 s 零覆盖**（实测，§6.3）。

**一条方法论警告（本审查自身就是实证）**：**读取代价可忽略 ≠ 读不会注入事件**。本次 5 次纯读会话新增的 fork/CPU 代价 <0.05 %，但观察窗口内就出现了一次**由只读取证命令派生出来的家族型崩溃**（19:29:05 `od` applet，§7.1 注 2 / §7.3）——只读管线同样会 fork 出被跟踪的子进程，它们同样受监督、同样可能命中家族记录。⇒ 任何只读观测窗都必须把观测者自产事件从事件计数中剔除（判据三定律之三：观测者污染）。

## 1. 事件面 vs 处理面（本报告的分水岭，读代码定论）

| 问题 | 定论 | 出处 |
|---|---|---|
| 是否每个信号投递都停？ | **是**。主循环只对 `SIGSEGV \|\| SIGBUS` 走 `handle_segv`（`:1146`），其余信号**原样放行**（`:1151` SIGSTOP→SIGCONT；`:1152` `PTRACE_CONT(pid,0,sig)`）。但"放行"本身要求跟踪者先被唤醒、先做一次 `PTRACE_CONT`——停已经发生。ptrace 没有"信号过滤"选项。 | `gw/src/nerepair.c:1143-1152` |
| fork/exec 是否每次一个事件？ | **每次 fork/vfork/clone 产生 2 次停**（父的 `PTRACE_EVENT_*` 停 `:1145` + 子的初始 SIGSTOP 停 `:1151`）；每次 exec 产生 1 次 `PTRACE_EVENT_EXEC` 停。选项在 attach 时一次设定、对所有 tracee 生效。 | `:1009`、`:1145`、`:1151` |
| 事件风暴能否让主循环"永远不阻塞"？ | **能**，且已发生过：v1.7 头注记载 5 次 284–651 s 心跳断流、两次看门狗重启，原因正是"waitpid 永远有排队停止可返"。 | `:41-45`、`:1088-1093` |
| 处理面有多窄？ | 只有两条判据路径（pop 型 `:834-882` + deref 型 `:702-773`），其余形态一律 `PASS`。 | `FIX.md:37-59` |

**实测侧的反证**：本窗（当前实例至今 103 min）STAT 的 `segv=2`，即 SIGSEGV/SIGBUS 处理事件 ≈ 0.03 次/min；而实测停事件率 ≥1,522 /s。**0.03/min 与 1,522/s 相差 3×10^6 倍**——停事件面**不可能**由 SIGSEGV/SIGBUS 解释。这同时证明：

- 任务书设问的"事件面是否窄"——**处理面窄、停面宽**；
- 用"崩溃率低"论证"nerepair 开销低"是**无效推理**（§8 给出正确口径）。

## 2. 逐项成本分解

### 2.1 全量 attach（启动 + 每 10 min 重扫）

- 启动：`attach_pid(1)`（`:1084`）→ `scan_proc()`（`:1085`，遍历 `/proc`）。
- 每个目标：`PTRACE_ATTACH`（`:987`）→ `WNOHANG` 轮询 `usleep(20000)`（`:999-1006`）→ 3 s 上限（`:997`）→ `SETOPTIONS`（`:1009`）→ `PTRACE_CONT`（`:1010`）。**在 CONT 之前目标一直冻结**（典型窗口 = 2–3 次系统调用 ≈ 数十 µs；最坏 = 3 s，然后 `DETACH` 放弃）。
- **关键代价（V2 残余）**：这 3 s 轮询**跑在主循环路径上**（`scan_proc` 是同步调用）。一个"停不下来"的目标（D 态/不可打断睡眠）能让**整机所有 tracee 的停被推迟最多 3 s**。历史实弹：v1.5 之前无上限，07:05–07:08 心跳静默 234 s、看门狗重启（`:52-55`）。本窗未观测到此类停顿（STAT 间隔恒 60 s，§7.2），发生频率 **[B] 未核实**。
- 重扫：启动后每 10 分钟一次 `scan_proc()`（`:1109`，`g_ticks % 10`），`traced()` 读 `/proc/<pid>/status`（`:970-982`）对每个 pid 一次 open+read+close。设备 259 个任务 ⇒ ≈780 次系统调用 / 600 s ≈ 1.3 次/s。**可忽略**。
- 实测：本窗 `ATTACH` 日志累计 127 行（4 个实例）；当前实例 STAT `attached=45`；我独立做的 TracerPid 普查（19:29，单 awk 读 259 个 `/proc/*/status`）= **11617→57 个任务、0→202 个任务**（与 Lead 独立普查 57–58 一致）。
- **口径澄清（原先看似矛盾）**：`attached=` **只统计显式 `attach_pid` 成功次数**（`:1011` 是唯一自增点），**不含** `PTRACE_O_TRACEFORK` 自动接管的子进程。所以 45（显式）+ 跟随来的子进程 ≈ 57 实时追随数。⇒ 把 `attached=` 当覆盖率判据（`FIX.md:521`、`FIX.md:254`）会**系统性偏低**，且 churn 下只增不减。

### 2.2 fork/vfork/clone/exec 跟随（成本主项）

- 设备侧 task 创建速率（实测两窗）：`Δprocesses/Δt` = **346.2 /s**、**344.3 /s**（`/proc/stat` 的 `processes` 行）。
- 结构性下界：2 次停/次 fork-clone ⇒ **≥688 停/s**（不需要任何假设，只依赖 `:1009` 的选项集与 `:1145/:1151` 的处理）。
- 再加 exec（1 停/次）、子退出给父的信号投递（1 次信号停，是否成立见 §8 假设 A4）⇒ 结构估计 1,376–1,522 停/s，与实测下界 1,522 /s 吻合。
- **本仓我们自己的守护只能解释其中一小部分**（可复算）：fast_watch 1 s 拍 ≈2.8 fork/s（五探针错峰 `1/1+1/2+1/6+1/10+1/300 ≈ 1.77`，加每拍 1 次 awk 扫 4 个 `/proc`——`gw/fast_watch.sh:29-30/:135/:272`）；watchdog 2 s 快路径 ≈7 fork × 15 次/30 s ≈ 3.5 /s（`gw/watchdog.sh:1018-1027`、`_kickwait :1048-1055`）；wan_eth ≈2 /s（`CFG_HEAL.md:107`）；avail_sampler 1 次/10 min（`AVAILABILITY_DESIGN.md:119`）⇒ **≈5–10 fork/s**。**其余 ≈335 /s 的归属未测**（厂商栈/实验进程/短命令），属 [B]。

### 2.3 信号投递全停

- 每次信号：目标进 signal-delivery-stop → 跟踪者 `waitpid` 返回 → `PTRACE_CONT(pid,0,sig)`（`:1152`）。1 次停 + 2 次上下文切换 + 2 次系统调用。
- 与 §2.2 合计即实测的 1,522 停/s。
- 注意：**SIGSEGV/SIGBUS 只是其中极小一部分**（本窗 2 次/103 min）。

### 2.4 命中（SEGV/SIGBUS）处理

每次进入 `handle_segv`（`:819`）的固定开销：`is_canary` → `readlink(/proc/pid/exe)`（`:359-383`）；`PTRACE_GETSIGINFO`（`:824`）；`PTRACE_GETREGSET`（`:826`，拷 272 B 结构）；`process_vm_readv(pc,4)`（`:827`）；`note_bin` 每 pid 一次 `readlink+stat`（`:261-274`）；日志（`comm_of` open/read/close + write + fstat，`:188-198/:203/:236`）；随后按分支做 `record_probe`（1 次 32 B readv，`:393-400`）与/或 `deref_attempt` 的 16 KB 行走（§3）。合计约 **40–90 µs CPU/次**（估算，见 §3.3）。
实测量级：当前实例 `segv=2`（103 min）；日志全量 `SEGV 715` 行 / `STAT 452` 条（≈7.5 h 累计、4 个实例）≈1.58 次/min（**口径不同**，见 §12）。

## 3. 每次命中判据的开销（读取原语 + 精确计数）

### 3.1 读取原语：process_vm_readv（不是 PEEKDATA，不是 /proc/pid/mem）

`read_mem()` = 一次 `process_vm_readv(pid, local, 1, remote, 1, 0)`，长度不匹配即失败（`:276-280`）。
⇒ 每次跨进程读是**一次系统调用**；不落 `/proc/pid/mem` 的 open 成本，也不用 `PTRACE_PEEKDATA` 的逐字往返。

### 3.2 shape_ok 与 16 KB 栈行走的精确计数

`shape_ok(w, fault)`（`:306-322`）本身只比较 4 个 qword（常数时间）。**贵的不是它，是找到它的那一次行走**：

| 项 | 值 | 出处 |
|---|---|---|
| 扫描窗口 | `DEREF_SCAN_BYTES = 16 KiB`，从 `sp & ~0xFFF` 起 | `:535`、`:632` |
| 每页读取 | 1 次 `process_vm_readv(4096)`（未映射页直接失败并跳过，不进内循环） | `:636-641` |
| 内循环步长 | 8 B；`off + 32 <= 4096` ⇒ 每页 **509** 个候选偏移 | `:649` |
| **全窗比较次数** | 4 页 × 509 = **2,036 次**（每次 4 个 qword 读 + 2–6 个比较） | `:649-684` |
| 调用点 | ① `deref_attempt` 第一次行走（`:715`）**不受任何预算约束**；② X3 第二次行走（`:721-722`）无 xrep 时受 50/s 预算；③ `xform_observe` 普查行走（`:806`）受 50/s 预算 | `:715/:721/:806` |
| **dry-run / 未布防下谁在付** | **① 照付**：`handle_segv` 在 `:850/:862/:874/:880/:940` 调用 `deref_attempt`，而 `g_dry` 只在 `:737` 之后才被检查（且只决定要不要写寄存器/吞信号）；②③ 需门控通过才付。⇒ **普查（`:806`）与 `:715` 的区别只在门控，不在是否执行** | `:715`、`:737`、`:806` |
| 预算实现 | `xform_budget()` 是函数内 `static` ⇒ **全局 50 次/s**（跨所有 tracee） | `:779-787` |
| 单次 32 B 读 | `record_probe`（`:393-400`）、`record_at`（`:326-333`）各 1 次 readv(32 B) | |

### 3.3 单次成本估算（可复算）

- 16 KB 行走 = 4 次 `readv(4 KB)`（≈4–12 µs，含地址空间查找与拷贝）+ 2,036 次迭代 ×（4 次加载 + 比较，≈4–8 cycles）≈ 8 µs（按 1 GHz 量级）⇒ **15–25 µs/次行走**。
- 一次"命中处理"（§2.4 固定开销 + 1 次行走 + 可能的第 2 次）⇒ **40–90 µs**。
- **实测交叉验证**：本窗 SEGV 停 ≈2 次/103 min = 3.2×10⁻⁴ /s ⇒ 判据路径总占用 <3×10⁻⁵ 单核——**在测量噪声之下**（[A]：它不可能从 2.4 % 的总占用里分辨出来）。
- **最坏情况**：(a) canary 风暴 20/min（`FIX.md:281`）⇒ 0.33 次/s × 60 µs = 20 µs/s ≈ 2×10⁻³ % 单核；(b) 若某进程以 1,000 次/s 反复触发 load 型故障（正常会死，但被修复后可能活着），第一次行走不受预算约束 ⇒ 1,000 × 20 µs = **2.0 % 单核**，与整机常驻成本同量级；**这是一个设计缺口**：`xform_budget()` 只约束 census/第二次行走，`:715` 的第一条行走只受故障率约束。建议把 `:715` 也纳入同一预算（或纳入 (pid,pc) 熔断计数）。

### 3.4 熔断（避免 CPU 空转的部分）

v1.7 **无熔断**（`FIX.md:110` 的 V4），循环内 `ldr` 会无限修复 → CPU 空转 + 日志风暴。v1.9+ 有 `(pid,pc)` 连续计数熔断（`BRK_N=128`、`NR_LOOP_MAX=8`，`:146-172`；使用点 `:943-950`、`:748-751`、`:921-936`）。
实测：`nerepair.log` 全量中 `PASS reason=repair-loop` **395 条**（占 PASS 533 的 74 %）⇒ 该守卫**确在役且被触发过**；注意 dry-run 下熔断仍先于 `g_dry` 生效（`:943-950` 在 `:951` 之前），故 dry-run 的 `WOULD_REPAIR` 是"被熔断截尾"的计数（与 `docs/review/NEREPAIR_EFFICACY.md` §1.3f 独立一致）。

## 6. 时延 / 稳定性副作用

1. **被修进程的信号投递时延**：每次信号投递都要等跟踪者唤醒并 `CONT` ⇒ 附加一次停-放行往返。CPU 侧 ≤16.2 µs（实测），**wall-clock 停等分布未测**（[B]：需要在内核侧或 supervisor 内打时间戳）。典型几十 µs；极端（supervisor 正卡在 3 s attach 轮询或一次 16 KB 行走）可达数 ms。
2. **每事件 2 次上下文切换的定性影响**：实测 nerepair 自身阻塞占**全系统 ctxt 的 17.9 %**（1,522/8,500，两窗一致）；加上被唤醒的 tracee 侧切换，ptrace 往返可能占全系统 ctxt 的 ~36 %（2×1,522/8,500，E2：假设 1 事件 = 1 次跟踪者阻塞 + 1 次 tracee 侧切换）。
3. **detach / re-attach 窗口（全系统失去覆盖）**：`kill_daemon` 注入实测 **81 s**（`docs/ACCEPTANCE_REPORT.md:44`）；设计恢复上界 90–120 s（`docs/SELF_HEALING_AUDIT.md:65`）。该窗口内**没有任何修复覆盖**，家族进程照死。旧实例未死透时 `traced()` 会让新实例跳过其 tracee（`docs/SIGSEGV/05_LOG/2026-11-01-fix-design.md:60`）——svc_lock 单实例启动（`gw/nerepair_launch.sh:9-12`、`gw/svc_lib.sh:340`）针对的正是这一风险。
4. **全系统停摆（最大的稳定性风险，非 CPU）**：supervisor 一旦卡住，**全部 57 个 tracee 停在 ptrace-stop**，用户态整体不推进。机制与历史：`:41-45`（5 次 284–651 s 心跳断流、两次看门狗重启）；`docs/SIGSEGV/05_LOG/2026-11-01-05-audit.md:1281/1343`。2026-11-03 17:45 旧 boot 全用户态停摆 → healthdog 应急复位，根因未定（`docs/SIGSEGV/00_STATE.md:30-31`）——**本审查不归因于 nerepair**，仅指出这是该架构的固有风险面。
5. **熔断 vs CPU 空转**：v1.7 无熔断（V4）；v2.2 有（§3.4，实测触发 395 次）。当前窗口 `loop=0`（STAT）⇒ 无空转。
6. **supervisor 死亡时**：未设 `PTRACE_O_EXITKILL`（`:1009` 仅四个 TRACE 选项）⇒ tracee 自动脱离并继续运行（可用性上的优点），代价是"无人看守"。

## 8. 可复算的数量级估算（假设 → 数字 → 区间）

**模型**
- A1 每停事件 = 1×`waitpid` + 1×`PTRACE_CONT` + 2 次上下文切换（`:1134-1152`）。
- A2 **事件数 ≥ `voluntary_ctxt_switches` 增量**：主循环唯一的阻塞点是 `waitpid`，一次阻塞至少换回一个待处理事件（`usleep` 只在 ECHILD 分支；EINTR 约 1 次/60 s，可忽略）。⇒ 用 Δvol 作事件数**下界**，得到的每事件 CPU 是**上界**。
- A3 事件数若按结构估计 = 2×fork/clone（`:1009/:1145/:1151`）+ 1×exec + 1×子退出信号 ⇒ ≈1.4–1.5 k/s（与 A2 下界 1,522 /s 同量级）。
- A4 "子退出给父的 SIGCHLD（默认动作=忽略）是否仍产生 ptrace 停"——**未核实**（[B]）。若不产生，则剩余事件更依赖 exec。
- A5 设备 4 核、`CLK_TCK=100`（jiffy = 10 ms，由 jiffies/秒 与 uptime 一致性反推）。

**结果（两窗一致）**
- 事件率 **≥1,522 /s** ⇒ **1.315×10^8 /日**；
- CPU **2.46–2.51 % 单核**（寿命平均 2.32 %）⇒ **≈35.4 min CPU/日**；
- 每事件 **≤16.2 µs**；用 A3 的结构事件数则 ≈**13–16 µs**（点估计）；
- 占四核机时 **0.62–0.63 %**；占忙时 CPU **3.91 %**；占内核态 CPU **4.54–4.68 %**（§7.1 注 1）；占全系统 ctxt（跟踪者侧）**17.9 %**、含 tracee 侧往返 ~36 %（E2）。
- **敏感度**：CPU% ≈ 事件率 × 每事件成本；事件率 ∝ 设备 task 创建速率（实测 344 /s，其中我们自己的守护仅 5–10 /s）。若 churn 降到 10 /s，同样 16 µs/事件 ⇒ ≈**0.07 % 单核**。⇒ **成本由 churn 决定，与 NE 率几乎无关**（本窗 SEGV 2 次/103 min）。
- **外推前提**：churn 与 tracee 集合（59 个用户进程）稳定；跨 boot/跨版本不可直接比较（沿用项目口径）。

**与设计期定性判断的对照**：`docs/SIGSEGV/05_LOG/2026-11-01-fix-design.md:61` 把 ptrace 开销评为"低-中"，`:59` 把 fork 跟随评为"中"。以实测口径（2.4 % 单核 / 3.9 % 忙时 / 4.54–4.68 % 内核态，且**不随崩溃率下降**），建议把这两条评级更新为"**中（常驻、且事件面由 churn 驱动）**"。

## 9. XREP / X1 / X2 / X3 布防后的成本变化

- **当前状态（实测）**：`xrep=0`、`xw=xr=0`、`xform=0/0/0/0/0/0/0/0`、`sd=0/0/0/0`；但路径**已被走到**（`segv=2`、`would2=1`、`dfhit=1`，日志尾部有 `WOULD_DREPAIR path=p2`）。
- **dry-run 也照付那一次 16 KB 行走（LOW-8）**：`:715` 的第一次行走在 **dry-run / 未布防下照付**——`handle_segv` 在 `:850/:862/:874/:880/:940` 调用 `deref_attempt`，`g_dry` 只在 `:737` 之后被检查（且只决定要不要写寄存器/吞信号）。**普查（`:806`）与 `:715` 的差别只在门控，不在是否执行**：前者还要过 `cls ∈ {store,regload,ldp,fp}` + `addr_family_plausible` + 50/s 预算。⇒ 本窗 `xform=0/…` **不代表没走 16 KB 行走**（`dfhit=1` 即证明走了），只代表没有一次通过普查门控。
- **XFORM 普查（未布防时也在跑）**：`xform_observe`（`:788-812`）只对 `addr_family_plausible`（`:693-698`）的故障开门，且受 `xform_budget()` 50 次/s 约束（`:804`）。上限 ≈ 50 × 15–25 µs = **0.75–1.25 ms/s ≈ 0.08–0.13 % 单核（最坏）**；本窗实测贡献 ≈0。
- **X1**（第二副本 `x2-0x240`，`:908-938`）：1 次 `record_at` = 1 次 readv(32 B) ≈1–3 µs；只在 pop 型 shape 失败后触发。
- **X2**（B0A2 复合地址，`:726-732`）：1 次全窗行走 ≈15–25 µs。
- **X3**（`:721-722`）：**第二次**全窗行走。**关键差异**：`if (!(g_xrep || xform_budget()) || !find_record_near_stack(...,2))` ⇒ **布防（`g_xrep=1`）后这条行走不再受 50/s 预算**，只受故障率约束 ⇒ 每个"小地址 load 故障"多付 15–25 µs。
- **布防后总量影响**：由**故障率**决定。本窗故障率 3.2×10⁻⁴ /s ⇒ 增量 ≈10⁻⁵ % 单核；canary 风暴 0.33 次/s ⇒ 增量 ≈10⁻³ % 单核。**布防不会改变那 2.4 % 单核的主项**（主项是停事件面）。
- **副作用**：修复成功 ⇒ 进程不死 ⇒ 同一站点可能反复触发；已由 `(pid,pc)` 熔断限到 8 次/站点（`:146-172`）。**建议**：把 `:715` 与 `:722` 两条行走都纳入同一个全局预算（或纳入熔断计数），以消除"未计数入口"。
- 另：布防还会让 `XREPAIR` 行大量出现（`rate_ok_prio` 200 行/s 预算），日志写量上限 24 KB/s（§4），本窗远未逼近。

## 11. 要实测必须怎么做（预注册）

**目标量 1 · nerepair 自身 CPU%（主判据）**
- 判据：`Δ(utime+stime)/Δuptime/CLK_TCK/100`（`/proc/<pid>/stat` 字段 14/15，`CLK_TCK=100`），同 boot、每分钟一点、`/proc/uptime` 锚定。
- 功效：测 0.1 % 单核需 24 h 内 ≥8,640 jiffies（0.1 %×86,400 s = 86.4 s）——远超噪声；**本报告 4.3 min 窗已把 2.5 % 定到 ±0.05 %**（两窗 2.508 vs 2.459），24 h 窗足以分辨 0.02 %。
- 停止规则：同一 boot；跨 boot 一律不可比。

**目标量 2 · 停事件率（停/s）**
- 判据：`Δvoluntary_ctxt_switches/Δt`（下界）**与** `Δ(/proc/stat processes)/Δt × {2,3,4}`（结构区间）**必须同向**；两者背离即判"事件构成未定"，不得只报其一。
- 功效：1,522 /s 下 10 min 窗 = 9.1×10⁵ 事件，泊松相对误差 ~0.1 %。

**目标量 3 · 每事件成本**
- 判据：`ΔCPU/Δ事件`，事件数取目标量 2 的下界 ⇒ 得上界；用 A3 结构事件数 ⇒ 点估计。报点估计 + 区间（本报告：13–16 µs）。

**目标量 4 · 归因到"被跟踪 vs 未跟踪"（替身 supervisor 实验，推荐）**
- 不建议 `killall nerepair` 做"无 nerepair"臂（丢覆盖；且要改 SVC_TABLE/rc.extend 属写操作与部署）。
- 推荐：**在设备上跑一个受控微基准**（例如 200×fork+exec + 1000 次信号投递），用**独立的最小 ptrace 监督者**（同 `:1009` 选项集）跑 A/B：基准是否被追随 × 基准 wall-time/CPU。这样主项（每事件成本、每 fork 延迟）可直接测，而不用碰在役实例。
- 该实验要在设备上执行新二进制 = **写操作**，必须 Lead 批准 + 回滚预案。

**目标量 5 · 停等延迟分布（tracee 视角）**
- 在 v2.3 里给 `waitpid` 返回与 `PTRACE_CONT` 各打一个时间戳（单调钟），STAT 增加 p50/p99；这是唯一能测"信号投递被推迟多久"的办法（本内核无 kprobe/ftrace/perf，`FIX.md` §6 R-8）。

**目标量 6 · XREP 布防 A/B**
- 预注册：同 boot、同负载、ABAB 各 30 min ×3 轮；A 臂 `xrep=0`（现状）、B 臂 `/data/gw/nerepair.xrep` 存在。变量唯一。
- 判据：`ΔCPU/(Δsegv+Δxr)` 与 STAT `xw/xr/xform` 增量；副作用面必须同时报（REPAIR/XREPAIR 行数、repair-loop 数、进程死亡率）。
- 布防本身是**写操作**（建标记文件）⇒ 需 Lead 批准并预置回滚（删标记 + `killall` 重启）。

**目标量 7 · churn 归属（为什么是 344 /s）**
- 只读做法：高频快照 `/proc/stat processes` 与 `/proc/loadavg`，与各候选守护的已知 fork 率对照 —— 只得总量曲线，**得不到归属**；
- 要归属必须在内核 fork 路径打点（本内核无 ftrace）或在 `/proc` 高频采样（会自己污染 churn，需按判据三定律扣减观测者）。
- 该项是**降低未来成本的前提**：若 335 /s 的 churn 来自少数几个厂商守护，可评估"按进程白名单跟随"（局部 ptrace）而不是全量跟随。

**观测者污染**：所有窗口必须同时报观测者自身的 fork 数（本报告 §7.3 的做法），并从 `processes` 速率中扣除。

## 13. 结论分级

### [A] 已核实（本机可复算 / 设备只读实测）

- 停事件面 = 所有信号 + 所有 fork/vfork/clone/exec；处理面仅 SIGSEGV/SIGBUS（`:1009/:1145-1152`）。
- 实测停事件率 **≥1,522 /s**（两窗 1,528.5 / 1,521.7；寿命 1,438.7），设备 task 创建 **344–346 /s**，全系统 ctxt **8,499–8,556 /s**。
- nerepair CPU **2.46–2.51 % 单核**（寿命 2.320 %；Lead 独立复核 2.56 %），占忙时 3.91 %、机时 0.63 %、内核态 **4.54–4.68 %**；每事件 **≤16.2 µs**（Lead 复核停事件 1,530 /s、ctxt 8,581 /s、fork 340 /s、vol/ctxt 17.8 %，均一致）。
- 内存 RSS **124 kB** / VmSize 256 kB / 1 线程；ELF 映射 97,484 B（可复算）。
- TracerPid 普查 57 追随 / 202 未追随（共 259 任务）；`attached=` 只计显式 attach（`:1011`）。
- 判据路径精确开销：4×readv(4 KB) + **2,036** 次 8 B 步进比较；`:715` 不受预算、`:722/:806` 受全局 50 次/s。
- 日志 2,069 行/255,354 B（0.077 行/s）、轮转未触发、STAT 间隔 117/117=60 s（无 >1 拍停顿）、PASS 原因分布（repair-loop 395/shape-fail 119/rt-ne-rn 18/not-load 1）。
- 覆盖窗口 81 s（`ACCEPTANCE_REPORT.md:44`）；md5 与 `ARCHITECTURE.md:60` 一致。
- **观察者自产事件已识别**：19:29:05 的 `od` 崩溃为只读取证管线派生（四信道一致），故只读观测窗的事件计数必须扣除观测者自产事件（§7.1 注 2 / §7.3）。
- 日志年化 **0.82 MB/日**、轮转后常驻上界 **2 MB**（§7.2）。
- 旁证：r7 的 wait4 缺页 33,959/9 min（≥63 wait4/s）；唯一 loadavg 序列 7.29→13.18。

### [B] 未核实（原因）

- **事件类型构成**（fork vs exec vs 信号各占多少）：线上无分类计数器；只有结构推断（A3/A4）。
- **SIGCHLD（默认忽略）是否产生 ptrace 停**：内核 `get_signal()` 路径顺序未在本仓取证，也未实测。
- **每 tracee 内核侧 ptrace 结构的内存**：本仓无数据（只能证明 tracer 侧 RSS 不随 tracee 数增长）。
- **停等延迟分布**（tracee 被停多久）：需要 supervisor 内时间戳或内核侧仪器（本内核无 ftrace/kprobe）。
- **3 s attach 超时的发生频率与全系统停顿**：本窗无观测手段；仅有代码路径与 v1.5 历史实弹。
- **344 /s churn 的进程归属**：只测到总量；高频 `/proc` 采样会自我污染，未做。
- **XREP 布防后的实测增量**：未布防（`xrep=0`），只有代码级上界。
- **设备 CPU 型号/主频**：未取证（仅知 aarch64、4 核、`CLK_TCK=100`）；每事件成本的绝对 µs 依赖此假设。

### [C] 必须上设备才能确认（含需要写操作/部署的项，须 Lead 批准）

1. v2.3 **分类事件计数器**（fork/exec/signal 三类 + 信号号直方），把 1,522 /s 拆开 —— 代码改动 + 部署（写）。
2. **停等延迟**（`waitpid` 返回 → `PTRACE_CONT` 时间戳，STAT 报 p50/p99）—— 同上（写）。
3. **3 s attach 停顿**：开机窗内给每次 attach 打时间戳并统计超时次数 —— 同上（写）+ 必要时在开机繁忙期复现。
4. **替身 supervisor 微基准 A/B**（每 fork/每信号成本、被追随 vs 未被追随）—— 需在设备执行新二进制（写，须批准）。
5. **XREP 布防 A/B**（预注册 ABAB）—— 建/删标记文件（写，须批准）。
6. **全系统停摆演练**（受控卡住 supervisor 观察 tracee 停摆与 watchdog 行为）—— 会中断服务，须预注册与回滚（写）。
7. **churn 归属**：按进程白名单跟随的可行性评估，需先知道 churn 源（内核打点或受控采样）。
