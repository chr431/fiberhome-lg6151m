# 09 · 命中的条件分布（R4，2026-11-01）

前置（见 [08_CORRELATION.md](08_CORRELATION.md)）：写入者锁定在**有线端口共用 EDMA RX 的「每 RX 包一次机会」路径**，
速率 1.3 ± 0.2 命中/千包；具体时序窗口未定位。

本文回答：**命中在时间、记录字段、流量形态上的条件分布是什么？**

## 方法

- 数据：设备 `/data/repro/h4_*.bin` 全量 **2554** 份（canary 转储，每份 120 B 头 + 8×4 KB 栈页）。
- 提取：`/data/repro/h4_meta.sh` → 每文件一行 `file ts pid hit x2 top fault_addr`（`fault_addr` = 记录 word0）。
- 拉取：分页 + **行数断言 2554 == 2554**（规避"大输出截断"坑）。主机副本 `_local/evidence/crash-root/h4_meta.txt`。

## 结果 1：**「命中成簇」不成立 —— 那是速率假象**（已自我撤回）

**初版错误做法**：把三段不同速率（静默 1.8/min、传输 127.6/min、回落 0.5/min）混在一起，
按 1 秒粒度统计"同秒 ≥2 个不同 canary"，得到 21.7%，据此宣称"成簇"。

**正确做法**：按段分开 + 速率匹配泊松零模型。干净的 T1–T2 LAN 段（λ = 631/300 = **2.10 命中/s**）：

| 量 | 观测 | 独立 4-canary 泊松零模型期望 | 判定 |
|---|---|---|---|
| 同秒 ≥2 个**不同 pid** 的秒数 | **131** | **127.0** | 比值 1.03，**无超额** |
| 同秒 ≥2 次命中的秒数 | 131 | 186.4（同速率泊松） | 观测**低于**泊松 |
| 同 canary 间隔 p50 / p90 | 1 s / 2 s | 1.32 s / 4.38 s（指数） | 尾部**更短**（比泊松更规则，不是突发） |

（静默段 n=9、回落段 n=3，样本太小，不做分布推断。）

**结论**：**速率匹配后与独立泊松过程无显著差异** → 没有证据支持"共享页/突发批次"模型。
教训：**在 1 秒粒度、2 次/秒的速率下，泊松过程本来就长得像"成簇"**；这是又一次「判据集合 ≠ 目标集合」。

## 结果 2：记录 word0 **既不是包长、也不是环槽位**

- 1723 / 2322 的 word0 < 1 MB；**1733 个不同取值**，范围 0–597004。
- 落在「包长区间 [0x500, 0x700]」的只有 **2 / 1723** → **不是包长**。
- 取值范围远超 512 项 RX 环的索引范围 → **不是槽位索引**。
- 高频重复值：`58511 (0xE48F) ×47`、`55439 (0xD88F) ×36`、`2103 (0x837) ×19`。
  - 但 58511 的 47 次分布在**两个独立会话**（分钟偏移 0/92.6/193.8 属旧会话，75566+ 属本轮），
    **不是某段时间卡住** → 不是"同一槽位被反复写"。
  - 58511 与 55439 相差 0xC00=3072 只是巧合：对全部 1733 个取值做 `%0xC00` / `%0x3000` / `%32` 检验，
    **均无集中**（`%32` 各余数 60–70 次，近乎均匀）。
- → 更像**数据相关的计数器 / 序列号 / 时间戳**，不是地址、不是索引、不是固定槽位。
- 附带确认：`top - x2` 在 **2322/2322** 恒等于 **912 (0x390)**（与既有 C-052 一致）。

## 结果 3/4：包长相关性与 CPU 相关性 —— 待流量形态实验（排队）

| 臂 | 工具 | 形态 |
|---|---|---|
| L 大包 | `_local/lan_rx_gen.py --rate-mb 2` | ≈1400 B/包、~1500 pps |
| S 小包 | `_local/lan_pkt_flood.py --pps 20000 --size 64` | 64 B/包、20 kpps |

- S 臂「命中/千包」显著高于 L 臂 → 小包更容易触发（每包固定概率）；
- 两臂相同 → 与"每包一次机会"一致，包长无关。
- 磁盘预算：S 臂 60 s × 20 kpps = 120 万包，按 1.3/千包 ≈ 1500 次命中 ≈ 48 MB；/data 余量 1.4 GB（已用 37%），足够。

## 结果 5：150 份近期记录的字段分布（只读提取）

方法：按 `off = 120 + (x2 - (top - 32768))` 定位记录在 h4 文件中的偏移，`od -j off -N 32` 取 4 个字
（150 份，分 3 批每批 50 条，避免单次 SSH 大输出）。原始数据 `_local/evidence/crash-root/h4_rec150.txt`。

**形状**：**150/150 的 `w1 = 0`、`w3 = 0`**，只有 `w0` 与 `w2` 非零。

**w2 = {IP, len}**（高 32 位 IP、低 32 位长度）：

| 字段 | 分布 |
|---|---|
| IP（高 32 位，按网络序解读） | **192.168.9.1 ×112**、0.0.0.0 ×36、110.65.x.x ×2 |
| 长度（低 32 位） | **1601 (0x641) ×112**、1664 (0x680) ×2、其余 57497 / 62310 / 63388 / 70029 / 70707 / 72085 等零散 |

**w0**：范围 55,656 – 7.5×10¹⁶，中位数 102,011；`%32` 无集中（余数 16 出现 39 次，其余 ≤8）。

### 推论（可证伪）

1. 记录高度**模式化**：75% 的记录是同一个 `{w0 变化, 0, 0x0109a8c0_00000641, 0}` —— **只有 w0 在变**。
2. 长度 1601 / 1664 **都大于 RX 缓冲长度 1536 (0x600)** → **不可能是原始包长**；
   更可能是 **GRO 聚合后的长度**（设备侧 GRO 把多段合并成一个 skb）。
3. IP 是设备**自己的 LAN 地址 192.168.9.1**（WAN 地址只占 2/150）→ 记录对应**本机收/发的 LAN 侧流量**，
   与"LAN RX 也能驱动命中"（08_CORRELATION 臂2）一致。

**含义**：记录不是任意内存垃圾，而是**与 RX 完成处理相关、携带本机 IP + GRO 量级长度的结构**。
下一步可查 GRO 相关结构（`skb_shared_info` / `napi_gro_*`）在 RX 路径里被写入的时机。

## 澄清：为什么第 1 轮说「WAN IP ×122」，本轮说「LAN IP ×112」

Lead 指出两次 IP 分布几乎相反。逐项核对后，**是同一字段、不同时段流量构成不同**：

| 项 | 第 1 轮（CRASH_ATTRIBUTION_2026-10-30） | 本轮（09_CONDITIONAL） |
|---|---|---|
| 数据源 | `h3_*.bin`（core 派生记录，106 份） | `h4_*.bin`（canary 转储，150 份） |
| 字段偏移 | **记录 +0x14 的 32 位**（= w2 的高 32 位，按网络序） | **w2 的高 32 位**（同一字段） |
| 采样时段 | 2026-10-30 夜间（客户端从 WAN 大量下载） | 2026-11-01 上午（LAN 灌流测试 + 日常） |
| 主导取值 | `0x1c28416e` = **110.65.x.x（eth0 WAN）** ×122 | `0x0109a8c0` = **192.168.9.1（LAN）** ×112 |

**结论（重要）**：该字段 = **包的本地端点地址**（入站包的目的地址 / 出站包的源地址）。
- 夜间 WAN 下载为主 → 入站包目的地址是 WAN 地址 → 记录里是 110.65.x.x；
- 本轮 LAN 灌流为主 → 入站包目的地址是 192.168.9.1 → 记录里是 LAN 地址。

→ **IP 分布反映的是「当时的流量构成」，不是写入者的属性。**
把 IP 分布当机制证据会犯「把流量构成误当机制」的错误；但它反过来**支持**「记录携带逐包 L3 信息」这个模型。

## 关于 GRO 假设的边界（Lead 的反证，成立）

若长度是 GRO 聚合后的 skb 长度，那是**协议栈软件字段**，DMA 硬件不可能知道。因此更准确的表述是：

> **某个持有「本机 IP + 一个 >1536 的长度」的 32B 结构**被 DMA **写**到了用户页上，
> 而**不是**「GRO 结构本身被写」。区别在于：写入者是 DMA，内容是它自己的描述符/状态，只是那个结构恰好携带了这些值。

另外注意：**1601 > 1536（描述符里的 DMA 长度 0x600）**，所以 1601 **也不可能是单缓冲包长**；
环配置里分配长度是 0x780=1920、DMA 长度是 0x600=1536，1601 落在两者之间 —— 这个数值的来源仍未知，**不作断言**。

## 下一步（Lead 建议，已排入）

在 vmlinux 里搜「同时含 `__be32` IP 与 `u32` len、且约 32B」的结构写入点，优先：
`tcp_skb_cb`（在 `skb->cb` 48B 内，含 seq/end_seq/tcp_flags，32B 量级）、`skb_shared_info`、`napi_gro_cb`。
判据：该结构的**字段顺序**必须能排出 `{?, 0, IP|len, 0}` 这个 32B 布局。

## 结果 6：流量形态实验 —— **命中率与流量无关，推翻「每包固定概率」**（2026-11-01 11:35）

执行：全程 `devop.py`（`ACQUIRED`/`RELEASED` 成对），先起 canary 并确认 h4 增长后才发流量。
canary 4 个（taskset CPU2/CPU3），采样器 CPU0，`corr4.tsv` 18 列含设备侧包计数。

| 臂 | 时长 | 命中 | RX 包数（**设备计数**） | 命中/千包 | 命中/min |
|---|---|---|---|---|---|
| 基线 | 99 s | 2 | **758** | 2.639 | 1.3 |
| 大包（`lan_rx_gen` 2 MB/s，120 MB） | 61 s | 2 | **79,514** | 0.025 | 2.4 |
| 静默 | 61 s | 2 | **795** | 2.516 | 2.4 |
| 小包（`lan_pkt_flood` 20 kpps × 64 B） | 61 s | 1 | **1,035,961** | **0.001** | 1.2 |

**判决：本会话内命中率与流量无关。** RX 包数跨 **1,366×**（758 → 103.6 万），命中/min 恒定 **1.2–2.4**。

推论：
1. **包长与包率都不相关**：小包臂 104 万包仅 1 次命中；大包臂 7.95 万包 2 次。
2. **「1.3 命中/千包」不是普适常数** —— 那是**上一会话那 4 个 canary 处于「热页」状态**时测得的。
3. **支持页竞争模型（假设 b）**：命中需要两个条件同时成立
   - (i) canary 的栈页恰好是某个 stale 描述符的目标页（本次 4 个 canary 都是"冷页"）；
   - (ii) 该页上发生 RX 写入。
   上一会话 canary 是热页 → 随流量线性；本次是冷页 → 只有恒定背景率。

**方法学修正**：先前把「命中/千包」当作写入者的固有速率是**错的**——它混淆了"写入概率"与"canary 页被选中的概率"。
正确口径应分开报告：**背景率（冷页）** 与 **流量敏感率（热页）**。

**下一步（优先级已调整）**：
1. **用户页占比/页复用实验**（Lead 已批 12×40 MB 版本）——直接操纵条件 (i)；
2. **canary 重启实验**（每次新进程 = 新栈页，30 s/次）——检验"热页/冷页"最直接；
3. 流量形态实验降级：已证明它不是决定性杠杆。

## 结果 7：canary 重启实验 —— **阴性；「热页」假设不成立，但指向环重置**

方法：连续 5 轮，每轮 kill 全部 canary → 起 4 个新进程（taskset CPU2/3）→ 计 60 s 内命中。
脚本 `/data/repro/restart_test.sh`，结果 `/data/repro/exp_r2/restart_test.txt`。

| 轮次 | 1 | 2 | 3 | 4 | 5 | 平均 |
|---|---|---|---|---|---|---|
| 命中 | 2 | 1 | 1 | 0 | 1 | **1.0 / min** |

对照：上一批**长时间运行**的 4 个 canary（pid 17410–17413）在 4 分钟内 11 次命中 = **2.75 / min**。

**判决**：**新起的 canary 并不更热（反而略低）** → 「新进程栈页来自近期回收池 ⇒ 热页」**不成立**。

### 那么 127.6 命中/min 怎么解释？只剩"两次会话之间设备状态变了"

候选（按可能性）：
1. **soak-qa 的链路类注入（ra0/rai0/br-lan down/up）会重置 EDMA 环** → 环中的 stale 描述符被清掉；
2. 时钟跳变 3 次（10:35 / 11:18 / 11:21）期间的重初始化/超时；
3. 长时间运行后页池状态变化。

这与 00_STATE §8 的 **H-STALE（环 teardown/重配置后留下 stale 描述符）** 高度一致：
**若为 1)，则"stale 描述符"是由环重置事件创造的，而不是常态存在** —— 这本身是机制级线索。

### 建议的判决实验（需 drill 窗口，涉及链路中断）

在受控窗口（`--drill-target eth1` 或 `wifi`）里做一次 `eth1 down/up`（或 `rai0 down/up`），立刻测命中率：

- 若命中率从 ~2/min **跳回 ~100/min** → **「环重置创造 stale 描述符」被实证**；
- 这能一次解释：为什么有时 127/min、有时 2/min，以及记录为何落在用户页。

## 方法学修正（Lead 要求，务必遵守）

> 先前把「1.3 命中/千包」当作**写入者的固有速率**是错的 —— 它混淆了「写入概率」与「canary 页被选中概率」。
> 正确口径：**背景率（冷页，与流量无关）** 与 **流量敏感率（热页，随流量线性）** 必须分开报告。

这是「判据集合 ≠ 目标集合」的又一实例：**用 canary 的命中率代表写入者的速率，集合错了**。

## 结果 8：EDMA 环重置实验（eth0 down/up ×2）—— **阴性**

方法：设备侧自治脚本 `/data/repro/reset_test.sh`（不依赖 SSH 在线）：每轮起 4 个新 canary → 120 s 基线 →
`ip link set eth0 down/up` → 120 s 后测。drill 窗口 `target=wan` 覆盖全程（579 s）。

| 轮 | 相 | 命中 | RX 包 | 命中/千包 |
|---|---|---|---|---|
| 1 | 重置前 | 1 | 201 | 5.0 |
| 1 | 重置后 | 3 | 172 | 17.4 |
| 2 | 重置前 | **38** | 8,325 | 4.6 |
| 2 | 重置后 | **21** | 4,952 | 4.2 |

- 两次重置后 `eth0_up=1`（`state UP` 恢复），无残留；canary 全 kill；h4 2570→2635。
- **第 2 轮重置前后无差异（4.6 → 4.2/千包）**；第 1 轮样本太小（1 vs 3）不具判别力。
- → **「环重置创造 stale 描述符」不被支持**：重置后没有出现 ~100/min 的跳升。

## 本轮最重要的负面结论：**canary 命中率不是可复现的量化指标**

同一批"新起 canary"的命中率在不同时间相差 **19 倍**：
- 重启实验 5 批新 canary 平均 **1.0 / min**；
- 环重置实验第 2 轮的新 canary **19 / min（4.6/千包）**。

而三个候选杠杆**都不能稳定移动它**：

| 杠杆 | 变化幅度 | 命中率响应 |
|---|---|---|
| 流量（RX 包数） | **1,366×** | 无（恒定 1.2–2.4/min） |
| canary 重启（新栈页） | 5 批 | 无（1.0 vs 长期运行 2.75/min） |
| eth0 环重置 | 2 次 | 无（4.6 → 4.2/千包） |

**结论**：
1. 写入者仍在**有线 EDMA RX 路径**（LAN-only 臂 ×71 支撑，未被动摇）；
2. 但**命中率由一个尚未控制的、慢变的设备状态主导**（页池组成 / stale 描述符存量 / 其它）；
3. **「1.3 命中/千包」只能在同一次连续观测内比较，跨会话不可比**——这是对上一轮量化结论的最终限定。

**建议的测量协议**（若继续）：同一次会话内、同一批 canary、连续测多个流量档位做内部对照；
每次记录 h4 增量与设备侧 RX 包数；**跨会话数字一律标注"不可比"**。
