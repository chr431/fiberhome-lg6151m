## 1. 问题

106 份 `h3b` 转储的 67% A / 32% 不明分类，是否因为检查了错误的 va_list 槽位？

## 2. 假设

- H1：fault-time va_list 是 ucontext 的 `regs[2]`（`0x7ffffff9c0`），不是 `attrib.py` 硬编码的 `0x7ffffff780`；按 x2 重算，绝大多数转储在同一记录上。
- H0：67/32 分类正确，x2 与 0x780 无实质差异。

## 3. 预测

- H1：`x2` 在 106/106 中等于 `0x7ffffff9c0`；按 x2 分类，`A0B2 + B0A2 >= 100/106`；按 0x780 分类，仍是 `71/35`。
- H0：按 x2 与按 0x780 的分类一致。

## 4. 判据

- PASS：x2 一致且 `A0B2+B0A2 >= 100`；0x780 复现 71/35。
- FAIL：x2 不一致，或 x2 分类仍 <90。
- INVALID：转储/ucontext 解析失败 >5 份。

## 5. 样本量/功效

- 106 份全量，不需要抽样；这是分类一致性检验，不是速率检验。

## 6. 混杂与控制

- 转储均来自 `vsurv3`，ASLR 关，栈布局固定；不能外推到自然 NE。
- `siginfo` 匹配用 `11,0,1,0 + addr`；tagged 情况遍历 0..255 的 tag。
- 0x780 复现用 `attrib.py` 的原槽位，作为阴性对照。

## 7. 停止规则

- 若 ucontext 解析失败 >5 份，停止并修解析器。

## 8. 分析计划

- 主终点：fault-time x2 的形状分布。
- 次终点：x2-0x240 的形状；`untag(w0-8)==addr`；0x780 的旧分类。
- 统计：计数 + 一致性；不做 p 值。

## 9. 变更记录

- 数据：`tmpfiles/an4/h3b/*.bin`（106）、`tmpfiles/an4/v3l/*.log`。
- 脚本：新 `tools/oneoff/sigsegv/va_scan.py`（本轮）。
- 设备：无（纯离线）。

## 10. 结果

- `x2 = 0x7ffffff9c0`：**106/106**。
- 按 x2：**71 A0B2 + 32 B0A2 + 3 other = 103/106（97.2%）**。
- 按 0x780（旧）：**71 有记录 + 35 无记录**，复现 `attrib.py` 的 71/34/1。
- 71/71：x2-0x240 也是 A0B2，且 A(pre-inc)/B 相同。
- 32/32：x2-0x240 是健康 va_list `{0x7ffffffa20,0x7ffffff760,0x7ffffff730,0xffffff80ffffffd8}`。
- `untag(w0-8)==addr`：104/106 直接相等；2 份 0x85 族因去 tag 后非规范地址，内核保留 tag；按 tagged/untagged 两种比较均一致。
- 3 个 other：`{0x603,0x273,0x5c3,0x5d5}`、`{0x12de,0x12d6,0x12d6,0x7bb}`、`{0xb55,0xb4d,0xb4e,0x54d}`。

## 11. 判决

- **H1 成立，H0 否定。** 67/32 分类是**槽位错误**：`attrib.py` 检查的是 0x780（更深副本），不是 fault-time 0x9c0。
- 对应 `01_CLAIMS.tsv`：C-002（active）、C-017（retracted）、C-006（active）。
- 追加撤回：`CRASH_ATTRIBUTION` 的 67/32/1 不再引用；`SIGSEGV_PATTERN_OFFLINE` 的“两条记录/ΔA=8”不再引用。

## 12. 偏差与教训

- 旧脚本 `h3table.py` 取“第一个匹配”（最低地址），天然落在 0x780；`attrib.py` 又硬编码 0x780。两个错误互相印证，形成“71/35”的假稳定。
- 6 份完整 core 的 x2 是可信的（pfcanary 无 handler）；16KB 转储必须用 ucontext，不能用 handler 的栈。
- 本轮只解决“分类”，不解决“因果/传输”；自然 NE 的记录占比仍未知。

# 追加：下一轮预注册（P0）

## E-01 自然 NE 栈普查

- **问题**：自然 NE（busybox/ip/logread/mipc）中，fault-time 栈上出现 B 记录且 fault addr 对齐的比例是多少？
- **假设**：H1 ≥50%；H0 <20%。
- **预测**：若 H1，记录是自然 NE 的主家族；若 H0，“一个写入者”战略对总体 NE 收益有限。
- **判据**：PASS = 可分类样本 ≥40/50 且记录因果 ≥50%；FAIL = 记录因果 <20%；INVALID = 栈快照失败 >10/50。
- **样本**：从 `ne_events.tsv` 按时间随机抽 50 条自然事件（排除 canary/自测），用 `core_meta v1.7 + stackdump` 落 16 页栈。
- **混杂**：进程类型、boot、流量、unsync；按进程类型分层。
- **分析**：记录因果 = fault addr 对齐 + 栈上记录；bystander = 记录在场但不对齐；other = 无记录/不同签名。

## E-02 三哨兵传输判定

- **问题**：B 记录的写入是 VA/uaccess、线性映射、还是 PA/DMA？
- **假设**：H1 = S1（uaccess）；H2 = S2（线性）；H3 = P0（PA/DMA）。
- **预测**：三选一；若 S1 有记录且 PF 触发 → H1；S1 有记录无 PF → DMA 绕过 PTE；S2 → H2；P0 → H3。
- **判据**：PASS = 一次崩溃/一次写入落在且仅落在一个哨兵；FAIL = 无记录；INVALID = 重定向后 60s 内自崩。
- **样本**：至少 3 次独立命中；每次 60s 稳定窗。
- **控制**：PF 正对照（模块对只读页 copy_to_user）；S1 只读；S2/P0 哨兵；同刻寄存器。

## E-03 探针正对照

- **问题**：PF/c2u/cfu/uw 的“0 命中”是否可能是仪器没工作？
- **判据**：每个正对照必须记录到预期字段；任一失败 → 该探针的阴性降级 E1。
- **样本**：每项 1 次故意触发 + 1 次不触发负对照。

## E-04 直接写入检测

- **问题**：B 记录的写入率是否远高于崩溃率？
- **方法**：`va2pa` + `pwatch` 盯一个已知 stale PA（例如 `sh.core` 那种死栈帧页），记录内容变化/时间戳；对照页同时监视。
- **判据**：若写入率/崩溃率 >10，支持“背景噪声 + 目标选择”；若 ≈1，不支持。
- **注意**：pin 的 observer effect；报告 pin 计数/页生命周期。
