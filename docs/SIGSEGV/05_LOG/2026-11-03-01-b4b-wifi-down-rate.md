# 01 · B4b 速率臂预注册：写入者活动速率是否依赖 WiFi 栈在场（arm1b · 2026-11-03）

> **预注册文档：设备会话之前写定。实验后只追加 §8–10，不改 §1–7。**
> 承接 B4 矩阵（2026-11-02-01-b4-ablation §11）：arm1（8 项遮罩：wifi 族 7 项 + mtk_wed）
> 按预注册 §4 二元判据（窗有效且 inj=0 ≥1）判 **P**，但实测速率 **4/1200s≈0.2/min**
> 远低于同夜三窗基线 **608/2700s≈13.5/min**（≈67× 差）。二元判据把它标成 P，
> 速率差被 §5「跨 boot 禁止速率比」挡在判据之外——本实验用**速率判据**正式检验该效应量。
> 执行单：`_local/investigations/sigsegv-tools/phase-AB/B4L-runbook.md`（遮罩机制/验证读点原样沿用）。
> 本文档中性信息：不含部署目标网络名与个人凭证。

## 1. 问题与假设

- **H_rate（速率依赖）**：32B 记录写入者的**活动速率**依赖 WiFi 栈（S1 全族 + mtk_wed）在场；
  arm1 的 4/1200s 不是方差，而是栈缺席导致的真实压制。
- **H_var（无压制）**：arm1 的低计数只是当晚慢变域的方差/流量构成波动；同一遮罩下再测
  两个 900s 窗，速率应回到基线量级（≥0.5× 基线）。
- 判据只回答「速率是否被压制到基线期望的 10% 以下」，**不**回答机制（哪一件模块、哪条路径）；
  机制归因仍受 B4 §6 的「S1 依赖 vs WiFi 流量构成依赖不可分」限制，本实验同样不可分。

## 2. 设计

| 项 | 值 |

**协变量（每窗记录，只记录不判 INVALID）**：`/proc/uptime` 起止锚点、boot_id、`/proc/modules`

WiFi 状态（`iw dev` / `ifconfig` 无 ra0/rai0、hostapd 全集合扫描无命中）、`/proc/net/dev`

## 3. 判据（预写死；判读时对号入座，不现场发挥）

**基线期望**：B4 同夜三窗（arm0/arm0'/arm0''，同镜像、同调用、窗有效）inj=0 合计
**608 / 2700 s = 13.511 /min**。按 1800 s 窗总时长线性缩放：

- **λ_pooled = 608 × 1800/2700 = 405.33**（主判据）
- **λ_lo = 143 × 1800/900 = 286.0**（三窗中最低速窗缩放的保守期望，敏感性判据）

**窗有效性（所有分支前提）**：每窗日志含 START（参数逐字=§2 固定调用）+ SELFTEST_PASS +
EXIT reason=duration + 全窗 probe_bad=0；遮罩验证通过（8 条 `masked … -> /etc/modules.d/…`、
8 项在 /proc/modules 缺席、mtk_warp/hw_nat 在位、挂载数=8）；无窗内 panic/重启；
日志 md5 双端一致。任一不满足 ⇒ 该窗 INVALID（单窗 INVALID 时若另一窗有效，判决只用有效窗，
按 900 s 重算 λ 并注明；两窗皆 INVALID ⇒ 实验 INVALID）。

| 分支 | 判据（全部满足） | 结论 |
|---|---|---|
| **压制确认（SUPPRESSED）** | N_total ≤ 40（=0.10×λ_pooled）**且** P(X≤N_total \| λ=405.33) < 1e-4 | 写入者活动速率被 WiFi 栈缺席压制到基线期望的 10% 以下（效应量级别；不判机制） |
| **无压制（NOT SUPPRESSED）** | N_total ≥ 203（=0.5×λ_pooled） | 今晚 arm1 的 4 条判为方差；速率判据不支持「依赖 WiFi 栈」 |
| **不确定（UNCERTAIN）** | 41 ≤ N_total ≤ 202 | 既非压制也非无压制；只能写「速率介于 10%–50% 基线期望之间」，不得写「压制」或「无关」 |

**敏感性（预写死，不改主判据）**：以 λ_lo=286 复算 ⇒ 压制侧阈值 N ≤ 28、无压制侧 N ≥ 143。
**若主判据与敏感性判据给出不同分支，最终判决取两者中更弱的一档**（即：主判 SUPPRESSED 而
敏感性判 UNCERTAIN ⇒ 最终 UNCERTAIN；主判 NOT SUPPRESSED 而敏感性判 UNCERTAIN ⇒ 最终 UNCERTAIN）。
此规则的目的=不让基线期望的选取方式抬高结论强度。

## 4. 功效与预期

- 若 H_rate 为真（沿用 arm1 观测率 0.2/min）：1800 s 期望 **≈6** 条 ⇒ 落在 ≤40 内，压制侧
  判据的泊松尾 p≈3e-133（λ_pooled）⇒ 判别力实际为 1。
- 若 H_var 为真（速率=基线）：期望 405 条，P(N≤40)≈3e-120 ⇒ 误判压制概率可忽略。
- 判据的可判别边界：10% 与 50% 之间（40–203 条）为设计上的「不确定」带，本实验不追求该带内定论。
- **与 B4 二元判据的关系**：arm1=P 的结论（「不需要该 8 模块」的存在/消失二分）不受本实验影响；
  本实验只新增「速率是否被压制」这一独立维度。两者不冲突：压制可以为真而 P 仍为真。

## 5. 混杂与控制

- **跨 boot 慢变域**：本实验把两窗放在同一 boot，但基线期望来自约 1.5 h 前的三窗（不同 boot）。
  慢变漂移是本设计的主要残余风险 ⇒ **预注册一个可选中性协变量窗**（见 §6-4）：只作漂移协变量，
  **不入判决**，用于事后解释（若中性窗也跌到低位，则 arm1b 的低计数不能归因于遮罩）。
- **WiFi 客户端流量**：arm1 遮罩下 WiFi 必无客户端流量（PC 在 eth1 有线侧）。本实验**不区分**
  「写入者依赖 S1」与「写入者速率依赖 WiFi 流量构成」——判决只在速率层面表述。
- **上行会话**：不判 INVALID，只记协变量（B4 §6 同款）。
- **04:00 定时重启**：全部工作在 03:30 前完成；跨过 03:30 停工。
- **一轮一变量**：窗内不加任何新仪器；除遮罩文件外不改配置。

## 6. 停止规则

1. 两窗完成（或两窗皆 INVALID）即停；得出 §3 分支即停，不追加窗口。
2. **8 分钟红线**：设备不可达连续 8 分钟 ⇒ 停工，如实报告（不擅自重启）。
3. **03:30 硬停线**：到线即停，按已完成窗判读（单窗有效则按 §3 的 900 s 重算规则判读）。
4. **可选中性协变量窗（预声明，不入判决）**：两窗结束后若距 03:30 余量 ≥25 min，跑
   1 × 900 s 中性遮罩窗（同调用、log `b4b_arm0b.log`）作漂移协变量；余量不足则跳过并注明。
5. **窗内非计划重启**：该窗 INVALID；查 pstore；连续第 2 次 ⇒ 停工，恢复中性遮罩并报告。
6. 安全红线：不写 p25/p38/p39；不碰 bootctrl；misc 只读；一切设备写经 deploy.py put。

## 8. 结果（2026-11-03 会话 · 执行代理追加；§1–7 未改动）

**判决：压制确认（SUPPRESSED）。** 同一 arm1 遮罩下 2×900 s 共 **5 条 inj=0 真命中 / 1800 s
= 0.167/min**，为基线期望 13.51/min 的 **1.2%**；主判据（λ_pooled=405.33，阈值 N≤40，
P(X≤N)<1e-4）与保守敏感性判据（λ_lo=286，阈值 N≤28）**同时满足**。同夜中性协变量窗
**108/900 s = 7.20/min** 证明环境并未整体静默 ⇒ 低计数可归因于遮罩本身。

### 8.1 逐窗（窗有效性判据逐条核对）

| 窗 | boot_id | 窗起 uptime | 窗长 | START 参数 | SELFTEST | EXIT | probe_bad | inj=0 | inj=1 | 判 |
|---|---|---|---|---|---|---|---|---|---|---|
| W1 | 4056a4df | 118.0 s | 900.007 s | 逐字=§2 固定调用 | PASS | reason=duration | 0 | **3** | 12 | 有效 |
| W2 | 4056a4df | 1108.2 s | 900.015 s | 逐字=§2 固定调用 | PASS | reason=duration | 0 | **2** | 12 | 有效 |
| arm0b（协变量） | 82e1241b | 144.1 s | 900.011 s | 逐字=§2 固定调用 | PASS | reason=duration | 0 | **108** | 12 | 有效 |

- 遮罩验证（两窗同 boot，开窗前后各查一次）：`masked_entries=8`、`/proc/mounts` 8 条
  `/etc/modules.d/` 挂载、8 项在 `/proc/modules` 全缺席、mtk_warp/hw_nat 在位、模块总数
  163→154、`iw dev` 0 个接口（WiFi 确认 down）。窗内无 panic/重启；日志 md5 双端一致
  （W1 `1493b23c…`、W2 `d24629f0…`、arm0b `bd5fb317…`）。
- 命中内容：W1 三条全为 `region=stack topva=0x4e0 spva=0xb0 len=1601 ip=192.168.9.1
  rule=15`；W2 两条全为 `region=stack topva=0x4e0 spva=0xb0 len=321 ip=110.65.x.x
  rule=3`（W2 时上行已恢复，故记录里出现设备 WAN 源地址）。两窗 topva/spva 与 B4 各臂
  同族（`0x4e0`/`0xb0`），非用户态自产。

### 8.2 判据计算（对号入座 §3）

- N_total = 5；窗总时长 1800 s。
- **主判据**：λ_pooled = 608 × 1800/2700 = 405.33 ⇒ 10% 阈值 40.5；5 ≤ 40 ✓；
  P(X≤5 | λ=405.33) = **8.5e-166** < 1e-4 ✓ ⇒ 压制侧成立。
- **敏感性**：λ_lo = 143 × 1800/900 = 286.0 ⇒ 阈值 28.6；5 ≤ 28 ✓；
  P = **1.0e-114** < 1e-4 ✓ ⇒ 同向。两判据一致，无需启用「取更弱一档」的 tie-break。
- **无压制侧**（N≥203）不成立；「不确定」带（41–202）不成立。
- 观测率 0.167/min vs 基线 13.51/min = **1.23%**（比值 1:81）。

### 8.3 归因（§5 预写死的协变量规则）

- 同夜中性协变量窗 **108/900 s = 7.20/min**：WiFi 全载（ra0/rai0/apcli0，rai0 上 1 个
  客户端）、上行在窗内全程可用（23:36:27 起 default via 110.65.x.x dev eth0）、
  记录 ip 以设备 WAN 源 110.65.x.x（64/108）与公网 peer 为主——与 B4 三个 arm0 窗同形。
- 因此「arm1b 低计数 = 环境整体变静」被排除：环境只比基线低到 53%（7.20 vs 13.51），
  而遮罩臂是 1.2%；**遮罩臂/同夜中性 = 1:43**。
- **归因边界（§5 预写死，不得越界）**：遮罩同时移除了「S1 模块」与「WiFi 客户端流量」，
  本实验**不区分**两者；结论只能表述为「写入者活动速率依赖 WiFi 栈在场（集合口径）」。
- 对 B4 arm1 的回溯：其 4/1200 s（0.2/min）在本判据下不再是「无法解释的低」，而是
  **真实压制**；B4 arm1=P 的判决不受影响（P 只要求 ≥1）。

### 8.4 结论表述（唯一允许）

> 32B 记录写入者的活动速率依赖 WiFi 栈（S1 全族 + mtk_wed 集合）在场：遮罩后速率降到
> 基线期望的 1.2%（5/1800 s vs 缩放期望 405 条），泊松尾 8.5e-166；同夜中性对照 7.20/min
> 排除环境漂移。机制层面（写入者需要 S1 模块 vs 写入者被 WiFi 流量驱动）不可分。

## 9. 偏差与终态

1. **W1→W2 间隔 61 s**（非严格背靠背）：W1 EXIT 于 uptime ~1018.2，W2 START 于 1108.2；
   其中约 35 s 为 PC 侧轮询延迟。遮罩态未变，只损失 61 s 未观测时间，不影响判据。
2. **W1 前 222 s 上行未起**：eth0 在本 boot 的 23:05:39（uptime ~340 s）才拿到
   110.65.x.x/25 与默认路由；W1 因此前段无 WAN 流量，W2 全程有。这是协变量（§5），
   不判 INVALID；且 W2 单独 2/900 s 仍在压制侧（阈值 28）。
3. **协变量窗起点选择**：arm0b 在上行恢复后才开窗（23:36:27 上行 up，23:36:52 开窗），
   目的是与基线环境（上行在）对齐。该选择在开窗前声明，且该窗不入判决。
4. **协变量窗速率低于基线池**（7.20 vs 13.51/min，53%；也低于三窗最低值 9.53）：环境确实
   比 B4 三窗安静一些。因判决用的是「≤10% 基线」这一极宽阈值，此漂移不影响结论；
   但报告里不得把 7.20 当作「基线复现」。
5. **设备时钟为 UTC**（`date` 显示 16:0x 而 PC 为 00:0x +0800）：全部锚点用
   `/proc/uptime` + `date +%s`（epoch，与时区无关），不依赖本地时间字符串。
6. **两次非计划重启（任务二 tuphook 仪器缺陷）**：23:59 与 00:03 各一次 oops→重启，
   均发生在 arm1b/arm0b 三窗全部完成且数据已 md5 对账拉回之后，不触及本实验证据；
   详见 C-198 与 06_INSTRUMENT_FIXES F-11。
7. **终态**：设备中性（`# b4 neutral`、masked_entries=0、163 模块、WiFi 4 接口 up、
   0 个我方模块在载、misc 未写）；p25/p38/p39 未写，bootctrl 未碰。

## 10. 给下一轮的输入

1. **机制二分（唯一未解）**：「写入者需要 S1 模块」vs「写入者被 WiFi 流量驱动」——
   需要「WiFi 栈在但无客户端流量」的臂（例如遮罩 hostapd + 关闭 ra0/rai0 但保留
   mt_wifi 全族），或「有 WiFi 流量但 S1 部分缺席」的镜像级设计。
2. **速率判据可复用**：本次把「二元存在/消失」升级为「速率 vs 缩放基线」的冻结判据，
   后续任何臂都可以在预注册里直接给出 λ 与阈值（λ 取同夜夹逼窗，不取历史池）。
3. **协变量窗成本低（15 min）**，建议此后每个速率臂都带一个同夜中性协变量窗——
   它是排除「环境漂移」的唯一手段，本次正是它把归因钉死的。
4. **仪器**：tuphook 已可用（C-197/C-198），下一轮可直接在 arm1 遮罩下跑 live 抓取，
   对比「WiFi 在/不在」时 tuple 入口的调用率——这是把速率效应拆到函数级的现成通道。
