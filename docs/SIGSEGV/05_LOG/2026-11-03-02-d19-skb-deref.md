# 02 · D19 预注册 · tuple 填充入口的 skb 解引用捕获（2026-11-03 夜间设备线 N1）

> **预注册文档：实验开窗之前写定并 commit。** 实验后只追加 §9–12，不改 §1–8。
> 仪器事实来源：`tools/oneoff/sigsegv/bmods/tuphook.c` v1.4（live 已通，C-197/C-198）、
> `REVIEW-tuphook.md`、C-196（同夜中性 32B 记录率 108/900 s = 0.12/s）。
> 本文档中性信息：不含部署目标网络名与个人凭证。

## 1. 问题

tuphook v1.4 已证实两个 tuple 填充入口（`wifi_tx_tuple_add` / `wifi_rx_tuple_add`）在
中性态以 ~10.7 次/s 被调用（7409 次 / ~11.5 min），而同一夜中性态 32B 记录真命中只有
0.12 次/s（108/900 s）——**≈90× 错配**（C-197，探索性 E1）。本实验回答：

> **哪一次填充调用携带「记录族」的数据？** 即：把入口寄存器里的 skb 指针解引用，
> 读 `skb->len` 与 `ip_hdr(skb)->saddr`，看它们是否落在 32B 记录的已知取值族
> `{len ∈ 321/1600/1601/4416/4480, ip = 流端点}` 上。

## 2. 假设

- **H（记录内容在填充入口可见）**：32B 记录的两个内容字段（len、ip）由填充入口
  可见的 skb 直接决定（或与其一一对应）；因此按 skb->len 分桶时，记录族取值会出现
  在填充调用的分布里，且族内调用率 ≥ 记录率。⇒ 填充上下文即生产链候选。
- **H'（填充只见元数据）**：填充入口看到的 skb 只提供与记录族无关的元数据
  （或根本不是记录字段的来源）；skb->len 分布是普通的 MTU/聚合分布，记录族取值
  在其中不出现或只占 <1%。⇒ 记录装配在更深处（填充之后的某个阶段），填充入口
  只是同一条链上的邻居而非生产者。

方向语义（预写死）：**族内调用率 ≥ 记录率是 H 的必要条件**——受害槽位看到的记录
不可能比产生它的填充调用更频繁；反之若族内调用率显著低于记录率，则 H 被排除。

## 3. 预测

- H 为真：捕获窗内 `len_ok` 调用的 len 直方图包含记录族取值（至少 3/5 个精确值或
  ±8 变体），且 `p_family = N_family / N_len_ok ≥ 5%`；族内调用的 ip 与记录端点的
  同族地址（同一公网对端 / 本机 WAN/LAN）有可观察重合。
- H' 为真：`p_family < 1%`，直方图顶部（top-5）与记录族重叠 ≤1 个取值，且 ip 分布
  不集中在记录端点。

## 4. 判据（预写死）

**窗有效性（前提，任一不满足 ⇒ INVALID）**

1. 捕获窗 600–900 s，`boot_id` 全程不变，无 panic/重启；`dmesg` 无 oops。
2. 仪器：`/proc/tuphook` 头行显示 v1.5 PATCHED；`offsets: len=0x70 nh=0xb4 head=0xc0`
   与静态核对值逐字一致（不一致 ⇒ 拒绝加载，见 §8）。
3. 解引用成功率：`len_ok / (len_ok+len_bad+head_bad) ≥ 90%`；`ip_ok / len_ok ≥ 50%`
   （非 IP 包/无网络头不计为失败，只计入分母外的解释项）。
4. 样本量：`N_len_ok ≥ 2000`（按 10.7/s × 600 s 的期望，功效下限）。
5. 设备态：中性 b4lab（masked_entries=0、163 模块、WiFi 4 接口 up、0 个我方模块在载
   除 dieblx/tuphook 外）；上行状态如实记录为协变量（不判 INVALID）。

**判决规则（对号入座，不追加事后规则）**

| 分支 | 条件（全部满足） | 结论 |
|---|---|---|
| **H 支持** | `p_family ≥ 5%` **且** 记录族 5 个取值中 ≥3 个出现在 top-8 桶（精确或 ±8）**且** 族内调用率 `r_family = p_family × 调用率 ≥ 0.12/s` | 填充上下文即生产链候选 |
| **H' 支持** | `p_family < 1%` **且** top-5 桶与记录族重叠 ≤1 **且** `r_family < 0.12/s` | 记录装配在更深处 |
| **不确定** | 其余（含 1%–5%、或 len 有族内值但 ip 全不匹配等） | 如实标 E1，不升级为强结论 |

- 补充报告（不入判决）：tx/rx 分开的 len 直方图、ip 提取成功率、ip 取值 top-10、
  `len∈family` 子集的 ip 列表、按 30 s 分桶的族内调用率时间序列。
- **LOD**：若 `N_family = 0`，给出规则三上界 `< 3/N_len_ok`（95%），并注明该上界
  相对于 `0.12/s` 记录率是否已足够排除 H（`3/N × 调用率 < 0.12/s` ⇒ 排除）。
- 记录率基准取**同夜中性协变量窗 108/900 s = 0.12/s（C-196）**，不做跨 boot 历史池比较
  （与 B4/D18 的冻结口径一致）。

## 5. 捕获协议

1. 先载 `dieblx.ko`（黑匣子，崩溃取证），再 `insmod tuphook.ko dryrun=1` 做正对照
   （不 patch 一字节，打印偏移与 ops 链），核对 §4-2 的 offsets 行。
2. `rmmod tuphook` 后 `insmod tuphook.ko`（live），确认 dmesg `INSTALLED` 与
   `/proc/tuphook` 头行 PATCHED。
3. 捕获 600–900 s：每 5 s 读一次 `/proc/tuphook`（`maxread=128`/CPU），PC 侧落盘
   原始输出；窗起/窗止各记 `date +%s`、`/proc/uptime`、`boot_id`。
4. 窗内不加任何新仪器、不改配置、不做 WiFi 关联/断开操作；正常流量（PC 在 eth1
   有线侧，WiFi 客户端可有可无，如实记录）。
5. 收窗：`rmmod tuphook; rmmod dieblx`，核对 dmesg `entries restored to paciasp`，
   模块数回 163、0 个我方模块；拉回原始数据并做 PC/设备 md5 双端一致。

## 6. 混杂与控制

- **调用率本身随流量变化**：填充调用率不是常量；判决只用窗内实测调用率与
  `p_family`，不用历史 10.7/s 作为判决输入（只作样本量规划）。
- **记录率基准的跨窗可比性**：0.12/s 来自同夜中性窗（WiFi up、上行在），本窗同态；
  若窗内上行中断，如实记录并降级为 E1 解释（不判 INVALID）。
- **saddr 的方向语义**：记录 ip 是「流端点」（82% 同一公网对端）。RX 调用的 saddr
  天然是远端；TX 调用的 saddr 通常是本机地址。因此 ip 匹配只对 RX 子集作强判据，
  TX 子集只报告分布、不入判决（§4 的 ip 条件限定在「族内调用」的合并报告里，
  并在结果里分方向列出）。
- **len 的形态**：记录族含 1600/1601 与 4416/4480（>MTU，疑似 GRO/软件量）与 321
  （小包）。若 skb->len 是这些值的来源，直方图应出现同族；若填充侧 len 恒 ~1500
  或恒 ~60，则 H' 方向。
- **时间戳对齐**：每条记录带 `cntvct_el0`（24 MHz 虚拟计数器），proc 头行给
  `cntfrq` 与读时刻的 `cntvct`；分析时换算相对秒。填充调用与 32B 记录无法直接
  逐条对齐（记录无时间戳），只做速率与分布层面的比较，不作逐事件因果断言。
- **04:00 定时重启**：全部工作在 03:45 前收窗；若窗内重启，该窗 INVALID，
  查 TRY_A 与 pstore 后按 §7 处理。

## 7. 停止规则

1. **崩溃预算**：同一仪器缺陷重复崩溃 ≥2 次 ⇒ 弃该路径，停工报告（不第 3 次尝试）。
2. 每次崩溃后先查 `TRY_A`（`hexdump -C -n 2 -s 2060 /dev/mmcblk0p1`）：>0 且未清
   ⇒ 暂停并报告（不擅自写 misc）。
3. **8 分钟 lgssh 不可达红线** ⇒ 停工，如实报告（不擅自重启、不等待用户）。
4. 窗内非计划重启：该窗 INVALID；恢复后只允许重跑 1 次（同一缺陷计 2 次）。
5. 安全红线：不写 p25/p38/p39；不碰 bootctrl；misc 只读；一切设备写经 `deploy.py put`。

## 8. 仪器变更（v1.4 → v1.5，实验前钉死）

**唯一目的**：在捕获路径上解引用入口 x2 的 skb，记录 `len`、`ip`、`cntvct`。
v1.4 的 4 参数记录（ctx/band/skb/x3）、per-cpu 256 环、guard 协议、文本窗口与
卸载还原全部保留。

**静态偏移核对（先于本预注册完成，读的是设备内核 Image，不是猜测）**：
设备内核 `kernel_Image.bin` + `kallsyms.pkl` 反汇编锚点：

| 字段 | 偏移 | 证据（设备 Image 反汇编） |
|---|---|---|
| `sk_buff.len` | **0x70** | `skb_pull` 0x6ace48: `ldr w2,[x0,#0x70]`；`skb_copy_bits`: `ldr w0,[x0,#0x70]` |
| `sk_buff.data_len` | 0x74 | `skb_copy_bits`: `ldr w21,[x24,#0x74]` |
| `sk_buff.end` | 0xbc | `skb_release_data`: `ldr w0,[x0,#0xbc]` |
| `sk_buff.head` | **0xc0** | `skb_release_data`: `ldr x20,[x19,#0xc0]`；`ip_rcv_core`: `ldr x3,[x19,#0xc0]` |
| `sk_buff.data` | 0xc8 | `__skb_pull`: `ldr x5,[x0,#0xc8]`；`skb_copy_bits`: `ldr x1,[x24,#0xc8]` |
| `sk_buff.network_header` | **0xb4** | `ip_rcv_core`: `ldrh w4,[x19,#0xb4]`，随后 `add x5,x3,x4; ldr w2,[x3,x4]`（= ip_hdr） |
| `iphdr.saddr` | +12 | IPv4 头固定布局；`ip_rcv_core` 同段以 `and w2,w2,#0xf` 取 IHL |

模块编译期以 `BUILD_BUG_ON(offsetof(...) != 上表值)` 固化：任何一项不符 ⇒ 构建失败，
不产生可加载的 .ko（等价于「偏移自洽门禁」）。运行期再加合理性判据（§4-3 与 §5-1）。

**捕获路径（新增）**：跳板保存 x0–x3/x8/x30/x19/x20（64 B 栈帧，恢复后 SP 与
`paciasp` 的 SP 修饰符一致），调用 `tuphook_probe(skb, is_rx)`；probe 内部全部
dereference 走 `copy_from_kernel_nofault`（extable 修复，坏指针只会 -EFAULT，
不产生 oops）；读 `skb->len` → `skb->head` → `skb->network_header` → 版本半字节
（必须 == 4）→ `saddr`。记录扩展为：
`{x0,x1,x2,x3, len_ip, meta, cntvct, pad}`（64 B/条，环布局不变）。
meta 位：0=rx，1=len_ok，2=head_bad，3=nh_bad，4=ipv4_bad，5=ip_ok，6=skb_null。

**/proc 输出**：改用 seq_file（v1.4 的 8 KB 静态缓冲会截断），头行打印
`offsets: len=0x70 nh=0xb4 head=0xc0`、`cntfrq`、读时刻 `cntvct`；每条记录一行
`#seq tx|rx skb ctx band x3 len ip st ts`。`maxread` 默认 64/CPU，上限 256。

**预执行钉死**：`tuphook.c` v1.5 与 `tuphook.ko` 的 md5 在开窗前的 docs-only
amendment 中登记（本预注册先于构建，故此处不填）。
