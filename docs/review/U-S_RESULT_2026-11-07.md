## 1. T3b 仪器链（此前全部是空白）

1. **exilewin 编译**：`pgprot_cached()` 在 5.15 不存在；改为保留 VMA 默认 `PAGE_SHARED`
   （MT_NORMAL + PTE_USER）→ `remap_pfn_range` 即 cached PFNMAP。构建 `exilewin.ko`
   123,800B, md5 **c9c80e1c**。
2. **wmd5 snapvia**：`snapvia <pa> <len> <dev> <out>` 用模块映射只读导出；RO 映射被
   `ex_mmap` 以 EINVAL 拒绝，改用 O_RDWR + PROT_READ|WRITE（只读不写）后成功。
3. **ISU off**：`echo "call ffffffc008722ee8 0" > /proc/emiuctl`（done=1 err=0）；
   `snapvia` 两次 30s 的 1MiB md5 **b6d81b36** 相同 ⇒ 冻结。
4. **映射自检**：`probevia` 未对齐读写 ok；1MiB store **419µs**（≈2.5GB/s，cached）；
   模块日志 `mapped ... (cached PFNMAP)`；`/proc/exilewin pfn_valid=1`。
5. **T3b 运行**：`scanary_exile --win-pa 0xbf000000 --win-dev /proc/exilewin
   --win-size 0x800000 --stack 0x100000 --decoy 0x800000 --duration 1200 --selftest 1`，
   2400pps 洪水；587s 时停在第一个 600s 窗边界（SIGTERM，EXIT 记录完整）。

- `awk` 的参数是 `avail_sampler`/`state_edge` 族的 `awk -v cur=... statef=...`；死亡在
  重启后 ~16min（实验负载窗内，ISU primer/洪水在跑）。

  **仍死** ⇒ q2..q7 覆盖不足；FP 保存突发掩蔽不是该家族机制。残留 q0/q1 对、数据 spill
  或页/地址层是更可能的解释（与 U-Q p9 的"形状干净仍死"一致）。

## 4. 写者相位门（per-CPU/纯 CPU 判别的阻塞）

- **p11 boot**（T0=1793980462）：uptime 18–28min 高 λ ~100/min（T3b：1147/1075 per 587s）。
- **重启后**（T0=1793982485）：uptime 5–19min 低 λ **0–2/min**；
  - port 9 2400pps：0–2/min；
  - U-H 原版 `udpflood_ug1.py`（192.168.9.1:37777，3×800pps）：0–2/min；
  - ISU 窗 primer（0xbf000000 真实窗栈）：12–18/min（短暂），窗口 arm CPU0 仍 2/1 per 60s。
- 判读：λ 的高相位跟**真实设备面向流量**（T3b 记录里的 WAN 客户端 IP）走，合成洪水不够；
  C-288 的 boot 依赖 + C-297 的活动依赖共同作用。**per-CPU 矩阵/纯 CPU 臂在当前 boot
  欠功效**；分进程 arm 也不继承 primer 的引擎注意力（引擎锁在触发它的进程/页上）。
- 这本身是一个判别结果：**写者不是常开噪声源，而是活动/相位门控的**；做 per-CPU 必须
  在真实高 λ 窗内、同进程/同页设计。
