# 05_LOG · 2026-11-01 · R7：谁会"缓存一个用户 VA"并在之后写 32 字节

**新事实（第 6 轮末）**：新起进程 7 min 内**一个记录槽都拿不到**（4 实例、11,200 次全扫），而自然槽都在**长驻**进程上
（nerepair 热槽 0.62 次/s、dnsmasq 静态）。⇒ 写入者手里应有"**按进程/线程建立一次的地址**"（H7）。

> 级别：**E3** 直接观测｜**E2** 强推断｜**E1** 弱/单点｜**X** 已排除。所有"不能"判定都能用给出的源码位置复核。

## ② rseq 专项（结论：**对不上，排除**）

1. **本机内核 `CONFIG_RSEQ=y`**：vmlinux 有 27 个 rseq 符号（`__arm64_sys_rseq`、`rseq_update_cpu_id`、`__rseq_handle_notify_resume` …）——E3。
2. **但本机 musl 不注册 rseq**：对 `rootfs_b/lib/libc.so`、`bin/busybox` 做 `grep -c rseq` **均为 0**（也没有 `__rseq_abi`）。
   musl 从不调用 `rseq(2)` ⇒ **设备上没有任何进程注册 rseq**（除非出现 glibc 二进制）——E3。
3. **注册地址在 TLS，不能在栈**：rseq 是每线程 32B、4×8 对齐、写在 TLS 的 `__rseq_abi`；内核在 `__do_sys_rseq` 里校验对齐与长度，
   且**每线程只允许一个**。⇒ 即使注册，也落在 TLS，不会落在用户栈 —— E2。
4. **形状能否对上：不能**（字段级）：
   `struct rseq`（5.15）= `{u32 cpu_id_start; u32 cpu_id; u64 rseq_cs; u32 flags; padding…}`，
   逐字对照记录（归一化后 `{q0=A, q1=0, q2={u32 len; __be32 addr}, q3=0}`）：
   * `q0`（17~18 位、最大 16.5 万）vs `cpu_id_start`（0~数十）⇒ **值域不符**；
   * `q1=0` vs `cpu_id`（正常运行时是当前 CPU 号，非 0）⇒ **不符**；
   * `q2={len,addr}`（低 32 位是 321/1601 这类小值，高 32 位是 IPv4）vs `rseq_cs`（一个用户指针或 0）⇒ 拼成 `0x0109a8c000000641` 不是合法指针 ⇒ **不符**；
   * 只有 `q3=0` vs `flags` 能对上。
   ⇒ **rseq 既写不到 32B，字段语义也两条不符 ⇒ X**。反证条件：若发现某进程真的调用了 `rseq(2)`（`strace` 或审计），且其 `__rseq_abi` 落在栈上，才需重审。

## ③ 能同时解释 (a) 帧相对、(b) 长驻有槽、(c) 新进程 7 min 无槽 的机制候选

**(a)** 记录位置随金丝雀"va_list 深度 D"等距平移（含 D=0x1000 移出栈顶页仍命中）⇒ 目标与**活栈 VA** 同步。
**(b)** 长驻进程有稳定槽（同一地址反复被写）。(c) 新进程 7 min 零槽。

### M-A（首选，E1）：**寄存器快照 + 延迟写**
某内核/固件路径**保存了某任务的用户 sp 或 x2**（来源：信号投递前的 `pt_regs`、`PTRACE_GETREGS` 的 regset、或停下任务时保存的寄存器），
之后**一次性写 32B**（正好是两个 16B 槽）到"快照值 + 常数偏移"。
* 解释 (a)：快照里的 sp/x2 随帧深度变化 ⇒ 目标随 D 平移 ✓
* 解释 (b)：长驻进程**反复被快照**（信号、ptrace、调度、审计）⇒ 同一地址反复被写 ✓
* 解释 (c)：**新进程还没有任何快照**（既没收到信号、也没被 ptrace 过）⇒ 7 min 零槽 ✓
* **可证伪预测（三臂，任一反向即否）**：
  P1 给新 canary 每 100ms 发 `SIGUSR1`（装空 handler、**不用 altstack**）⇒ 应 ≪7 min 出现槽；
  P2 另一批新 canary 用 `sigprocmask` **全阻塞** ⇒ 应 0 槽；
  P3 第三批新 canary 由 nerepair 式 `ptrace` attach ⇒ 应**立刻**出槽。

### M-B（备选，E1）：**长驻页 + stale PA**
只靠"页身份"解释 (b)(c)（新进程栈页是新分配的、历史上没当过 RX 缓冲 ⇒ 没有陈旧描述符指向它），但**解释不了 (a)**（固定页内偏移已被 D 臂否定）。
* 反证/复活条件：若 P1 也 0 槽 ⇒ M-A 弱化、M-B 权重上升，那时必须解释 D 臂（例如"页内偏移由 VA 推出"）。

### M-C（备选，E1）：**注册型异步缓冲**（io_uring registered buffers / userfaultfd / AIO）
唯一"注册一次 → 内核或设备异步写 ≥32B"的族，但**都要求受害进程自己 opt-in**。
* **可证伪（2 min）**：`ls -l /proc/{dnsmasq,nerepair,procd}/`fd` 找 `anon_inode:[io_uring]`/`aio`/`userfaultfd` 特征；
  没有 ⇒ M-C 在这几个进程上不成立。

### ③-补 · uffd 方案四条静态核查（2026-11-01 追加）

> **⚠️ 更正（推翻我自己上一轮的说法，也推翻"设备有 uffd"的前提）**：本内核 **`CONFIG_USERFAULTFD=n`**，uffd 方案在本机**不可用**。证据三条（E3）：
> ① `__arm64_sys_userfaultfd` @0xffffffc00814fb78 的代码是 `mov x0,#-0x26; paciasp; autiasp; ret` = **-ENOSYS**，
>    与 `sys_ni_syscall` @0xffffffc00814f098 **逐字节同形** ⇒ 它是 `kernel/sys_ni.c` 的 **`COND_SYSCALL` 占位**，不是实现；
> ② **vmlinux 符号表与设备 kallsyms（61,689 条）里 0 个 uffd 实现符号**：`handle_userfault`/`userfaultfd_register`/
>    `dup_userfaultfd`/`free_userfaultfd`/`mwriteprotect_range`/`userfaultfd_unmap_prep` 全部缺席；
> ③ 正对照成立（同一份 kallsyms 里 `__handle_mm_fault`/`handle_mm_fault`/`do_page_fault`/`do_swap_page`/`wp_page_copy` 都在）。
> ⇒ 上一轮我写"设备真的有 ⇒ 与 .config 不符"是**误判**（把占位符当成实现），据此提出的 M-C 里 uffd 一支**作废**；`.config` 是对的。

**四条核查的结论（即使启用也需知）**：
1. **WP 模式：arm64 5.15 不支持**（E3）。`CONFIG_HAVE_ARCH_USERFAULTFD_WP` 只出现在 `arch/x86`（x86 的 Kconfig 才 select），
   `arch/arm64/include/asm/userfaultfd.h` **不存在**；uapi 里虽有 `UFFDIO_REGISTER_MODE_WP` 常量，但 arch 未实现 ⇒ **只能用 MISSING 模式**。
2. **EL1 uaccess 缺页会不会走 `handle_userfault`：会（若 uffd 启用）**（E2，源码级）。匿名页的钩子在 `do_anonymous_page()`
   （`mm/memory.c:3755` 起）内两处：`3798-3800`（只读零页快路径）与 `3840-3843`（正常分配路径），条件都是 `userfaultfd_missing(vma)`，
   **没有任何"仅用户态才走"的门**（只检查 `vma->vm_flags & VM_UFFD_MISSING`）⇒ 内核态 uaccess 写同样会卡住。
3. **原子上下文（softirq/中断）里缺页会怎样：不是优雅失败，而是 splat/BUG**（E2）。`handle_userfault` 内有 `might_sleep()` 与
   `schedule()` ⇒ 原子上下文里会触发 "scheduling while atomic" BUG ⇒ **pstore 里的栈恰好就是写入者的调用链**（这条推断成立）。
4. **vmlinux 地址（给 kdev 验证用）**：`__handle_mm_fault`=0xffffffc00824c470(1632B)、`handle_mm_fault`=0xffffffc00824cad0(360B)、
   `do_page_fault`=0xffffffc008126bdc(840B)、`do_translation_fault`=0xffffffc008126f24(96B)、`sys_ni_syscall`=0xffffffc00814f098；
   **`handle_userfault` 与 `do_anonymous_page` 不存在符号**（后者被内联进 `__handle_mm_fault`，前者因 `CONFIG_USERFAULTFD=n` 只剩头文件里的 static inline 桩）。

**保住方案意图的替代（不需要 uffd、不需要重编内核）**：用**自建模块 + 自定义 `vm_ops.fault`** 给受害者栈提供映射
（模块建 char 设备，受害进程把它 `mmap` 成栈页；缺页时我们的 `fault` 回调会**睡在缺页进程的上下文里**并打印调用链，
等价于 uffd 的"卡住写入者"）。设备允许 `insmod`（patrace.ko/rzring.ko 已验证）⇒ 这条路可行；
代价是要改 canary 的栈来源（不再是普通匿名页），因此**只能测"经页表的写"**，对 DMA 直写无效——这一点与 uffd 方案相同。

## ⑤ 边界（必须一起引用）

* 本文所有"不能凑 32B"的判断依据是**该结构的内核写点长度**（源码位置已给），不是"没找到"；反证条件都写成"发现更长的写点即推翻"。
* `CONFIG_RSEQ/AIO/IO_URING/USERFAULTFD` 都是**按符号存在性**判定（vmlinux 有对应 syscall/handler），不是读 `.config`——本仓库没有设备 `.config`。
* 未覆盖：169 个厂商 `.ko` 的私有结构（无 BTF/DWARF，见 F-10）、SRAM/MMIO 区、以及"固件（MD/SCP）侧自己的缓存"——
  若 M-A 的"快照"发生在**固件侧**，本表的 AP 侧源码证据只能证明"AP 侧没有别的候选"，不能证明"固件侧没有"。
