## 1. 写入模式：7 份转储给出同一张表

从 8 份独立转储（pfcanary core ×6、vsurv3 栈镜像 ×2；跨不同会话、不同二进制、不同 ASLR 基址）
里按形状 `{A, 0, B, 0}` 提取，命中 7 份（c27834 那份形状不符，未计入）：

| 转储 | 记录数 | 地址 1 | 地址 2 | A1 / A2 | B (hi32:lo32) |
|---|---|---|---|---|---|
| c27830.core | 2 | 0x7fec6a0e30 | 0x7fec6a1070 | 0x1a3e4 / 0x1a3ec | 1c28416e : 00001140 |
| c27836.core | 2 | 0x7ffe8a36e0 | 0x7ffe8a3920 | 0x0f096 / 0x0f09e | 1c28416e : 00000680 |
| c9409.core | 2 | 0x7fc10e1e30 | 0x7fc10e2070 | 0x1e816 / 0x1e81e | f9f91068 : 0000112c |
| r11228.core | 2 | 0x7ff87d1750 | 0x7ff87d1990 | 0x04f71 / 0x04f79 | 010013ac : 00000640 |
| r3850.core | 2 | 0x7ff34a30e0 | 0x7ff34a3320 | 0x18be1 / 0x18be9 | 1c28416e : 00001140 |
| h3_new.bin | 2 | 0x7ffffff780 | 0x7ffffff9c0 | 0x14f37 / 0x14f3f | 1c28416e : 00000640 |
| h3_11307_1.bin | 2 | 0x7ffffff780 | 0x7ffffff9c0 | 0x12c8f / 0x12c97 | 0109a8c0 : 00000641 |

### 不变量（7/7 全中）
1. **每条记录 32 字节，布局恒为 `{A, 0, B, 0}`** —— word1、word3 永远是 0。
2. **一次崩溃恰好留 2 条**，两条**相距 0x240**（576 字节）。
3. **两条的 A 恰好差 8**（0x1a3e4→0x1a3ec、0x4f71→0x4f79 …），**B 完全相同**。

### 变量
- `A ∈ [0x4f71, 0x1e81e]`（20 337 … 124 958），每次不同；A×8 落在 160 KB … 1 MB 量级。
- `B = {hi32, lo32}`：`lo32 ∈ [0x640, 0x1140]`（1 600 … 4 416，**像长度**）；
  `hi32 ∈ {0x1c28416e (4/7), 0xf9f91068, 0x010013ac, 0x0109a8c0}`，**不是随机值**（跨重启复用）。

### 上下文不变量（前几轮实测）
- 落点是**主线程** `start_stack-0xc0` 的活 `va_list`；目标随进程走，不随任意线程走。
- 经受害者**自己的用户页表**；非线性映射、非 DMA。
- **不是 `copy_to_user`**（四种过滤 × 200 次崩溃，探针字节级在位）。
- 只在受害者**正在执行那次可变参调用**时发生（只读金丝雀页 24 进程 × 5 分钟 0 命中，同期 12 次崩溃）。
- 受害者 `/proc/<pid>/syscall` 采样 600/600 = `running` ⇒ 发生在**打断用户态的中断上下文**。

### 这张表读出来的形状
两条 32 字节记录、地址相距 0x240、A 每次 +8、B 恒定 —— 不像"一次 memcpy 写 32 字节"，
更像**同一份 32 字节描述符被写两次**，其中 A 是**随写递增的偏移/序号**（步长 8），
B 是**本次崩溃期间恒定的 `{标记, 长度}`**。
"A×8 = 160 KB…1 MB" 与 "B.lo = 1.6…4.4 KB" 都是**日志/环形缓冲**里常见的量级。

## 2. 嫌疑分层（用数字说话）

| 层 | 规模 | 是否排除 | 依据 |
|---|---|---|---|
| 厂商用户态守护（10 个） | 33 个 ioctl 点 | **排除为写入者** | 调试模式把这些全 `bind /dev/null` 后仍照崩 |
| 厂商内核模块 | 172 个 .ko，其中加载的约 12–14 个是 MTK/Quectel | 已扫 12 个：**0 个内联 `sttr`**；唯一 32 字节 user copy 在 `hw_nat`（同步 ioctl） | 静态枚举 |
| 厂商内核镜像 | 1278 个 user-copy 站点里 **50 个（19 个函数）** 是厂商命名，且全是 read/ioctl/write 同步处理器 | 未排除，但面很窄 | `vendor_class.py` |
| mainline 内核代码 | 1278 站点里 **1228 个** | **未排除，且是最大的一块** | 同上 |

19 个厂商 uaccess 函数：`aed_ke_write / aed_ee_write / aed_ioctl / ccci_log_read / ccci_dump_read /
ccci_sib_read / ccci_fsm_ioctl / ccci_lp_mem_read / atf_log_read / atf_raw_buf_read /
mtk_do_priv_ioctl / mt_printk_ctrl_write / mcupm_log_read / scp_A_log_read / sspm_log_read /
mtk_lp_sysfs_procfs_write / mtk_rtc_ioctl / mtk_afe_debugfs_write / mtk_qdma_ioctl`。

**结论：嫌疑并不"全在厂商二进制上"。** 厂商面已被枚举得很小；最大的嫌疑面其实是 mainline 内核代码，
而 mainline 我们**有源码**（`_local/legacy/linux-5.15.134`，已用它核对过 `do_page_fault` 的
permission-fault 分支行为）。要注意的反而是：整份内核是厂商 BSP 构建的，config 与 BSP patch 无源码，
所以"长得像 mainline"的函数仍可能被改过。

## 3. "残留厂商固件 = 底层硬件操作、无害" 这个评估要不要改

**要改，但不是改成"全部替换"。** 三条具体修订：

1. **评估对象错位。** 那条结论是对**用户态守护**下的；实测写入者在**内核侧**。
   换掉守护不解决问题（调试模式已证）。真正的"厂商黑盒"是**内核镜像 + 模块**。
2. **"底层硬件操作"恰恰是最可疑的画像，不是最无害的。** 这类代码同时具备两个必要条件：
   (a) 在中断/工作队列里跑；(b) 需要把状态/日志推给用户态。
   上一轮的"无害"依据是"没观察到危害"，不是"没有能力"——而能力已被正对照证实
   （`ktu.ko`：无 mm 的内核线程 32 字节 `copy_to_user` 成功落进借用进程的地址空间）。
3. **风险是非对称的。** 概率低，但影响面是**任意进程的栈**、静默、不可归因；
   这支持"**定位并摘除那一个**"，而不是"重写整个 BSP"。

### 建议的动作分级

| 动作 | 代价 | 现在做? |
|---|---|---|
| 继续仪器化，点名写入者 | 低 | **是**（300 站点探针已建成，需修掉坏站点） |
| 按模块 unbind/blacklist 做 A/B 测速率 | 很低 | **是**——见下方具体假设 |
| 替换用户态守护 | 中 | 否（已证无关） |
| 重写内核/模块 | 极高 | 否，除非定位到具体模块且无法绕开 |

### 一条可以直接测的假设（本轮离线分析新增）

"A 是偏移、B 是长度、一次写两条"这个形状，最像**固件日志环形缓冲的推送**。
厂商集合里只有两处这种设计：

- `conninfra.ko`：`connsys_log_read_to_user(user_buf,len)` + `connlog_to_user_register` +
  IRQ 喂环 + 排空线程 `__check_object_size` → `__arch_copy_to_user(user_buf+off, ring_seg, len)`；
- `gps_drv.ko`：`gps_fw_log_data_copy_to_user`（全模块只有 1 个调用者，当前看是同步 read 路径）。

设备回来后先做这两件事：
1. `echo <dev> > /sys/bus/*/drivers/*/unbind` 或 `rmmod gps_drv` / 对 conninfra 做同样处理，
   分别测 300 s 崩溃速率（同一窗口、多臂对照，遵守既有方法论）；
2. 把设备上 22 份 `h3_*.bin` 全部拉下来，把上面那张表从 7 行扩到 20+ 行，
   看 `B.hi32` 是否与某个模块的 ID/句柄族对应。
