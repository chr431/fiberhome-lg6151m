# 可靠性验收规范（RELIABILITY SPEC）v1.0 · 2026-10-31

> 本文是**验收合同**。项目负责人（Lead）据此拆分任务、审核交付。
> 任何"改了什么"都必须能映射到本文某一条需求；任何"完成"都必须有设备侧证据。
> 判据优先级：**实测证据 > 设计文档 > 口头结论**。禁止"应该/理论上"。

## 0. 术语与总原则

- **设备**：LG6151M（SSH `toor@192.168.9.1`，经 `lg6151m-public/tools/lgssh.py`）。
- **固件**：`lg6151m-public/gw/` 下部署到 `/data/gw/` 的脚本/二进制/GUI。
- **事故（incident）**：任何导致或可能导致服务不可用/降级的事件。
- **证据（evidence）**：设备上可持久化、可复核的机器可读记录（tsv/log），不是截图不是叙述。
- **诚实性第一**：宁可显示"未知/陈旧"，绝不显示假的绿。
- **假状态演练**：每条判据改动必须附一次"制造故障→判据必须变红→恢复→必须回绿"的实弹记录，
  无演练记录的判据改动视为未完成（沿用 AVAILABILITY_DESIGN §8.4）。

## 1. 运行时指标 → 工程需求

### M1 事故可溯源性
> 任何可靠性事故必须有日志持久化保存；严重事故保存 >7d，一般事故/事件 >1d。

| ID | 需求 | 验收证据 |
|---|---|---|
| R1.1 | 统一事故台账 `/data/gw/logs/incidents.tsv`（append-only，单行含 ts/severity/category/component/duration/evidence_ref/detail），所有来源归一：watchdog FAIL 迁移、NE、KE/panic、boot 异常、守护重启、netcfg 修复、计划/非计划重启、服务中断（来自 M3） | 文件存在、字段稳定、≥5 类来源各有真实行 |
| R1.2 | 严重度分级：**SEV1**=KE/panic/NE/启动失败/服务中断>20s；**SEV2**=守护重启/中断 5–20s/网络修复风暴；**SEV3**=degraded 迁移/一般事件 | 分级规则单点实现（一个脚本函数），台账内每行有正确 severity |
| R1.3 | 分级留存：SEV1 ≥**90d**、SEV2 ≥**30d**、SEV3 ≥**7d**（均高于合同下限 7d/1d）；留存不得被常规轮转破坏 | `retention_audit` 输出每级最老记录龄与条数，SEV1 最老龄 >7d 断言通过 |
| R1.4 | 留存可证明且可自检：`tools/` 侧或设备侧 `retention_audit` 命令，输出各 tier 的 oldest_age_days/rows/bytes，并对合同阈值做 PASS/FAIL | 报告文件 + 单测 |
| R1.5 | 崩溃前证据不丢：panic/KE 现场（pstore/ramoops/core_meta/最后 N 行 syslog）在重启后仍可回溯；重启原因可判定（计划/非计划/看门狗/掉电） | 断电演练后能读出上一次死亡原因 |
| R1.6 | 磁盘守卫：`/data` 剩余空间低于阈值时按 SEV3→SEV2→SEV1 顺序降级清理，**SEV1 永不自动删除**，并在台账记一条自保事件 | 填充演练 |

### M2 监测诚实性
> GUI 显示和设备指示灯必须反映实际设备状态；设备状态更新时，检测指标滞后 <3s。

| ID | 需求 | 验收证据 |
|---|---|---|
| R2.1 | 单一状态源：所有组件状态由 `/data/gw/run/state.json`（原子 rename 写入）+ `state_events.tsv`（迁移流）发布，GUI/LED/API 一律读它，禁止各自另算 | 文件存在；GUI 与 LED 读同一 version |
| R2.2 | 迁移检测时延：状态真正改变到被检测到 ≤**1s**（关键链路事件驱动：netlink/uevent/inotify；非关键 ≤1s 轮询）。**现状 30s watchdog 周期 + 10min 采样器不满足，必须重构** | 每个组件声明 detect 机制与实测 detect 时延 |
| R2.3 | GUI 呈现滞后：状态元素刷新 ≤**1s**（现状 status 3s / 其他 8s 不满足）；页面必须显示数据新鲜度，陈旧>3s 显示"陈旧/未知"而非绿 | 滞后审计 p99 <3s |
| R2.4 | LED 呈现滞后 ≤**1s**，且每次写 GPIO 后读回校验；LED 状态必须由 state.json 驱动（禁止 LED 自己判断） | 滞后审计 + 读回校验记录 |
| R2.5 | 滞后审计：每次迁移记录 t_change/t_detect/t_publish/t_render，落 `lag_audit.tsv`；GUI 回传其渲染的 version 与本地时刻 | 台账 + p50/p99 统计 |
| R2.6 | 诚实性分级：判据按 L1/L2/L3 标注，**L1-only 组件不得显示为绿**（现 sys.ssh 为已知盲区，须补 L2 或显式黄标） | 组件判据表 + 演练 |
| R2.7 | 假状态演练：注入 20 次真实状态变更（杀服务/断链路/改配置），断言 GUI 与 LED 均在 3s 内变红/变绿且落账 | 演练报告 |

### M3 服务稳定性
> 对通过 WiFi/以太网/RNDIS 接入的设备，固件不稳定导致的 <5s 中断 <5 次/d，>5s <1 次/d，>20s <1 次/7d。
> 定时重启、网络供应商服务中断不计入。

| ID | 需求 | 验收证据 |
|---|---|---|
| R3.1 | **定义**：客户端侧"服务中断"= 对该接入路径的网关可达性（ICMP→网关 / DNS 查询网关 / TCP:80 / TCP:22 四选一，按路径适用）在 ≤1s 采样下连续失败 ≥2 次（去抖，最小可判中断 ≈2s）。时长 = 首次失败到首次成功 | 定义写入文档并被采样器实现 |
| R3.2 | 双端测量：设备侧（各接口自观测）+ 客户端侧（PC 经 WiFi/以太/RNDIS 主动探测），两者独立落账；**客户端侧为验收口径**，设备侧用于归因 | 两套台账均有数据 |
| R3.3 | 中断台账 `/data/gw/logs/svc_outages.tsv`（start/end/dur/path/probe/severity/attrib/excluded）+ 日聚合 `svc_daily.tsv`（按 <5s/5–20s/>20s 三档计数） | 文件 + 至少一次真实捕获 |
| R3.4 | 排除规则可审计：计划重启窗（reboots.log + boot 完成时刻 ±2min）、上游供应商中断（WAN 侧断且 LAN 侧正常）必须打 `excluded=1` 并注明原因，不计入验收计数 | 排除行可见、有原因 |
| R3.5 | 归因：每条 >5s 中断必须归因到具体组件（GUI/dnsmasq/hostapd/dropbear/内核/上游/未知），归因要有证据链 | 归因表覆盖率 100%（未知也要标未知） |
| R3.6 | 修复：由固件导致的每一类中断必须修掉或显著降低；修复前后有对照数据 | 修复记录 + 前后对比 |
| R3.7 | 验收报告：任意 7d/30d 窗口可生成 `acceptance_report`，给出三档计数与 PASS/FAIL | 报告样本 |

### M4 自持性
> 在每天一次定时重启的情况下，能运行 >30d 不需要人工干预。

| ID | 需求 | 验收证据 |
|---|---|---|
| R4.1 | 守护覆盖审计：每个常驻进程/功能都在 SVC_TABLE 或有等价监督；每个恢复路径有界（≤60s）；无"只能人工救"的状态 | 覆盖表 + 缺口清单（缺口必须闭环） |
| R4.2 | 资源不泄漏：/data 增长、/tmp、fd、内存、日志轮转在 30d 尺度有界；每日 checkpoint 记录趋势 | checkpoint 台账 + 趋势判定 |
| R4.3 | 30d soak 装置：每日自动 checkpoint（uptime/重启原因/三档中断计数/资源/告警），自动生成日报与漂移告警 | 装置 + 已运行样本 |
| R4.4 | 故障注入campaign：≥30 次注入（杀守护/断链路/塞盘/时钟跳变/网络风暴/断电），全部自动恢复且落账；失败项必须修 | 注入台账 + 通过率 |
| R4.5 | 无人干预声明：列出所有仍需要人工的动作（若有），并消除或自动化 | 声明文档 |

## 3. 交付判定（Definition of Done）

一个任务算完成，必须同时满足：
1. **代码/脚本已部署到设备**且经 `deploy.py doctor` 复核一致；
2. **有设备侧证据**（台账行/审计报告/演练记录），且证据是本次改动之后产生的；
3. **有假状态演练**（判据类改动）或**前后对照**（性能类改动）；
4. **注册表已 bump**（`tools/VERSIONS.tsv`），`vercheck check` 全绿；
5. **文档已更新**（设计/运维/陷阱表按需），且不含隐私数据；
6. Lead 复核通过。

## 4. 协作规则（所有子代理必须遵守）

1. **设备锁**：任何**写设备**的操作（deploy/重启/改配置/杀进程）前必须抢 `_local/device.lock`
   （`mkdir` 原子创建，内含 owner/时间/目的），完成后释放；持有 >15min 视为陈旧可夺取但需记录。
   只读查询（cat/ls/grep）不需要锁。
2. **部署只走 `deploy.py push`**（`MSYS_NO_PATHCONV=1`）；二进制/任意文件用 `put`。
   手推 = 违例。推完必须 `deploy.py doctor`。
3. **不改别人的文件**：写入范围以任务卡声明为准；需要改他人文件时先报 Lead。
4. **提交协议（v1.1 修订，2026-11-01）**：`deploy.py push` 要求文件已 commit 且在 MANIFEST 中，
   因此**允许**各流自行提交，但必须严格遵守：
   - 只 `git add`/`commit` **自己的文件**；禁止 `git add -A` / `git add .`；
   - 提交命令一律用**路径限定式**，避免踩到别人已 staged 的内容：
     `git commit -m "<流名>: <说明>" -- <路径1> <路径2> ...`
   - 新 gw 脚本必须同时改三处：`deploy.py` 的 MANIFEST（只加你自己的行，并 bump deploy.py 版本行）、
     `tools/VERSIONS.tsv`（你的行 + deploy.py 版本行）、`docs/ARCHITECTURE.md`（跑
     `python tools/vercheck.py render` 重生成，勿手改）。
   - 提交前必须 `python tools/vercheck.py check` 全绿；若因**别人的**半成品行而不绿，
     等 60s 重试，仍不绿则报 Lead，**禁止去修别人的行**。
   - 并发提交撞 `index.lock` 属正常，等 2s 重试（≤5 次）。
   - 只允许快进式提交；禁止 `git push`（Lead 统一推远端）、禁止 rebase/reset/checkout 他人改动。
5. **不擅自重启设备**（每日 04:00 已自动重启）；确需重启必须持锁并在报告中写明。
6. **不把隐私数据写进任何文件/对话**；引用 IP/MAC 时用脱敏形式。
7. **报告格式**：完成时向 Lead 提交「做了什么 / 证据在哪（绝对路径+行号）/ 验收哪几条 R/ 未决风险」。
8. **失败要直说**：做不到就报告"做不到 + 证据"，禁止粉饰。
