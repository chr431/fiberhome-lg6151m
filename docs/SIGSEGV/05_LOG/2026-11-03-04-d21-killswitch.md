# 04 · D21 预注册 · kill-switch 归因：mt_wifi 7 个 copy_to_user 包装器克隆（2026-11-03 夜间 N3-build）

> **预注册文档：实验开窗之前写定并 commit。** 实验后只追加 §10–12，不改 §1–9。
> 编号说明：NN=03 已被同日 N1 的 `2026-11-03-03-d20-uaccess32-catcher.md` 占用，
> 本文件按 README「NN 是当天序号」顺延为 04。
> 本文档中性信息：不含部署目标网络名与个人凭证。

## 1. 问题

32B 记录族（`{u32 X, 0, u32 len∈{321,1600,1601,4416,4480}, __be32 ip=流端点, 0…}`）
是不是由 **mt_wifi 的 7 个 `copy_to_user` 包装器克隆（168 个静态调用点）** 写出的？

一句话判决：**关掉这 7 个克隆的全部用户拷贝之后，记录率是否塌向 0。**

## 2. 假设

- **H1（点名）**：记录族由这 168 个调用点中的某一条路径写出 ⇒ 杀开关窗口内
  记录率相对中性窗**塌向 0**（≤10%）。
- **H0（未点名）**：杀开关对记录率**无明显影响**（≥50%）⇒ 写者不在这 7 个克隆里
  （可能在内联 5 站点、netlink、或其它模块）。

## 3. 仪器与补丁语义

- **被测模块**：`wdkill.ko`（md5 **28278ac9b4548f684e4554228594f5dd**，180,064 B，
  vermagic `5.15.134 SMP mod_unload aarch64`）。源码/审阅见
  `tools/oneoff/sigsegv/bmods/{wdkill.c,REVIEW-wdkill.md}`。
- **补丁**：把 7 个克隆尾部的 `bl __arch_copy_to_user` 改成 `bl wdkill_stub`，
  stub = `mov x0,x2; ret` ⇒ 168 个调用点全部**不写用户内存**并返回 len(失败)。
  **不是** N2b §7.0 的 `mov x0,xzr`：本内核 `CONFIG_HARDENED_USERCOPY=y` +
  `CONFIG_PANIC_ON_OOPS=y`，NULL dst 会在 `__check_object_size` 里
  `usercopy_abort("null address")→BUG()`，第一个 ioctl 就重启。
- **记录率仪器**：用户态 canary（`scanary_c2`，同 D20 §2：固定调用 600 s，
  只统计 `inj=0` 真命中）。**不使用 uacatcher 计率**——它与 wdkill 争用同样的
  7 条 `bl`（二者互斥，见 §6）。
- **dryrun=1**：定位 + 7 站点 4~5 字指纹 + BL 目标名，**不写一字节**。

## 4. 预测（H1 为真时）

| 量 | 中性窗 | 开关窗 |
|---|---|---|
| canary 真命中率 | 基线（同夜同客户端态） | ≤10% 基线，理想 0 |
| 管理面 ioctl（`iwpriv`/`iwinfo` 查询） | 正常 | **返回错误**（-EFAULT 上抛） |
| WiFi 数据面（关联/转发） | 正常 | 正常（不经过这些拷贝） |
| `/proc/wdkill` 头行 | — | `PATCHED` |
| dmesg | — | `INSTALLED ... stub=...`，无 oops |

## 5. 判据（预写死，不改）

### 5.1 窗有效性（任一不满足 ⇒ 该窗 INVALID）

1. `insmod wdkill.ko dryrun=1`：dmesg/`/proc/wdkill` 出现
   **`VALIDATION OK: 7/7 clones match`**，且 7 行指纹全 `ok`；
   `sprint_symbol` 行含 `[mt_wifi]`；双路定位（链表/页扫描）一致。
2. live：dmesg `INSTALLED: 7/7 wrappers diverted`；`/proc/wdkill` 头行 `PATCHED`。
3. 正对照（开关有效性）：安装后执行一次已知走 W1/W5 的管理查询
   （建议 `iwpriv ra0 stat` 与 `iwinfo ra0 info` 各一次），**至少一条返回错误**；
   `rmmod` 后同一命令**恢复成功**。若两条都始终成功 ⇒ 开关未生效 ⇒ INVALID。
4. 设备态：boot_id 窗内不变；无 oops/panic/重启；`TRY_A`（misc[2060] 低字节）
   窗后为 0。
5. canary 自身：`selfcrash=0`、`probe_bad=0`、`overflow=0`。

### 5.2 判决规则（主终点 = canary 真命中率）

三窗配对，每窗 **900 s**：`N1(中性) → S(开关) → N2(中性)`，同客户端态、同流量档。

- `R_neutral = (hits_N1 + hits_N2) / 1800 s`，`R_switch = hits_S / 900 s`
- **PASS（H1）**：`R_neutral > 0` 且 `R_switch ≤ 0.10 × R_neutral`
  且 `hits_N1 + hits_N2 ≥ 6`（中性窗有足够事件）。
- **FAIL（H0）**：`R_switch ≥ 0.50 × R_neutral`。
- **INVALID**：任一窗 §5.1 不满足；或 `hits_N1 + hits_N2 < 6`（功效不足，
  只能标“探索性”，不得写“无效应”）。
- 中间带（10%–50%）⇒ **不确定**，如实报告，不加窗追打（避免 p-hacking）；
  如要追打，另开新预注册。

### 5.3 次终点（只报告，不入判决）

- 每站点实际调用率（需 catcher 才能测；本实验不可得，留空）。
- 管理面失败的具体命令/返回值清单。
- 开关窗内 WiFi 关联/转发是否保持。

## 6. 混杂与控制

- **仪器互斥（关键）**：uacatcher 把同样的 7 条 `bl` 改成 `b stub_i`，
  与 wdkill **不能同时加载**。因此本实验只用 canary 计率；
  catcher 若要用，只能在**中性窗**（wdkill 未加载时）跑，或改用 wdone（改的是
  `ldr`，与 catcher 的 `bl` 不冲突）。
- **配对**：N1/S/N2 三窗连续，客户端数、信道、上行流量档如实记录；
  客户端状态变化 ⇒ 该组作废重做。
- **时间**：记录窗起止 epoch/uptime/boot_id；跨午夜不跨窗。
- **温度/负载**：窗内不改配置、不跑其它实验；`cat /proc/loadavg` 每窗记录。
- **同窗对照**：开关窗内同时记录"管理查询失败率"，作为开关确实生效的旁证。

## 7. 停止规则

1. **崩溃预算**：任何 oops/panic/重启 ⇒ 立即停止，保留 `/data/gw/logs/ne_events.tsv`
   与 console-ramoops；同一仪器缺陷重复 ≥2 次 ⇒ 弃该路径，停工报告。
2. **还原断言**：`rmmod wdkill` 后 dmesg 必须出现 `restored 7/7 sites, 0 skipped`；
   否则视为设备处于**半补丁态**，立即停止并报告（不重复 insmod/rmmod 试探）。
3. **TRY_A 红线**：每次加载前/卸载后 `hexdump -C -n 2 -s 2060 /dev/mmcblk0p1`；
   低字节（TRY_A）非 0 ⇒ 暂停并报告（bootctrl 语义见 AGENTS.md）。
4. **可达性**：lgssh 连续 8 min 不可达 ⇒ 停工报告，不擅自重启。
5. **硬停**：06:00 前必须收窗并 `rmmod`；未收窗不得离开。
6. 安全红线：不写 p25/p38/p39；不碰 bootctrl；misc 只读；
   一切设备写经 `deploy.py put`。

## 8. 样本量/功效

- 预期：无客户端中性窗 0.40/min（D20 §2 实测）⇒ 900 s ≈ 6 条；
  有客户端 7.20/min ⇒ 900 s ≈ 108 条。
- 最小可检效应：`R_switch/R_neutral ≤ 0.10`（PASS）或 `≥0.50`（FAIL）。
- 过散假设：泊松；6 条基线在 0.10 比值下的判别力有限 ⇒ 若只有无客户端态，
  判决强度标 **E2**；有客户端态可到 **E3**。
- 若不足：标“探索性”，不得写“无效应”。

## 10. 结果（实验后追加）

**部署与仪器（全部通过）**

- `deploy.py put` → `/data/gw/wdkill.ko`，设备侧 md5 `28278ac9b4548f684e4554228594f5dd`（双次一致）。
- dryrun：`VALIDATION OK: 7/7 clones match the N2b snapshot`；7 站点 4~5 字指纹全 `ok`；
  双路定位一致（`base=ffffffc000daf000`，页扫描同址）；`sprint_symbol(base+0x25be4)`
  含 `[mt_wifi]`；6×`9a9f00a0` + 1×`9a9f0080`；bl 目标均为
  `ffffffc00843b680 __arch_copy_to_user`；stub `ffffffc0019f7000`（`aa0203e0 d65f03c0`）。
- live：dmesg `wdkill: INSTALLED base=ffffffc000daf000 stub=ffffffc0019f7000`；
  `/proc/wdkill` 头行 `wdkill v1.0: PATCHED`。
- 还原：`rmmod wdkill` → dmesg `restored 7/7 sites, 0 skipped`；`/proc/wdkill` 消失；
  模块总数回 162、我方模块 0。
- 安全：窗内 boot_id `acde1339-4ef2-454a-b831-01d7dc665b13` 全程不变；无 oops/panic/重启；
  每窗前后 `TRY_A`（misc[2060..2061]）= `0f00`（低字节 0）；p25/p38/p39/misc 未写。

**正对照（开关确实在生效）**

预注册建议的 `iwpriv ra0 stat` 与 `iwinfo ra0 info` 在补丁下**仍成功**（它们不走 7 个克隆）。
改用 D20 已证实走克隆的 `iwconfig ra0`（ESSID 拷贝）做差分对照：

| 状态 | `iwconfig ra0` 含 `ESSID` 行 |

| 未打补丁（rmmod 后） | **10/10**（`ESSID:"MyHome"`） |

⇒ 开关在已知克隆路径上生效且可逆；数据面不受影响（WiFi 客户端 103,350 B 静态文件
拉取 5.7 MB/s，关联保持 STA=1→2）。

## 11. 判决（实验后追加）

- **数值上 FAIL（H0）**：`R_switch = 20.33/min` 远高于 `0.10 × R_neutral`
  （R_neutral=(259+208)/1800=15.56/min，比值 **1.31**）；同客户端态配对
  （S vs N2，均 2 客户端）比值 **1.47**。关掉 7 个克隆的 168 个调用点后记录率
  不但没塌，反而略升 ⇒ **32B 记录族的写入者不在 mt_wifi 的 7 个 copy_to_user
  包装器克隆里**（本窗的蜂窝/WiFi 混合流量档下）。
- **形式上 INVALID（§6）**：第二台客户端在 S 窗内（03:17 前后）才关联，客户端数
  1→2 发生变化 ⇒ 按预注册 §6「客户端状态变化 ⇒ 该组作废重做」。两种可辩护配对
  （冻结 N1+N2；同态 S-vs-N2）都落在 FAIL 侧，故方向结论稳健，但判决强度按 E1
  记录，不写「正式 PASS/FAIL」。
- **对应 claims**：`C-202`（D21 判读与速率分解，含 C-196 口径修正）。
- **对 N3 的输入**：克隆族出局 ⇒ 剩余候选 = 4 个内联站点（D22 对象）、5 个内联
  调用点之外的 mt_wifi copy 路径、以及 N2c 指出的 `hw_nat` 单站点。下一步用
  uacatcher 在有流量态直接抓站点（E4），而不是继续杀开关。

## 12. 偏差与教训（实验后追加）

1. **AP 根本没在发信标（关键发现）**：开窗时 PC 扫描不到 `MyHome`（`hostapd_cli`
   却 `state=ENABLED`）——正是 AGENTS 陷阱表「ENABLED ≠ 信标在发」。执行
   `mwctl dev ra0/rai0 set no_bcn 0` 后，独立接收者（PC）立即看到
   `MyHome / d8:f6:07:db:2a:90(2.4G ch8) / d8:f6:07:db:2a:98(5G ch36)`；
   PC 以 WPA2-PSK 关联成功（IP 192.168.9.145）。此前所有「无客户端」夜
   （0.4–0.6/min 档）应重新解读为**信标缺失导致的客户端缺席**，不是用户不在场。
2. **设备 AP 口令 = `GW_PASS`（settings.conf WPAPSK）**，不是 `WIFI_PASS`
   （后者是上游 WiFi 口令）。以 sha256 对比设备 WPAPSK 与本地 secrets 证实。
3. **正对照命令选错**：`iwpriv ra0 stat` / `iwinfo ra0 info` 不走 7 个克隆，
   补丁下仍成功；差分对照改用 `iwconfig ra0`（0/10 vs 10/10）后成立。
4. **客户端数窗内变化**：第二台客户端（本地管理 MAC `da:f1:6b:41:a4:1a`，
   疑似同房间手机，rx 12.7 MB / tx 790 MB）在 S 窗内关联 ⇒ 组按 §6 作废。
   教训：开窗前应把「客户端集合」按 MAC 固定并全程记录，而不是只记数目。
5. **流量协变量**：PC 侧流量发生器用 `/dev/null` 写盘在 Git-Bash 下失败
   （curl rc=23，body 0 字节），三窗一致地只产生请求/响应头流量；因此三窗的
   「客户端在场」是稳定的，但「大包数据面」未被本发生器覆盖。已如实记录，未中途改。
6. **速率分解（与 N2c 合并口径）**：热（有客户端数据面）≈13.5–20/min、
   无客户端背景 ≈0.6/min、WiFi 栈遮罩残余 ≈0.2/min ⇒ arm1 的「1.2% 压制」
   主要是客户端流量消失所致（写入活动的主载体是 WiFi 客户端数据面），
   C-196 的「压制」措辞需按此修正为「流量构成依赖」。
