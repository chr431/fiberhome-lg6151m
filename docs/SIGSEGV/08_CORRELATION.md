## 判读

1. **WiFi TX 不是主驱动**：D 臂期间 rai0_tx 从 38.4 掉到 **10.7 KB/s（−3.6×）**，命中率却从 26.5 升到 **40.6/min（+1.53×）**。
   → 命中与 WiFi TX **反向**；排除"WiFi TX 路径写入"。
2. **命中强依赖流量**：Q2 静默臂（eth0_rx 0.4、rai0_tx 0.7 KB/s）掉到 **7.4/min（−3.6×）**。
   → 不是定时器/背景 DMA 的固定速率。
3. **eth0 RX 正相关但严重次线性**：eth0_rx ×10.2 → 命中仅 ×1.53。若"每个 RX 缓冲回收事件有固定命中概率"，应近似线性。
4. **近零 eth0 流量下仍有 7.4/min 残余** → 存在第二贡献项（LAN/WiFi RX 软中断，或少量周期流量）。
5. 逐 10s 相关系数（77 个区间）：**srx 0.873 > eth0_rx 0.725 ≈ eth0_tx 0.667 ≫ rai0_tx 0.172 > eth1 0.06–0.20**。

### 仪器发现（可复用）
- `echo edma dump ring_status|recycle_mode|free_count|flow_ctrl|rx_ring_max_dist > /proc/mtkfe/dbg_dma` 可用，输出走 **dmesg**。

## 方法论笔记（本轮踩到的坑，写给后续轮次）

### A. 「大输出截断」是系统性问题，不是个案
本轮我首次 `cat /proc/mtkfe/dump_dma`（设备侧 5656 行）只拿回 **602 行**就去做形状分析——
与 svc-probe 的 `tail -n 4000` 拿回 8 行、soak-qa 的 1611 行变 8 行是**同一类缺陷**：
**单条 SSH 通道的大输出会被静默截断，且工具返回"成功"**。
**纪律**：任何跨 SSH 的批量拉取，必须先取设备侧 `wc -l`，再分页（≤250 行/页）拉取，并**断言 fetched == wc -l**；
不等即判失败重取。本轮此后所有拉取（corr.tsv 106==106、corr4.tsv 68==68）都带此断言。

### B. FOE/hw_nat 只能写「无法证实」
`/proc/hnat/{hnat_entry,hnat_mib,hnat_usage,hnat_type}` **全部返回空**（`cat` 与 `dd` 均空），
`hnat_entry` 在重载下仍 0 行；但 `/proc/mtkfe/users` 显示 FE 的消费者是 `ethernet` + **`hw_nat dr`**（已注册）。
→ 正确表述是 **"无法证实 hw_nat offload 在工作"**；**不能**写成"未启用"——proc 全空也可能是驱动没实现导出。

### 判决

**LAN RX 单独足以驱动 32B 记录写入。** 臂是干净的：传输期间 eth0 RX **反而下降**（2.2→0.2 KB/s）、rai0 TX 全程 0，
所以增量只能来自 eth1。命中/CPU-s 与原始命中率同向（×71），CPU 归一不改变结论（三段 canary CPU 几乎相同）。

### 意外收获：命中与 RX 包数**近乎严格线性**

- 逐 10s 分箱：**corr(命中, RX 包数) = 0.965**；corr(命中, eth1 包) = 0.965；corr(命中, eth0 包) = −0.05。
- 三段单位换算：**1.05 / 1.38 / 1.14 命中 每千个有线 RX 包** —— 在 70× 包率跨度上稳定在 **1.3 ± 0.2 /千包**。

> **修正上一轮的"严重次线性"**：那次只采了字节没采包数，eth0 的包率被低估，才得出次线性。
> **以包为单位，命中率是线性的** → 写入者是「**每个有线 RX 包一次机会**」的路径，而不是"每 N 个事件"或"环回绕"。

### 与既有结论的合并

- WiFi TX：**排除**（臂1 D 臂反向 + 臂2 全程 rai0 TX=0 仍命中 127.6/min）。
- eth0 专属路径：**排除**（臂2 中 eth0 RX 下降而命中 ×71）。
- **写入者的必要条件 = 有线端口（eth0/eth1）共用的 EDMA RX 环上、每 RX 包一次的写机会。**
- 定量锚点：**~1.3×10⁻³ 命中/RX 包**，可用于反推「每个 RX 缓冲回收事件命中率 ~0.1%」还是「某个固定槽位/条件组合」。

## 风险量化（1.3/千包意味着什么）

- 每千个有线 RX 包 ≈ **1.3 次**「32B 记录落进 canary 栈页」的写事件。家用 500 pps ⇒ **~5.6 万次/天**写机会（单个目标页）。
- 而自然 NE 只有 ~4/h（≈96/天）→ **约 580 次写机会才产生 1 次进程死亡**：绝大多数写入落在无害位置（未映射/已释放/非指针字段）。
- **这解释了「为什么系统还能跑」，但同时说明"NE 数低 ≠ 问题小"**：NE 计数只统计了"写到了 va_list 且解引用"的那一小撮；
  真正的内存破坏面比 NE 数大 2–3 个数量级。
- 也解释了 canary 与自然进程的差异：canary 的栈页是**刚分配的**（大概率来自回收的 RX 缓冲页池），
  而自然进程的栈页通常是长寿命页，落在"曾经是 RX 缓冲"的页上的概率低得多 → 自然 NE 率远低于 canary 率，
  **不能用 canary 率外推自然 NE 率**（与 00_STATE §6 停止规则一致）。

## 静态：EDMA RX 路径（vmlinux.elf，符号齐全，capstone 反汇编）

对象：`analysis/kern/vmlinux.elf`（18 MB，47,910 符号）。工具：`_local/work/crash-root/vml_dis.py <sym>`。

| 函数 | 事实 |
|---|---|
| `mtk_poll_rx_edma0/1` | NAPI RX 轮询：描述符基址 `[ring+0x28]`，**步长 0x20（32B）**，索引按 `ring+0x20`(cidx) 与 `ring+0x1c`(环深) 取模；取描述符后 `tbz w28,#0x1f` 检查 **w1 的 bit31（DD/完成位）**，未置位即退出循环 → **消费侧的顺序是对的**（先确认 DMA 完成再消费） |
| `recycle_fe_dma_buf` | 薄壳：`container_of(x0-0x40)` → 调 `ops->[0x48]` |
| `fe_edma_recycle_buf` | 把缓冲挂进**延迟回收链表**（自旋锁内 `str x5,[x3,#8] / str x3,[x20,#0x7d8]`），**不做 dma_unmap** |
| `fe_dma_set_rx_recycle` | 只置 `+0x540` 的回收模式字节 |
| `mtk_rx_clean_edma` | 环 teardown：逐缓冲 `dma_unmap_page_attrs(desc->w0)` → `page_frag_free()` |
| 分配器 | **无 page_pool**；缓冲来自 `__netdev_alloc_frag_align` / `build_skb`（page_frag） |

**静态判决（如实）**：**路径已锁定，具体窗口未定位。**
- 消费侧（DD 位检查）顺序正确，未发现"未等 DMA 完成就消费"。
- 回收是**延迟链表**（不是立即回填），也未发现"先 free 后 unmap"。
- 因此**未能在静态层面指出明确的 bug 点**。可能的位置收敛为：延迟回收链表与回填/环复用的交错时序，
  或 `page_frag` 在跨 CPU 回收时的可见性——两者都需要运行时证据（kprobe 被 `CONFIG_KPROBES=n` 堵死，
  `pagemap` 也不存在），故本轮**不作断言**。

**形状线索（待验证假设，不是结论）**：RX 描述符 = 32B、`w0=缓冲 PA`、`w1=状态/长度（bit31=DD）`、
`w2..w7` 在空闲态为 0（`dump_dma` 实测）。记录 = `{小整数, 0, len, src_ip}`，**尺寸吻合但内容与"空闲态描述符"不符**；
若硬件在 DMA 完成时把 L3/L4 信息写回 `w2..w7`（MT7988 EDMA 支持 RSS/L3L4 信息），则记录可能是**写回后的描述符片段**。
验证方法：在收到包后立刻 dump 该槽位的 8 个字，与记录逐字段比对（下一轮可做，需 1 次 `dbg_dma` + 1 次记录抓取）。

## 描述符写回假设：**阴性（Lead 实测，2026-11-01 11:20）**

Lead dump `/proc/mtkfe/dump_dma` 的 RX 段（两环共 1024 条），抽样 200 条：

- **w2..w7 全部为 0**（`entries_with_w2plus_nonzero = 0`）
- 全部条目形如 `w0 = 缓冲 PA, w1 = 0x00060000, w2..w7 = 0`

→ **环描述符里看不到任何含 IP/长度的写回**。两种解释（都未排除）：
① EDMA 的 L3/L4 信息不落在环描述符里，而在独立的 status 结构；
② dump 抓到的是**静止态**——所有条目都是"已武装待收"（DD 未置位），消费过的条目被立刻重填了。

**"收包后立刻 dump 该槽位"这条路基本不可行**：DD 置位→重填的窗口可能只有几微秒，shell 抓不到；
退而求其次的"记下槽位 PA，命中后比对"又卡在**拿不到 canary 栈页 PA**（无 pagemap）。
→ **本条假设不再投入**，记录在此以免下一轮重复试。

## 本轮最终结论（定稿）

1. **写入者 = 有线端口（eth0/eth1 共用 EDMA RX 环）的「每 RX 包一次机会」路径**，速率 **1.3 ± 0.2 命中/千个有线 RX 包**。
   支撑：LAN-only 臂 ×71 且 eth0 RX 反向下降；WiFi TX 全程 0 仍命中；逐包线性（corr 0.965）。
2. **WiFi TX 排除、eth0 专属路径排除、WED tuple 路径排除**（后者见 00_STATE §10 P1 诊断）。
3. **具体窗口未定位**（静态未发现明确 bug：消费侧 DD 顺序正确、回收走延迟链表、无"先 free 后 unmap"）。
   定位需要运行时证据，而 kprobe（`CONFIG_KPROBES=n`）与 pagemap（`CONFIG_PROC_PAGE_MONITOR=n`）双双不可用。
